배선 다음 단계 · 2026.10.22

어느 Pi에서 실행할지,
무엇이 나오면 성공인지.

명령은 한 상자씩 실행하세요. 각 단계의 확인 결과가 맞을 때 다음으로 넘어갑니다. PC 터미널이 아니라 표시된 Pi의 터미널에서 실행합니다.

현재 출발점
사용자가 H–L 약 60Ω을 확인했습니다. 이제 각 Pi를 평소 전원 입력으로 켭니다. 전원이 켜진 뒤에는 배선을 바꾸지 않습니다.
이 안내는 실행 절차이며, 실제 장비에서 명령을 실행해 검증한 결과가 아닙니다.

처음에는 ①~⑤까지만 진행하면 됩니다. 제품 코드와 1,200회 실험은 그 뒤입니다.

① 공통 준비② ECU 설정③ IVI 설정④ Pi3 설정⑤ 세 노드 통신⑥ ADC·제품·화면⑦ IDS·실험문제 해결

① 먼저, 세 Pi에서 같은 준비

ECU에서 실행한 다음 IVI와 공격 Pi3에서도 반복합니다. SSH로 접속해도 되지만 화면 확인은 IVI 데스크톱 터미널을 사용합니다.

STEP 01
세 노드 각각

내가 어느 장비에 접속했는지 확인

터미널 창 제목이나 메모에 ECU / IVI / 공격을 적어 두세요. 실제 호스트 이름은 장비마다 다릅니다.

터미널에 입력
hostname
cat /etc/os-release
uname -m
확인 결과
호스트 이름과 OS를 기록합니다. IVI 제품 화면 기준은 Debian 13 + Qt 6.8 이상입니다.
여기서 멈추는 경우
다른 OS라고 바로 재설치하지 마세요. CAN 설정은 실제 부팅 파일을 확인하고 진행하며, IVI 앱 빌드는 OS·Qt 조건을 별도 확인합니다.

기본 도구 설치

Debian / Raspberry Pi OS의 apt 환경 기준입니다. 네트워크 연결이 필요합니다.

pgrep -af 'adaptive_ecu|ivi_dashboard|security.ids|security.experiments'
systemctl --no-pager --type=service --state=running | grep -Ei 'ivi|ecu|can|ids'
확인 결과

여기서 멈추는 경우
기존 송신 프로그램은 해당 터미널에서 Ctrl+C로 종료합니다. 서비스로 실행 중이면 확인된 서비스만 중지하세요. 서비스 이름을 추측해서 일괄 종료하지 않습니다.
STEP 03
세 노드 각각

부팅 설정 파일 찾고 백업

아래 명령은 파일 내용을 출력하고 백업합니다. 기존 설정을 자동으로 바꾸지는 않습니다.

터미널에 입력
if [ -f /boot/firmware/config.txt ]; then
  CAN_CONFIG=/boot/firmware/config.txt
elif [ -f /boot/config.txt ]; then
  CAN_CONFIG=/boot/config.txt
else
  CAN_CONFIG=
  echo "부팅 설정 파일을 찾지 못했습니다. 여기서 중지하세요."
fi
if [ -n "$CAN_CONFIG" ]; then
  printf "확인할 파일: %s\n" "$CAN_CONFIG"
  sudo cp -p "$CAN_CONFIG" "$CAN_CONFIG.before-three-node-$(date +%Y%m%d-%H%M%S)"
  sudo cat "$CAN_CONFIG"
fi
확인 결과
실제 설정 파일 경로와 백업 파일을 확인합니다. 이후 같은 터미널에서 CAN_CONFIG를 사용합니다.
여기서 멈추는 경우
내용이 다른 경로로 이동하라는 안내문이거나 include가 있으면 그 파일도 확인해야 합니다. [pi4] 등 조건 구역 아래에 Pi3 설정을 넣지 않습니다. 기존 디스플레이 설정은 보존합니다.

STEP 04
ECU Pi4

이 노드의 부팅 설정 편집

공통 단계에서 확인한 실제 파일을 엽니다. 터미널을 새로 열었다면 파일 찾기 단계를 다시 실행하세요.

터미널에 입력
if [ -n "${CAN_CONFIG:-}" ] && [ -f "$CAN_CONFIG" ]; then
  sudo nano "$CAN_CONFIG"
else
  echo "먼저 부팅 설정 파일 찾기 단계를 실행하세요."
fi

이전 dtoverlay=mcp2515... 줄은 앞에 #을 붙여 비활성화하고, 아래 CAN 설정 한 개만 적용합니다. 기존 같은 SPI 설정이 있으면 중복하지 마세요. 포함된 파일의 중복 overlay도 확인합니다. 디스플레이·카메라 등 무관한 설정은 지우지 않습니다.

nano 안에 넣을 설정 — 터미널 명령 아님
[all]
dtparam=spi=on
dtparam=i2c_arm=on
dtoverlay=mcp2515,spi0-1,oscillator=16000000,interrupt=25

저장: Ctrl+O → Enter → Ctrl+X. 이 단계는 CAN0 하나만 활성화합니다. CAN1·UART 예제를 통째로 추가하지 마세요.

ECU는 dtoverlay=ads1115를 추가하지 않습니다. 현재 제품 코드가 I²C 장치를 직접 사용합니다. 이전에 추가했다면 주석 처리하고, 다른 ADC 프로그램도 종료합니다.
터미널에 입력
sudo reboot
확인 결과
재부팅 후 해당 Pi에 다시 접속합니다. SSH 연결이 끊기는 것은 정상입니다.
STEP 05
ECU Pi4

can0를 찾고 500k로 켜기

기존 송신 프로그램과 can0를 자동 관리하는 서비스가 중지된 준비 상태에서 실행합니다.

터미널에 입력
ip link show can0
터미널에 입력
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 500000 listen-only off loopback off restart-ms 0
sudo ip link set can0 up
ip -details -statistics link show can0
확인 결과
bitrate 500000과 ERROR-ACTIVE를 확인합니다. 다른 노드 설정 중에는 송신하지 않습니다. 이 명령은 재부팅하면 다시 필요합니다.
여기서 멈추는 경우
can0가 없으면 다음 명령을 실행하지 말고 아래 문제 해결의 커널 로그를 확인합니다. BUS-OFF면 배선·종단·클럭·상대 노드 준비를 확인하며 자동 재시작으로 숨기지 않습니다.
STEP 06
ECU Pi4

I²C 장치가 생겼는지 확인

ADC 프로그램은 아직 실행하지 않습니다. 먼저 장치 파일만 확인합니다.

터미널에 입력
sudo modprobe i2c-dev
ls -l /dev/i2c-1
확인 결과
/dev/i2c-1이 보입니다. ADC 값은 제품 소스 준비 뒤 별도 단계에서 읽습니다.
여기서 멈추는 경우
장치 파일이 없으면 i2c_arm 설정과 재부팅을 확인합니다. 강제 주소 점유 옵션으로 우회하지 않습니다.

STEP 13
ECU → IVI → Pi3 순서

각 노드의 두 번째 터미널에서 1프레임 전송

격리된 이 시험 버스에서만 쓰는 통신 확인 프레임입니다. 제품 프로그램 실행 중에는 보내지 않습니다. 아래 세 명령을 한 Pi에서 모두 실행하지 마세요.

ECU 두 번째 터미널
cansend can0 123#0102030405060708
IVI 두 번째 터미널
cansend can0 123#1112131415161718
Pi3 두 번째 터미널
cansend can0 123#2122232425262728
마지막으로 세 노드 각각에서 확인
ip -details -statistics link show can0
확인 결과
송신한 장비가 아닌 다른 두 장비에서 해당 123 프레임과 바이트가 보여야 합니다. 송신 노드 자신의 echo만으로 성공 판정하지 않습니다. 오류 카운터가 증가하지 않는지 확인하고 candump를 Ctrl+C로 종료합니다.
여기서 멈추는 경우
이 시험은 배선·CAN 송수신 확인입니다. SecOC 인증·ADC·IDS·화면 성공은 아직 아닙니다. 오류가 생기면 다음 단계 대신 배선을 점검합니다.

⑥ 소스 준비 → ADC → 제품 ECU → IVI

여기부터는 이 작업 PC에서 수정한 소스가 각 Pi에 전달되어 있어야 합니다. 단순 git pull만으로 미커밋 변경이 전달되지는 않습니다.

ECU · 프로젝트 루트

ECU 빌드하고 ADC만 읽기

새 CAN 회로 설정은 유지하고, 기존 ADC 취득 프로그램은 종료합니다.

터미널에 입력
sudo apt install -y build-essential cmake libssl-dev libgtest-dev
cmake -S adaptive_ecu -B adaptive_ecu/build -DECU_BUILD_TESTS=ON
cmake --build adaptive_ecu/build -j2
ctest --test-dir adaptive_ecu/build --output-on-failure
터미널에 입력
sudo ./adaptive_ecu/build/ads1115_can_smoke
확인 결과
시험 통과 후 ADC_ONLY와 RAW/A0/PACK이 보이고 가변저항을 천천히 돌리면 값이 변해야 합니다. 확인 후 Ctrl+C로 종료합니다. 이 명령은 CAN 송신 없이 ADC만 확인합니다.
여기서 멈추는 경우
ADC ERROR, I²C 오류가 반복되면 다른 ADC 프로세스·배선·주소를 확인합니다. 이전 ADC 보드의 끝점 측정값을 새 보드 검증으로 쓰지 않습니다.
STEP 16
IVI · 프로젝트 루트

Qt와 대시보드 빌드

Debian 13에서는 저장소의 설치 스크립트를 사용합니다. 다른 OS에서는 이 스크립트가 중지되므로 Qt 6.8 이상 제공 여부부터 확인하세요.

터미널에 입력
sudo ./ivi_platform/scripts/install_rpi_dependencies.sh
cmake -S ivi_platform -B ivi_platform/build -DIVI_BUILD_QT_APP=ON -DIVI_BUILD_TESTS=ON -DIVI_BUILD_EXPERIMENT_TOOLS=ON
cmake --build ivi_platform/build -j2
ctest --test-dir ivi_platform/build --output-on-failure -E '^test_socketcan_receiver$'
test -x ivi_platform/build/ivi_dashboard && echo "대시보드 생성 확인"
IVI 화면의 데스크톱 터미널에서 실행
./ivi_platform/build/ivi_dashboard --demo normal
확인 결과
대시보드 파일이 존재하고 데모 화면이 보입니다. 확인 후 Ctrl+C로 종료합니다. SocketCAN 자동시험은 별도 vcan 환경이 필요해 이 명령에서는 제외했습니다.
여기서 멈추는 경우
CMake가 성공해도 Qt 6.8이 없으면 화면 바이너리가 안 생길 수 있습니다. offscreen 실행은 실제 터치 화면 확인이 아닙니다.
STEP 17
ECU와 IVI

동일한 시험용 SecOC 키 준비

기존에 사용하던 팀 합의 32바이트 키 파일을 사용합니다. 각 장비의 실제 경로를 아래 입력으로 지정합니다. 내용을 출력하거나 HTML·Git에 넣지 않습니다.

터미널에 입력
read -r -p "이 장비의 기존 시험용 키 파일 절대경로: " SECOC_KEY
sudo test -f "$SECOC_KEY" && sudo wc -c -- "$SECOC_KEY"
확인 결과
두 장비의 파일 길이가 32바이트인지 확인하고, 같은 키를 배치했는지는 기존 키 배포 기록으로 확인합니다. 길이가 같다고 키가 같은 것은 아닙니다.
여기서 멈추는 경우
기존 키가 없으면 먼저 합의된 키 배치가 필요합니다. 각 Pi에서 서로 다른 키를 새로 만들면 인증되지 않습니다.
STEP 18
IVI 화면 터미널 → ECU 터미널 순서

인증된 센서 값을 화면에 표시

IVI를 먼저 실행한 뒤 ECU 송신을 시작합니다. 각 터미널에서 위 SECOC_KEY 입력이 되어 있어야 합니다.

IVI 데스크톱 터미널
sudo setcap cap_net_raw=ep ./ivi_platform/build/ivi_dashboard
./ivi_platform/build/ivi_dashboard --interface can0 --secoc-key "$SECOC_KEY"

setcap은 이 로컬 바이너리에 CAN raw 소켓 권한을 부여합니다. 재빌드하면 다시 필요할 수 있습니다. 키 읽기 권한 오류가 나면 기존 키 배포 정책을 확인하고 파일을 모두에게 공개하지 마세요.

ECU 터미널
sudo ./adaptive_ecu/build/adaptive_ecu --interface can0 --sensor-mode ads1115 --secoc on --key "$SECOC_KEY"
확인 결과
ECU 센서 취득이 정상이고 IVI에 인증된 값이 갱신되는지 확인합니다. 노브를 천천히 돌려 전압 변화를 비교합니다. SOC는 노브 각도와 선형 관계가 아닙니다.
여기서 멈추는 경우
화면이 뜨는 것과 인증 성공을 구분하세요. MAC 오류·stale·ADC 오류가 있으면 로그부터 확인합니다. 종료는 각 터미널에서 Ctrl+C입니다.

⑦ IDS와 1,200회 실험 준비

정상 ADC·CAN·화면 경로를 확인한 뒤 진행합니다. 본실험 자동 실행에는 학습 데이터·SSH·키·원격 경로 준비가 추가로 필요합니다.

STEP 19

Python 실험 환경 준비

ECU는 IDS, Pi3는 공격과 일괄 실행을 담당합니다. IVI에도 remote_process 실행용 Python 환경이 필요하므로 같은 환경을 준비할 수 있습니다.

터미널에 입력

.venv-handoff/bin/python -m security.experiments.live_three_node --help

STEP 20
공격 Pi3 · 프로젝트 루트

원격 설정 파일 만들기

새 파일 이름을 입력합니다. 아래 복사는 이미 있는 설정을 덮어쓰지 않습니다.

터미널에 입력
mkdir -p tmp
cp -n security/experiments/live-three-node-settings.template.json tmp/live-three-node-settings.json
nano tmp/live-three-node-settings.json
  1. ECU·IVI의 SSH 사용자/호스트와 프로젝트 경로를 실제 값으로 교체합니다.
  2. ECU·IVI 키 경로와 ECU 로그 디렉터리를 지정합니다.
  3. ECU의 독립 정상 학습·보정 캡처를 준비합니다. 각각 frames.jsonl과 유효 manifest.json이 필요합니다.
  4. IVI 빌드 경로를 이번 안내의 ivi_platform/build/ivi_dashboard_experiment로 맞춥니다. 템플릿의 build-handoff와 다릅니다.
  5. ECU의 I²C/키 접근과 원격 supervisor의 종료 권한, SSH BatchMode와 필요한 sudo -n 권한을 확인합니다. blanket NOPASSWD를 추가하지 않습니다.
템플릿은 offscreen 수신을 사용하므로 실제 화면 표시 증거가 아닙니다. 기본 실험 입력도 constant이며 가변저항 실측과 별도입니다. 검토할 PR 브랜치의 live_three_node와 remote_process를 각 노드에 전달했는지 다시 확인하세요.

grep -n REPLACE tmp/live-three-node-settings.json
.venv-handoff/bin/python -m json.tool tmp/live-three-node-settings.json >/dev/null
확인 결과
REPLACE가 남지 않고 JSON 검사가 성공해야 합니다. 이것만으로 원격 실행 준비가 완료되는 것은 아닙니다.
여기서 멈추는 경우
학습/보정 캡처나 SSH 권한이 준비되지 않았다면 pilot을 실행하지 말고 아래 상세 실험 절차에서 준비합니다.

12회 파일럿 통과 후 1,200회 실행

학습·보정 데이터 생성부터 결과 해석까지는 상세 실험 절차를 따릅니다. 중단 캠페인 부분 재개는 제공하지 않습니다.

STEP 22
문제가 있는 Pi

can0가 없거나 BUS-OFF일 때

아래 읽기 명령으로 원인을 확인합니다.

터미널에 입력
sudo dmesg | grep -Ei 'mcp251|spi|can|i2c' | tail -60
ip -details -statistics link show can0
  • can0 없음: 활성 설정 파일·중복 overlay·재부팅·SPI CS/INT 선택 확인.
  • BUS-OFF: 세 노드 500000 일치, H/L 연결, 상대 노드 UP, 종단 두 개, 클럭 확인.
  • ADC 장치 사용 중: 기존 ADC 프로그램과 kernel ads1115 overlay 확인.
  • 화면 없음: DSI 데스크톱부터 확인. SSH 환경의 빈 DISPLAY와 실제 화면 고장을 혼동하지 않기.
  • 키 오류: 실제 파일 경로·권한·동일 키 배치를 확인. 키 내용은 공유하지 않기.
확인 결과
문제를 해결한 뒤 해당 노드의 CAN 활성화 단계부터 다시 확인합니다. 배선을 바꿀 때는 정상 종료 후 전원을 모두 뽑습니다.
