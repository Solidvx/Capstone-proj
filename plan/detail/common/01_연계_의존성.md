## 보안 상세 계획의 현행 과제 편입 — 2026-09-09

**선행과 적용:** 유선 IP+상호 TLS는 Q2의 계획상 우선안이다. 기존 ‘수단 미선정’은 제품 적용 확정 전 상태이며 설계 부재를 뜻하지 않는다. 양측 M1이 환경을, IVI M3가 producer를, ECU M4가 receiver/IDS consumer를 제공한다.

| 인계 | 제공자→수신자 | 인수 내용 |
|---|---|---|
| 플랫폼 | 양측 M1→M3/M4 | 대상 revision·TLS/권한·유선 가능성, 정상/거부 근거 |
| 계약/설정 | 공동→양측 | profile/schema·신원·epoch·기한·큐 예산, 채택 상태와 영향 문서 |
| 이벤트 | IVI M3→ECU M4 | 5종 의미·ready/최초 status·원장, 규약 §10의 worker/FIFO 순서 |
| 증거 | 양측 M5/M7→공동 | 동일 run의 producer/receiver/consumer, 설정 hash·단위·drop·복구 |

**수행:** [규약 및 송신 정책](../../../docs/development/security/인증이벤트_메시지_상태규약.md#planning-final)과 [설정 확정 절차](../../../docs/development/security/보안계획_구현전_인계_및_진행현황.md#planning-complete)를 양측 제공물의 인수 기준으로 사용한다. 실제 계약 전환 시 ICD/SRS/양측 SDD/ADR/TARA/TEST_PLAN과 구현·시험의 영향 목록을 하나로 검토한다.

**실패 대응:** 버전·사유·누적 정의가 다르면 제공 단계로 돌려보낸다. 상세 수단 적용 실패 시 근거와 대안을 보고하며 새 CAN ID·평문·사후 분석으로 자동 전환하지 않는다. 필요한 합의 후 양측을 함께 전환한다.

- [ ] 실제 제공물과 규약/설정이 일치하며 오류·차단·미검증 상태를 공동 원장에 남겼다.


## 1. 왜 병렬 개발이 가능한가

이 프로젝트의 설계 원칙은 **`docs/ICD.md`를 계약으로 삼아 양 노드를 독립 개발**하는 것이다. CAN 버스가 물리적으로 두 노드를 나누므로, 바이트 레벨 인터페이스만 합의하면 나머지는 각자 만들 수 있다.

```
┌────────────────────────┐                              ┌────────────────────────┐
│       Node A (ECU)     │      CAN Bus (ICD 계약)      │       Node B (IVI)     │
│  ┌──────────────────┐  │  0x100 BMS_Status (100ms)    │  ┌──────────────────┐  │
│  │ C++17 ECU        │  │ ─────────────────────────►   │  │ AOSP / Ubuntu    │  │
│  │ ├ BSW / CAN CDD  │  │  0x101 BMS_FailSafe (이벤트) │  │ ├ SocketCAN Rx   │  │
│  │ ├ BMS (EKF/SOH)  │  │ ─────────────────────────►   │  │ ├ Service (IPC)  │  │
│  │ ├ SecOC HMAC     │  │  0x102 / 0x103 SecOC MAC     │  │ └ Dashboard UI   │  │
│  │ └ Fail-safe FSM  │  │ ─────────────────────────►   │  └──────────────────┘  │
│  └──────────────────┘  │                              │  ┌──────────────────┐  │
│  ┌──────────────────┐  │  0x200 IDS_Alert (이벤트)    │  │ DevOps           │  │
│  │ Python           │  │ ─────────────────────────►   │  │ ├ Docker ARM64   │  │
│  │ ├ IDS (3종 탐지) │  │                              │  │ ├ CI/CD 4-Stage  │  │
│  │ └ 트래픽·실험    │  │   ICD가 정하는 것:           │  │ └ QEMU Test      │  │
│  └──────────────────┘  │   CAN ID·레이아웃·SecOC·HAL  │  └──────────────────┘  │
└────────────────────────┘                              └────────────────────────┘
```

- **M1**: ICD를 양측이 합의해 확정 → 계약 체결
- **M2~M3**: 각자 Mock/Stub으로 상대 없이 개발·시험 → 병렬
- **M4**: 물리 CAN 연결로 실제 통합 → 계약 이행 확인

### 대안 비교

| 접근 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **ICD 계약 기반 병렬 (채택)** | 병렬 작업, 독립 시험, 책임 경계 명확 | ICD 변경 시 양측 동기화 필요 | **채택** |

| 단일 코드베이스 통합 빌드 | 코드 재사용 | C++/Java/Kotlin/Python 혼재, 빌드 복잡, 책임 불명확 | 기각 |
| REST/gRPC 마이크로서비스 | 언어 독립 | CAN 100ms 주기 실시간성 보장 불가, 도메인 부적합 | 기각 |

**가장 위험한 구간**: M3의 SecOC C++ 이식 → HAL 검증. 여기가 밀리면 M4 물리 통합과 M5 실험이 연쇄로 밀린다.

> **핵심**: `0x100`은 `0x102` 검증을 통과한 뒤에 UI로 간다. 이 순서가 깨지면 변조 데이터가 화면에 뜨고 IT-004가 실패한다.

### 공식 측정 구간과 증적

근거 없는 내부 구간별 예상 ms 배분은 실행 기준에서 제외한다. 실제 정의는 [공동 통합시험](02_통합시험.md) §6을 따른다.

| 지표 | 공식 시험 | 계획에서 지킬 구분 |
|---|---|---|
| CAN 수신→UI 반영 | TC-PERF-001 | 평균·최대·필수 표본을 모두 검증. ECU 계산/송신부터 시작하는 다른 구간으로 대체하지 않음 |
| BMS 전송 주기 | TC-BMS-007, TC-PERF-002 | 100ms 주기 정확도와 end-to-end 지연은 별개 |
| 공격→0x200 수신 / 공격→UI 경보 | TC-PERF-003 / TC-INT-004 | 종료 지점을 분리해 같은 공격 이벤트로 계측 |

ADS1115 실제 취득은 ECU M3의 선행조건이며 위 센서 흐름의 CONSTANT/PROFILE_CSV는 시험 입력 예시다. 최초/오류/복구 품질, 인증 후 원자적 반영, 작업 복구는 공동 규약의 Q/R 정책을 함께 적용한다. 현 경로는 단일 프로세스 C++ Service와 Qt queued signal이며 D-Bus/gRPC 분리는 후속 범위다.

```

       │

       │
       ▼

       │
       ├─ ERR_HMAC_VERIFY_FAIL 로그
       ├─ 연속 실패 카운트 증가 (ICD §2.5.2)
       └─ **데이터 폐기 — 콜백 호출 안 함**
       │
       ▼

```

[Replay 공격]은 MAC이 유효해도 **롤링 카운터**가 막는다. 이미 쓴 카운터는 `delta == 0`이 되어 거부된다 (ICD §2.4).

### 시나리오 1 — ICD 확정이 밀림

| ECU 영향 | Mock 구현 지연. 단 `can_cdd`·`Publisher`는 ICD와 무관하게 병렬 진행 가능 |

| 완화 | ICD §1~2를 먼저 확정하고 §3(HAL)은 IVI가 병렬 작성. 90% 확정으로 시작 |
| 위험도 | **낮음** |

### 시나리오 2 — SecOC C++ 이식이 밀림

| 항목 | 내용 |
|---|---|

## 6. 기술 스택 간 연결

| 경계 | 전달 방식 | 계약 |
|---|---|---|
| C++ ECU → CAN | SocketCAN raw socket | ICD §1 바이트 레이아웃 |
| Python IDS → CAN | python-can | ICD §1.5 |
| C++ ↔ Python (SecOC) | 동일 HMAC 입력 규칙 | ICD §1.4, 테스트 벡터 |
| CAN → C++ HAL | SocketCAN read | ICD §1 |
| SocketCAN/인증 → Service | 프로세스 내부 C++ API | ICD §3 |
| Service → UI | Qt queued signal, QObject/Q_PROPERTY, QML binding | SDD-IVI |
| 소스 → ARM64 | Docker + toolchain | CICD_SPEC |
| 빌드 → 실장비 | SSH + systemd | CICD_SPEC |

**언어가 4개인데도 통합이 가능한 이유**: 언어 경계마다 **바이트 단위 계약**이 있고, 그 계약이 ICD 한 곳에 모여 있다. 계약을 벗어난 곳에서는 각자 자유롭게 만든다.

## 7. CI/CD가 협업에 미치는 영향

| 메커니즘 | 효과 |
|---|---|
| PR 필수 + 상대 Approve | 상대 코드를 반드시 한 번은 읽게 된다 |
| Stage 1 정적 분석 | 사소한 결함이 상대에게 넘어가지 않는다 |
| Stage 2 ARM64 빌드 | "내 PC에서는 되는데" 문제를 조기에 잡는다 |
| Stage 3 QEMU + Coverage | 시험 없는 코드가 머지되지 않는다 |
| Stage 4 배포 + Health Check | 실장비에서 도는 것까지 확인한다 |
| `interface-change` 게이트 | 계약 변경이 한쪽 판단으로 일어나지 않는다 |

**Coverage를 공유 품질 지표로 쓴다.** 어느 쪽 코드든 같은 기준(라인 ≥80%, Fail-safe 브랜치 100%)을 적용한다.

## 8. 협업 운영 규칙

- [ ] **인계물은 "만들었다"가 아니라 "상대가 쓸 수 있다"로 완료 판정한다.** SecOC 벡터를 넘겼으면 상대가 그것으로 검증에 성공했는지 확인한다
- [ ] 인계가 지연되면 **먼저 알린다.** 상대가 대기하는 시간이 가장 큰 손실이다
- [ ] 상대를 막고 있는 항목에는 `blocked` 라벨과 의존 Issue 번호를 남긴다
- [ ] ICD 관련 의문은 추측으로 구현하지 말고 미팅 안건으로 올린다
- [ ] 파라미터(IDS 임계 등)를 바꾸면 상대에게 사전 통지한다. 상대의 측정값이 바뀐다
- [ ] 측정·실험 시간대가 겹치면 미리 나눈다 (M5)
- [ ] 문서 교차 리뷰는 기한을 정한다 (48시간 권장)

## 10. 공식 요구사항에서 수행·검증까지의 매핑

기준은 [SRS](../../../docs/SRS.md)의 36개 FR·13개 NFR이다. 아래 요구 요지는 탐색용이며 수치·예외·계약의 정본을 대체하지 않는다. TC 열은 SRS 추적표의 연결을 보존하되 본문 불일치는 주의사항으로 드러낸다. **49개 행의 존재는 의미상 인수 완료나 기능 구현 완료가 아니다.**

각 행은 담당 상세에서 `요구 ID / 구현 대상의 실제 존재 여부 / 공식 TC 본문과 필요한 하위 시험 / 선행조건 / 실행 환경 / 대상 버전·해시 / 명령·원시 결과 / 판정·미실시 사유`를 기록한 뒤 닫는다. 증적은 해당 단계의 검증 절에 연결하며, 임시 로그만 남기지 않고 보존할 요약을 문서에 남긴다. 현재 모든 행의 실행 증적 인수는 미확인이다.

### 추가 불일치와 인터뷰

- **MAP-05 — SOH:** 과거 누적 방전과 열화 용량 혼동은 S-4=A로 정정했다. 현재 공식 시험은 초기 50Ah/추정 45Ah의 용량비 90%를 검증하며 실제 시험 전환·실행이 남아 있다.
- **MAP-06 — 실험 범위:** S-5=A로 ECU M4/M5와 공식 시험을 실제 CAN 4종 공격×3구성 기준에 맞췄다. 합성은 준비·분석용이며 실제 실행·증적은 남아 있다.
- **점수 방향:** TEST_PLAN TC-SEC-006의 정상 점수>공격 점수는 raw decision_function 기준이다. 현재 `anomaly()`는 부호를 반전하고 `wire_score()`는 큰 값이 이상인 전송값으로 매핑한다. 같은 이름으로 평균을 비교해 잘못된 합격/실패를 만들지 않도록 ECU M4의 증적에 표현 종류를 명시한다.

1차 전수 의미 검토와 MAP-05/06 방향 반영은 완료했지만 실제 시험과 세션·평가·장비 조건이 남아 있어 49개 요구 전체 인수는 보류다. 신규 제품 요구를 만들거나 공식 기준을 낮춘 것은 아니다.


## S-4~S-6 답변 반영 상태

- MAP-05: S-4=A로 SOH 용량비 기준을 SRS·SDD-ECU·TEST_PLAN·ECU M3에 맞췄다. 과거 인터뷰 대기 표기보다 이 결정이 우선하며 제품 시험 전환·실행은 남아 있다.
- MAP-06: S-5=A로 합성은 준비·분석, 4종 공격×3구성 최종 평가는 실제 CAN으로 확정했다. ECU M4/M5에 실행 과제를 반영했으며 실장비 인수 통과는 아니다.
- S-6=A는 준비 확인 후보의 검토 방향이다. [세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §12의 실패 경계·계약 영향 검토가 끝나기 전 최종 세션 계약으로 사용하지 않는다.



## SOC 정확도 검토 후속 — S-7

FR-BMS-002/TC-BMS-002는 S-7=A에 따라 합성 참 상태와 관측을 분리하고 NASA는 재생·데이터 검증으로 유지한다. [ECU M3](../ecu/M3_EKF_Failsafe_SecOC.md)와 TEST_PLAN의 S-21=A 고정 시나리오·합격 적용이 최신 기준이다. 생성 조건 미확정이라는 과거 상태는 종료했으며 생성기·제품 실행·정확도 인수는 남아 있다. SDD SOC 예측식의 부호·3600 단위 환산은 기존 코드·TC-BMS-001 이론값에 맞춰 정정했으며 새 인터페이스 변경은 없다.



## 복구 시간 검토 후속 — 4번 단계

FR-BSW-006·NFR-REL-001/002와 TC-BSW-006/007은 [ECU M3](../ecu/M3_EKF_Failsafe_SecOC.md)의 복구 상태·시간 구분을 따른다. 3초 임계·1초 감시는 유지하되 실제 감지 지연과 복구 완료 시간을 구분한다. 감지 횟수와 실제 재시작 실패 횟수는 다르다. snapshot 연령·종료 상한은 실제 작업 회수 측정과 S-7 공백 오차 검토 후 R-5=A 인터뷰로 정한다. 회수 불가 시 운영자 재시작이라는 기존 결정을 유지한다. CAN 수신 작업은 BMS 추정기 snapshot을 그대로 적용하지 않고 해당 작업의 별도 종료/진행 경계로 검증한다.

## TARA 범위 재검토 후속

[TARA §11](../../../docs/TARA.md#11-현재-실험-범위의-위협별-재검토)에 TS-001~007 각각의 현재 피해·기존 가정 문제·검증 연결을 기록했다. 과거 화재/주행 중 전원 차단 등급과 잔여 위험 수치는 현재 확정값으로 사용하지 않는다. Node A root 파일 권한과 물리 SD 탈취 대응 범위를 구분한다. S-9=A로 통제된 실험의 SD 관리와 위험 명시를 수행하고 오프라인 읽기 기술 방어는 필수에서 제외한다. 이 질문은 기존 서비스 실행 선택의 재승인이 아니다. 세션 후보·0x200 보호 범위·공격자 정보/물리 접근 가정의 근거 확인과 위험 등급 재확정이 남아 있어 일관성 최종 판정은 계속 보류다.

## 통합 직전까지의 자율 진행 범위 — 최신 지시

사용자는 추가 ‘계속’ 지시 없이 plan 개선·심사를 이어가도록 지시했다. PLAN 통합은 사용자가 별도로 지시하기 전 수행하지 않는다. 답변이 필요한 정책만 인터뷰 대기하며 독립적인 문서 검토/정정은 계속한다.

S-17=A·S-18=A 반영과 제한 모형 재검증을 수행했고, 세션 설계안 §25에 구세션 송신 종료/HAL 사유 표현 후보를 작성했다. ECU M3에는 합성 평가의 구체 조건·대조군/주 비교/민감도 후보를 작성했다. TARA의 입증되지 않은 의무 준수 표현은 참조와 준수 증거를 구분하도록 정정했다. 기존 위험 점수를 새 등급으로 추정하지 않았다.

S-19~S-21은 모두 A로 답변·반영됐으며, 운영 수치는 세션 설계안 §24와 R-5 측정/승인 절차를 따른다. 세부 ID/형식·HAL/양측 코드/시험의 공식 전환, 완료된 하드웨어/S-23 사실에 따른 위험 근거 평가와 Android 입력 확인, 최종 24개 계획의 의미·중복·경로/ID 재검사 후 네 기준 심사가 남아 있다. 현재 결과를 통합 준비 완료로 표시하지 않는다.


### 세션 계약 영향 정리 후 현재 상태

세션 설계안 §27에서 현재 ICD/실제 구현/승인 방향/후보 형식을 대조하고 전환 순서를 정리했다. S-19~S-21은 반영 완료다. 일반 BMS 큐 초과는 S-22=A로 신규 BMS 거부 정책을 확정했으며 실장비 인수는 남아 있다. 상세 형식의 최종 승인·운영 수치·독립 벡터/장비 인수는 별도 게이트다. 다음 독립 작업은 운영·복구 측정 조건과 위험 근거 정리이며 Android §6 입력 후 장비 실행 적합성을 심사한다.

### S-22 반영 후 다음 작업

S-22=A 반영 완료. 세션 설계안 §28에서 운영·복구 수치의 측정 담당/증적/승인 시점을 연결했다. 값은 실제 코어·장비 측정 전 미정이며 이것만으로 계획 최종 통과라 하지 않는다. 다음은 TARA 위험 근거와 Android 실행 조건 대조, 전체 계획 의미·중복·추적성 심사다.

### 위험·Android 조건 검토 후 종료 조건

TARA §12와 IVI M1의 장비별 호환성 인수표에 현재 증거·미확인 범위를 연결했다. S-23의 공개/접근/보관 사실은 반영 완료했고, Android 호환성은 확인사항 §6의 선택 환경 입력이 필요하다. 해당 정보 없이 점수·부팅·HAL/CAN/화면 호환성을 통과로 처리하지 않는다. 전체 문서의 정적 추적성 심사는 독립 수행 가능하며 최종 종합 판정은 이 보류 조건을 포함한다.

### S-23 답변으로 갱신한 실행 가정

현재 팀 내부·향후 private GitHub 관리, 팀원만 CAN 접근, 팀장(ECU 담당)의 장비/SD 보관을 확인했다. 논문 작성은 예정이며 공개 범위는 추후 점검한다. RPi SSH/vcan0 사용 경험은 사용자 보고로만 확인됐고 물리 CAN/Android 검증은 아니다. S-23-4는 백업 생성·공유 미수행으로 확인됐고 Android §6은 미입력이다. TARA의 과거 점수를 자동 승인하지 않으며 전체 심사의 보류 근거로 구분한다.

### S-23 추가 답변 후 현재 보류

S-23 사실 확인은 완료했다. SD 이미지/키 포함 복사본 생성·공유는 미수행이라는 사용자 답변을 TARA에 반영했다. Android A-1~A-13도 접수 종료됐으며 서버 주 빌드·2026-09-18 시연 마감과 소스 후보 대조를 반영했다. 대상 Android 호환성은 실제 시험 전 보류다. 상세 계약 승인과 실제 운영/위험 근거를 포함한 최종 심사는 남아 있다.

세션 후보의 ID·형식·타이머는 현행 ICD 시험에 조용히 적용하지 않는다. 전환 승인 후 ICD·양측 구현·공식 시험을 함께 맞추는 절차가 선행한다. 기존 TARA 위험 점수는 S-23 사실 확인만으로 재승인되지 않는다. 다음 심사는 상세 계약의 미결 승인 범위·위험 처리 근거와 네 기준 최종 판정이다.

## 14. plan 종합 판정과 다음 실행 과제 (2026-09-08)

이 절은 이전 실행 중심 판정 기록이다. 현재 계획 완성의 판단은 §15에 따라 제품 인수와 분리한다. 기존 미실행 시험을 통과로 바꾸는 것은 아니다.

**종합 판정: 최종 확정 보류.** 사용자가 요구한 네 기준 모두 통과라는 조건을 아직 충족하지 못했다. 계획 구조·알려진 불일치의 정정·담당/시험/증거 연결은 진행됐지만, 상세 계약과 대상 실행 가능성에 필요한 증거는 남아 있다. 문서 검토 단계가 끝난 것을 전체 프로젝트 계획 확정이나 제품 인수로 표현하지 않는다.

이번 정적 재검사는 활성 plan 24개, 코드 블록 밖 로컬 경로 453회, FR/NFR/TC/ADR 표기 738회를 대조해 오류 0건이다. 링크 앵커의 실제 렌더링이나 모든 문장의 의미상 정확성 증명은 포함하지 않는다. §10의 49개 요구 매핑 존재는 앞선 검사에서 확인했다. 이번 의미 검토에서는 상위 IVI의 실패 시 Plan B 전환 문장을 사용자 인터뷰·계약 승인 후 전환으로 정정했다.

### 자율 진행 후 실제 증거 갱신 (2026-09-08)

세션 설계안 §30~31에서 Windows C++·Python·.NET 29필드 교차 계산, 수신 거부 시험 6개, 결합 모형 변조/복구 10시나리오를 추가 검증했다. 이는 Linux/OpenSSL·Android·물리 CAN 시험의 완료가 아니다. 위 1번 과제의 호스트 사전 검증은 진척됐으며 대상 구현·전체 상태 경계 검증은 남아 있다.

Android 환경설정 §7에는 공개 manifest·보드·커널 식별자와 서버 실행 절차를 준비했다. A-14 답변은 접수됐고, 2026-09-08 사용자 지시에 따라 서버에서 받아오는 작업은 사용자 담당으로 현재 수행 범위에서 제외한다. 위 2번의 실제 빌드·HIDL 호출은 여전히 미검증이며 다른 실험의 선행 차단 조건으로 삼지 않는다.

S-21의 7개 합성 조건에 대한 계획 모델 사전 계산을 수행했다. 전압 무오차 주 비교 2개는 엄격 우위였으나 전압 바이어스 민감도 4개는 모두 역전됐다. [SOC 사전 실험 결과와 후속 계획](../../../docs/development/experiments/SOC_합성실험_결과.md)을 따른다. 제품 C++·장비 시험과 네 기준 최종 통과는 미완료이며 당시 Plan 통합은 보류 상태였다. 현재 현행 계획의 보안 상세 편입은 [현행 보안 인계 절](#security-integration)에 완료했으며 제품·장비 인수와 구분한다.

## 15. 계획 완성을 위한 의존성·검토 기준 (2026-09-08)

당시 범위는 문서 검토·계획 보완이었으며 제품 추가 구현·서버 가져오기·Plan 통합은 제외했다. 앞선 절의 과거 ‘입력 미정’·‘다음 실행’ 기록은 최신 사용자 답변과 실제 파일 상태를 대조해 읽는다. Android A-1~14, SOC-1=B, SOC-2=A, ADC-1/2=A 답변은 접수됐으며 이를 다시 질문하지 않는다. 현재 현행 계획의 보안 상세 편입은 [현행 보안 인계 절](#security-integration)에 완료했으며 제품·장비 인수와 구분한다.

### 계획 인수와 제품 인수의 구분

계획은 각 필수 과제의 담당·입력·선행조건·산출물·검증 방법·실패 시 처리·종료 기준이 서로 모순 없이 연결되어야 한다. 실제 빌드·장비 시험 결과가 아직 없는 과제는 실행 시 인수 항목으로 남길 수 있다. 다만 시험 방법 자체가 없거나 필수 설계 선택이 충돌하는 경우는 계획 결함으로 남긴다. 미래 측정값은 측정 담당·방법·확정 시점·초과 시 대응을 갖춘 미결 항목으로 관리한다. 이를 근거 없이 채우거나 제품 통과로 표시하지 않는다.

### 정확도·신뢰도·확장성 검토 기준

- 정확도: 요구·TC 식별자, 단위, 시각, 모델/설정, 목표·실측 표현을 원천과 대조한다. 계산 일치가 실측 정확도를 입증하지 않으며 독립 근거 없는 피팅 주장은 제거한다.
- 신뢰도: 실패·복구·중복·늦은 결과·유효값 부재·버전 불일치의 처리와 시험을 명시한다. ‘통신 유지’와 ‘센서 정상’, ‘코드 존재’와 ‘시험 통과’를 구분한다.
- 확장성: 현재 승인 범위는 단일 AIN0·10직렬 가상 모델이다. 채널/팩 모델/플랫폼 확장은 입력 단위·모델 식별·설정·관련 시험의 변경 영향으로 관리한다. 미사용 다채널 기능이나 범용 프레임워크를 선제 구현하지 않는다. ICD 변경은 기존 승인 절차를 따른다.

### 이번 검토 결과와 남은 문서 작업

상세 대조 2차: IVI M2의 기한 초과 자동 Plan B 전환을 사용자 판단으로 정정했다. ECU M6의 누락 결과 0% 대체를 오류 처리로 바꾸고 M5→M6의 분모·단위·실패 포함 인수 조건을 연결했다. 공동 제출의 양 노드 Linux 명령 예시를 Node A로 제한하고 Android 검증 절차를 분리했다. 전체 M1~M8의 모든 절을 완료 판정한 것은 아니다.

인계 경계 보완: ICD 부분 확정률·수동 배포·단축 안정성 시험이 공식 인수를 대체하는 듯한 표현을 정정했다. 공동 통합시험 §2.1에 계약·ADC/BMS·SecOC/HAL·Service/UI·대상 빌드·실험 보고의 6개 경계별 제출/인수 담당, 증거, 실패 복귀 조건을 추가했다. 전체 단계의 상세 누락 검토를 이 표 하나로 완료 처리하지 않는다.

후속 정리: ECU 상위 D2의 선형/2.6Ah 현재 구현 설명, ECU M3의 센서 계약 미승인·S-21 입력 미정·snapshot 모델 세대 설명, IVI M1의 Android 답변 미입력 설명을 최신 근거에 맞춰 정정했다. 제품 시험·장비 인수는 계속 미완료다. 이번 변경 후 활성 24문서의 코드 펜스·로컬 링크 검사를 다시 수행했으며 의미 검토 전체 완료로 표시하지 않는다.

정적 검사 결과: 활성 plan 24개 문서에서 코드 펜스와 코드 블록 밖 로컬 링크 460회를 확인해 오류 0건이었다. FR/NFR/TC/ADR 고유 표기 107개가 SRS·TEST_PLAN·ADR 원문에 존재함을 확인했다. 이는 ID 존재 검사이며 의미상 매핑·앵커 도달·모든 인수 조건의 완전성 검사를 대신하지 않는다.

확인된 결함: 과거 상태와 현재 상태 혼재, 계획 종료와 제품 인수의 혼동, 실제 셀 OCV 피팅 근거 부재. 계획 종료 경계를 이 절로 분리하고 SDD의 피팅 설명을 정정했다. 센서 상태 목표는 ICD §8에서 이미 승인됐으며 제품 전환은 별도다.

남은 순서: (1) 활성 문서의 오래된 상태·상수·승인 표현 정리 → (2) 위 의존성별 담당·산출물·실패 처리의 상세 누락 대조 → (3) 의미 검토와 경로/앵커/ID 검사 → (4) 남은 필수 설계 판단만 종합 인터뷰 → (5) 네 기준 및 정확도·신뢰도·확장성의 계획 인수 보고. 이번 절 추가만으로 전체 의미 검토를 통과했다고 하지 않는다. 당시 Plan 통합은 별도 사용자 지시 전까지 보류했다. 현재 현행 계획의 보안 상세 편입은 [현행 보안 인계 절](#security-integration)에 완료했으며 제품·장비 인수와 구분한다.

## 16. 미결 항목의 분류와 종료 관문 (2026-09-08)

최신 인수 검토는 [계획검토 결과 §7](../../../docs/development/reviews/계획_검토.md#plan-final-verdict)에 기록했다. 계획 문서 최종 확정과 제품·장비 인수를 구분한다. 아래 미결 관문은 계속 유지한다.

최신 결정: REP-1=A 답변을 반영해 M7/M8 재현성 차이를 5%p 이하로 통일했다. 해당 인터뷰는 종료됐고 아래 승인 대기는 과거 발견 이력이다. 기존 보안 TC와 재현성 추가 기준은 별도로 판정한다.

### 검증·실패 대응·완료 체크

사후 로그 상관분석은 실시간 경로의 증거를 보완한다. 가짜 이벤트 수신·전송 성공 로그만으로 Node A IDS 반영을 입증하지 않는다. 후보 설계 작성 완료와 제품 계약 채택·환경 검증 대기를 구분한다. 채택·검증 전에는 해당 제품 전환을 보류하고 독립 입력/규칙/계측 준비를 계속한다. 상대 제공물의 버전·reason·시각 의미가 다르면 제공자 단계로 복귀하여 재인수한다.

- [ ] Q2 수단별 영향안과 양측 제공/수신 책임을 작성했다.
- [ ] N01~N08 인계물의 기대값·실패값·환경·해시와 미검증 범위를 기록했다.
- [ ] 실제 전달·IDS 집계·기존 경보 회귀는 공동 통합의 실행 증거로 인수했다.
