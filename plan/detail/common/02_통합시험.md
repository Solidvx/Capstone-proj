## 보안 상세 계획의 현행 과제 편입 — 2026-09-09

**선행:** COM-INT-01/COM-EVAL-01에서 양측 실제 구현·설정·계약 인계 상태를 확인한다. 기존 공식 TC와 성능 기준을 유지한다.

**수행:** [Q2-D 시나리오](../../../docs/development/security/인증이벤트_전달_설계안.md)와 [Q2-P01~P08](../../../docs/development/security/인증이벤트_메시지_상태규약.md#planning-final)을 기존 보안 통합의 하위 사례로 편입한다. 정상/거부 인증→producer→receiver→IDS 소비를 같은 epoch/event_seq/run으로 연결하고 기존 0x200·BMS/UI 회귀를 확인한다.

**추가 경계:** ready 직전/중/후 생성과 옛 worker, FIFO 포화 시 status 예약, snapshot 교체, 부분 read/write·종료 취소, 설정 변경과 새 epoch, 재연결 예산, 로그/consumer 실패, 인증서 갱신을 포함한다. 일반 MAC 거부·source 만료·프로토콜 오류·receiver 폐기를 구분한다.

**증거·실패 대응:** 각 사례는 기대값/관측값/원본/환경/판정/복구로 한 번 기록하고 양측 M7에서 참조한다. 같은 손실을 producer drop+event gap+receiver drop으로 합산하지 않는다. 모형 결과와 실장비 결과를 분리하고 공식 시험의 미탐·미달을 INVALID로 숨기지 않는다.

- [ ] Q2-D/P·Q1 A5/A6와 기존 공식 시험의 대응 및 실제 실행/미검증을 기록했다.
- [ ] 재연결/포화/종료에서도 안전·수신·UI 기능이 보존되는지 실제 증거로 판정했다.


<a id="m5-handoff-order"></a>
### M5 공동 인계 순서 — 상대 단계 전체 완료를 기다리지 않음

1. ECU·IVI가 공동 계측 정본을 확인하고 run/trial 식별, 입력·구성·시계·단위·증거 형식을 사전 합의한다. run 식별은 실험 결과가 아니라 준비 산출물이다.
2. ECU는 M4 송신/공격/IDS 준비와 시행 manifest를, IVI는 M3/M4 수신/UI 준비와 계측 어댑터를 제공한다. 양측 M5의 준비 작업은 병행한다.
3. 준비물을 공동 인수한 뒤 같은 run으로 실행하고 ECU/CAN/IVI 원본을 수집한다.
4. IVI는 수신/UI 구간과 계측 유효성·손실을 ECU에 인계한다. ECU는 공격/판정 원장과 결합해 집계하고, 양측이 대조한 결과를 공동 인수와 M7로 넘긴다.

원본 부족·식별 불일치는 해당 제공물만 재인수한다. ECU M5 완료와 IVI M5 완료를 서로의 착수 조건으로 두지 않는다. 단계별 최종 완료는 각자의 실제 인수 증거로 판정한다.

### 보안 하위 사례별 인수 기록

아래는 향후 실행에서 작성할 기록 규칙이며 시험 통과 기록이 아니다. [Q2-D01~D08](../../../docs/development/security/인증이벤트_전달_설계안.md)과 [Q2-P01~P08](../../../docs/development/security/인증이벤트_메시지_상태규약.md#planning-final)의 입력·기대 결과를 정본으로 삼고, 각 ID마다 독립된 판정 행을 작성한다. N01~N08의 역할 배정은 [공동 의존성](01_연계_의존성.md#security-adoption)을 따른다.

| 사례 | 준비·원본 작성 담당 | 공동 인수에 필요한 증거 |
|---|---|---|
| Q2-D01·D08 | IVI M3 verifier/producer, ECU M4 receiver/IDS | 동일 사건의 인증 결과·commit·수신·IDS 소비와 raw/IF 회귀 |
| Q2-D02·P08 | 양측 M1 환경, IVI M4 배포, ECU 수신 담당 | 신원·신뢰 설정 식별, 허용/거부 연결 결과, 진단 입력 수와 정상 CAN 유지 |
| Q2-D03·P04 | 양측 M3/M4 송수신 담당 | 분할 입력·길이/타입 오류·부분 송신·취소의 입력과 기한/자원/종료 결과 |
| Q2-D04·P01·P05 | IVI producer, ECU receiver | epoch·순번·cutoff·profile별 원장과 중복/과거 자료 미반영 |
| Q2-D05·P06 | 양측 송수신·배포 담당 | 단절/재시작/동시 연결의 상태 전이·backoff·시도 예산과 복구 결과 |
| Q2-D06·P02·P03·P07 | IVI 큐/worker, ECU collector, 양측 M5 계측 | FIFO·status snapshot·drop 구분·종료 결과와 verifier/UI 비차단 증거 |
| Q2-D07 | 양측 M5 계측 | 각 시계의 의미·CAN 수신 유무·status·freshness와 유효한 계산 구간 |
| N01~N08·Q1 A5/A6 | 공동 의존성의 해당 ECU/IVI 담당 | 입력·설정·공격 주입/복구·Findings·분모·자원 측정·원자료 연결의 해당 증거 |

공동 통합 담당이 양측 원본을 대조해 판정하고, 양측 M7과 공동 제출은 같은 기록을 참조한다. 모든 행에 `사례 ID / 담당 / run·trial / 환경(모형·vcan·실장비) / 소스·설정 식별 / 입력·주입 절차 / 기대 결과의 정본 위치 / 관측 결과 / 판정 / 원본 경로·해시 / 관련 공식 TC 또는 보조 사례 / 검토자 / 실패·재실행 조건`을 기록한다. 증거가 없으면 미실행 또는 미검증으로 남긴다.

Q2 보조 사례를 공식 TC와 동일시하지 않는다. 인증·pending, IDS/경보, 연결, 성능의 기존 공식 TC 대응은 하단 검증 절을 따르며, 직접 대응이 없는 경우 `보조 사례 — 공식 TC 없음`으로 기록한다. 같은 실행을 여러 사례에 참조할 수 있지만 각각의 기대 결과와 판정은 생략하지 않는다. 실패를 계측 invalid로 숨기거나 미검증을 통과로 처리하지 않는다.

### 2.1 인계 산출물과 실패 시 복귀 기준

아래는 후속 개발에서 사용할 인수 절차다. 계획 검토 중 실제 빌드·장비 시험을 모두 실행하라는 뜻이 아니다. 송신 담당은 증거와 한계를 전달하고 수신 담당은 자신의 인수 시험 결과를 기록한다. 파일이 있다는 이유만으로 후행 단계를 통과시키지 않는다.

| 인계 경계 | 제출 담당 → 인수 담당 | 최소 인계 산출물·확인 | 실패 시 복귀·종료 기준 |
|---|---|---|---|
| 계약 → 독립 개발 | 공동 → ECU/IVI | ICD 기존 형식·승인 목표·후보 구분, 적용 버전, FR/TC 연결 | 미승인·혼합 형식은 계약 검토로 복귀. 합의된 범위의 Mock 개발만 계속 |
| ADC → BMS | ECU BSW → ECU BMS | 단위·변환 설정·새 변환 식별·오류/복구 상태·시간 마감 시험 | 전송 실패/늦은 결과를 새 정상값으로 세면 취득 단계로 복귀. 실제 취득·복구 증거 전 ADC 인수 보류 |
| ECU/SecOC → HAL | ECU → IVI | 명시적 더미 벡터·바이트 구성·정상/거부 기대값·소스 식별 | MAC/상태 불일치는 인코딩·검증 단계에서 재현. 값이 맞는 사례만 골라 통합하지 않음 |
| 수신/인증 → Service/UI | IVI SocketCAN → Service → Qt UI | 동일 snapshot의 값·stale·sensorState, 인증·정상 수신 시각의 의미 | 필드 누락·오류값 정상 표시·이전 상태 혼입은 전달 경계로 복귀. Mock과 실제 CAN 결과를 분리 |
| 대상 빌드 → 물리 통합 | ECU/IVI → 공동 | 양측 이미지/소스 식별·부팅·장치 설정·통신 smoke·계약 모드 | 플랫폼 실패는 해당 환경 단계로 복귀. 단위 로직 검증으로 물리 인수를 대신하지 않음 |
| 실험 → 보고·제출 | ECU 실험/IVI 계측 → 공동 리뷰 | 조건·분모·단위·반복·원시 출력 위치·해시·실패 포함 결과 | 재현 불가/분모 불명/미달은 실험 설계·실행으로 복귀. 기준 변경은 승인 절차 후 재검증 |

## 3. 물리 CAN 연결

### 3.1 배선

```
[RPi4-A]──SPI0──[MCP2515-A]──CANH──┬────────────┬──CANH──[MCP2515-B]──SPI0──[RPi4-B]
                                    │            │
                [MCP2515-A]──CANL──┬┴──120Ω     120Ω──┴┬──CANL──[MCP2515-B]
                                   └─────────────────────┘
                                    양쪽 끝에 종단저항
```

**MCP2515 ↔ RPi4 SPI (양쪽 동일)**

| MCP2515 핀 | RPi4 |
|---|---|
| VCC | 5V — 브레드보드 레일에서 MCP2515와 LC#1·LC#2 HV로 분배 |
| GND | GND (Pin 6) |
| CS | CE0 (Pin 24, GPIO 8) ↔ LC#1 Ch3 ↔ MCP CS |
| SO (MISO) | Pin 21 (GPIO 9) ↔ LC#1 Ch4 ↔ MCP SO |
| SI (MOSI) | Pin 19 (GPIO 10) ↔ LC#1 Ch2 ↔ MCP SI |
| SCK | Pin 23 (GPIO 11) ↔ LC#1 Ch1 ↔ MCP SCK |
| INT | Pin 22 (GPIO 25) ↔ LC#2 Ch1 ↔ MCP INT |

각 노드에서 LC#1·LC#2의 LV는 3.3V, HV는 5V에 연결하고 모든 GND를 공통으로 한다. 상세 물리 핀과 전원 분배는 [사용자 기존 배선표](../../../하드웨어%20정보/컨버터O_배선완결판.html)를 따른다. 전원 인가 전 두 노드 각각 HV/LV 역결선과 단락을 확인한다.

**CAN 버스**

| 연결 | 설명 |
|---|---|
| A CANH ↔ B CANH | 신호선 H |
| A CANL ↔ B CANL | 신호선 L |
| 120Ω (CANH–CANL) | **양쪽 끝 2개.** 모듈에 내장돼 있으면 점퍼 확인 |

> 종단저항은 두 개다. 하나만 달거나 중간에 달면 반사가 생겨 통신이 불안정해진다.

### 3.2 노드별 CAN 설정 확인

> 아래 sudo·부팅 파일 명령은 Node A Linux 환경의 예시다. Node B Android에는 선택 이미지의 device tree·커널 모듈·init·SELinux 조건을 확인하여 별도 절차를 작성한다. 같은 버스 조건을 맞추는 것과 같은 OS 명령을 실행하는 것은 다르다. 장비 정보 입력 전 예시를 확정 절차로 사용하지 않는다.

```bash
# /boot/firmware/config.txt (이미 설정돼 있으면 생략)
# dtparam=spi=on
# dtoverlay=mcp2515-can0,oscillator=8000000,interrupt=25

sudo ip link set can0 up type can bitrate 500000
ip link show can0
# 기대: can0: <NOARP,UP,LOWER_UP> mtu 16 ... state UP
```

**비트레이트가 양쪽 동일해야 한다.** 하나라도 다르면 프레임이 전혀 오가지 않는다.

### 3.3 양방향 통신 확인

**물리 smoke 전용:** 아래 4바이트·역방향 프레임은 ECU/HAL/IDS 애플리케이션을 종료한 상태에서 배선·드라이버만 확인하는 입력이다. 정식 ICD 메시지·방향의 합격 증거로 사용하지 않는다. 시험 후 controller loopback을 해제했는지 확인하고 상대 노드 캡처로 수신을 증명한다. 정식 계약 시험은 §4.5 및 §5의 8바이트·정방향·인증 모드로 진행한다.

```bash
# Node A:

# Node B 기대: can0  100   [4]  DE AD BE EF
```

```bash

# Node A:

# Node B:
```

## 4.5 중간 통합 시험 — 구현 전에 ICD 레이아웃을 조기 검증한다

IT-001~005는 양측 구현이 끝나야 수행할 수 있다. 그런데 **ICD 해석이 어긋났는지는 그보다 훨씬 먼저 알 수 있다.** `cansend` 한 줄이면 된다.

M3 단계(양측 파서·인코더 초안이 나온 시점)에 아래를 수행한다. 물리 CAN이 아직이면 각 노드의 `vcan0`에서도 레이아웃 대조는 가능하다.

### 4.5.1 기본 송수신

이 절의 원본 프레임 단독 입력은 parser 시험 또는 명시적인 인증 OFF 시험이다. SecOC ON 통합시험에서는 원본만으로 UI가 갱신되면 안 되며, 더미 키로 생성한 유효한 `0x102`/`0x103` 쌍을 제공한다. 정상 벡터는 8바이트인지 기계 검사하고, 비정상 DLC는 별도 거부 시험으로 관리한다.


```bash
# Node B
candump can0

# Node A — ICD §1.2 기준으로 손으로 만든 0x100 프레임
cansend can0 100#C83C106800144100
```

```text
기대 (Node B): can0  100   [8]  C8 3C 10 68 00 14 41 00
```

### 4.5.2 레이아웃 대조 — 양측이 각자 디코드해 값을 맞춘다

위 payload를 ICD §1.2로 풀면 아래가 나와야 한다. **문서를 낭독하지 말고 각자 코드로 디코드해 비교한다.**

| Byte | Raw | 필드 | 스케일 | 결과 |
|---|---|---|---|---|
| 0 | `0xC8` = 200 | SOC | ×0.5 | **100.0%** |
| 1 | `0x3C` = 60 | SOH | ×0.5 | **30.0%** |
| 2-3 | `0x1068` = 4200 | Voltage (uint16 BE) | ×0.01 | **42.00V** |
| 4-5 | `0x0014` = 20 | Current (int16 BE) | ×0.1 | **+2.0A** (충전) |
| 6 | `0x41` = 65 | Temperature | −40 | **25°C** |
| 7 | `0x00` | Reserved | — | 0 |

**부호·오프셋을 잡아내는 추가 벡터** — 이 둘이 실제 결함을 드러낸다.

```bash
# 방전 전류: 0xFFEC = -20 -> -2.0A  (int16 캐스트 누락 시 +6553.2로 읽힌다)
cansend can0 100#963C1068FFEC4100

# 고온: raw 130 -> 90C  (int8_t 캐스트 시 -166으로 깨진다)
cansend can0 100#963C106800148200
```

### 4.5.3 이벤트·경보 프레임

```bash
# 0x101 Fail-safe: NORMAL(0) -> WARNING(1), reason 0x01, SOC 20.0%, 25C
cansend can0 101#0001012841000000

# 0x200 IDS_Alert: Flooding(4), score 2.55, suspect 0x0100
cansend can0 200#04FF010001020304
```

| 프레임 | 기대 해석 |
|---|---|
| `0x101` | prev=0, new=1, reason=`0x01`, socAtEvent=20.0%, tempAtEvent=25°C |
| `0x200` | attackType=4, anomalyScore=2.55, suspectCanId=`0x0100`, timestamp=`0x01020304` |

### 4.5.4 합격 기준

- [ ] 양측이 같은 바이트열에서 **같은 값**을 얻는다
- [ ] 전류 부호(충전 `+`, 방전 `−`)가 일치한다
- [ ] 온도 raw > 127에서 값이 깨지지 않는다
- [ ] `0x101` 사유 코드가 ICD §1.3 표와 일치한다 (`0x07` 포함)
- [ ] 불일치가 나오면 **어느 쪽이 ICD와 맞는지** 먼저 판정한다. 구현이 틀렸으면 구현을 고치고, ICD가 모호하면 [00_협업_규약](00_협업_규약.md)의 `interface-change` 게이트로 간다

> 이 시험은 M4 물리 통합 전에 인터페이스 불일치를 걸러내는 **조기 게이트**다. 여기서 통과하면 IT-001~005에서 레이아웃 문제로 시간을 잃지 않는다.

이 시험은 ECU 내부 SOC 추정·FSM·송신부터 IVI 표시까지 검증한다. `--soc`는 없으며, potentiometer 모드 선택만으로 값을 조작할 수 없다. 현재 `main.cpp`에는 `setAdc*()` 입력 연결이 없다.

**선행 산출물 (ECU M3에서 신규 구현·검증):** `adaptive_ecu/data/failsafe_demo.csv`와 실행 manifest. 입력 단위·모델 용량·OCV·초기 상태·dt·전이 예상 순서를 기록하고, 독립 시험에서 프로파일을 실행해 WARNING → CRITICAL이 발생함을 먼저 증명한다. 기존 battery_profile.csv를 검증 없이 대신 사용하지 않는다.

```bash
# 신규 프로파일 검증 및 ECU M3 완료 후, 프로젝트 루트에서 수행
./adaptive_ecu/build/adaptive_ecu --interface can0 --secoc on     --sensor-mode profile_csv --profile adaptive_ecu/data/failsafe_demo.csv
```

- [ ] 초기 상태·모델 설정이 프로파일 manifest와 같음
- [ ] ECU 추정 SOC가 WARNING 조건을 먼저 만족하고 이후 5% 미만으로 내려감
- [ ] `0x101`의 CRITICAL 전이·사유·당시 SOC와 `0x103`의 인증 확인
- [ ] 인증 성공 후 Node B 경고 Dialog와 SOC 색상 확인, 실패 인증으로 전이하지 않음
- [ ] 예상 순서·실제 전이 시각·candump·화면 증적 기록

프로파일로 결정적인 재현이 불가능하면 단위·정규화 문제를 해결한다. 시험 입력 어댑터가 필요하면 ECU M3 과제로 구현하고 생산 실행 경로와 활성 조건을 구분한다. 프레임 직접 주입에 의한 IVI 화면 시험은 보조 시험이며 이 ECU 통합시험 완료를 대신하지 않는다.

### IT-004 — 변조 MAC 차단 (TC-INT-002)

```bash
# Node A: 정상 ECU 실행
./adaptive_ecu/build/adaptive_ecu --interface can0 --secoc on &

# 아래는 바이트 형식 예시이며 단독으로 MAC 실패 시험을 보장하지 않는다.
# 실제 시험은 아래 입력 통제 절차를 따른다.
# 공격자 역할: 가짜 MAC을 가진 0x102 주입
cansend can0 102#DEADBEEF00000001
# TruncatedMAC=0xDEADBEEF (가짜), RollingCounter=1
```

**Pass 기준**

- [ ] Node B 로그: `ERR_HMAC_VERIFY_FAIL`
- [ ] **가짜 데이터가 UI에 반영되지 않는다**
- [ ] 정상 `0x102`는 계속 정상 처리된다

> 합격은 해당 변조 MAC의 거부와 위조값 미반영을 같은 사건으로 확인하는 것이다. 정상 인증 데이터의 UI 갱신은 유지되어야 하며, 화면 전체의 정지를 합격 기준으로 삼지 않는다.

**입력 통제:** 격리된 시험 fixture에서 정상 송신과 주입 순서를 제어한다. 수신 이력을 알고 있는 상태에서 허용 윈도우의 counter와 대응 raw payload를 정하고, 시험용 더미 키로 생성한 정상 MAC의 1비트만 반전한다. raw→auth 순서와 pending 유효 시간 안의 도착을 보장하고 그 사이 다른 raw에 의한 교체를 방지한다. counter=1 고정·orphan auth·pending 만료로 거부된 경우는 MAC 실패 시험 통과가 아니다. MAC 실패 시 counter·기존 반영값 보존을 확인한 뒤, 정상 쌍의 수신·갱신과 정상 송신 재개를 검증한다. 시험 종료·예외 시 송신을 복구하고 제품 counter 초기화로 시험 조건을 만들지 않는다. 위조 MAC 거부와 별도의 counter 거부 사례를 각각 기록한다.

| TC-INT-004 / FR-SEC-006, FR-SEC-007, FR-IVI-006 | 실제 공격 시작 → 해당 경보 화면 표시 | 공식 통합시험의 ≤3초, 위 수신 지연과 별도 열에 기록 | 공동 M4·M7, 화면·공격·경보 증적 |

TEST_PLAN v1.4는 TC-PERF-001을 T1→T4로 정정했다. 이 정의를 유지하며 ECU→HAL 수치는 진단값으로 별도 기록한다. SRS의 NFR 추적표 일부 TC 연결도 TC 본문과 대조한다. NFR-QA-003은 TC-CI-002, NFR-PERF-003은 TC-PERF-003을 직접 근거로 사용하며 연관 통합시험도 함께 남긴다.

### 6.2 원시 데이터와 유효성

- 기간·ID 필터는 캡처 후 명시적으로 적용한다. 다른 ID가 섞인 전체 로그의 프레임 delta를 `0x100` 주기로 사용하지 않는다. 캡처 어댑터는 실제 도구 출력 fixture로 검증하고 절대 또는 단조 수신 시각을 정규화한다.
- 공통 키는 `(run_id, boot_id, sample_id)`다. Node B 수신 시 로컬 sample_id를 부여해 내부 진단 문맥으로 T2~T4까지 전달한다. SecOC 카운터는 별도 메타데이터이며 필수 키가 아니다. 비인증 Config 1도 같은 방법을 사용한다. CAN Reserved·HAL 공용 계약에는 측정용 필드를 임의로 추가하지 않는다.
- 지연 입력은 `run_id,boot_id,sample_id,stage,timestamp_ns`; 주기는 `run_id,boot_id,sample_id,can_id,timestamp_ns` CSV다. 정수 나노초·시계 종류·시작/종료 조건을 manifest에 기록한다. 행 누락·중복·비정상값·음수·순서 역전은 조용히 제외하지 않고 INVALID로 판정한다.
- 렌더되지 않은 표본도 manifest와 원시 로그에 남긴다. coalescing·프레임 드롭·측정 손실을 구분하고 손실 수·분모를 보고한다. 표본을 골라 합격시키지 않는다. 측정 구간에 수집 손실이 있으면 공식 PASS를 보류하고 원인을 해결해 재측정한다.
- 서로 다른 Node의 monotonic 값을 직접 빼지 않는다. 공격→경보 측정은 시작/수신을 같은 관찰 시계로 기록하거나, 양측 시계를 동기화하고 측정 전후 오프셋·오차 상한을 확보한다. 상한을 확보하지 못하면 INVALID다. 관측 지연에 오차 상한을 더해도 기준 이내여야 PASS다.
- 공격 trial마다 수집기를 먼저 시작하고 준비 완료를 확인한 뒤 공격 프로세스가 **첫 주입 시점**을 기록한다. 셸 명령 실행 시각을 주입 시각으로 대신하지 않는다. 양 노드 로그를 같은 분석 호스트로 수집하고 trial ID·공격 유형·suspect ID·주입 시간창을 대조한다. 관련 없는 이전 `0x200`을 사용하지 않는다.
- 미검출·미수신·미표시를 지연 0이나 누락행으로 처리하지 않는다. 실행은 유효하지만 반응이 없으면 FAIL, 계측 자체가 깨졌으면 INVALID이며 둘 다 공식 PASS가 아니다.

### 6.3 분석 도구와 실행 순서

1. IVI M3에서 계측 훅·캡처 어댑터를 구현한다. 위 정규화 형식과 실제 프레임 수를 대조하는 fixture 시험을 작성한다.
2. [IVI M5](../ivi/M5_성능_UI개선.md)에서 분석 도구를 구현·회귀 검증한다. 정상·경계·50ms 주기·음수·중복·누락·다른 run/boot·ID 혼합 입력을 포함한다.
3. 단위 분석 검증 → vcan 파이프라인 → 물리 CAN/실기기 순으로 수행한다. 합성 입력 검증을 실제 장비 성능 증거로 사용하지 않는다.
4. 결과는 `PASS / FAIL / INVALID / NOT_RUN`으로 기록한다. CLI는 PASS만 종료 코드 0, FAIL은 1, INVALID·오류는 2를 사용한다. 모든 요약에는 단위·측정 구간·표본 수·손실·오차 조건을 포함한다.

## 7.1 물리 장비·장애 복구 인수

장비별 배선·PGA·클록·Android 이미지는 확인사항의 사용자 입력 후 확정한다. 다음 검사는 실제 장비 실행 과제이며 수행 완료가 아니다.

| 단계 | 확인 항목 | 완료 증거 |
|---|---|---|
| 전원 전 | 모듈·트랜시버 전압·SPI/INT/I2C pull-up·CANH/L·기준 GND·종단 위치·클록 | 제품 사양과 대조한 배선표, 각 노드 전원·전류 용량·접지 방식 |
| 단일 노드 | 안정된 부팅·driver·can0·bitrate·키 접근·ADC 입력·Android HAL 접근 | 버전/설정 manifest, 실제 로그, 과열·저전압 점검 |
| 두 노드 | 양방향 peer 캡처·ACK·필터·bus 상태·오류/드롭 | 로컬 loopback만 본 결과와 구분, 상대 노드 캡처와 송신 계수 대조 |
| 장애 | 케이블 분리·bus-off·프로세스 종료·노드 재부팅·ADC 분리 | 장애 전후 counters·마지막 유효 BMS·stale·로컬 Fail-safe·복구 시각 |
| 복구 | 원인 제거 후 CAN·서비스·인증·BMS·화면 순차 확인 | is-active뿐 아니라 실제 유효 데이터, 세션 상세 승인 후 재부팅 시험 |

물리 배선·전원 변경은 전원을 차단하고 제품 사양을 확인한 뒤 수행한다. CANH는 CANH, CANL은 CANL에 연결하며 접지/절연 구성은 모듈 사양으로 확정한다. 종단저항은 버스 양 끝을 기준으로 확인한다. 자동 bus-off 재시작 정책·복구 시간은 설정과 실제 결과를 기록하고 무조건 재시작 명령 반복으로 정상 판정하지 않는다.

## 8. 실패 시 대응

**`can0` 인터페이스가 안 보임**
```bash
dmesg | grep mcp251x
```
드라이버가 안 잡히면 [ECU M1](../ecu/M1_환경구축_ICD확정.md) 5장 순서로 진단한다.

**프레임이 오가지 않음**
1. 양쪽 비트레이트 500000 일치
2. 종단저항 120Ω 두 개
3. CANH↔CANH, CANL↔CANL 연결과 제품별 기준 GND/절연 구성
4. 한 방향만 되면 peer 수신 필터·송신 권한·ACK·드라이버·배선을 각각 확인한다

**`bus-off` 에러**
```bash
sudo ip link set can0 down
sudo ip link set can0 up type can bitrate 500000
ip -s link show can0        # 에러 카운터 확인
```
반복되면 배선·종단·전원 노이즈를 본다.

**SecOC가 항상 실패**
1. 양 노드 키 해시 일치 (`sha256sum`)
2. 키 파일 32바이트
3. HMAC 입력이 14바이트(CAN_ID 2B + Counter 4B + Payload 8B)
4. 검증에 쓰는 CAN ID가 **원본 `0x100`** 인지 (인증 프레임 ID 아님)
5. 현재 고정키 계약과 새 세션 목표를 구분한다. MAC 유효성만으로 재부팅을 판단하거나 카운터를 되돌리지 않는다. 세션 계약 미확정 상태는 보안 복구 인수 보류다.

**IT-004에서 가짜 값이 화면에 뜸**
- `0x100`을 `0x102` 검증 전에 전달하고 있다. **이것은 통합 시험 실패이자 보안 결함이다** ([IVI M3](../ivi/M3_HAL_Service_대시보드.md) 3.2)

**IT-005에서 배너가 3초를 넘김**
- 구간을 나눠 본다: IDS 윈도우(1초) / 판정 / `0x200` 송신 / 수신·파싱 / UI
- 미달이면 실제 수치를 기록한다. 통과로 적지 않는다

**물리 통합 자체가 안 됨**
- `vcan0` 단일 노드 구성으로 논리 통합만 검증하고 진행한다
- **IT-001~005는 미완료로 표기한다.** `vcan0` 결과를 물리 통합 결과로 적지 않는다

### Q 답변 반영 추가 인수 시나리오 — 계약 확정 후 수행

공동 규약의 Q 공통 정책을 아래 조건으로 검증한다. 새 공식 TC ID를 임의 부여하지 않으며 양측 M3에서 TEST_PLAN의 대응 TC와 하위 조건을 연결한다.

| 입력/장애 | 기대 결과 |
|---|---|
| 최초 유효 측정 전 ADC 오류 | 측정값 없음·센서 오류, 초기 상수를 실제 측정값으로 표시하지 않음 |
| 정상 측정 후 ADC 오류, 인증된 통신 지속 | 마지막 정상값·오류 표시, 마지막 정상 데이터 수신 기준점 유지(R-2=A), 통신 단절과 구분 |
| 정상 2회→오류→정상 3회 | 오류에서 횟수 초기화, 마지막 연속 세 번째 새 입력에서 복구; 동일 샘플/프레임 반복으로 조기 복구하지 않음 |
| 센서 오류와 기존 CRITICAL/SHUTDOWN 동시 | 마지막 확정 Fail-safe 보존, 센서 오류만으로 새 사유/정상 복귀 없음 |
| 센서 오류 중 통신 단절·세션 재수립 | 통신/인증 복구와 센서 복구를 독립 판정, 센서 오류만으로 재인증 반복 없음 |
| 정상 snapshot 복원 | 계산 상태 일관성·누적값 연속성·heartbeat 확인 후 성공, 세션/counter 임의 초기화 없음 |
| snapshot 부재/손상 또는 이전 작업 회수 불가 | 성공 오보고·중복 작업 없음, 회수 불가 시 운영자 재시작 요구; 자동 프로세스 재시작으로 우회하지 않음 |

물리 ADC 분리/재연결은 장비 정보와 배선 절차 확정 후 수행한다. 먼저 Mock으로 오류/반복 샘플/복구를 검증하고, 실장비에서는 변환 완료와 취득 기록을 증적으로 남긴다. 위 표는 시험 계획이며 실행 결과가 아니다.


### R 답변 반영 인수 조건 — 미실행 계획

공동 규약의 R 정책을 위 Q 시험과 함께 검증한다. 아래 조건은 공식 TC의 하위 시험으로 매핑하며 새 TC 번호를 임의 확정하지 않는다.

| 조건 | 확인할 결과 |
|---|---|
| 최초 새 정상 입력 1·2·3회 및 중간 오류 | 3회 전 측정 준비/판정 대기, 오류에서 횟수 초기화. 같은 변환 재조회·CAN 재송신으로 횟수가 늘지 않음 |
| 정상·센서 오류·복구 확인 중·최초 대기·미지원 품질 | 양측 같은 상태 의미와 마지막 정상값 존재 여부. 기존 예약값 0을 새 규약의 정상으로 자동 해석하지 않음 |
| 오류 메시지 지속 수신 | 통신 수신 기록은 유지되더라도 화면의 마지막 정상 데이터 수신 기준점은 변경되지 않음 |
| 수신 이력 없는 IVI 재시작 | 경과시간 확인 불가. 임의 0초나 실제 측정 후 시간으로 표시하지 않음 |
| BMS 작업 중단 후 snapshot 복구 | 관측 공백을 임의 적분하지 않음, 재개 시간 기준과 공백 로그 확인. 실행 성공과 정확도 복구를 구분 |
| 연속 입력 정확도 시험 중 공백 발생 | 해당 시행을 유효한 연속 입력 정확도 PASS로 처리하지 않음. 원시 기록을 보존하고 공백 없는 시행과 구분하여 공식 조건에 맞게 재시험 |

R-5의 수치는 아직 미확정이다. Mock 종료 경로와 상태 저장 간격을 먼저 조사하고 장비 기반 결과와 구분한다. 후보 수치 승인 전 임의 timeout으로 시험을 통과 처리하지 않는다. 이 표를 추가한 것은 실제 시험 통과 증거가 아니다.


## 장비 실행 게이트 — 5번 검토 결과

1. 확인사항 §1·§6을 받은 뒤 노드별 전원/신호 전압·SPI/INT·발진 주파수·종단·CAN bitrate·커널 설정을 대조한다. 동일 커넥터나 모듈 외형만으로 배선을 확정하지 않는다. Node B 설정은 IVI M1의 별도 Android 절차를 따른다.
2. Node A→B와 B→A를 각각 반대 노드에서 관측한다. 송신 노드의 로컬 echo나 `vcan0` 수신을 물리 링크 증거로 사용하지 않는다. SocketCAN의 loopback·raw socket 동작은 [Linux 커널 문서](https://docs.kernel.org/networking/can.html)를 기준으로 구분한다. 시험용 입력은 제품 서비스와 분리해 기록하고 미승인 세션 CAN ID를 제품 계약으로 도입하지 않는다.
3. 양측 실제 서비스 권한으로 송수신·인증·HAL/Service/앱까지 확인한다. root shell, can0 존재, 프로세스 실행만으로 통합 통과를 판정하지 않는다. Android UID/도메인·ABI·HAL 등록은 IVI M1의 게이트를 통과해야 한다.
4. ICD 현행 계약과 승인된 다음 목표, 미확정 세션 후보의 버전을 run별로 명시한다. 혼합 배포·형식 불일치·키 오류·변조·유실·재부팅 시 실패/상태 표시를 확인한다. 후보 미확정이면 해당 인수를 보류한다.
5. 센서 오류와 통신 단절을 별개로 주입한다. 통신이 계속되는 센서 오류에서 불필요한 세션 재인증이 없는지, 단절에서는 stale과 마지막 값이 올바르게 표시되는지 확인한다. 위험 판단/경고를 유효하지 않은 입력으로 해제하지 않는다.
6. S-5=A의 4종 공격×3구성 실제 CAN 최종 평가와 IT-001~005를 각각 완료한다. vcan·합성은 준비/백업 증거이며 물리 시험을 대체하지 않는다. 실패한 물리 데모를 vcan으로 바꾸면 발표·결과에서 전환 사실과 미검증 범위를 남긴다.
7. 지연에는 시작/끝 사건·관측 위치·시계 동기 근거를 붙인다. 서로 다른 노드의 단조 시각을 바로 빼지 않는다. 부팅 시간·서비스 준비 후 세션 복구·센서 정상 복귀·화면 갱신을 별도 측정한다.

통과 증거는 보드/소프트웨어 식별·설정·연결 확인·원시 로그·TC 대응·실패 결과다. 이번 작업은 실행 계획 보강이며 장비 연결·빌드·배포·실험은 수행하지 않았다. 장비 정보의 기존 빈칸은 유지한다.



## S-10=A 상태 동기화 후속 인수

세션 상세 계약 승인/구현 후 IT-002/003의 후속 시나리오로 연결 대기 중 NORMAL 유지, WARNING 지속, WARNING 후 정상 복귀, 더 높은 위험 상태 도달, 센서 오류 중 상태 유지, 동기화 유실/중복/실제 전이 경합을 검증한다. 기대값은 [세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §14를 따른다. IVI는 현재 상태를 표시하고 ECU 진단 기록은 과거 전이를 보존해야 한다. 메시지 수신 증거 없이 동기화 완료라고 하지 않는다. 새 공식 TC ID와 wire 코드는 임의로 추가하지 않는다.



## S-11=A·S-12=A 후속 통합 인수

상태 동기화는 전용 메시지 인증·IVI 반영·ECU의 인증 receipt 검증을 각각 관측한다. READY 완료와 일반 BMS 수신을 상태 동기화 성공으로 대체하지 않는다. 원본/인증/receipt 각각의 유실·중복·변조·구세션 재생, 실제 상태 변화와 재시도 경합, 양측 재부팅을 결합한다. 상세 검증 목록은 [세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §16을 따른다. 후보 전체 검증과 공식 전환 전에는 새 ID의 실장비 인수를 완료라고 하지 않는다.



## S-13=A·S-14=A 경합 인수 추가

READY 후 최신 상태 receipt 전 일반 BMS가 전송되지 않는지, 로컬 계산은 계속되는지 관측한다. WARNING 대기 중 CRITICAL, WARNING→NORMAL→WARNING, 이전 receipt 지연/중복, 최신 receipt와 상태 변경의 동시 경계, 연속 상태 변경 시 전체 기한을 시험한다. 기대값은 [세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §18이다. 기존 중앙 모형의 불변 snapshot 시험을 이 경합 시험의 통과 증거로 대신하지 않는다.



## 독립 상태 동기화 모형의 인수 증거 범위

[세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §19에 S-13/A·S-14/A 독립 ECU/IVI 모형 결과를 기록했다. 원본에 counter를 넣지 않고 MAC으로 인증 쌍을 찾으며, 이전 상태 확인 거부·동일 상태 재등장·조립 만료·예산 유지의 제한 검증을 수행했다. 이는 READY 이후 로컬 상태 검증이며 receipt 조각·자동 세션 교환·실제 일반 데이터/전이 counter 경쟁·HAL/화면은 미검증이다. 기존 통합시험의 장비 인수 체크를 완료로 바꾸지 않는다.



## 수신 확인 조각 혼합·재시도 인수 조건

[세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §20에서 receipt 5조각의 120가지 순서·누락·변조·혼합을 제한 모형으로 검증했다. 같은 transfer ID의 이전 재시도 조각이 새 receipt와 충돌할 수 있으므로, 해당 거부가 정상 교환의 영구 중단으로 이어지지 않는지도 자동 스케줄러에서 검증해야 한다. 조립 실패 후 수동 모형 재생성을 자동 복구 증거로 사용하지 않는다. 기존 대기 예산을 무한 갱신하거나 모형 상수를 공식 기한으로 복사하지 않는다.



## 독립 교환 복구 검증의 연결 조건

[세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §21의 논리 메시지 유실 243개·교환 중 재부팅 15개와 별도 receipt 자동 재개는 제한 모형 결과다. 다음 통합 검증은 READY 이전 조각 수신부터 최신 상태 적용·receipt·일반 데이터 송신 허용까지 동일 실행에서 확인한다. READY 캐시 재전송/종료와 정상 세션 수명을 구분하고, 재부팅 후 구세션 조각 및 공유 counter 경합을 포함한다. 두 개의 부분 모형 통과를 전체 CAN 세션 인수로 취급하지 않으며, 시험용 타이머와 조립 슬롯은 인터뷰 없이 공식 설정으로 채택하지 않는다.



## 전체 후보 프레임 결합 결과와 추가 인수 조건

[세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §22에서 READY 이전부터 상태 확인·일반 BMS/전이까지 독립 노드 프레임 흐름으로 연결했다. 첫 유실 31개, 재부팅 시점 30개와 상태 변경·구세션 입력을 제한 모형에서 확인했다. 검사 8개 중 하나는 해결되지 않은 역순 counter 반례 재현이며 전체 세션 합격이 아니다.

일반 데이터와 전이의 인증 순서가 뒤집힐 때 BMS가 계속 폐기되는지 확인하고, 반복 전이 수신으로 BMS stale을 해제하지 않는다. [질문리스트](../../../docs/development/governance/의사결정_기록.md#part1-questions)의 S-15 선택 후 대기열/송수신 순서·최대 지연·누락·자원 상한을 검증한다. S-16은 receipt 조각 식별과 제한 재시도의 검토 방향이며 기존 최신 상태 확인 조건을 완화하지 않는다. 제품·실장비 시험 및 공식 계약 변경은 수행하지 않았다.



## S-15=A·S-16=A 선택 후 재검증

[세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §23의 제한 모형 검사 12개가 통과했다. 기존 역순 배치 반례에서 BMS·전이가 함께 반영됐고 첫 유실 31개/재부팅 30개 조건을 재검증했다. 중복/잘못된 MAC·대기 기한·누락 번호·큐 포화·구세션 큐 폐기를 확인했다. receipt 반복 충돌 검사는 별도 suffix 범위이며 모든 조합이나 제품 인수 통과는 아니다.

후속 인수에는 정렬 큐·raw/auth 큐·receipt 조립·세션 캐시가 동시에 차거나 만료되는 조건, 늦은 정상 데이터의 허용 범위, 위험 전이 지연·포화, counter 소진 뒤 새 세션을 포함한다. TC-SEC-002/003과 TC-INT-002/003의 하위 조건으로 추적하고 정렬 대기를 TC-PERF-001 측정 구간에서 제외하지 않는다. 운영 수치가 정해지면 직전/경계/직후와 부하 조건을 시험한다. 이 문단 작성 당시에는 Plan 융합·재검사가 범위 밖이었다. 이후 현행 계획 편입은 완료했으며 최신 실행 조건은 이 문서의 보안 병합 절을 따른다.



## 큐 예외 정책·운영 기한 인수 준비

[세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §24에서 시험 큐 포화 시 인증된 전이 누락과 동일 counter의 인증 상충 본문이 먼저 온 값으로 선택되는 조건을 재현했다. 검사 2개는 반례 확인이며 인수 통과가 아니다. S-17/S-18 답변 후 예약/포화·상충·실패 표시·제한 재동기화를 검증한다. 수신 실패를 ECU 로컬 SHUTDOWN 발생으로 오표시하지 않는다.

조립·정렬·단계/전체 교환·캐시·재시도·큐/진단량은 §24의 기산점·근거·종료 조건에 따라 측정/확정한다. 각 기한 직전/정각/직후와 동시 입력·timeout, 예약 공간까지 포화되는 경우를 포함한다. 장비/Android 미입력 상태에서는 수치를 추정하지 않고 해당 장비별 인수를 보류한다. 기존 화면 지연/통신 신선도 기준을 유지한다.



## 예약 큐·상충 실패 후 재검증 결과

[세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §25에서 S-17=A·S-18=A를 반영한 제한 모형 검사 16개가 통과했다. BMS 구역 포화 시 위험 전이를 보존하고, 위험 구역 포화/인증 상충은 미반영 큐를 폐기한 뒤 제한 재연결했다. 첫 유실 31개·재부팅 30개 조건도 유지됐다. 실제 표시 경로·전체 운영 수치·장비 인수는 별도다.

다음 계약 검토는 S-19 구세션 송신 중단 시점과 S-20 HAL 사유 부재 표현을 기존 READY/최신 상태 receipt 조건에 연결한다. TC-INT-002/003에서 구세션 큐·캐시·미반영 snapshot과 화면 이벤트 중복을 확인한다. 제품 구현 전 필요한 계약 변경을 계획 검증 결과만으로 완료 처리하지 않는다.


### S-19~S-21=A 인수 연결

세션 설계안 §26에 따라 위조/정상 CONFIRM, READY 유실, 상태 변경과 늦은 receipt, 구세션 미전송 큐와 이미 제출된 프레임을 구분해 TC-SEC-003·TC-INT-002/003에서 검증한다. HAL 사유 없음=0과 기존 1~7 표시, 최초 미수신·센서 오류, 현재 상태 snapshot의 전이 콜백 미발생을 함께 확인한다. 모형 통과가 커널 송신 큐나 Android 시험을 대신하지 않는다.

합성 정량 평가는 TEST_PLAN의 TC-BMS-002 S-21=A 추가 조건을 따른다. 주 비교 두 조건 모두 엄격 RMSE 비교를 통과해야 하며 대조군과 네 민감도 결과도 제출한다. 실제 ADC·NASA 재생 결과와 합산하지 않는다.

### S-22=A와 운영 수치 근거

일반 BMS 구역만 차면 신규 BMS를 거부·진단하고 기존 대기 건과 위험 예약 공간을 보존한다. 해당 포화만으로 즉시 재연결하지 않으며 지속 누락의 counter/timeout 처리는 기존 정책을 따른다. 위험 구역 포화·인증 상충은 계속 세션 실패다. 상세 인수와 담당별 수치 측정·승인 기준은 [세션 설계안](../../../docs/development/security/CAN_세션인증_설계안.md) §28을 따른다. 실제 UI 시각·커널 송신 경계·장비 부하는 후속 검증이다.

<a id="security-adoption"></a>
## 보안 차용 보강 — 통합 인수와 증거

### 목적·선행 조건
[선별 반영 규약](00_협업_규약.md#security-adoption)과 [담당·설계 관문](01_연계_의존성.md#security-adoption)을 적용한다. COM-INT-01·COM-EVAL-01의 추가 수행 조건이며 공식 TEST_PLAN의 TC와 합격 기준을 대체하지 않는다. 아래 항목은 수행할 계획이고 통과 결과가 아니다. Q2의 실제 노드 간 시험은 전달 계약·보호 방식·운영 한도 확정과 양측 구현을 선행 조건으로 둔다.

### 수행 순서
1. 양측 버전·설정·입력 출처·시계 조건을 고정한다. 정상 시작/재시작 시 보안 설정과 키 준비 실패를 확인하고, 비보안 C0는 격리 실험 설정으로 식별한다(N01).
2. Q4의 현재 raw pending 정책에서 raw/auth 정상 순서, 역순, 교체, 만료, orphan auth, 잘못된 MAC, 연속 입력을 확인한다. 별도 승인된 세션 후보의 정렬 큐 시험을 이 정책의 변경으로 취급하지 않는다.
3. Q2는 정상 인증·실패 이벤트의 생성→전송→Node A 수신→검출기 입력을 동일 run으로 추적한다. 누락·중복·역순·위조·Replay·재부팅·버스트·채널 단절을 주입하고, 확정된 인증/중복 제거/상한/복구 정책과 비교한다. 전달 장애를 정상 인증으로 간주하지 않으며 BMS 수신·UI와 raw 기반 IDS가 진단 큐 때문에 멈추지 않는지 확인한다.
4. 기존 4공격×3구성×100회와 정상 FPR 시험을 유지한다. Q1의 A5 중단·A6 masquerade는 별도 보조 시험으로 두고 반복 수는 파일럿 근거로 정한다. 공격 도구의 허용 대상·격리 확인·rate/duration 제한 실패 시 전송 0건, sender 중단 시험 종료/예외 시 복구를 확인한다(N04·N05).
5. N02 입력 출처와 이상 유형, N03 Findings 근거를 ECU 로그와 연결한다. 센서 결함·공격·인증 실패·IDS 탐지·실제 Fail-safe 전이를 별도 결과로 판정한다. 기존 0x200 경보는 현재 ICD 계약 그대로 검증한다.
6. [ECU M5](../ecu/M5_Ablation.md#security-adoption)·[IVI M5](../ivi/M5_성능_UI개선.md#security-adoption)의 지표와 기존 본문 §6 계측 정의로 공동 결과를 작성한다. Q3의 보조 통계가 공식 표본 수·측정 구간·합격 기준을 줄이지 않는다.

### 산출물·인계
기존 원본 CSV와 manifest를 보존하고 필요한 진단 JSONL을 연결한다. run ID, 구성, 입력/설정/모델 해시, seed(사용 시), 장비·버전, 시간 단위/시계 기준, 실제 주입 시작·종료, 검출 결과, drop/invalid 사유와 원본 경로를 기록한다. 비밀 키는 기록하지 않는다. Git이 없으면 파일 해시와 실행 환경으로 식별한다.

추가 로그 필드는 실행 증거의 확장안이다. CAN/HAL 필드 변경 승인으로 해석하지 않는다. 원본 작성은 역할 담당, 공동 문서는 같은 run의 판정·증거 링크를 취합한다. 호스트 모형·vcan·실장비 결과는 분리한다.

### 검증·실패 처리
인증/pending은 TC-SEC-002~004, IDS/경보는 TC-SEC-005~007, 양측 연결은 TC-INT-001~004, 성능은 기존 TC-PERF 조건에 추적한다. 공식 TC에 없는 Q2 전달 장애나 공격 CLI 사전 거부는 보조 시나리오명으로 기록하고 공식 TC를 새로 부여하거나 통과 처리하지 않는다.

시계 불일치·증거 누락·주입 실패·복구 실패는 invalid/실패 사유와 함께 보존한다. 재실행은 새 run으로 남긴다. TP/TN/FP/FN은 평가 단위와 분모를 먼저 고정하고, F1/MCC 등 정의 불가능한 값은 N/A로 표시한다(N06). 처리량은 frames/s와 windows/s를 구분하고 관측값을 최대 처리 용량으로 주장하지 않는다(N07).
