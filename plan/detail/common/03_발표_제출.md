## 3. 데모 시나리오

### 3.1 사전 준비 (데모 5분 전)

Node B의 CAN·서비스·앱 기동은 선택한 Ubuntu 이미지에서 검증한 SocketCAN·서비스 계정·Qt 그래픽 세션 절차를 사용한다. 미준비이면 리허설 준비 미완료로 기록한다. 명령 실행과 실제 버스·화면 동작 확인을 구분한다.

```bash
# Node A Linux 예시. Node B는 별도의 Ubuntu/Qt 실행 절차를 따른다.
sudo ip link set can0 up type can bitrate 500000
ip link show can0

# Node A
systemctl is-active ecu-node-a.service || sudo systemctl start ecu-node-a.service

# Node B
# 대시보드 앱을 미리 띄워 둔다
```

- [ ] CAN 케이블·종단저항 연결
- [ ] 공유 키 양 노드 배치, 해시 일치
- [ ] 공격 스크립트 경로·실행 권한

- [ ] 화면 녹화 준비

### 3.2 시나리오 A — 정상 동작 (약 4분)

| Step | 실행 | 보여줄 것 | 설명 |
|---|---|---|---|
| 1 | ECU 실행 | 터미널 로그 | "BMS 애플리케이션을 시작합니다. 배터리 프로파일을 기반으로 `0x100`을 100ms 주기로 전송합니다." |
| 2 | 대시보드 | SOC/전압/전류/온도 실시간 갱신 | "CAN 버스를 통해 100ms 주기로 데이터가 전달됩니다." |
| 3 | SOC 저하 | 게이지 색상 Green → Orange | "SOC 20% 미만에서 WARNING으로 전이합니다." |
| 4 | SOC 추가 저하 | CRITICAL 풀스크린 Dialog | "5% 미만에서 CRITICAL로 전이하고 경고를 띄웁니다." |
| 5 | 복귀 | NORMAL 표시 | — |

```bash
./adaptive_ecu/build/adaptive_ecu --interface can0 --secoc on \
    --sensor-mode profile_csv --profile adaptive_ecu/data/battery_profile.csv
```

**상태 전이 유도**: `--soc`와 `--sensor-mode potentiometer`는 **동작하지 않는다.** 주 경로는 `--sensor-mode ads1115`(가변저항으로 팩 전압 42.0V→30.8V), 백업은 전압 램프 프로파일(`failsafe_demo.csv`)이다. 구현·생성 절차는 [ECU M3](../ecu/M3_EKF_Failsafe_SecOC.md) 3.11·3.12.

> **전이 순서 주의**: NORMAL → CRITICAL 직행 경로가 없다. SOC를 20% 아래로 내려 WARNING을 먼저 만든 뒤 5% 아래로 내린다. 또 `manualReset()`은 **SHUTDOWN에서만** 동작하므로, 리셋을 시연하려면 온도를 60°C 초과로 올려 SHUTDOWN까지 가야 한다 ([ECU M3](../ecu/M3_EKF_Failsafe_SecOC.md) 3.5). 리허설에서 어느 경로를 쓸지 미리 정한다.

### 3.3 시나리오 B — 공격과 방어 (약 5분)

**시연 준비·구성 전환:** ECU M5의 방어 구성 정의에 따라 Node A 송신과 Node B verifier를 함께 설정하고 양측 적용 로그를 확인한다. ECU의 `--secoc off/on`만으로 Node B 설정이 바뀌지 않는다. 무방어는 격리된 시험 설정으로만 사용한다. 이전 ECU·IDS 프로세스 종료를 확인한 뒤 다음 구성을 시작하며, 종료·예외 시 정상 보안 설정과 송신을 복구한다. 정상값과 위조값을 구분할 입력·관측 구간을 준비하고 적용 계약의 품질 조건을 맞춘다. 공격 raw의 교체·만료 때문에 화면 증거가 없으면 위조값 표시 성공으로 보고하지 않는다.

| Step | 설정 | 보여줄 것 | 설명 |
|---|---|---|---|
| 1 | SecOC off + Spoofing | **가짜 SOC=100%가 화면에 표시됨** | "인증이 없으면 조작된 값이 그대로 운전자에게 보입니다." |
| 2 | SecOC on + Spoofing | **위조값 미반영·정상 인증값 갱신 유지** | "인증되지 않은 위조값은 반영하지 않고, 정상 인증값은 계속 전달합니다." |
| 3 | Flooding + IDS | AlertBanner 3초 내 표시 | "IDS가 이상을 탐지해 `0x200` 경보를 보내고 배너가 뜹니다." |
| 4 | 공격 중단 후 사용자 확인 | 경보 확인으로 배너 해제; 정상 수신·공격 중단은 별도 증거로 확인 | — |

```bash
# 1) 무방어
./adaptive_ecu/build/adaptive_ecu --interface can0 --secoc off &
sudo .venv/bin/python -m security.attack_simulator \
  --type spoofing --channel can0 --duration 1 --run-id DEMO-SPOOF-UNPROTECTED \
  --confirm-isolated-test-bus --log ~/demo-spoof-unprotected.json

# 2) SecOC 방어
./adaptive_ecu/build/adaptive_ecu --interface can0 --secoc on &
sudo .venv/bin/python -m security.attack_simulator \
  --type spoofing --channel can0 --duration 1 --run-id DEMO-SPOOF-SECOC \
  --confirm-isolated-test-bus --log ~/demo-spoof-secoc.json

# 3) IDS 탐지
sudo .venv/bin/python -m security.ids.runtime \
  --interface can0 --train-normal ~/ids-normal.jsonl \
  --normal-manifest ~/ids-normal.manifest.json \
  --secoc-key /etc/secoc/key.bin --log ~/demo-ids.jsonl \
  --duration 30 --send-alerts &
sudo .venv/bin/python -m security.attack_simulator \
  --type flooding --channel can0 --duration 3 --run-id DEMO-FLOODING \
  --confirm-isolated-test-bus --log ~/demo-flooding.json
```

**시연의 핵심은 1단계와 2단계의 대비다.** 1단계에서 가짜 값이 실제로 뜨는 것을 보여야 SecOC의 가치가 전달된다. 2단계에서는 **위조값 미반영과 정상 인증값 갱신 유지**를 수신·인증·화면 기록으로 확인한다. raw-only 주입의 교체·만료·인증 미성립을 MAC 불일치와 구분하고, 특정 MAC 실패 로그를 필수로 요구하지 않는다.

- [ ] 각 단계 사이에 이전 프로세스를 종료한다
- [ ] 인자 표기는 `--secoc on` / `--channel`이다

## 8. 실패 시 대응

**데모 당일 하드웨어 장애** — `vcan0` 전환 또는 백업 영상. 전환 사실을 밝힌다.

**공격이 탐지되지 않음** — 리허설에서 찾은 안정 구간을 쓴다. 실패하면 백업 영상으로 넘기고 Q&A에서 원인을 설명한다.

**발표 시간 초과** — 슬라이드 5·9를 압축하고 3·10·13(아키텍처·Ablation·데모)을 남긴다. 데모는 줄이더라도 뺀다.

**질문에 답을 모름** — "확인하고 답변드리겠습니다"가 지어낸 답보다 낫다.

**수치가 목표에 미달** — 미달값과 원인 분석, 개선 방향을 함께 제시한다. 미달 자체보다 **분석의 부재**가 더 문제다.

## 보안 차용 보강 — 발표 근거와 재현 인계

### 목적·선행 조건
COM-FINAL-01과 기존 15장 발표 구성을 유지하면서 N08의 설명·증거를 보강한다. [담당 매핑](01_연계_의존성.md#security-adoption), [공동 인수](02_통합시험.md#security-adoption), [ECU 문서 검토](../ecu/M6_문서_품질.md#security-adoption)를 선행 자료로 사용한다.

### 수행·산출물
- 아키텍처 그림에 Node A의 Rule/Spec·시간 기반 검사·필수 IF, Node B의 검증/품질/UI 역할을 표시한다. Q2 이벤트 전달은 실제 구현 여부와 계약 확정 상태를 함께 표시한다.
- 원자료의 제안 방식과 우리 프로젝트의 채택 방식/수정 이유를 대응시킨다. 현재 계약을 유지한 항목, 보조 시험, 제외 항목을 구분한다.
- 정상→공격/센서 결함→검증/탐지→표시/안전 상태→복구를 같은 run의 로그·그래프로 설명한다. IDS 경보와 ECU 안전 전이가 항상 같은 사건이라고 설명하지 않는다.
- SecOC는 무결성·인증·freshness를 위한 것으로 설명하고 기밀성/암호화 제공으로 표현하지 않는다. 실제 사용하지 않은 도구·표준 인증·외부 논문의 수치를 프로젝트 성과로 넣지 않는다.
- 기존 공식 결과에 N06 보조 지표와 N07 자원 측정을 연결한다. 구성·분모·단위·실험 환경·목표/실측 구분 및 미달/invalid를 보존한다.
- 재현 안내에 입력/설정/모델 해시, 실행 절차, 도구 제한, 원본 결과 위치를 포함하고 키·토큰은 제외한다. 녹화/vcan/모형은 실장비 실시간 시연과 구분한다.

### 검증·실패 처리
표·발표·보고서의 수치를 동일 원본과 대조하고 질문에 근거 경로로 답할 수 있는지 리허설한다. 미구현 Q2 경로를 그림의 실선이나 녹화만으로 구현 완료처럼 표시하지 않는다. 미확정/미검증은 한계와 후속 담당으로 남긴다. 발표 문구를 맞추려고 공식 합격 기준을 낮추지 않는다.

### 완료 체크리스트
- [ ] 원자료→채택 방식→모듈→시험→증거 추적이 가능하다.
- [ ] 기밀성, IDS, 인증, 안전 전이의 역할을 구분했다.
- [ ] 원본과 발표 수치가 일치하며 미검증 범위가 표시됐다.
