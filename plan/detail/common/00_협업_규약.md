- 공식 계약·요구사항·시험의 우선순위는 [AGENTS의 Source of Truth](../../../AGENTS.md)를 따른다. 개발 후보 문서나 최신 날짜가 공식 계약을 자동으로 덮어쓰지 않는다.
- 현재 과제는 `plan/`의 본문과 `security-integration`·`security-adoption`을 함께 적용한다. 후자는 초기 보강 이력도 포함하므로 Q2 세부 정책은 [상태 규약 §10](../../../docs/development/security/인증이벤트_메시지_상태규약.md#planning-final)을 참조한다. 공식 계약과 충돌하면 채택·동기화 전 제품 전환을 보류한다.
- 사용자 선택과 적용 범위는 [이 문서의 선별 반영 절](#security-adoption)을 따른다. 과거 원자료와 `plan/_archive/`의 다른 배치·선택적 IF·과거 보류 문구는 현재 실행 지시가 아니다. Node A IDS·필수 IF와 기존 실험 구성을 유지한다.
- `계획 반영 완료`, `후보 설계 작성 완료`, `공식 계약 채택`, `제품 구현 완료`, `실장비 검증 완료`를 별도로 기록한다. 모형의 기존 검증 결과를 이후 보완된 모든 정책의 시험 통과로 확대하지 않는다.

## 1. 목적과 범위

현행 계획은 `plan/ECU.md`, `plan/IVI.md`와 `plan/detail/`다. Plan 원문은 `plan/_archive/`의 역사 자료로 보존하며 실행 지시로 사용하지 않는다. 별도 `Plan/` 폴더는 제거했다. 공식 계약·요구사항의 우선순위는 [AGENTS](../../../AGENTS.md)를 따른다.

### 문서·예시 사용 규칙

- 상위 계획은 목표·책임·단계·진행 상태, 역할 상세는 절차·산출물·검증, 공동 상세는 공유 규칙을 관리한다.
- 코드 블록은 별도 검증 표시가 없으면 **미완성 구현 골격 또는 작성 예시**다. 누락된 import·빌드 설정·의존성과 오류 처리를 완성하고 시험해야 한다. 설명용 `text`는 실행 명령이 아니다.
- 명령 블록도 대상 파일·도구·장비가 갖춰진 뒤 수행하는 **예정 실행 절차**다. 미구현 파일을 호출하는 경우 앞 단계에서 생성·검증하는 것이 선행조건이다.
- 검증된 실행 예시는 적용 환경·검증일·명령·출력·관련 TC 증적이 있어야 한다. 문서 편집 완료를 기능 구현·장비 시험 완료로 표시하지 않는다.
- 전체 CI 절차는 [IVI CI 참조](../ivi/ref_CI파이프라인_명령모음.md), 측정 정의는 [공동 통합시험](02_통합시험.md) §6을 한 곳에서 관리한다. 구현 이후 실행 정본은 실제 소스·CI 설정이며 문서는 진입점과 검증 조건만 유지한다.

### 착수·진행·완료 운영

역할 담당은 ECU=팀원A, IVI=팀원B다. 마일스톤은 양측 완료 승인 뒤 **IVI 담당이 릴리즈 조정자로서 동일 태그를 한 번만 생성**하고 ECU 담당이 증적을 확인한다. 계정 실명·장비 예약·가용 시간은 착수 회의에서 기록하며 추정하지 않는다.

1. 현재 폴더는 Git이 없으므로 저장소 복구/연결과 원격·권한 확인을 공동 M1 선행 작업으로 수행한다. 복구 전 PR·태그·원격 보호가 완료됐다고 쓰지 않는다.
2. 각 담당은 M1에서 소스·장비·시험 현황을 재확인하고 상위 진행 표를 채운다. 소스가 있어도 증적이 없으면 `검증대기`다.
3. 단계 착수 시 실제 가용 시간에 맞춘 작업량·예상 기간을 기록한다. M1~M8 순서는 유지하고 과거 절대 날짜를 재사용하지 않는다. 기간 미산정은 해당 단계 착수 준비 미완료로 처리한다.
4. 선행 단계 미완료라도 Mock·단위시험 등 독립 작업은 진행할 수 있다. 전체 마일스톤 완료·공동 태그는 의존 작업과 필수 시험까지 완료한 뒤 처리한다.
5. 상태는 `미착수 / 진행 / 검증대기 / 차단 / 완료`. 모든 완료에는 FR/NFR, TC, 실행 환경, 소스 버전 또는 해시, 실행 명령·결과·증적 위치와 검토자를 기록한다.
6. 필수 시험 실패·미실시는 다음 연구 작업을 금지하는 사유와는 구분하되, 완료 게이트를 통과시키지 않는다. 선택 시험의 Skip과 필수 미완료를 혼동하지 않는다.

### 차이·의사결정 기록

기존 구현과 문서가 다르면 `현재 사실 / 상위 요구 / 영향 / 선택지 / 사용자 답변 또는 승인 근거 / 변경 대상 / 회귀 시험`을 해당 상세 문서에 기록한다. 모델·요구 범위·ICD 변경은 묵시적으로 승인됐다고 쓰지 않는다. 이미 승인된 사실은 근거를 연결하고, 새로 모호한 선택은 사용자에게 인터뷰한다.

ICD의 `stale` 전달 설명과 C++ Service snapshot·observer 사이처럼 계약 내부에서 모순이 발견되면 양측 M1 인터페이스 검토 안건으로 등록한다. S-3=A로 승인된 다음 목표 필드는 ICD §8을 따르고 기존 11필드와 혼용하지 않는다. 승인 목표의 제품/시험 동시 전환은 미완료다. 그 밖의 새 필드·메서드는 미승인 후보로 분리한다.

### 승인된 개선 방향 — 2026-09-06

결정 정본은 [확인사항](../../../docs/development/governance/의사결정_기록.md#part2-confirmed) §3~5다. 아래는 구현 완료가 아닌 실행 계획이다.

| 선택 | 승인된 목표 | 담당·완료 게이트 |
|---|---|---|
| 3=A | VehicleData에 bool stale 추가, 기존 콜백 유지 | IVI M1·M3: C++ snapshot·observer·ViewModel·QML·Mock 매핑과 timeout/복구 시험. ECU와 계약 검토 |
| 4=B | CAN 교환을 통한 인증 세션 기반 자동 재동기화 | 양측 M3: 상세 설계 검토→공식 문서·양측 구현·Python 참조·시험 동기화. 구체적 계약 확정 전 자동 복구 구현 차단 |
| 5=C | Node A ECU root 서비스 실행 | IVI M4·ECU: 더미 키 기동·실제 CAN 송신 검증. 전용 계정 전환은 후속 개선 |

기존 11필드 데이터 모델은 과거 HIDL 계약이었고 현재 ICD §3은 C++ Service API 기준이다. 승인된 stale 추가 목표와 구분하고 실제 변경 단계에서 생성 코드·사용자 전체를 함께 갱신한다. 세션 인증을 통과하지 않은 카운터 재설정은 새 계획의 복구 절차로 사용하지 않는다.

세션 인증의 CAN 전송과 IVI→ECU 메시지 추가 방향은 사용자 승인 완료다. 구체적인 메시지·복구 절차는 [CAN 세션 인증 설계안](../../../docs/development/security/CAN_세션인증_설계안.md)에 단일화한다. 해당 문서의 SES-D1~D5는 제안이며 현재 ICD가 아니다. ECU M3·IVI M3·공동 통합시험은 승인 후 이 설계의 역할별 과제·인수 조건을 반영한다.

센서 데이터와 통신 상태는 독립적으로 관리한다. 인증된 오류 payload 수신은 통신 수신 기록을 갱신할 수 있지만 마지막 정상 **측정**의 시각·품질을 갱신하지 않는다. 통신 timeout의 `stale`을 센서 오류 비트로 재사용하지 않는다. 세션 재수립 성공만으로 센서 오류를 해제하지 않는다. 정상 입력 3회는 서로 다른 완료된 ADC 취득을 세며 같은 변환값 재조회나 BMS 재송신을 세지 않는다. 복구 확인 중에는 오류 표시를 유지한다. 정상 운전의 화면 갱신을 세 샘플 단위로 묶지 않는다.

예약 영역 확장도 계약 변경이다. 기존 수신기가 예약 바이트를 무시하거나 0만 허용하는 경우를 조사하고 양측·Python 참조·Mock·시험을 함께 전환한다. 실제 비트값·HAL 필드·초기/미지원 상태·snapshot 노후도·종료 상한이 필요한 단계에서는 구체안을 작성해 인터뷰하며 빈칸을 임의 수치로 채우지 않는다. 세션 후보의 ID는 센서 상태 전송에 재사용하지 않는다.

### R 서면 답변 반영 — 다섯 항목 모두 A

근거는 [질문리스트](../../../docs/development/governance/의사결정_기록.md#part1-questions)의 R 상세 답변이며 [확인사항](../../../docs/development/governance/의사결정_기록.md#part2-confirmed) §14에 결정 이력을 기록한다. Q 결정 중 시간 표시와 최초 인수 조건은 아래처럼 구체화한다.

| 결정 | 공통 목표 동작 | 미확정·후속 과제 |
|---|---|---|
| R-1=A | 정상 / 센서 오류 / 복구 확인 중 / 최초 측정 대기를 구분하고 마지막 정상값 존재 여부를 전달한다. 이전 형식·미지원 상태값은 `상태 확인 불가`로 취급하고 정상으로 해석하지 않는다 | 기존 byte 7 예약값 0과 구분되는 인코딩·HAL 매핑·조합 유효성의 변경 전후표 작성. CAN ID·DLC·HMAC 입력 순서는 이번 답변으로 변경하지 않음 |
| R-2=A | IVI에서 `마지막 정상 데이터 수신 후 …`로 표시한다. 인증·품질 확인을 통과한 정상 데이터의 수신 기록을 사용한다. 실제 측정 후 경과시간이라고 표시하지 않는다 | 수신 기록을 유지할 계층·경과시간 시계·재시작 수명 설계. 기존 정상 측정 시각 전송 과제는 이 화면 표시를 위해 요구하지 않음 |
| R-3=A | 최초 시작에도 새 정상 입력 3회 확인한다. 최초 인수 전 `측정 준비 중`·`판정 대기`, 입력 오류면 센서 오류를 구분해 표시한다 | 최초/오류/복구 상태 전이와 HAL 표현 검토. 새 CAN Fail-safe 상태·사유 코드를 추가하는 결정은 아님 |
| R-4=A | 검증된 전체 계산 상태를 복원하고 새 유효 입력부터 재개한다. 관측하지 못한 구간을 마지막 전류나 임의 값으로 적분하지 않는다. 공백을 로그·평가 증적에 남긴다 | 공백 후 추정 품질의 표시·정상 추정 재인수 조건·평가 분리 명세. 작업 실행 복구가 정확도 복구의 증거는 아님 |

오류·복구 확인 중·미지원 품질 프레임의 수신은 마지막 정상 데이터 수신 시점을 갱신하지 않는다. 수신 이력이 없는 재시작에서는 `경과시간 확인 불가`를 표시한다. 이 경과시간은 실제 센서 샘플의 나이를 보장하지 않는다. 통신 `stale`·센서 품질·추정 계산의 공백을 구분하며, 센서 입력 3회가 정상이라는 사실만으로 공백 후 SOC/SOH 정확도까지 검증됐다고 표시하지 않는다.

최초 시작과 오류 후 복구 모두 중간 오류에서 연속 정상 횟수를 초기화하고, 같은 ADC 변환 재조회나 CAN 재송신을 새 입력으로 세지 않는다. 정상 운전 중에는 즉시 갱신을 유지한다. 이전에 확정한 Fail-safe 경고가 있다면 센서 복구 대기·사용자 IDS 확인으로 지우지 않는다.

### 실행 계획의 최종 사용 가능 판정

사용자는 다음 네 기준을 모두 통과한 경우에만 완성된 실행 계획으로 사용하도록 요구했다. PASS는 검사 근거가 있는 항목만 부여한다. 계획의 필수 설계 판단·공식 문서 충돌·담당이나 검증 방법 누락은 계획 인수 보류 사유다. 실행 시 확보할 장비 정보·측정값은 담당·확정 시점·실패 처리를 정한 후속 관문으로 관리한다. 링크 검사 통과로 의미 검토를 대신하지 않는다.

| 기준 | 필수 확인 |
|---|---|
| 일관성 | ICD/SRS/SDD/TEST_PLAN/ADR과 충돌 해소, 승인된 목표와 현 구현 차이 구분 |
| 통일성 | 용어·단위·파일명·측정 정의·역할·표/본문/체크리스트 일치, 규칙 정본 한 곳 |
| 호환성 | 양측 CAN/HAL/API·키·ABI·배포·센서 단위 연결, 계약 변경의 동시 인수 과제 |
| 적합성 | 가상 배터리 목표·실기기 선행조건·오류/복구·독립 평가·검증 증적·재현 절차 확보 |

현재 판정은 **계획 문서 인수 완료**다. [계획검토 결과 §7](../../../docs/development/reviews/계획_검토.md#plan-final-verdict)의 기준별 근거와 제한을 따른다. 승인 목표의 제품 전환·세션 상세 승인·운영 측정·Node B Ubuntu/Qt 장비 시험은 담당과 종료 조건이 있는 후속 실행 관문 E1~E6로 유지한다. 계획 통과와 구현/장비 시험 통과는 별개다.

각 필수 FR/NFR의 추적 행에는 `정본 요구 / 담당 단계·구현 대상 / 공식 TC 본문과 추가 하위 조건 / 선행 입력·결정 / 증적 경로 / 결과·미실시 사유`를 포함한다. ID 등장 횟수만으로 추적성 완료를 주장하지 않는다. 새 공식 TC ID는 TEST_PLAN 등록 전 확정하지 않는다.

### 2.1 브랜치 보호 규칙

**경로**: Settings → Rules → Rulesets에서 `main`·`develop` 대상 규칙을 관리한다. 기존 Branch protection을 사용하는 저장소는 Settings → Branches에서 대응 규칙을 확인한다.

`main`:
- Require a pull request before merging → ON, Required approvals = **1**
- Require status checks to pass before merging → ON
- Block force pushes → ON
- Do not allow deletions → ON

`develop`:
- Require a pull request before merging → ON, Required approvals = **1**
- Require status checks to pass before merging → ON
- Block force pushes → ON

> CI가 아직 없으므로 status check의 **구체 항목은 [IVI M1](../ivi/M1_AOSP_Docker_CI.md) 3.7에서 `stage1-static-analysis`를 만든 뒤 지정한다.** 지금 지정하면 존재하지 않는 체크를 기다리며 모든 PR이 막힌다.

<a id="branch-protection-check"></a>

검증은 작업 파일이나 브랜치 이력을 변경하지 않고 다음 순서로 진행한다.

1. 저장소의 **Rules** 화면(저장소 URL 뒤 `/rules`)에서 `main`·`develop`에 실제 적용되는 규칙을 확인한다. Ruleset은 **Active**여야 한다. 설정 편집 화면에서 두 담당자의 계정·역할이 의도치 않게 규칙을 우회하도록 지정되지 않았는지도 확인한다.
2. PR 필수, 상대 Approve, 실제 등록된 필수 CI, force push 차단을 위 기준과 대조한다. CI를 아직 만들지 않았다면 그 항목은 미완료로 기록한다.
3. 정상 작업 PR에서 승인·필수 CI가 부족할 때 병합이 차단되는지 확인한다. 직접 push 거부는 기존 거부 응답 또는 사용 가능한 Rule Insights의 **Active 규칙에 의한 실패 기록**으로 확인한다. Evaluate 모드 결과는 실제 차단 증거로 쓰지 않는다.
4. 대상 브랜치·계정/역할·적용 규칙·확인일과 결과를 작업 증거에 남긴다. **설정 확인과 실제 차단 관찰은 구분**한다. 거부 증거가 없으면 직접 push 차단은 미검증으로 남기며 설정 화면만으로 동작 시험 완료라고 하지 않는다.

시험용 커밋을 보호 브랜치에 push한 뒤 이력을 되돌리는 절차는 사용하지 않는다. 규칙이 잘못되어 있으면 시험 커밋이 원격에 반영될 수 있기 때문이다. 이 확인에는 로컬 stage·commit·reset·파일 삭제가 필요 없다. [GitHub 규칙 조회·활동 확인 안내](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository)

|---|---|---|

| `docs` | `#0075CA` | 문서 작업 |

**조합 원칙**: 유형(`feat`/`bug`/`docs`/`test`/`chore`/`refactor`) + 도메인(`security`/`interface-change`, 해당 시) + 담당자(`ECU`/`IVI`). 상태 라벨(`blocked`)은 기존 라벨에 덧붙인다.

**담당별 조합 예시**

| 작업 유형 | ECU | IVI |
|---|---|---|
| 새 기능 | `feat` + `ECU` | `feat` + `IVI` |
| 보안 모듈 | `feat` + `ECU` + `security` | `feat` + `IVI` + `security` |
| 버그 수정 | `bug` + `ECU` | `bug` + `IVI` |
| 시험 작성 | `test` + `ECU` | `test` + `IVI` |
| 환경·CI | `chore` + `ECU` | `chore` + `IVI` |
| 정리 | `refactor` + `ECU` | `refactor` + `IVI` |
| 문서 | `docs` (+ 도메인 한정 시 담당 라벨) | 동일 |
| 인터페이스 변경 | `interface-change` + `docs` + `ECU` + `IVI` | 동일 |

D8~D9 수정 작업과 IVI M7 연속 24시간 시험의 충돌은 IVI M7 §3.2의 시작 전 점검으로 관리한다. 수정본 안정성 증거→M7 검토→M8 최종 인계 순서는 유지한다. 담당자는 실제 준비/빌드/측정/재시험 소요를 반영해 마감 위험을 보고하고, 충돌이 확인되면 근거와 선택안을 제시해 사용자 판단을 받는다. 이번 계획 검토로 마감 내 전체 구현 가능성을 보장하지 않는다.

## 4. `interface-change` 게이트

**ICD의 CAN ID·방향·DLC·바이트 레이아웃·스케일·엔디언·SecOC 입력 순서·HAL API는 승인 없이 바꾸지 않는다.** ([AGENTS.md](../../../AGENTS.md) HARD RULE 1)

### 필수 5단계

1. **Issue 생성** — 제목 `[ICD] 변경 사유`, 라벨 `interface-change` + `docs` + 영향 도메인(`ECU`/`IVI`)
2. **영향 분석 코멘트** — 양측이 각자 영향받는 파일·모듈·TC를 나열한다
3. **PR로 동시 갱신** — ICD + 영향 모듈의 SDD를 **한 변경 단위로** 갱신
4. **양측 Approve 필수** — 본인 단독 머지 금지
5. **후속 Issue 번호 명시** — PR 본문에 `Affects #N, #M`

적용 대상: `docs/ICD.md`, Node B C++ Service API, CAN ID·레이아웃, SecOC 프로토콜.

**승인 후에는** ICD → SRS → 양측 SDD → TEST_PLAN → 구현 → 시험을 같은 변경 단위로 동기화한다.

### 자주 걸리는 경우

| 상황 | 판단 |
|---|---|
| Node B Service API 또는 IPC 경계 변경 | **게이트 대상** (ICD §3 변경). CAN 레이아웃(§1)·SecOC(§2)는 불변 |
| Watchdog 재시작 초과 시 새 Fail-safe 사유 코드 필요 | **게이트 대상** (ICD §1.3) |
| 파서 값이 ECU와 달라 한쪽을 고침 | 먼저 **어느 쪽이 ICD와 맞는지** 판정. 구현이 틀렸으면 게이트 불필요 |
| TC-SEC-005-d의 5,000 fps 기준 변경 | TEST_PLAN은 이미 부하 ≥50% 기준. 재변경 시 계산 가정·실측·영향을 분리해 제시하고 양측 합의 |

> 구현이 문서와 다를 때 **조용히 한쪽을 맞추지 않는다.** drift를 식별해 보고한 뒤 어느 쪽이 정본인지 정한다.

## 5.5 요구사항 추적 매트릭스 — M7 공동 산출물

각 요구사항이 **어느 파일로 구현되고 어느 시험으로 검증되는지**를 한 표에서 확인한다. 문서 곳곳에 흩어진 ID 연결을 한 번에 점검하는 수단이고, 최종 보고서·발표의 "요구사항을 다 만족했는가"에 답하는 근거다.

`docs/SRS.md` §3에 이미 추적 매트릭스가 있다. **M7에서 그 표에 "구현 상태"와 "TC 결과" 두 열을 채운다.**

### 5.5.1 형식

| 요구사항 ID | SDD 섹션 | 구현 파일 | TC ID | 구현 상태 | TC 결과 |
|---|---|---|---|---|---|
| FR-BSW-001 | SDD-ECU 3.2 | `adaptive_ecu/src/bsw/can_cdd.cpp` | TC-BSW-001 | 완료 | Pass |
| FR-IVI-002 | SDD-IVI 3.1 | `ivi_platform/hal/can_parser.cpp` | TC-IVI-002 | | |
| NFR-PERF-001 | — | — | TC-PERF-001 | | |

**구현 상태 값**

| 값 | 의미 |
|---|---|
| `완료` | 구현 + 대응 시험 통과 |
| `부분` | 구현했으나 시험 미완 또는 일부 조건 미충족 |
| `미착수` | 구현 전 |
| `범위 제외` | 승인된 범위 변경으로 제외 — **결정 근거를 함께 적는다** |

**TC 결과 값**: `Pass` / `Fail` / `Skip`(사유 필수) / `INVALID`(계측 실패) / `NOT_RUN`

### 5.5.2 작성 분담

| 범위 | 담당 |
|---|---|
| FR-BSW, FR-BMS, FR-SEC | ECU |
| FR-IVI, FR-CI | IVI |
| NFR 전체 (PERF·SEC·QA·REL) | 공동 |

### 5.5.3 규칙

- [ ] **ID가 표에 등장하는 것과 검증이 끝난 것은 다르다.** 상태·결과 열이 비어 있으면 미검증이다
- [ ] `Skip`은 "기술적으로 실행 불가"인 경우만 허용하고 **대체 검증 방법**을 함께 적는다 (예: ADS1115는 QEMU에서 `/dev/i2c-*` 미지원 → 실 RPi4 수동 검증)
- [ ] 구현이 있다는 이유로 상위 요구를 낮추지 않는다. 요구를 못 지키면 `부분`으로 남기고 사유를 적는다
- [ ] SRS·TEST_PLAN의 ID와 대조해 **없는 ID를 쓰지 않는다**
- [ ] `NFR-QA-004`(코드 리뷰 완료율 100%)는 이 문서 §3의 PR 규칙으로 검증한다. 머지된 PR 중 상대 Approve 없이 들어간 건이 0인지 확인한다

## 7. 실패 시 대응

**status check 미지정으로 모든 PR이 막힘**
- CI가 만들어지기 전에 required check를 지정하면 이렇게 된다. 지정을 해제하고 CI 생성 후 다시 건다

**비밀을 커밋함**
1. **즉시 해당 키·토큰을 폐기하고 새로 만든다.** 이력에서 지우는 것보다 이게 먼저다
2. `.gitignore`에 패턴을 추가한다
3. 이미 push했다면 이력 재작성이 필요하다. 양측이 함께 판단한다

**`develop` → `main` PR에서 CI 실패**
- 머지하지 않는다. 실패 원인을 고친 뒤 다시 시도한다
- 단계 마감이 급하다는 이유로 게이트를 우회하지 않는다

**양측 Approve를 못 받는 상황 (상대 부재 등)**
- 인터페이스 변경이면 기다린다. 그것이 게이트의 목적이다
- 일반 PR이면 미팅에서 합의한 예외 규칙을 따른다. 예외를 만들었다면 기록한다

**Milestone Close 시점에 Open Issue가 남음**
- 다음 Milestone으로 옮기고 사유를 코멘트로 남긴다
- 조용히 닫지 않는다. 나중에 무엇이 밀렸는지 추적할 수 없게 된다

S-1~S-3 모두 A로 확정했다. S-1 경고 즉시 표시+장식 효과, S-2 가상 배터리 상태 통보 범위는 공식 SRS·양측 SDD·TEST_PLAN·ADR·TARA에 반영했다. S-3의 실제 byte 7 번호와 HAL 확장 목표는 [ICD §8](../../../docs/ICD.md#8-승인된-다음-전환-목표--s-3a-제품-반영-전) 한 곳에서 관리한다.

위 Q/R 표에서 상태 인코딩·HAL 변경안을 제시하고 승인을 받도록 한 단계는 완료됐다. 남은 것은 구현·생성 코드·Mock·Python 참조·시험의 동시 전환이며 제품 구현은 이번 문서 작업 범위 밖이다. 현재 ICD 본문 형식과 승인된 다음 목표를 구분한다. 세션 후보와 제한 시간은 여전히 별도 검토 대상이다.


## S-9=A 장비·SD 관리와 키 노출 한계

통제된 실험에서 장비·SD 보관/반출/반납 확인 담당과 공유 범위를 정해 기록한다. 담당자를 임의로 지정하지 않으며 장비 정보 입력 시 함께 확인한다. SD 오프라인 읽기 방어는 필수 구현에서 제외하지만 키 파일 접근 제한·비공개·인증 시험은 유지한다. 실제 키를 포함한 이미지·백업·로그를 공유/제출하지 않고 공개 재현 자료에는 더미 키를 사용한다.

분실·키 노출 의심 시 영향을 기록하고 기존 키 신뢰 상태와 재개 조건을 검토한다. 세션 재교환을 공유 키 교체로 간주하지 않는다. 승인 범위와 후속 보안 저장 개선은 [TARA](../../../docs/TARA.md)의 S-9=A 절을 따른다. 물리 키 탈취 방어를 달성했다고 발표하지 않는다.
