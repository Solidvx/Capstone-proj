## 현행 과제에 병합한 보안 수행·인수 조건 — 인증 송신·배포의 안정성 인수

이 절은 2026-09-09 보안 상세 계획을 기존 단계에 반영한 실행 조건이다. 초기 보안 보강 절과 함께 적용하며 제품 실행 완료 기록은 아니다. 상세 규칙은 [메시지·상태 규약](../../../docs/development/security/인증이벤트_메시지_상태규약.md)과 [송신·큐·실패 정책](../../../docs/development/security/인증이벤트_메시지_상태규약.md#planning-final)을 참조한다.

**선행 조건:** IVI M3~M5 구현·배포·계측 결과와 ECU M7 인계물을 확인한다.

**수행:** ready/worker 경쟁, 제어 공간을 포함한 FIFO 포화, 느린 부분 read/write, 반복 재연결, 인증서 갱신, 로그 실패와 종료 취소를 Q2-P01~P08로 재현한다. thread 회수·키 권한·sender 정상 복귀·BMS/UI 기능 보존을 실제 증거로 확인한다.

**실패 대응·인계:** 설정/profile/verifier 변경 시 새 진단 epoch를 사용하고 CAN 세션/안전 상태 초기화와 구분한다. 정상 유지 구간 전 재시도 예산 초기화를 금지하고 한도 소진을 명시적 중단으로 보고한다. 검증 불가 항목은 공동 인수에 남긴다.

**완료 확인:**

- [ ] 양측 교차 검토·실장비 한계·반복 실패/복구 증거를 공동 제출에 인계했다.
- [ ] 기존 공식 시험 결과와 추가 보조 시나리오의 실제 증거·미검증 사유를 구분했다.

## 3. 수행 절차

### 3.0 확정된 사용자 정책의 회귀 인수

I-4-1=B: 숫자·게이지 모두 즉시 갱신하고 값 보간을 사용하지 않는다. 장시간 갱신·숫자 폭 변경·글자 확대에서도 위치 흔들림/잘림/깜빡임과 실제 표시 지연을 함께 기록한다.

I-4-2=A: 배너는 사용자 확인까지 유지한다. 같은 유형의 새 경보, 확인 직전 새 경보, UI 재구성·앱 재연결에서 이전 확인이 새 경보를 지우지 않는지 시험한다. 사용자 확인을 공격 종료·센서 정상·Fail-safe 해제로 취급하지 않는다.

I-2=B: 센서 품질 계약 확정 후 정상/오류·통신 단절·세션 재수립의 조합을 검증한다. 오류 동안 유지된 데이터의 나이와 실제 정상 입력 복구를 대조한다. 정책 정본은 [M3](M3_HAL_Service_대시보드.md)·[M4](M4_대시보드_Alert_배포.md)·[M5](M5_성능_UI개선.md)다.

### 3.1 메모리 누수 점검 — AddressSanitizer

먼저 CMake에 옵션을 추가한다. ECU `CMakeLists.txt`에는 `ENABLE_COVERAGE`만 있고 ASan 옵션이 없다.

```cmake
option(ENABLE_ASAN "Enable AddressSanitizer" OFF)
if(ENABLE_ASAN)
    add_compile_options(-fsanitize=address -fno-omit-frame-pointer -g)
    add_link_options(-fsanitize=address)
endif()
```

> **컴파일 플래그와 링크 플래그를 둘 다 넣어야 한다.** 하나만 넣으면 링크 에러가 나거나 검출이 동작하지 않는다. `ENABLE_COVERAGE`와 동시에 켜지 않는다 — 서로 간섭한다.

```bash
# IVI HAL 시험
cmake -S ivi_platform -B ivi_platform/build-asan -DENABLE_ASAN=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build ivi_platform/build-asan
ctest --test-dir ivi_platform/build-asan --output-on-failure

# ECU 실행 시간 점검
cmake -S adaptive_ecu -B adaptive_ecu/build-asan -DENABLE_ASAN=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build adaptive_ecu/build-asan
ASAN_OPTIONS=detect_leaks=1 ./adaptive_ecu/build-asan/adaptive_ecu --interface vcan0 &
sleep 60
kill %1
```

기대 (정상):

```text
==12345==SUMMARY: AddressSanitizer: 0 error(s) found.
```

누수 발견 시:

```text
ERROR: LeakSanitizer: detected memory leaks
Direct leak of 128 byte(s) in 1 object(s) allocated from:
    #0 ... in operator new
    #1 ... in VehicleHalImpl::init
```

→ 해당 함수의 할당·해제 짝을 확인한다. 스레드 정리(`join()`)와 소켓 `close()` 누락이 흔한 원인이다.

**Valgrind 대안** (x86 네이티브 빌드에서만):

```bash
sudo apt install -y valgrind
cmake -S adaptive_ecu -B build_valgrind -DCMAKE_BUILD_TYPE=Debug
cmake --build build_valgrind
timeout 60 valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes \
  ./build_valgrind/adaptive_ecu --interface vcan0 2>&1 | tee valgrind_report.txt

grep "definitely lost" valgrind_report.txt
# 기대: definitely lost: 0 bytes in 0 blocks
```

> Valgrind는 ARM64 크로스 바이너리에 쓸 수 없다. 네이티브 x86 빌드에서만 의미가 있다. 두 방법 중 실행 가능한 쪽을 쓰고, **어느 것으로 점검했는지 기록한다.**

### 3.2 장시간 안정성 시험

일정 인계: M6에서 인수한 소스/이미지·설정·증거를 고정한 뒤 연속 시험을 시작한다. M8 준비는 병행할 수 있지만 24시간 종료·로그 검토 전 안정성 완료로 인계하지 않는다. 시험 중 대상 코드/이미지/설정을 바꾸면 변경 전후 결과를 합쳐 24시간 통과로 만들지 않고 수정본 시험을 다시 확보한다. 9/18 시연 전 24시간과 결과 검토·복구 시간을 확보할 수 있는지 IVI 담당이 D8~D9 작업 시작 전에 점검한다. 부족하면 실패 근거와 소요를 보고해 일정/범위 판단을 요청하며 시험 단축을 자동 승인하지 않는다.

```bash
# Node A 가동
ssh deploy@<Node-A-Host> "sudo systemctl start ecu-node-a.service"
echo "Start: $(date -Iseconds)" | tee -a stability_24h.log

# Node A Linux: 별도 터미널에서 1시간 주기 모니터링 (Android 명령이 아님)
while true; do
    date -Iseconds
    ps -eo pid,comm,rss,%cpu,%mem | grep -E "vehicle|dashboard|adaptive_ecu" || true
    ip -details -statistics link show can0 | grep -E "errors|dropped|overrun" || true
    echo "---"
    sleep 3600
done | tee -a stability_24h.log
```

Node B Android는 별도로 IVI 담당이 M1~3에서 검증한 ADB·대상 프로세스 식별·로그 수집 경로로 HAL/Service/앱의 생존, 메모리 추세, 재시작, CAN 오류 및 실제 화면 갱신 증거를 같은 시험 구간에 수집한다. 아래 Node A의 ps/journalctl 결과로 Node B를 통과시키지 않는다. Android 수집 명령·권한을 시험 전에 확인하고 수집 실패는 미검증으로 기록한다. Plan B는 사용자 전환 승인 뒤 해당 Linux 앱의 계측 절차를 적용한다.

24시간 후 Node A에서 확인:

```bash
# 1) 프로세스 생존
pgrep -a adaptive_ecu

# 2) 서비스 재시작 여부
journalctl -u ecu-node-a.service --since "24 hours ago" | grep -ci "started\|restart"

# 3) CAN 에러 카운트
ip -s link show can0

# 4) 메모리 추세
grep adaptive_ecu stability_24h.log | awk '{print $3}'    # RSS 열
```

**결과 기록 표**

| 항목 | 결과 |
|---|---|
| 운행 시간 | ___시간 (중단 시 사유) |
| 프로세스 재시작 | ___회 |
| RSS 시작 → 종료 | ___MB → ___MB (___% 증가) |
| CPU 평균 | ___% |
| CAN error / dropped / overrun | ___ / ___ / ___ |
| 대시보드 값 갱신 지속 | 예 / 아니오 |
| 판정 | PASS / FAIL |

**판정 기준**

- [ ] 프로세스가 살아 있다
- [ ] RSS가 **단조 증가하지 않는다.** 초기 상승 후 평탄해지는 것은 정상이다
- [ ] `Restart=always`가 재시작을 감췄을 수 있다. `journalctl`로 실제 재시작 횟수를 확인한다
- [ ] CAN 에러가 시간에 비례해 늘지 않는다
- [ ] 대시보드가 마지막까지 갱신된다

> **24시간을 채우지 못했다면 채운 시간을 적는다.** "24시간 통과"로 반올림하지 않는다. 단축 시험으로 합의했다면 그 합의 내용을 기록한다.

### 3.3 CI 4단계 최종 점검

| TC | 검증 내용 | 방법 | 결과 |

**TC-CI-002 확인 방법** — 게이트가 실제로 막는지 본다.

```bash
git switch -c test/ci-gate-check
cat > /tmp/ci_gate_probe.cpp << 'EOF'
void intentional_leak() {
    int* p = new int[100];
    (void)p;            // delete 없음 -> cppcheck memleak
}
EOF
cp /tmp/ci_gate_probe.cpp adaptive_ecu/src/bsw/ci_gate_probe.cpp
git add adaptive_ecu/src/bsw/ci_gate_probe.cpp
git commit -m "test(ci): cppcheck 게이트 동작 확인용 임시 커밋"
git push origin test/ci-gate-check
# PR 생성 -> Stage 1 실패 확인 -> PR 닫고 브랜치 삭제
```

- [ ] **확인 후 반드시 브랜치와 파일을 제거한다.** `develop`이나 `main`에 남기지 않는다
- [ ] 게이트가 막지 못하면 그것이 결함이다. cppcheck 대상 경로와 `--error-exitcode=1`을 확인한다

### 3.4 ICD ↔ 구현 교차 검토

**IVI가 검토받을 것** (ECU 담당자가 IVI 코드를 본다)

- [ ] `can_parser.cpp`의 디코딩이 ICD §1.2~1.5와 일치하는가
- [ ] 전류가 `int16_t` 2의 보수로 복원되는가
- [ ] 온도가 `int` 확장 후 −40인가 (`int8_t` 캐스트 금지)
- [ ] `secoc_verifier.cpp`의 HMAC 입력이 ECU `secoc_module.cpp`와 바이트 단위로 같은가
- [ ] 카운터 윈도우 규칙이 양측 동일한가 (unsigned delta 1~100)
- [ ] `0x200` 레이아웃 해석이 ICD §1.5와 일치하는가

**IVI가 검토할 것** (IVI 담당자가 ECU 문서를 본다)

`docs/SDD-ECU.md`:
- [ ] CAN 레이아웃 서술이 ICD와 일치하는가
- [ ] SecOC HMAC 입력 구성이 ICD §1.4와 일치하는가
- [ ] Fail-safe 전이 조건이 ICD §1.3 Reason 코드와 대응하는가
- [ ] TC 매핑이 TEST_PLAN과 정확히 대응하는가
- [ ] 코드 예시의 함수·변수명이 실제 구현과 일치하는가
- [ ] IDS 특징 벡터 서술이 실제 `feature_extractor.py`와 일치하는가 ([ECU M6](../ecu/M6_문서_품질.md) 3.3의 필수 갱신 항목)

`docs/TARA.md`:
- [ ] 위협 시나리오가 실제 공격 생성기와 대응하는가
- [ ] Risk Level이 Feasibility Rating과 일관되는가
- [ ] 대응 방안이 실제 구현(SecOC, IDS)과 매핑되는가
- [ ] 수치가 목표값인지 실측값인지 구분되는가

**검토 방법**: 같은 프레임 바이트열을 양측이 각자 디코드해 값을 비교한다. 문서를 낭독하는 방식으로는 부호·오프셋 오류를 못 잡는다.

```bash
git switch develop && git pull origin develop
# 항목별 검토 후 PR에 코멘트. 불일치는 구체적 위치와 함께 기록
```

- [ ] 불일치 발견 시 [00_협업_규약](../common/00_협업_규약.md)의 `interface-change` 게이트를 따른다
- [ ] 어느 한쪽을 조용히 맞추지 않는다

## 5. 실패 시 대응과 우회

**ASan에서 누수 검출**
- 스택 트레이스의 `#1` 프레임부터 본다. 할당 지점이다
- HAL의 스레드 `join()` 누락, 소켓 `close()` 누락, 콜백 목록 정리 누락이 흔하다
- 시험 종료 시점에만 잡히는 "still reachable"은 누수가 아닐 수 있다. `definitely lost`와 구분한다

**24시간 시험 중단**
- 중단 시각과 사유를 기록하고 재시작한다
- 채운 시간만 적는다. 부족한 시간을 채운 것처럼 쓰지 않는다
- 전원·네트워크 문제로 중단됐다면 그것도 안정성 정보다

**RSS가 계속 증가**
1. 증가율을 본다. 24시간에 수 MB면 캐시일 수 있고, 선형으로 수백 MB면 누수다
2. ASan/Valgrind로 재현한다
3. 대시보드 쪽이면 Compose recomposition 누적이나 리스너 미해제를 본다

**서비스가 계속 재시작됨**
- `Restart=always`가 실패를 감추고 있다. `journalctl`에서 종료 사유를 본다
- CAN 인터페이스 부재로 즉시 종료되는 경우가 가장 흔하다

**교차 검토에서 불일치 다수 발견**
- 목록을 만들고 심각도순으로 처리한다. 계약 위반(ICD) > 문서 오류 > 표기 불일치
- 계약 위반은 코드를 ICD에 맞춘다. ICD가 틀렸으면 게이트를 거친다
- 시간이 부족하면 **해결한 것과 남은 것을 나눠 기록한다.** 남은 것을 숨기지 않는다

**TC-PERF 최종 수치가 M5보다 나빠짐**
- 측정 조건이 달라졌을 수 있다. 구간·시계·부하를 대조한다
- 실제 회귀면 M5 이후 변경을 되짚는다. 로그 추가가 원인인 경우가 많다
