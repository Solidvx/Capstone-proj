### 3.2 데모 시나리오 A — 정상 동작 (약 3분)

| 단계 | ECU 동작 | IVI가 보여줄 것 |
|---|---|---|
| 1 | `--sensor-mode profile_csv` 실행 | 대시보드 값 갱신 시작 |
| 2 | `0x100` 100ms 주기 송신 | SOC/SOH/전압/전류/온도 실시간 표시 |
| 3 | SOC 서서히 감소 | SocGauge 색상 전환 Green → Orange → Red |
| 4 | SOC < 20% → WARNING | FailSafeIndicator가 WARNING으로 변경, 사유 코드 표시 |
| 5 | SOC < 5% → CRITICAL | 풀스크린 Dialog 표시 |
| 6 | 수동 리셋 (SHUTDOWN에서) | NORMAL 복귀 |

> **주의**: `manualReset()`은 ECU 구현상 **SHUTDOWN 상태에서만** 동작한다. CRITICAL에서 리셋을 시연하려 하면 아무 일도 일어나지 않는다 ([ECU M3](../ecu/M3_EKF_Failsafe_SecOC.md) 3.5). 리허설에서 어느 상태로 진입시킬지 미리 정한다.

```bash
# 상태 전이 유도 (주 경로): ADS1115 가변저항으로 팩 전압을 낮춘다
./adaptive_ecu/build/adaptive_ecu --interface can0 --secoc on --sensor-mode ads1115

# 백업 경로: 전압 램프 프로파일
./adaptive_ecu/build/adaptive_ecu --interface can0 --secoc on     --sensor-mode profile_csv --profile adaptive_ecu/data/failsafe_demo.csv
```

> `--sensor-mode potentiometer`는 값 주입 경로가 없어 동작하지 않는다. 삭제 대상이다 ([ECU M3](../ecu/M3_EKF_Failsafe_SecOC.md) 3.11.1).

### 3.3 데모 시나리오 B — 공격과 방어 (약 3분)

| 단계 | 설정 | IVI가 보여줄 것 |
|---|---|---|
| 1 | SecOC off + Spoofing | 가짜 SOC=100%가 **화면에 그대로 표시됨** (위험성 시연) |
| 2 | SecOC on + Spoofing | **위조값 미반영·정상 인증값 갱신 유지**, 실제 폐기 사유 기록 |
| 3 | Flooding 공격 | 3초 내 AlertBanner 표시 |
| 4 | 공격 중단 후 경보 확인 | 사용자 확인으로 AlertBanner 해제; 정상 데이터 수신과 공격 중단 증거는 별도 확인 |

시연 전 [공동 발표의 시연 준비·구성 전환](../common/03_발표_제출.md)을 따른다. 양측 방어 설정, 이전 프로세스 종료, 정상 송신 복구와 입력·관측 조건을 먼저 확인한다.

```bash
# 1) 무방어
./adaptive_ecu/build/adaptive_ecu --interface can0 --secoc off &
python3 security/attacks/spoofing_attack.py --channel can0 --count 5

# 2) SecOC 방어
./adaptive_ecu/build/adaptive_ecu --interface can0 --secoc on &
python3 security/attacks/spoofing_attack.py --channel can0 --count 5

# 3) IDS 탐지
python3 security/ids/realtime_ids.py --channel can0 &
python3 security/attacks/flooding_attack.py --channel can0 --duration 5
```

**시연의 핵심은 1단계와 2단계의 대비다.** 1단계에서 가짜 값이 실제로 화면에 뜨는 것을 보여줘야 SecOC의 가치가 전달된다. 2단계에서는 **위조값은 반영되지 않고 정상 인증값은 계속 갱신된다는 것**을 수신·인증·화면 기록으로 설명한다. raw-only 주입은 MAC 불일치 로그를 반드시 발생시키지 않으므로 실제 교체·만료·인증 결과를 구분한다.

- [ ] 4단계에서 사용자 확인으로 배너가 해제되고 새로운 동일 유형 경보는 다시 표시되는지 확인한다 ([M4](M4_대시보드_Alert_배포.md) 3.3). 배너 해제를 공격 종료 증거로 사용하지 않는다.
- [ ] 각 단계 사이에 이전 프로세스를 반드시 종료한다

### 3.5 IVI 발표 슬라이드

| 슬라이드 | 핵심 메시지 | 증적 |
|---|---|---|
| IVI 아키텍처 | HAL → Service → App 3계층 분리 | 구조도 |
| CAN Parser | ICD 기반 바이트 단위 파싱, 부호·오프셋 처리 | TC-IVI-002 결과 |
| SecOC Verifier | ECU 벡터 교차 검증, Replay 차단 | 시험 결과, IT-004 |
| Dashboard UI | SOC 게이지·Fail-safe·AlertBanner | 데모 스크린샷 |
| CI/CD | Stage 1~4 파이프라인 | Actions 녹색, Coverage |
| 안정성·성능 | e2e 지연, 장시간 시험 | CSV, 로그 |

**아키텍처 슬라이드 도식**

```text
┌─────────────────────────────────────────┐
│           App Layer (Kotlin)            │
│  SocGauge │ AlertBanner │ FailSafeInd.  │
│      DashboardViewModel (StateFlow)     │
├─────────────────────────────────────────┤
│         Service Layer (Java)            │
│  VehicleDataService (Binder IPC)        │
│  VehicleDataManager (Client API)        │
├─────────────────────────────────────────┤
│           HAL Layer (C++)               │
│  can_parser │ secoc_verifier            │
│  vehicle_hal_impl (SocketCAN rx thread) │
└─────────────────────────────────────────┘
```

Plan B로 전환했다면 Service Layer를 D-Bus 기준으로 바꾸고, **전환 사유(ADR-010)를 슬라이드에 포함한다.** 실패를 숨기는 것보다 판단 근거를 보여주는 편이 낫다.

**직무 역량 정리**

```text
1. HAL 설계 + CAN 파서 C++ 구현 (ICD 계약 준수)
2. Service 계층 IPC 설계 + Compose UI
3. CI/CD 4단계 파이프라인 설계·운영
4. Docker 크로스컴파일 + QEMU 에뮬레이션 시험 자동화
5. 성능 측정 지점 정의와 병목 분석
```

**발표 수치 규칙**

- [ ] 실측값만 쓴다. 원출력과 대조한 뒤 슬라이드에 넣는다
- [ ] 목표값과 실측값을 같은 문장에서 구분한다
- [ ] 미달 항목은 빼지 말고 "현재 x, 원인 y"로 말한다
- [ ] `vcan0` 측정이면 그 사실을 밝힌다

## 5. 실패 시 대응과 우회

**데모 중 CAN 하드웨어 실패** — `vcan0`로 전환한다. 전환 사실을 발표에서 밝힌다.

**대시보드가 값을 안 받음**
1. `candump can0`으로 프레임이 오는지
2. HAL 로그에 파싱 결과가 찍히는지
3. Service → StateFlow 전파
4. 순서대로 좁힌다. 세 지점 중 어디서 끊기는지 알면 즉석에서 설명할 수 있다

**SecOC 차단 시연에서 위조값이 반영됨**
- 정상 인증값의 갱신은 정상 동작이다. 주입한 위조값이 반영됐는지 원본·인증 결과·UI 기록을 먼저 대조한다. 인증되지 않은 `0x100`을 전달했다면 결함이다 ([M3](M3_HAL_Service_대시보드.md) 3.2)
- 데모 직전이면 백업 영상으로 대체하고, 결함을 보고서에 기록한다

**AlertBanner가 3초를 넘김**
- 리허설에서 미리 재본다. IDS 윈도우 1초 + 전파 지연이 예산의 대부분이다
- 넘으면 실제 수치를 말한다. "3초 이내"라고 말하지 않는다

**Release 작성 중 수치가 확정 안 됨**
- 확정된 것만 넣고 나머지는 "미측정"으로 둔다. 나중에 릴리즈 노트를 편집할 수 있다

**시간 초과**
- IVI 파트는 5~7분 목표다. 아키텍처와 CI/CD를 남기고 나머지를 압축한다
