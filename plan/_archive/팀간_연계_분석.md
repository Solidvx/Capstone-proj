## 1. 전체 구조: 왜 2인 병렬 개발이 가능한가

### 1.1. ICD.md를 계약으로 삼는 아키텍처

이 프로젝트의 핵심 설계 원칙은 **"ICD.md를 계약(Contract)으로 삼아 양 노드를 독립 개발한다"**는 것이다.

```
┌────────────────────────┐                              ┌────────────────────────┐
│       Node A           │      CAN Bus (ICD.md)        │       Node B           │
│      팀원A             │                              │      팀원B             │
│  ┌──────────────────┐  │  0x100 BMS_Status (100ms)    │  ┌──────────────────┐  │
│  │ C++17 ECU        │  │ ─────────────────────────►   │  │ Android 13 AOSP  │  │
│  │ ├ BSW/CDD        │  │  0x101 BMS_FailSafe (이벤트) │  │ ├ Vehicle HAL    │  │
│  │ ├ BMS (EKF)      │  │ ─────────────────────────►   │  │ ├ HIDL Service   │  │
│  │ ├ SecOC HMAC     │  │  0x102/0x103 SecOC MAC       │  │ ├ SystemService  │  │
│  │ └ ara::com       │  │ ─────────────────────────►   │  │ └ Jetpack UI     │  │
│  └──────────────────┘  │                              │  └──────────────────┘  │
│  ┌──────────────────┐  │  0x200 IDS_Alert (이벤트)    │                        │
│  │ Python 3.10      │  │ ─────────────────────────►   │  ┌──────────────────┐  │
│  │ ├ IDS Engine     │  │                              │  │ DevOps           │  │
│  │ ├ Attack Sim     │  │     CAN ID 규격: ICD.md      │  │ ├ Docker ARM64   │  │
│  │ └ SecOC Proto    │  │     SecOC 프로토콜: ICD.md    │  │ ├ CI/CD 4-Stage  │  │
│  └──────────────────┘  │     HAL API: ICD.md          │  │ └ QEMU Test      │  │
└────────────────────────┘                              └────────────────────────┘
```

- **M1(6월)**: ICD.md를 양측이 합의하여 확정 → 계약 체결
- **M2~M3(7~8월)**: 각자 Mock/Stub을 만들어 상대방 없이도 개발·테스트 → 병렬 개발
- **M4(9월)**: 물리 CAN 연결로 실제 통합 검증 → 계약 이행 확인

### 1.2. 왜 이 접근법인가? — 대안 비교

| 접근법 | 장점 | 단점 | 판정 |
|--------|------|------|------|
| **ICD 계약 기반 병렬 개발 (채택)** | 4개월 병렬 작업, 독립 테스트 가능, 명확한 책임 경계 | ICD 변경 시 양측 동기화 필요 | **채택** |
| 순차 개발 (A 완료 후 B 시작) | 인터페이스 불일치 위험 없음 | 총 개발 기간 2배, B가 4개월 유휴 | 기각 — 8개월 내 불가능 |
| 공유 코드베이스 (Monorepo 단일 빌드) | 코드 재사용 용이 | C++/Java/Kotlin/Python 4개 언어 혼재, 빌드 복잡도 폭증, 책임 불명확 | 기각 — 언어 경계 붕괴 |
| 마이크로서비스 (REST/gRPC) | 언어 독립 통신 | CAN 버스 실시간성(100ms 주기) 보장 불가, AUTOSAR 직무 어필 안 됨 | 기각 — 도메인 부적합 |

**핵심 논리**: CAN 버스는 물리적으로 분리된 2개 노드를 연결하는 프로토콜이므로, 바이트 레벨 인터페이스(ICD)만 합의하면 양쪽이 완전히 독립적으로 개발할 수 있다. 이것이 AUTOSAR의 실제 개발 방식(OEM이 ICD 배포 → Tier1이 독립 구현)과 동일하다.

### 1.3. 개발 패턴 요약

```
M1         M2         M3         M4         M5         M6~M7      M8
계약 수립   Mock 독립   핵심 연쇄   물리 통합   실험 분담   교차 검토   발표
  │           │           │           │           │           │         │
  ▼           ▼           ▼           ▼           ▼           ▼         ▼
[ICD.md]──►[각자 Mock]─►[SecOC 체인]─►[CAN 연결]─►[Ablation]─►[문서 QA]─►[데모]
  │         ┌─┴─┐        ┌─┴─┐        ┌─┴─┐        ┌─┴─┐        ┌─┴─┐
  │         A   B        A   B        A   B        A   B        A   B
  │         ↕           ↕   ↕         ↕   ↕        ↕   ↕        ↕   ↕
  │        독립         의존↔독립     완전연동     분담+동기    상호검증
```

> **발표 Talking Point**: "AUTOSAR 실무에서 OEM이 ICD를 배포하고 Tier1이 독립 구현하는 것과 동일한 방식으로, ICD.md를 1개월차에 확정하여 계약 기반 병렬 개발 체제를 확립했습니다."

## 2. 월별 연계 흐름 (M1~M8)

### M1 (6월) — 계약 수립: 모든 것의 기초

```
팀원A                                          팀원B
──────                                         ──────
RPi4 Ubuntu 22.04 세팅                         AOSP 빌드 서버 + repo sync
    │                                              │
can_driver.h 추상 인터페이스 설계                  │
    │                                              │
    ├─── PR 리뷰 요청 ──────────────────────────►  리뷰 + 피드백
    │    "CAN 프레임 구조가 HAL 파싱에              (HAL에서 이 구조체로
    │     적합한가?"                                바로 파싱 가능한가?)
    │                                              │
ICD.md 초안 작성                                   │
    │                                              │
    ├─── PR 리뷰 요청 ──────────────────────────►  리뷰 (HAL 관점 피드백)
    │    "0x100 레이아웃에 필요한                    "VehicleData 구조체에
    │     필드가 모두 포함되었는가?"                  매핑 가능한 레이아웃인가?"
    │                                              │
    │                                          IVehicleHal.hal 초안 작성
    │                                          (ICD.md 초안의 CAN ID/필드 기반)
    │                                              │
    │◄──── HAL 초안 리뷰 요청 ─────────────────────┤
    │  "HAL 콜백 구조가 CAN 이벤트                  │
    │   모델과 호환되는가?"                          │
    │                                              │
    └──────────── ICD.md 최종 확정 미팅 ───────────┘
                  (4주차 — 이후 독립 개발 가능)
```

**왜 이 순서가 필수인가? (인과 관계)**

1. **can_driver.h가 먼저**: CAN 프레임의 바이트 구조를 정의한다. 이 구조가 확정되어야 팀원B가 HAL에서 동일한 프레임을 파싱하는 로직을 설계할 수 있다. A의 `struct can_frame` 정의가 B의 `can_parser.cpp` 입력이 된다.

2. **ICD.md가 다음**: can_driver.h의 프레임 구조를 기반으로, 0x100~0x200의 바이트 레이아웃, 스케일링, 유효 범위를 확정한다. 이것이 양측의 "계약서"이다.

3. **IVehicleHal.hal이 마지막**: ICD.md의 CAN ID 규격에 직접 의존한다. 예를 들어 VehicleData 구조체의 `float soc` 필드는 ICD 0x100의 Byte 0 (uint8, x0.5 스케일링)에서 파생된다. ICD 없이 HAL을 설계하면 타입 불일치가 발생한다.

**A의 출력 → B의 입력**:

| 팀원A 산출물 | 팀원B 입력으로 사용 |
|-------------|-------------------|
| `can_driver.h` 추상 인터페이스 | HAL에서 동일한 CAN 프레임 구조 사용 |
| ICD.md 0x100~0x103 레이아웃 | `can_parser.cpp` 파싱 로직의 바이트 오프셋 |
| ICD.md 0x200 레이아웃 | `onSecurityAlert()` 콜백 파라미터 정의 |
| SecOC HMAC 프로토콜 규격 | `secoc_verifier.cpp` 검증 로직 설계 |

> **발표 Talking Point**: "M1에서 ICD.md를 확정함으로써 이후 3개월간의 독립 개발 기반을 마련했습니다. 이는 AUTOSAR 실무에서 OEM-Tier1 간 인터페이스 합의와 동일한 절차입니다."

    │                                          Plan A/B 판단 ◄── 프로젝트 분기점
Publisher<T> 구현                              (7월 말까지 AOSP 부팅 성공 여부)
(ara::com 경량 Pub/Sub)                            │
    │                                          Dockerfile.arm64 빌드
NASA 배터리 데이터 확보                        (팀원A의 C++ 코드 크로스컴파일용)

    │                                          toolchain-aarch64.cmake 작성
    │                                              │
    ◄── 크로스컴파일 환경 제공 ────────────────────┤
    │   "docker run으로 A의 코드를                  │

**왜 Mock이 필요한가? — 병렬 개발의 전제 조건**

Mock/Stub이 없으면 팀원A는 "팀원B의 HAL이 내 CAN 프레임을 제대로 파싱하는지" 확인하려면 팀원B의 코드가 완성될 때까지 기다려야 한다. 반대로 팀원B는 "Node A가 보내는 실제 CAN 프레임"이 없으면 HAL 테스트가 불가능하다.

Mock은 ICD.md 규격을 따르므로, 나중에 실물로 교체해도 인터페이스가 동일하다:

```
[개발 시]  팀원A 코드 ──► MockCanDriver ──► 가짜 CAN 응답 (ICD 규격)
[통합 시]  팀원A 코드 ──► SocketCanCdd  ──► 실제 CAN 프레임 (ICD 규격)
                                               │
                           인터페이스 동일 ◄─────┘
```

**Plan B 영향 분석 — M2의 가장 중요한 의사결정**

ADR-010에 따르면 7월 말까지 AOSP 부팅 실패 시 Plan B(Ubuntu + D-Bus/gRPC + Qt/Flutter)로 전환한다. 이 결정이 팀원A에게 미치는 영향:

| 항목 | Plan A (AOSP 성공) | Plan B (AOSP 실패) |
|------|-------------------|-------------------|
| CAN 버스 레이어 | 변경 없음 | 변경 없음 |
| 팀원A 코드 변경 | 없음 | 없음 (CAN 프레임은 동일) |
| 팀원B HAL 계층 | HIDL C++ 바인딩 | D-Bus/gRPC 서비스 |
| 팀원B UI 계층 | Jetpack Compose | Qt/Flutter |
| ICD 영향 | 없음 | §3 HAL API만 변경 |

**핵심 인사이트**: CAN 버스가 양 노드의 물리적 경계이므로, Node B의 OS가 Android든 Ubuntu든 팀원A의 코드에는 영향이 없다. 이것이 ICD 계약 기반 설계의 강점이다.

**크로스컴파일 협업 구조**:

팀원B가 `Dockerfile.arm64`와 `toolchain-aarch64.cmake`를 제공하면, 팀원A는 `docker run` 한 줄로 자신의 C++ 코드를 ARM64 바이너리로 빌드할 수 있다. **"팀원A가 코드를 쓰고, 팀원B가 빌드 환경을 제공한다"** — 이 구조가 CI/CD 협업의 시작점이다.

> **발표 Talking Point**: "Mock/Stub 패턴으로 하드웨어 의존성을 제거하여, 2개월간 완전한 병렬 개발을 달성했습니다. Plan B 전환 시에도 팀원A 코드 변경이 0건인 것은 ICD 계약의 효과입니다."

**가장 중요한 의존성: SecOC 3단계 체인**

이 달에 프로젝트에서 가장 긴밀한 연계가 발생한다:

```
단계 1 [팀원A]                단계 2 [팀원A]              단계 3 [팀원B]
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ secoc_module.py  │────►│ secoc_module.cpp │────►│ secoc_verifier  │
│ (Python)         │     │ (C++)            │     │ .cpp (C++)      │
│                  │     │                  │     │                  │
│ 빠른 프로토타입  │     │ 실제 서명 모듈   │     │ 서명 검증 모듈   │
│ 테스트 벡터 생성 │     │ 교차 검증 통과   │     │ 동일 키/알고리즘 │
└─────────────────┘     └─────────────────┘     └─────────────────┘
       1~2주                   2~3주                   3~4주
```

**왜 이 순서인가? (인과 관계)**

1. **Python 프로토타입이 먼저**: Python의 `hmac` 표준 라이브러리로 HMAC-SHA256을 5줄로 구현할 수 있다. 빠르게 정확한 테스트 벡터(입력→MAC 쌍)를 생성한다. 이 벡터가 이후 모든 검증의 기준이 된다.

2. **C++ 이식이 다음**: Node A는 C++17이므로 실제 서명은 OpenSSL `libcrypto`로 수행해야 한다. Python 테스트 벡터와 동일한 출력을 내는지 교차 검증하여 **언어 간 HMAC 결과 일치**를 보장한다.

3. **HAL 검증이 마지막**: 서명 로직(키, 알고리즘, 절단 방식)이 확정되어야 검증 로직을 정확히 구현할 수 있다. 팀원B는 팀원A가 공유한 테스트 벡터로 자신의 검증 로직을 독립 테스트한다.

**교차 검증 프로세스 (3개 언어/플랫폼에서 동일한 MAC)**:

```
입력: key=0xABCD...1234 (32B), canId=0x100, counter=1, payload=0xDE...EF (8B)

[Python]  hmac.new(key, msg, sha256).digest()[:4]  → MAC = 0x7A3B9C1E
                                                        │
[C++]     HMAC(EVP_sha256(), key, ...)              → MAC = 0x7A3B9C1E  ← 일치 필수
                                                        │
[HAL]     수신 MAC 0x7A3B9C1E vs 재계산 MAC         → 검증 성공         ← 일치 필수
```

**실패 시 영향 (Cascading Failure)**:
- Python↔C++ MAC 불일치 → Node B에서 모든 정상 프레임을 ERR_HMAC_VERIFY_FAIL로 폐기
- → 0x100 BMS_Status 데이터 전달 안 됨 → 대시보드에 SOC 미표시
- → 0x101 BMS_FailSafe 무시 → 안전 상태 전이 실패
- → **시스템 전체 통신 두절**

**EKF → CAN → Parser 데이터 흐름**:

```
[NASA Battery Data]
        │
        ▼
   EKF 추정기 (팀원A)
   SOC = 75.0% (예측+관측 융합)
        │
        ▼
   BmsComponent (팀원A)
   Byte[0] = 150 (75.0 / 0.5)    ◄── ICD §1.2 스케일링 규칙
        │
        ▼
   CanPublisher (팀원A)
   CAN 0x100 [96, BE, ...] 전송
        │
   ════ CAN Bus ════
        │
        ▼
   can_parser (팀원B)
   raw=150, soc = 150 * 0.5 = 75.0%  ◄── ICD §1.2 역스케일링
        │
        ▼
   VehicleData.soc = 75.0f (팀원B)
```

> **발표 Talking Point**: "SecOC 구현을 Python 프로토타입 → C++ 이식 → HAL 검증 3단계로 분리하여, 언어 간 HMAC 일관성을 교차 검증 벡터로 보장했습니다."

| 관점 | 팀원A가 실험을 수행하는 이유 | 팀원B가 측정을 수행하는 이유 |

**시간 분리가 필요한 이유**:

팀원A의 Ablation 실험 중 Flooding 공격은 CAN 버스를 포화시킨다(~10,000 msg/s). 이 상태에서 팀원B가 정상 레이턴시를 측정하면 비정상적으로 높은 값이 나온다. 따라서:

```

[오후] 팀원B: 레이턴시 측정 (CAN 버스 정상 상태)
[저녁] 양측: 데이터 교차 확인 + 이상치 논의
```

**Ablation Study 3가지 구성 (ADR-008)**:

| 구성 | SecOC | IDS | 측정 목적 |
|------|:-----:|:---:|-----------|
| Config-1 (무방어) | OFF | OFF | 공격 성공률 100% 기준선 |
| Config-2 (SecOC only) | ON | OFF | SecOC 단독 효과 — Spoofing/Replay 차단율 |
| Config-3 (SecOC + IDS) | ON | ON | 최종 통합 효과 — Flooding/Fuzzy 추가 탐지 |

> **발표 Talking Point**: "Ablation Study로 SecOC와 IDS 각각의 방어 기여도를 정량적으로 분리 검증했습니다. SecOC만으로 Spoofing/Replay 100% 차단, IDS가 Flooding을 보완하는 계층별 역할을 수치로 입증했습니다."

### 4.3. SecOC 방어 흐름 (공격이 HAL에 도달하기 전 차단)

```
[공격자]
    │
    ▼ Spoofing: 가짜 0x100 + 0x102 (잘못된 MAC)
    │
════╪════════════════ CAN Bus ═══════════════════════════
    │
    ▼
┌──────────────┐
│ can_parser   │  0x100 수신 → 버퍼링
│              │  0x102 수신 → SecOC 검증 시작
└──────┬───────┘
       │
┌──────┴───────┐
│secoc_verifier│
│              │
│ Step 1: Counter 검사                     
│   last_counter = 55                      
│   received = 42  ← 과거 값              
│   42 <= 55 → ❌ ERR_COUNTER_MISMATCH     
│   → 즉시 폐기 (Replay 차단)              
│                                          
│ Step 2: (Counter 통과 시) HMAC 재계산    
│   재계산 MAC ≠ 수신 MAC                  
│   → ❌ ERR_HMAC_VERIFY_FAIL              
│   → 즉시 폐기 (Spoofing 차단)            
│                                          
│ ※ 폐기된 프레임은 HAL 콜백에              
│   전달되지 않음 → UI 오표시 방지          
└──────────────┘

→ 결과: 공격 프레임이 VehicleDataService에 도달하지 못함
→ 대시보드에는 마지막 유효 데이터가 유지됨
→ 300ms(3주기) 타임아웃 시 "통신 끊김" 표시 (ICD §2.5.1)
```

### 시나리오 4: IDS 탐지율 ≤90% 미달

```

    (목표: ≥90%, TC-EXP-003 기준)

영향:
  └─ 실험 유효성에 대한 질문 발생 가능
  └─ TARA §7.3 예측값과 실측값 불일치
```

| 영향 항목 | 상세 |
|-----------|------|
| **실험 유효성** | Ablation Study 결과의 신뢰도 의문. "방어 시스템이 충분한가?" 질문에 답변 어려움 |
| **TARA 영향** | §7.3 예측 탐지율(≥90%)과 실측값 불일치 → 위험 평가 재수행 필요 |
| **발표 영향** | "IDS 탐지율 85%"를 그대로 보고해야 하나, 부정적 결과로 인식될 수 있음 |
| **완화 전략** | (1) IDS 파라미터 재튜닝: contamination 0.01 → 0.05 조정, threshold 재설정. (2) 특징 벡터 확장: 7차원 → 추가 특징 (예: payload entropy, DLC 분포). (3) 85% 결과를 투명하게 보고하되, "추가 튜닝으로 X% 개선 가능" 전망 제시 |
| **위험도** | **중간** — 탐지율 미달 자체보다 분석의 부재가 더 큰 문제. 원인 분석 + 개선 방향 제시가 핵심 |

### 8.2. CI가 통합 문제를 사전에 방지하는 메커니즘

| CI 단계 | 방지하는 문제 | 문제 발견 시점 (CI 없는 경우) |
|---------|-------------|----------------------------|
| Stage 1 (cppcheck) | 메모리 누수, 널 포인터, 미초기화 변수 | M4 물리 통합 시 세그폴트 |
| Stage 2 (ARM64 빌드) | x86/ARM64 간 바이트 오더, 타입 크기 차이 | M4 RPi4 배포 시 크래시 |
| Stage 3 (QEMU 테스트) | EKF 계산 오류, SecOC MAC 불일치 | M4 통합 테스트 시 데이터 불일치 |
| Stage 4 (SSH 배포) | 바이너리 호환성, 런타임 의존성 누락 | 수동 배포 후 "왜 안 되지?" |

### 8.3. Coverage를 공유 품질 지표로 활용

```
Coverage 측정 흐름:

팀원A 코드          CI Stage 3              Coverage 리포트
─────────          ─────────              ────────────────
can_cdd.cpp   →   QEMU GoogleTest   →   Statement: 85%
bms_ekf.cpp   →   gcov/lcov         →   Branch:    78%
secoc.cpp     →                     →   Fail-safe: 100%
                                         │
                                         ▼
                            ┌────────────────────────┐
                            │ 품질 게이트 판정         │
                            │                        │
                            │ Statement ≥ 80% → ✅    │
                            │ Fail-safe Branch        │
                            │   = 100% → ✅           │
                            │ cppcheck 0건 → ✅       │
                            └────────────────────────┘
```

Coverage는 **양측이 공유하는 품질 언어**이다:
- 팀원A: "내 코드의 테스트 커버리지가 80%를 넘기도록 테스트를 작성한다"
- 팀원B: "CI가 80% 미만을 자동으로 차단하여 품질 하한선을 보장한다"
- 합의: "Fail-safe 관련 코드는 100% 브랜치 커버리지 의무"

> **발표 Talking Point**: "팀원A가 코드를 push하면 팀원B가 구축한 4단계 CI가 자동으로 정적 분석, ARM64 빌드, 단위 테스트, RPi4 배포까지 수행합니다. 팀원 간 코드 품질을 CI가 객관적으로 보증하는 구조입니다."

## 10. 요약: 프로젝트 성공의 핵심 요인

### 10.1. 네 가지 핵심 메커니즘

```
┌─────────────────────────────────────────────────────────────┐
│                  프로젝트 성공의 4대 기둥                      │
│                                                             │
│  ① ICD-First         ② Mock/Stub         ③ Cross-Review    │
│  ┌──────────┐        ┌──────────┐        ┌──────────┐      │
│  │계약을 먼저│        │독립 개발 │        │상호 검증 │      │
│  │확정하여  │        │가능하게  │        │으로 품질 │      │
│  │병렬 개발 │        │하는 추상 │        │보증      │      │
│  │기반 마련 │        │화 레이어 │        │          │      │
│  └──────────┘        └──────────┘        └──────────┘      │
│       │                    │                   │            │
│       └────────────────────┼───────────────────┘            │
│                            │                                │
│                    ④ CI/CD Safety Net                        │
│                    ┌──────────────────┐                      │
│                    │자동 빌드·테스트·  │                      │
│                    │배포로 통합 품질   │                      │
│                    │을 객관적으로 보증 │                      │
│                    └──────────────────┘                      │
└─────────────────────────────────────────────────────────────┘
```

**① ICD-First (인터페이스 선행 확정)**: CAN 버스의 바이트 레벨 규격을 M1에서 확정함으로써, 이후 3개월간 양측이 서로의 코드를 기다리지 않고 독립 개발할 수 있는 기반을 마련했다. ICD 변경은 GitHub Issue (`interface-change` 라벨) + PR + 양측 합의를 거치도록 관리하여, 계약의 안정성을 보장했다.

**② Mock/Stub (추상화를 통한 독립 개발)**: MockCanDriver(팀원A)와 VehicleHalMock(팀원B)은 ICD 규격을 따르는 가짜 객체이다. 실물 하드웨어 없이도 각자의 전체 로직을 테스트할 수 있게 해주었다. M4 물리 통합 시 Mock을 실물로 교체했을 때 인터페이스 불일치가 0건이었다는 것이 이 패턴의 효과를 증명한다.

**③ Cross-Review (교차 검토)**: 모든 PR과 설계 문서를 상대방이 리뷰했다. 팀원A가 쓴 SDD-ECU의 CAN ID가 ICD와 일치하는지 팀원B가 IVI 관점에서 검증하고, 팀원B가 쓴 SDD-IVI의 HIDL API가 실제 구현과 일치하는지 팀원A가 ECU 관점에서 검증했다. "자기가 쓴 문서는 자기가 못 찾는 오류가 있다"는 원칙에 기반한다.

**④ CI/CD Safety Net (자동 품질 보증)**: 팀원B가 구축한 4단계 CI/CD 파이프라인은 팀원A의 코드를 자동으로 정적 분석 → ARM64 빌드 → QEMU 테스트 → RPi4 배포한다. 커버리지 80% 미만, cppcheck Critical/Error 발견 시 자동으로 PR을 차단하여, 품질 하한선을 객관적으로 보장한다.
