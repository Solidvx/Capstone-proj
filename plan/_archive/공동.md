## 매월 반복 작업 (M1~M8 공통 마일스톤 완료 절차)

매월 마일스톤 완료 시 아래 절차를 동일하게 수행한다. 각 월별 섹션에서 "M완료 처리"로 참조한다.

### 절차 A: develop → main PR 생성 + Merge (예상 시간: 20분)

```bash
# 1. develop 최신 상태 확인
git switch develop && git pull origin develop

# 2. GitHub 웹에서 PR 생성
#    base: main ← compare: develop
#    Title: "MN: (마일스톤 요약)"
#    Body: 해당 월 완료 항목 bullet 나열
```

**GitHub 웹 → Pull requests → New pull request**
- Base: `main` ← Compare: `develop`
- Title 예시: `M1: 환경 구축 완료 — ICD.md 확정, 개발 환경 동작`
- Merge 전략: **Merge Commit** (Create a merge commit)
- CI 전체 통과 확인 후 Merge 버튼 클릭

### 절차 B: Tag 생성 + Push (예상 시간: 5분)

```bash
git switch main && git pull origin main
git tag -a v0.N.0 -m "MN: 완료 내용 요약"
git push origin --tags
```

**검증:**
```bash
git tag -l "v0.N.0"
# 기대 출력: v0.N.0
```

### 절차 C: Milestone Close (예상 시간: 3분)

**GitHub 웹 → Issues → Milestones → 해당 MN → Close milestone**

- 열려 있는 Issue가 있으면 다음 Milestone로 이동하거나 Close 처리 후 진행
- Close 전 Open Issue 0건 확인

### 절차 D: GitHub Release 작성 (예상 시간: 10분)

**GitHub 웹 → Releases → Draft a new release**

1. Tag: `v0.N.0` (Choose an existing tag)
2. Title: `v0.N.0 — MN: (마일스톤 요약)`
3. Description 템플릿:

```markdown
## 변경 내역

### 신규 기능
- (이번 달 구현 완료 기능 나열)

### 문서
- (이번 달 완성/갱신 문서 나열)

### 테스트
- (통과한 TC 나열)

### 알려진 이슈
- (미해결 이슈 있으면 기록)

## 실험 데이터
- (해당 월에 실험 데이터가 있으면 파일 첨부)
```

4. Attach files: 해당 월 산출물 (CSV, 바이너리 등) 있으면 첨부
5. **Publish release** 클릭

### 수행 절차 1: 브랜치 보호 규칙 설정 (예상 시간: 15분)

**경로**: GitHub 웹 → `Settings` → `Branches` → `Add branch ruleset`

**`main` 브랜치:**

1. Branch name pattern: `main`
2. 체크 항목:
   - `Require a pull request before merging` → **ON**
     - Required approvals = **1**
   - `Require status checks to pass before merging` → **ON**
   - `Block force pushes` → **ON**
   - `Do not allow deletions` → **ON**

**`develop` 브랜치:**

1. Branch name pattern: `develop`
2. 체크 항목:
   - `Require a pull request before merging` → **ON**
   - `Require status checks to pass before merging` → **ON**
   - `Block force pushes` → **ON**

> CI 워크플로우가 아직 없으므로 status checks 구체 항목은 M1 4주차에 지정한다.

**검증:**
- Settings → Branches 페이지에서 `main`, `develop` 두 규칙이 보이는지 확인
- 직접 `main` 브랜치에 push 시도 → 거부되는지 확인:

```bash
git switch main
echo "test" > _test_protection.txt
git add _test_protection.txt && git commit -m "test: branch protection check"
git push origin main
# 기대 결과: rejected - push is restricted
git reset HEAD~1 --soft && git restore --staged _test_protection.txt
rm _test_protection.txt
```

### 수행 절차 2: GitHub Labels 생성 (예상 시간: 10분)

**경로**: Issues → Labels → New label

기본 제공 라벨(bug, documentation, enhancement 등)을 삭제한 뒤, 아래 11개를 생성한다.

| Name | Color (Hex) | Description |
|------|-------------|-------------|

| `test` | `#5319E7` | 테스트 작성 |
| `chore` | `#FEF2C0` | 빌드·CI·환경 설정·디렉토리 구조 등 기능 외 작업 |
| `refactor` | `#D4C5F9` | 동작 변경 없는 코드 정리 |
| `security` | `#E4820E` | SecOC / IDS / TARA 관련 |
| `interface-change` | `#FF6600` | ICD.md 인터페이스 변경 — 양측 합의 필수 |
| `ECU` | `#BFDADC` | 팀원A 담당 (Node A) |
| `IVI` | `#C5DEF5` | 팀원B 담당 (Node B) |
| `blocked` | `#000000` | 다른 이슈/PR에 의존하여 진행 불가 |

> **라벨 사용 원칙**: `feat`/`bug`/`docs`/`test`/`chore`/`refactor`는 작업 유형, `security`/`interface-change`는 도메인, `ECU`/`IVI`는 담당자, `blocked`는 상태를 나타낸다. 하나의 Issue에 유형 + 도메인(해당 시) + 담당자를 조합하여 할당한다.

**검증**: Issues → Labels 페이지에서 11개 라벨이 올바른 색상으로 표시되는지 확인

| Byte | Raw Hex | Raw Decimal | 필드 | 스케일링 | 결과 |
|------|---------|-------------|------|---------|------|
| 0 | 0xC8 | 200 | SOC | ×0.5 | 100.0% |
| 1 | 0x3C | 60 | SOH | ×0.5 | 30.0% |
| 2-3 | 0x1068 | 4200 | Voltage (BE) | ×0.01 | 42.00V |
| 4-5 | 0x0014 | 20 | Current (BE) | ×0.1 | 2.0A |
| 6 | 0x41 | 65 | Temperature | offset +40 | 25°C |
| 7 | 0x00 | 0 | Reserved | — | 0 |

**확인 항목:**
- [ ] CAN ID 0x100 바이트 오프셋이 ICD.md §1.2와 일치
- [ ] 스케일링 계수 적용 결과가 예상 범위 내
- [ ] Byte order(Big Endian) 올바르게 해석됨

### 수행 절차 1: MCP2515 × 2 물리 CAN 연결 (예상 시간: 2시간)

**필요 부품:**
- MCP2515 CAN 모듈 × 2
- 점퍼 와이어 (Female-Female) × 12 이상
- 120Ω 종단저항 × 2 (모듈에 내장된 경우 점퍼 확인)
- CAN 통신 케이블 (CANH, CANL 2선)

**배선도:**

```
[RPi4-A GPIO]──SPI0──[MCP2515-A]──CANH──┬──120Ω──┬──CANH──[MCP2515-B]──SPI0──[RPi4-B GPIO]
                                        │        │
              [MCP2515-A]──CANL──────────┘        └──────────CANL──[MCP2515-B]
                                                             120Ω (종단)
```

**MCP2515-RPi4 SPI 연결 (양쪽 동일):**

| MCP2515 핀 | RPi4 GPIO |
|-----------|-----------|
| VCC | 3.3V (Pin 1) |
| GND | GND (Pin 6) |
| CS | CE0 (Pin 24, GPIO 8) |
| SO (MISO) | MISO (Pin 21, GPIO 9) |
| SI (MOSI) | MOSI (Pin 19, GPIO 10) |
| SCK | SCLK (Pin 23, GPIO 11) |
| INT | GPIO 25 (Pin 22) |

**CAN 버스 연결 (두 MCP2515 모듈 간):**

| 연결 | 설명 |
|------|------|
| MCP2515-A CANH ↔ MCP2515-B CANH | 고전압 신호선 |
| MCP2515-A CANL ↔ MCP2515-B CANL | 저전압 신호선 |
| 120Ω: CANH-CANL (양쪽 끝) | 종단 저항 (임피던스 매칭) |

**양쪽 RPi4 설정:**

```bash
# /boot/firmware/config.txt 에 추가 (이미 되어 있으면 skip)
# dtparam=spi=on
# dtoverlay=mcp2515-can0,oscillator=8000000,interrupt=25

# 재부팅 후 CAN 인터페이스 활성화
sudo ip link set can0 up type can bitrate 500000
ip link show can0
# 기대: can0: <NOARP,UP,LOWER_UP> mtu 72 qdisc pfifo_fast state UP
```

**양방향 통신 테스트:**

```bash
# 테스트 1: A → B
# Node B: candump can0 &
# Node A: cansend can0 100#DEADBEEF
# Node B 기대 출력: can0  100   [4]  DE AD BE EF

# 테스트 2: B → A (역방향)
# Node A: candump can0 &
# Node B: cansend can0 200#CAFEBABE
# Node A 기대 출력: can0  200   [4]  CA FE BA BE
```

**트러블슈팅:**
- `can0`이 안 보이는 경우: `dmesg | grep mcp251x` 로 드라이버 로드 확인

- `bus-off` 에러: `sudo ip link set can0 down && sudo ip link set can0 up type can bitrate 500000`

### 수행 절차 5: e2e 레이턴시 측정 (예상 시간: 1시간)

**측정 방법 개요:**
- Node A CAN 전송 타임스탬프 vs Node B 수신 타임스탬프 차이
- 1,000회 샘플링
- 목표: avg ≤50ms, max ≤100ms (TC-PERF-001)

**레이턴시 측정 Python 스크립트** (`scripts/measure_latency.py`):

```python
#!/usr/bin/env python3
"""e2e CAN 레이턴시 측정 스크립트 — Node B에서 실행"""

import can
import time
import statistics
import csv
import sys

CAN_INTERFACE = sys.argv[1] if len(sys.argv) > 1 else "can0"
TARGET_CAN_ID = 0x100
NUM_SAMPLES = 1000
OUTPUT_CSV = "latency_results.csv"

def measure():
    bus = can.interface.Bus(channel=CAN_INTERFACE, bustype="socketcan")
    latencies = []
    count = 0

    print(f"Collecting {NUM_SAMPLES} samples on {CAN_INTERFACE} (CAN ID 0x{TARGET_CAN_ID:03X})...")

    while count < NUM_SAMPLES:
        msg = bus.recv(timeout=1.0)
        if msg is None:
            continue
        if msg.arbitration_id == TARGET_CAN_ID:
            # msg.timestamp = 커널 CAN 수신 타임스탬프 (epoch seconds)
            recv_time = time.time()
            latency_ms = (recv_time - msg.timestamp) * 1000
            latencies.append(latency_ms)
            count += 1
            if count % 100 == 0:
                print(f"  {count}/{NUM_SAMPLES} collected...")

    bus.shutdown()

    # 결과 계산
    avg = statistics.mean(latencies)
    p95 = sorted(latencies)[int(0.95 * len(latencies))]
    p99 = sorted(latencies)[int(0.99 * len(latencies))]
    max_val = max(latencies)
    min_val = min(latencies)
    stdev = statistics.stdev(latencies)

    print(f"\n=== Latency Results ({NUM_SAMPLES} samples) ===")
    print(f"  avg:   {avg:.2f} ms")
    print(f"  stdev: {stdev:.2f} ms")
    print(f"  min:   {min_val:.2f} ms")
    print(f"  P95:   {p95:.2f} ms")
    print(f"  P99:   {p99:.2f} ms")
    print(f"  max:   {max_val:.2f} ms")

    # Pass/Fail 판정
    if avg <= 50.0 and max_val <= 100.0:
        print(f"\n  PASS: avg({avg:.2f}) <= 50ms, max({max_val:.2f}) <= 100ms")
    else:
        print(f"\n  FAIL: avg({avg:.2f}) vs 50ms, max({max_val:.2f}) vs 100ms")

    # CSV 저장
    with open(OUTPUT_CSV, "w", newline="") as f:
        writer = csv.writer(f)
        writer.writerow(["sample", "latency_ms"])
        for i, lat in enumerate(latencies):
            writer.writerow([i + 1, f"{lat:.4f}"])

    print(f"\n  Results saved to {OUTPUT_CSV}")

if __name__ == "__main__":
    measure()
```

#        배터리 프로파일 데이터를 기반으로 CAN 0x100을 100ms 주기로 전송합니다."

# 설명: "Node B 대시보드에서 SOC, 전압, 전류, 온도가 실시간으로 갱신되고 있습니다.
#        CAN 버스를 통해 100ms 주기로 데이터가 전달됩니다."

# Step 3: SOC 저하 시뮬레이션 — Fail-safe 전이 (90초)
# Node A 재시작 (SOC 강제 조절):

./adaptive_ecu --interface can0 --secoc-enabled --sensor-mode constant --soc 80
# 설명: "SOC가 복귀하면 NORMAL 상태로 돌아갑니다."
