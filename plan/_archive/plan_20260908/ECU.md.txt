# ECU 프로젝트 진행 계획

갱신: 2026-09-05 · 담당: 팀원A · 범위: Node A C++17 ECU 및 Python 보안·실험

[공동 일정·통합·릴리즈](Common.md) · [IVI 계획](IVI.md)

## 1. 현재 상태와 바로 할 작업

`adaptive_ecu/`에는 CAN·Mock·Publisher·센서·SOC·SOH·Fail-safe·SecOC·Watchdog 소스, CMake, 9개 테스트 파일이 있다. `security/`에는 Python SecOC, 합성 공격, 규칙·사양·Isolation Forest 탐지기, 평가·측정 및 2개 테스트 파일이 있다. **소스 존재가 공식 시험 통과나 전체 요구사항 구현 완료를 뜻하지 않는다.**

현재 재확인할 차이가 있다. `main.cpp`는 Watchdog 타임아웃을 로그로 처리하며 스레드 재시작·Fail-safe 연계 완료를 입증하지 않는다. 센서의 ADS1115 분기는 주입된 ADC 데이터를 반환하며 실제 I2C 읽기를 구현한 증거가 아니다. 합성 트래픽 평가는 실제 CAN 공격 CLI·실시간 IDS·경보 송신의 완료 증거가 아니다. 이를 아래 과제에 남긴다.

우선 ECU-ENV-01로 환경·시험 상태를 확인하고, ECU-CAN-01·ECU-BMS-01·ECU-SEC-01의 기존 코드와 필수 요구사항을 대조한다. 새 소스 구조를 먼저 만들지 않는다. 날짜·공동 게이트·상태 정의는 [Common](Common.md#schedule)을 따른다. 모든 과제의 완료 증거는 아직 재확인 대상이다.

## 2. 원천과 담당 경계

- 계약: [ICD](../docs/ICD.md). 송신 레이아웃·카운터·HMAC·HAL 영향은 원천을 직접 확인한다.
- 기능·시험: [SRS](../docs/SRS.md), [TEST_PLAN](../docs/TEST_PLAN.md).
- 설계·보안: [SDD-ECU](../docs/SDD-ECU.md), [TARA](../docs/TARA.md), [ADR](../docs/ADR.md).
- 팀원A는 ECU 송신·BMS·보안·공격/IDS·실험을 수행하고, IVI 구현은 팀원B가 맡는다. 공동 TC와 결과 취합은 Common에서만 관리한다.

## 3. 단계별 실행 과제

<a id="ecu-env-01"></a>
### ECU-ENV-01 — 환경·기존 시험 확인 (M1)

상태: 재확인 · 선행: [COM-BASE-01](Common.md#com-base-01)에서 환경 확인 시작

1. RPi4 Ubuntu와 CAN 장비, C++17/CMake/OpenSSL/Threads/GoogleTest 및 Python 의존성 가용 여부를 확인한다. 버전은 실제 실행 환경에서 기록한다.
2. [CMakeLists.txt](../adaptive_ecu/CMakeLists.txt)로 빌드하고 등록된 단위시험을 실행한다. Python은 [requirements.txt](../security/requirements.txt)와 설치 환경을 대조한다. 미설치·장비 부재는 실패 원인과 구분해 기록한다.
3. 기존 소스와 공식 요구사항을 대조하고 남은 구현·회귀 시험·물리 시험을 해당 과제에 표시한다. 문서의 `bms_component.cpp` 같은 예정 모듈을 현재 코드처럼 취급하지 않는다.

산출물: 환경·빌드·시험 결과와 미구현 목록. 완료 조건: 현재 재현 가능한 기반과 제한을 확인하고 ECU-CAN/BMS/SEC/IDS 과제에 연결했다. 인계: 팀원B에 빌드·입력 준비 상태와 차단 요인을 전달한다.

<a id="ecu-can-01"></a>
### ECU-CAN-01 — CAN·Publisher·센서 입력 (M2)

상태: 재확인 · 선행: ECU-ENV-01, 계약 기준 확인

1. `CanDriver`, SocketCAN과 Mock의 경계, 비동기 수신·콜백·종료를 대조하고 부족한 동작을 보완한다. Publisher의 다중 구독·동시 접근을 시험한다.
2. BMS·Fail-safe 인코딩을 ICD에 맞춰 시험한다. 경계값·부호·온도 오프셋·예약 바이트·DLC는 계약을 읽어 확인한다.
3. 센서 CONSTANT/PROFILE_CSV/RANDOM_WALK/ADS1115_HARDWARE 요구를 대조한다. 실제 ADC 연결·오류 처리는 장비 과제로 유지하고 입력 주입 시험과 구분한다.
4. `battery_profile.csv`는 기존 회귀 입력으로 보존한다. 장기 SOC 비교에 필요한 프로파일은 출처·변환·단위·길이를 기록해 별도 준비한다. 현재 소형 CSV를 장기 데이터셋으로 간주하지 않는다.

산출물: 기존 `adaptive_ecu/include/`, `src/bsw/`, `src/app/sensor_simulator.cpp`와 대응 시험의 필요한 보완, 송신 샘플·입력 재현 방법. 기준: FR-BSW-001~005, FR-BSW-007, TC-BSW-001~005, TC-BSW-008. 완료 조건: 단위시험과 가능한 CAN/센서 시험의 증거가 있고 하드웨어 미검증을 별도 표시했다. 인계: [IVI-HAL-01](IVI.md#ivi-hal-01)에 Mock 입력과 실제 송신 조건 제공.

<a id="ecu-bms-01"></a>
### ECU-BMS-01 — SOC·SOH·Fail-safe·주기 (M3)

상태: 재확인 · 선행: ECU-CAN-01

1. EKF의 관측·예측 모델과 단위·전류 부호를 확인하고, 알려진 입력 및 장기 프로파일에서 쿨롱 카운팅과 비교한다. 기준 데이터와 초기 조건을 보존한다.
2. SOH 누적 방전량의 계산과 실행 루프 연계를 확인한다. 별도 클래스 시험만으로 main의 정상 갱신을 보장하지 않는다.
3. 모든 Fail-safe 전이·복귀·수동 리셋 조건과 사유를 시험한다. 상태 전이의 이벤트 송신과 SecOC 연계는 실제 실행 흐름에서 확인한다.
4. BMS 주기를 타임스탬프로 측정한다. 단위시험 결과와 RPi4 실행의 주기·부하 측정을 구분한다.

산출물: `src/app/` BMS 로직·`main.cpp` 연계의 필요한 보완, 대응 테스트, 비교·주기 결과. 기준: FR-BMS-001~008, TC-BMS-001~007, TC-PERF-002, NFR-PERF-002, NFR-QA-002. 완료 조건: 공식 입력·전이·장기 비교·주기 기준의 증거 확보. 인계: [IVI-APP-01](IVI.md#ivi-app-01)에 정상·경계·전이·복귀 데이터 제공; 통합 결과는 COM-INT-01에 연결.

<a id="ecu-wdg-01"></a>
### ECU-WDG-01 — Watchdog·수신 복구 (M3)

상태: 재확인 · 선행: ECU-CAN-01, ECU-BMS-01

기존 타임아웃 감시에서 요구하는 태스크 감시·재시작·재시도 한계·Fail-safe 연계까지 구현됐는지 대조한다. 의도적 지연·수신 스레드 종료·복구 실패를 주입해 정상 재시작과 최종 실패 처리를 시험한다. 로그 출력만으로 복구 성공으로 처리하지 않는다.

산출물: Watchdog·CAN 수신 수명주기의 보완과 회귀 시험. 기준: FR-BSW-006, NFR-REL-001, NFR-REL-002, TC-BSW-006, TC-BSW-007. 완료 조건: 복구 및 재시도 실패 경로의 실행 증거. 인계: IVI 측에 복구 시 데이터 중단·재개 관찰 조건 제공.

<a id="ecu-sec-01"></a>
### ECU-SEC-01 — SecOC 송신·교차 벡터 (M3)

상태: 재확인 · 선행: ECU-CAN-01, ECU-BMS-01

1. 기존 [C++ SecOC](../adaptive_ecu/src/bsw/secoc_module.cpp)와 [Python SecOC](../security/secoc_module.py)를 ICD의 분리 프레임·HMAC 입력·카운터 예외·constant-time 비교 규칙과 대조한다.
2. 명시적 더미 키로 정상·변조·동일 카운터 Replay·초기값·wrap 등 계약이 요구하는 사례의 교차 벡터를 확정한다. 불명확한 재시작·동기화 정책은 임의로 추가하지 않는다.
3. BMS와 Fail-safe 데이터/인증 프레임의 실제 송신을 확인하고, 키 로드 실패·인증 비활성 시험 조건을 구분한다. 실제 키·장비 비밀은 저장소 밖에서 관리한다.

산출물: 대응 C++/Python 테스트 및 비밀 없는 교차 벡터·키 준비 절차. 기준: FR-SEC-001~004, NFR-SEC-001~002, TC-SEC-001~004. 완료 조건: 양 언어 벡터·거부 조건 일치 및 실제 송신 확인. 인계: [IVI-SEC-01](IVI.md#ivi-sec-01)에 제공하고 인증 통합은 COM-INT-01에서 판정한다.

<a id="ecu-ids-01"></a>
### ECU-IDS-01 — 실제 공격·IDS·경보 경로 (M4)

상태: 재확인; 합성/오프라인 코드 존재, 실제 CAN 경로 미구현 항목 확인 필요 · 선행: ECU-CAN-01, ECU-SEC-01

1. [traffic_gen.py](../security/attacks/traffic_gen.py)의 합성 트래픽과 실제 CAN 송신기를 구분한다. Fuzzy/Replay/Spoofing/Flooding을 선택 실행·중지하고 실제 프레임으로 검증할 CLI를 구현·시험하는 과제를 유지한다.
2. 정상 데이터 수집·라벨·학습/평가 분리·특징·모델 저장/로드·실시간 윈도우 처리를 연결한다. 합성 배경 CAN ID가 프로젝트의 정상 ICD 트래픽과 같지 않음을 명시한다.
3. 기존 규칙·사양·IF 탐지기는 비교 대상으로 보존한다. Isolation Forest는 공식 요구 구현이며, 선택적 의존성 미설치로 평가가 생략됐다고 완료 처리하지 않는다.
4. 공격 탐지에서 ICD 경보 송신까지 연결한다. 공격 유형·이상 점수·의심 ID·시간 필드는 ICD를 따른다. 실제 프레임을 수신해 검증하고 IVI 인수를 요청한다.
5. 연구 HTML의 masquerade 등 추가 분석은 기존 실험 자산으로 보존하되 공식 4종 공격을 대체하지 않는다. 새 보안 정책·인터페이스 도입은 별도 검토한다.

산출물: 실제 공격·실시간 IDS·경보 송신 코드와 대응 시험(예정), 모델/데이터 재현 방법. 기준: FR-SEC-005~007, TC-SEC-005~007, NFR-SEC-003~004, NFR-PERF-003. 완료 조건: 실제 입력에서 탐지·경보까지 시험하고 합성 결과와 구분했다. 인계: IVI-APP-01·IVI-MEAS-01에 경보 입력과 공격 시각 제공.

<a id="ecu-exp-01"></a>
### ECU-EXP-01 — Ablation·탐지 성능·재현 (M5, M7)

상태: 재확인 · 선행: ECU-IDS-01, [COM-INT-01](Common.md#com-int-01), [IVI-MEAS-01](IVI.md#ivi-meas-01)의 측정 준비

1. [ADR-008](../docs/ADR.md#adr-008)과 공식 TC-EXP에 따라 무방어 / SecOC only / SecOC+IDS 구성을 고정한다. 구성 전환은 실제 CLI·프로세스 상태로 확인한다.
2. 공식 4종 공격별 반복·입력·분모·통과 조건은 TEST_PLAN을 따른다. 공격 성공·인증 거부·IDS 탐지·IVI 전달 결과를 구분한다. 정상 데이터 오탐도 별도 측정한다.
3. 학습·평가 분리, seed, 데이터 출처, 모델·임계, 하드웨어·부하, 시계 조건, 실행 버전을 남긴다. 경량 CSV 요약과 재현 명령을 보존하고 원시 로그/모델은 제외 경로로 관리한다.
4. 기존 `run_eval.py`는 오프라인 탐지기 비교다. 물리 CAN을 사용하는 3구성 Ablation과 동일한 실행으로 보고하지 않는다. `measure_can_secoc.py`의 단일 연산·버스 계산도 UI end-to-end 지연을 대체하지 않는다.
5. M7에 동일 조건으로 재현하고 seed·반복 편차와 한계를 기록한다. 미달 수치를 숨기거나 기대 패턴을 실측으로 작성하지 않는다.

산출물: 실험 재현 방법, 구성별 결과·오탐·지연·비교 그래프와 한계. 기준: TC-EXP-001~005, TC-PERF-002~003 및 해당 NFR. 완료 조건: 공식 실험 조건을 수행하고 결과 원본을 검토했다. 인계: [COM-EVAL-01](Common.md#com-eval-01)에 IVI 결과와 함께 전달.

<a id="ecu-qa-01"></a>
### ECU-QA-01 — 품질·문서·교차 검토 (M6~M7)

상태: 재확인 · 선행: ECU 구현·실험 과제, [IVI-CI-01](IVI.md#ivi-ci-01)의 환경 제공

변경 모듈 시험과 전체 회귀를 실행하고 C++ 커버리지·정적 분석을 공식 기준으로 확인한다. 실제 구현 경로·시험 ID를 SDD-ECU/SRS/TEST_PLAN과 연결한다. TARA에는 실제 방어·실험 근거와 미해결 위협을, ADR에는 채택된 판단만 반영한다. IVI 파서·인증·상태 반영을 교차 검토한다.

산출물: 테스트·커버리지·분석 결과, 문서 갱신과 리뷰 근거. 기준: NFR-QA-001~004, ECU 담당 FR·TC 전 범위. 완료 조건: 구현-문서 drift를 해결하거나 명시적 미결정으로 관리했다. 인계: [COM-REVIEW-01](Common.md#com-review-01).

<a id="ecu-final-01"></a>
### ECU-FINAL-01 — 재현·데모 인계 (M8)

상태: 재확인 · 선행: ECU-QA-01, ECU-EXP-01

검증된 정상·Fail-safe·공격/방어 입력과 실행 설정을 준비한다. 새 실행 환경에서 ECU·보안 실험 재현 절차를 점검하고 BMS·SecOC·IDS 설계와 실측 근거를 제출한다. 존재하지 않는 데모 옵션·데이터 파일을 안내하지 않는다.

산출물: ECU 실행·복구 방법, 입력 데이터, 실험 요약·발표 근거. 완료 조건: [COM-FINAL-01](Common.md#com-final-01)의 양측 리허설에서 인수됐다. 공동 발표 대본·릴리즈 절차는 이 문서에 복제하지 않는다.

## 4. 요구사항·시험 연결

아래 표는 상세 요구·합격 수치를 복사하지 않는 과제 색인이다. 공식 시험의 경로가 현재 파일과 다르면 QA에서 차이를 기록한다.

|---|---|---|
| FR-BSW-001, FR-BSW-002, FR-BSW-003, FR-BSW-004, FR-BSW-005 | ECU-CAN-01 | TC-BSW-001~005 |
| FR-BSW-006 | ECU-WDG-01 | TC-BSW-006~007 |
| FR-BSW-007 | ECU-CAN-01 | TC-BSW-008 |
| FR-BMS-001, FR-BMS-002, FR-BMS-003, FR-BMS-004 | ECU-BMS-01 | TC-BMS-001~004 |

## 5. 현재 코드 기준 실행 진입점

프로젝트 루트에서 실행한다. 아래는 코드와 대조한 명령이며 이번 정리에서 실행·통과를 인증한 목록이 아니다. C++는 Linux SocketCAN 헤더와 OpenSSL·Threads·GoogleTest가 준비된 환경이 필요하다. 의존성 설치는 환경에 맞게 수행하고 임의로 우회하지 않는다.

```text
cmake -S adaptive_ecu -B adaptive_ecu/build -DECU_BUILD_TESTS=ON
cmake --build adaptive_ecu/build
ctest --test-dir adaptive_ecu/build --output-on-failure
python -m pytest security/tests -v
python security/experiments/run_eval.py
python security/analysis/measure_can_secoc.py
```

Linux/RPi4에 사용 가능한 `vcan0`가 준비된 경우의 기존 ECU 실행 예시:

```text
./adaptive_ecu/build/adaptive_ecu --interface vcan0 --sensor-mode profile_csv --profile adaptive_ecu/data/battery_profile.csv --secoc off
```

인증 시험은 별도 준비된 시험 키 경로와 실제 `--secoc on --key` 옵션을 사용한다. 키 값은 명령 예제·로그에 쓰지 않는다. 현재 `--secoc-enabled`, `--secoc-disabled`, `--soc` 옵션은 구현되지 않았으므로 사용하지 않는다. 실제 공격 CLI·실시간 IDS·Ablation 실행 명령은 ECU-IDS/EXP 과제에서 구현·검증 후 추가한다.

## 6. 차단 요인과 기록

실제 ADC/CAN 미확보, 복구 구현 부족, IDS 실시간 경로 미구현, 장기 데이터 부족은 해당 과제의 차단 원인으로 기록한다. 목표·계약을 바꿔 해결하지 않는다. 상대 제공물 지연과 일정 변경은 [공동 위험 관리](Common.md#risks)를 따른다.

현재 완료 증거 기록: 없음. 과제별 실행 후 Common의 기록 필드로 근거를 남긴다. 코드·입력 데이터는 보존하며 정리 과정에서 기능을 삭제하지 않는다.
