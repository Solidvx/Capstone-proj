# IVI 프로젝트 진행 계획

갱신: 2026-09-05 · 담당: 팀원B · 주 계획: Android AOSP · 전환 대안: Qt/C++

[공동 일정·통합·릴리즈](Common.md) · [ECU 계획](ECU.md)

## 1. 현재 상태와 바로 할 작업

현재 작업 폴더에는 Android·Qt IVI 소스, HAL·Service·UI·측정 도구, CI·ARM64 빌드 환경이 없다. 0바이트 측정 자리표시자는 제거했다. 아래 `ivi_platform/`와 CI 관련 경로는 **구현 예정 경로**이며 실행 가능한 파일 목록이 아니다.

사용자 결정에 따라 Android AOSP를 주 계획으로 작성한다. 기존 문서의 Android 13/RPi4, HIDL, Java/Kotlin 구성은 설계 기준이며 실제 소스·BSP·빌드 환경의 가용 여부는 IVI-ENV-01에서 확인한다. Qt는 자동 전환 대상이 아니다. 날짜와 과거 완료 표시는 재확인 대상으로 두고 M1~M8 순서는 [Common](Common.md#schedule)에서 따른다.

바로 할 일은 빌드 환경·RPi4 이미지·CAN 접근 조건을 확인하고, ICD를 기준으로 HAL Mock 입력과 파서 시험을 준비하는 것이다. 기존 계획의 코드를 통째로 복사하거나 다른 브랜치의 구현을 자동 도입하지 않는다.

## 2. 원천과 담당 경계

- 계약·기능: [ICD](../docs/ICD.md), [SRS](../docs/SRS.md).
- 설계·시험: [SDD-IVI](../docs/SDD-IVI.md), [TEST_PLAN](../docs/TEST_PLAN.md).
- 플랫폼·환경 결정: [ADR](../docs/ADR.md), [CICD_SPEC](../docs/CICD_SPEC.md).
- 팀원B는 IVI 수신·인증·HAL·Service·UI·측정·CI 구현을 맡는다. 공동 일정·릴리즈·최종 판정은 Common, 보안 실험 구성·입력 원본은 ECU 계획에서 관리한다.

## 3. 단계별 실행 과제

<a id="ivi-env-01"></a>
### IVI-ENV-01 — AOSP 환경과 전환 판단 (M1~M2)

상태: 재확인; 현재 코드 없음 · 선행: [COM-BASE-01](Common.md#com-base-01)에서 환경 확인 시작

1. 기존 설계에 맞는 AOSP 소스·RPi4 BSP·커널·빌드 서버·저장 공간·접근 조건을 확인하고 실제 버전·manifest·빌드 타깃을 기록한다. 확인하지 않은 다운로드 URL이나 lunch 타깃을 실행 명령으로 남기지 않는다.
2. 재현 가능한 이미지 빌드·부팅·shell/ADB 접근·화면·CAN 접근을 확인한다. MCP2515 커널·Device Tree·권한·SELinux 설정은 실제 환경에서 검증한다.
3. 부팅·CAN·UI 개발의 차단 원인, 해결 시도, 남은 작업과 일정 영향을 기록한다. 전환 판단 시점은 과거 7월 말 날짜를 승계하지 않고 Common의 M2 게이트에서 재확인한다.
4. AOSP 진행이 막히면 Qt/C++ 대안의 환경·HAL 대체 API·시험·일정 영향을 제시하고 사용자 인터뷰를 거친다. 전환 전까지 Android 계획을 유지한다. 기존 ADR-010은 전환 대안의 근거이지 이번 정리에서 Qt 구현을 채택했다는 뜻이 아니다.

산출물: 빌드·부팅·CAN 증거와 플랫폼 판단 기록. 기준: SDD-IVI, ADR-004/010, ICD HAL 계약. 완료 조건: AOSP 독립 개발 환경이 확인되거나 전환 필요가 명시적 결정 대상으로 관리된다. HAL API 변경이 필요하면 AGENTS의 변경 게이트를 거쳐 ICD·SRS·SDD·시험을 함께 갱신한다.

<a id="ivi-hal-01"></a>
### IVI-HAL-01 — HAL Mock·CAN 수신·파서 (M2~M3)

상태: 미착수(현재 코드 없음) · 선행: 계약 확인; 실제 장비 실행은 IVI-ENV-01, [ECU-CAN-01](ECU.md#ecu-can-01) 인계

1. ICD의 HIDL 데이터·콜백 계약을 읽고 Mock 입력을 준비한다. ECU 실장비가 없어도 정상·경계·이벤트 입력으로 파서 시험을 먼저 작성한다.
2. CAN reader·수신 스레드·콜백·종료/복구를 HAL 경계 안에 구현한다. 5개 CAN ID의 DLC·부호·스케일·엔디언·예약 필드를 원천대로 검사한다.
3. 파서가 내놓는 값과 인증 후 전달되는 값을 구분한다. 인증 검증·상태 반영 순서는 IVI-SEC-01과 함께 검토한다.
4. 실제 CAN 수신에서 Callback까지 확인하고, Mock 성공과 물리 수신 성공을 구분해 기록한다.

산출물: `ivi_platform/hal/`와 파서/Mock 테스트(예정). 기준: FR-IVI-001, FR-IVI-002, TC-IVI-001, TC-IVI-002 및 ICD. 완료 조건: 알려진 입력·경계·잘못된 프레임의 처리를 시험하고 실제 수신 경로를 확인했다. 인계: ECU에 파싱 결과와 계약 불일치를 전달하고 [COM-HAND-01](Common.md#com-hand-01)에서 확인한다.

<a id="ivi-sec-01"></a>
### IVI-SEC-01 — 수신 SecOC 인증 (M3)

상태: 미착수 · 선행: IVI-HAL-01, [ECU-SEC-01](ECU.md#ecu-sec-01)의 교차 벡터

1. 데이터 프레임과 분리 인증 프레임, 카운터와 MAC을 ICD 기준으로 처리한다. 인증되지 않은 입력이 정상 상태로 반영되지 않는지 확인한다.
2. 더미 키 교차 벡터로 정상·변조·키 불일치·Replay·초기값·wrap 등의 계약 사례를 시험한다. constant-time 비교와 인증 오류 전달을 검토한다.
3. 누락·순서 변경·재시작 등 원천에서 불명확한 처리 정책은 새 timeout/윈도우 값으로 임의 보완하지 않고 공동 미결정으로 올린다.
4. 실제 키는 장비에서 별도로 관리하고 시험 로그에는 입력 식별자·판정만 남긴다. 정상과 거부 결과를 ECU 측 벡터와 교차 확인한다.

산출물: HAL 인증기와 대응 테스트(예정). 기준: FR-SEC-001~004 중 수신·교차 검증 책임, NFR-SEC-001~002, TC-SEC-001~004, TC-INT-002. 완료 조건: 정상 데이터 수용과 비정상 데이터 거부·미반영을 증명했다. 인계: [COM-INT-01](Common.md#com-int-01)의 정상/변조 조건으로 연결한다.

<a id="ivi-app-01"></a>
### IVI-APP-01 — Service·상태 전달·대시보드 (M3~M4)

상태: 미착수 · 선행: IVI-HAL-01, IVI-SEC-01; UI Mock 개발은 병행 가능

1. AOSP의 VehicleDataService·Manager 등록과 `getSystemService("vehicle_data")` 접근, HAL 콜백 → Binder IPC → ViewModel StateFlow 전달을 구현한다. 앱 전용 서비스로 대체해 공식 요구를 완료 처리하지 않는다.
2. SOC·SOH·전압·전류·온도 표시와 SOC 경계 색상을 구현한다. Fail-safe 이벤트와 IDS 공격 유형을 각각 경고 팝업·배너에 반영한다. 계약 상태와 UI 표현을 대조한다.
3. 실제 정상·전이·복귀 입력과 합성 UI 테스트를 분리하고 인증 실패 시 잘못된 데이터로 UI가 갱신되지 않는지 확인한다.
4. 상태 전달·화면 갱신의 측정 지점을 마련하고 IVI-MEAS-01과 연결한다. 전체 화면 레이아웃 개선보다 공식 필수 표시·안전 경고·데이터 경로를 먼저 검증한다.

산출물: `ivi_platform/service/`, `ivi_platform/app/`와 Service·Compose UI 테스트(예정). 기준: FR-IVI-003~008, TC-IVI-003~008. 완료 조건: 공식 경계 입력·콜백·서비스 접근·상태 갱신·경고 표시를 검증했다. 인계: ECU-BMS/IDS 제공물에 대한 화면·상태 결과를 COM-HAND-01에 전달한다.

<a id="ivi-meas-01"></a>
### IVI-MEAS-01 — 지연 측정 도구·실험 지원 (M4~M5, M7)

상태: 미착수 · 선행: IVI-APP-01, ECU 송신·경보 인계; 물리 측정은 COM-INT-01 준비

1. 실제 timestamp collector와 분석 도구를 구현한다. `ivi_platform/scripts/measure_latency.py`는 향후 가능한 경로이며 현재 명령으로 제공하지 않는다.
2. CAN 수신, 인증, Service, StateFlow, UI 반영 시점을 구분한다. 서로 다른 노드의 시계를 뺄 경우 동기화 방법·오차를 기록한다. 시작/종료 지점이 다른 측정을 같은 이름의 수치로 합치지 않는다.
3. TC-IVI-008의 내부 상태 전달 측정과 TC-PERF-001의 전체 경로 측정을 따로 수행한다. TC-PERF-002의 주기는 ECU와 대조하고 TC-PERF-003의 경보 수신 지연을 공격 시작과 연결한다.
4. 샘플 수·평균·최대·분포·누락 여부를 원천 시험 기준으로 보고한다. 추가 P95/P99·자원 측정을 하더라도 공식 지표를 대체하지 않는다.
5. [ECU-EXP-01](ECU.md#ecu-exp-01)의 방어 구성별 실험에 수신·UI 결과를 제공한다. 동일 run 식별자와 데이터 조건을 사용하고 원시 로그 대신 경량 요약·재현 절차를 인계한다.

산출물: 측정 도구·단위 검증·실제 측정 요약(예정). 기준: FR-IVI-008, NFR-PERF-001~003, TC-IVI-008, TC-PERF-001~003. 완료 조건: 도구의 시간 계산·샘플 매칭을 검증하고 공식 측정 지점과 실측 근거를 명시했다. 문서 간 지점 불일치는 [COM-EVAL-01](Common.md#com-eval-01)에서 확인하며 기준을 임의로 바꾸지 않는다.

<a id="ivi-ci-01"></a>
### IVI-CI-01 — CI·ARM64 빌드·배포 구현 (M1 준비, M2~M6 구축)

상태: 미착수(현재 관련 파일 없음) · 선행: COM-BASE-01의 저장소·환경 결정, ECU 빌드 입력

1. CICD_SPEC·ADR-006/007과 실제 CMake 타깃을 대조해 환경을 확정한다. GitHub Actions 트리거, 정적 분석, Docker ARM64 빌드, GoogleTest/커버리지, 배포/Health Check를 순서대로 구축한다.
2. ECU의 OpenSSL·Threads·GoogleTest ARM64 의존성과 QEMU 실행 조건을 확인한다. 센서/I2C·물리 CAN 시험은 가상 환경에서 완료했다고 표시하지 않는다.
3. 성공 경로뿐 아니라 분석 오류·시험 실패·커버리지 미달·배포 실패 시 중단·실패 보고를 검증한다.
4. 서비스 실행·종료·로그·재시작·이전 동작 버전 복구 방법을 준비한다. 장비 경로·계정·자격 증명은 실제 환경에서 정하고 저장소에 비밀을 넣지 않는다.
5. 구현된 CI의 설정·사용 명령과 증거를 ECU 측에 제공한다. 공통 PR·태그·릴리즈 순서는 Common 한 곳에서 유지한다.

산출물: `.github/workflows/`, Docker/toolchain, 배포·Health Check 설정 및 검증(모두 예정). 기준: FR-CI-001~006, TC-CI-001~006, NFR-QA-001~003. 완료 조건: 실제 트리거·실패 게이트·ARM64 결과·배포 상태 확인이 입증됐다. 인계: [ECU-QA-01](ECU.md#ecu-qa-01), [COM-REL-01](Common.md#com-rel-01).

<a id="ivi-qa-01"></a>
### IVI-QA-01 — 안정성·설계·교차 검토 (M6~M7)

상태: 미착수 · 선행: IVI 기능·측정·CI 과제

1. 실제 플랫폼에서 수신·서비스·화면·인증 회귀를 실행한다. 기존 계획의 24시간 안정성 시험을 수행 과제로 유지하고 메모리·CPU·크래시·통신 중단/복구를 기록한다. 날짜만 경과했다고 통과 처리하지 않는다.
2. 장시간 시험이 막히면 부분 실행의 시간·조건·한계를 기록한다. 이전 문서의 단축 시험 예시를 동등 합격으로 적용하지 않는다.
3. SDD-IVI에 실제 계층·데이터 경로·오류 처리를, CICD_SPEC에 실제 구축 결과를 반영한다. 아직 없는 파일·기능은 예정으로 표시한다.
4. ECU 인코딩·SecOC·상태 전이를 교차 검토하고 FR/TC/증거의 누락을 공동 리뷰에 전달한다.

산출물: 회귀·안정성 기록, 설계·CI 문서 갱신, 리뷰 결과. 기준: IVI/CI 담당 FR·TC, 관련 NFR, 기존 장시간 시험 계획. 완료 조건: 시험 근거와 미달·미검증 범위를 남기고 [COM-REVIEW-01](Common.md#com-review-01)에서 검토했다.

<a id="ivi-final-01"></a>
### IVI-FINAL-01 — 데모·제출 인계 (M8)

상태: 미착수 · 선행: IVI-QA-01, IVI-MEAS-01

실제 장비에서 앱·수신 서비스 시작, 정상/전이/보안 시연, 종료·복구를 재현한다. 검증된 화면·지연·안정성 요약과 IVI 설계 설명을 준비한다. 공통 제출 목록과 릴리즈는 [COM-FINAL-01](Common.md#com-final-01)과 COM-REL-01에서 관리한다.

산출물: IVI 실행·재현 안내, 측정 요약, 데모 화면·발표 근거. 완료 조건: 양측 리허설에서 정상·경고·거부·복귀 흐름이 검증됐다.

## 5. 실행 명령과 진행 기록

현재 IVI 빌드·실행·측정 명령은 없다. IVI-ENV-01에서 실제 manifest·빌드 타깃을 확인하고 각 도구를 구현·검증한 뒤 이 절에 재현 명령을 추가한다. 과거 AOSP·Qt 설치 명령, 완성형 CI YAML, 없는 측정 스크립트의 옵션은 복제하지 않는다.

현재 완료 증거 기록: 없음. 상태·증거 필드는 [Common](Common.md#rules)을 사용한다. 부팅·CAN·서비스 권한·인증 정책·측정 시계가 불명확하면 관련 작업을 차단/미결정으로 남기고 인터뷰한다. 코드나 계약을 추측으로 생성하지 않는다.
