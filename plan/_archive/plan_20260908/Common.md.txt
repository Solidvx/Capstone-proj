# 공동 프로젝트 진행 계획

갱신: 2026-09-05 · 담당: 팀원A + 팀원B · 사용자 결정: 공동 내용은 Common.md에서 단일 관리

[ECU 담당 계획](ECU.md) · [IVI 담당 계획](IVI.md)

<a id="rules"></a>
## 1. 계획 사용 방법과 현재 기준

- 역할별 구현·검증·산출물 상태는 ECU.md 또는 IVI.md 한 곳에만 기록한다. 공동 일정·통합 결과·릴리즈 상태는 이 문서에만 기록한다. 상대 문서에는 과제 링크와 자신의 행동만 둔다.
- M1~M8은 수행 순서다. 기존 달력 날짜와 체크 표시를 승계하지 않는다. 목표일은 모두 재확인 대상이며 양측이 실제 진척과 가용 시간을 확인한 뒤 이 문서에서만 확정한다.
- 상태는 **재확인 / 미착수 / 진행 / 검증대기 / 완료 / 차단**을 사용한다. 재확인은 과거 실행 여부를 확정할 증거가 없다는 뜻이다. 완료에는 실행 환경·명령 또는 절차·날짜·결과 파일·검토자 근거가 필요하다.
- 현재 폴더에는 `.git`이 없다. GitHub 저장소·브랜치·릴리즈·장비 설치 상태도 재확인한다. 소스가 없는 기능은 미구현 과제로 유지한다.
- Android AOSP가 IVI 주 계획이며 Qt는 전환 대안이다. 실제 IVI 코드는 없다. 계약이나 플랫폼 전환의 승인이 필요한 변경은 임의로 수행하지 않는다.

규칙은 [AGENTS](../AGENTS.md), 계약은 [ICD](../docs/ICD.md), 요구사항은 [SRS](../docs/SRS.md), 시험은 [TEST_PLAN](../docs/TEST_PLAN.md), 설계 결정은 [ADR](../docs/ADR.md)를 따른다. 계획의 과제 ID는 공식 FR·TC·ADR ID를 대체하지 않는다. 기준값과 바이트 레이아웃을 별도 복사하지 않는다.

## 2. 단계·일정·공동 게이트

각 행은 해당 과제의 링크만 제공한다. 상세 완료 상태는 링크된 과제에서 관리한다. 공통 목표일은 모두 **재확인 후 확정**, 게이트 상태는 모두 **재확인**으로 시작한다.

| M3 핵심 기능 | [BMS](ECU.md#ecu-bms-01), [SecOC](ECU.md#ecu-sec-01) | [파서·인증](IVI.md#ivi-sec-01), [Service·UI](IVI.md#ivi-app-01) | COM-HAND-01: 정상·변조 벡터와 상태 이벤트 양측 대조 |

| M8 제출 | [ECU 인수](ECU.md#ecu-final-01) | [IVI 인수](IVI.md#ivi-final-01) | [COM-FINAL-01](#com-final-01), [COM-REL-01](#com-rel-01): 데모·제출·릴리즈 |

일정 변경은 영향받는 단계·선행 과제·원인·새 목표일·양측 확인을 이 절 아래에 기록한다. 현재 확정된 변경 일정은 없다. 날짜가 지나도 미검증 과제를 완료로 바꾸지 않는다.

<a id="com-base-01"></a>
## 3. COM-BASE-01 — 환경·계약·진척 기준 확보

상태: 재확인 · 주관: 공동 · 선행: 없음 · 단계: M1

1. 각자 실제 장비·OS·도구 버전·네트워크 접근·소스 위치를 확인한다. Node A·B의 CAN 접근과 RPi4 빌드/실행 가능 여부를 증거로 남긴다.
2. ECU/IVI 과제별 실제 파일과 시험 기록을 점검하고, 소스 존재·시험 통과·물리 통합 완료를 별도로 구분한다.
3. ICD와 구현의 차이, SRS·SDD·TEST_PLAN의 예정 경로·기준 불일치를 기록한다. 불일치를 계획 축약으로 숨기거나 계약을 조용히 바꾸지 않는다.
4. 새 Git 저장소와 원격 위치·공유 작업 방식은 실제 설정할 때 확정한다. 이 계획 작성이 저장소 생성·푸시를 수행한 뜻은 아니다.
5. 양측 담당 과제, 우선 실행 순서, 목표일을 합의한다. 장비 미확보·플랫폼 전환 등 결정이 필요한 경우 인터뷰 후 진행한다.

산출물: 환경·진척 근거, 미결정 목록, 확정한 일정. 완료 조건: 양측의 독립 검증을 시작할 환경과 계약 원천을 확인하고 차단 항목을 식별했다.

<a id="com-int-01"></a>
## 5. COM-INT-01 — 물리 통합 시험

상태: 재확인 · 주관: 공동, 팀원B 결과 취합 · 선행: COM-HAND-01 및 양측 대응 과제 · 단계: M4, M7 재검증

1. MCP2515 연결·종단·CAN 인터페이스·비트레이트와 양측 실행 설정을 확인한다. 실험용 키는 별도 전달하며 키 자체를 결과에 포함하지 않는다.
2. [공식 통합 시험](../docs/TEST_PLAN.md)의 TC별 준비·입력·기대 결과를 확인하고 실행한다. 계획의 옛 실행 예제를 그대로 사용하지 말고 실제 CLI를 확인한다.
3. 같은 실행의 ECU 이벤트·CAN 수신·IVI 상태/화면을 연결한다. 각 결과에 환경·날짜·run 식별자·Pass/Fail·증거 위치를 기록한다.

| 공식 TC | 보존할 수행 조건 | ECU 행동 | IVI 행동 |
|---|---|---|---|
| TC-INT-001 | BMS 데이터 정상 전달 | 정상 입력·상태 송신 | 파싱·Service·화면 일치 확인 |
| TC-INT-002 | 정상 인증, 키 불일치/변조 거부, Replay 관련 단위시험 연결 | 정상·비정상 시험 입력 제공 | 인증 결과와 비정상 입력의 상태 미반영 확인 |
| TC-INT-003 | Fail-safe 전이 및 화면 반영 | 전이 재현·이벤트 송신 | 경고 화면과 상태 일치 확인 |
| TC-INT-004 | 공격 → IDS → 경보 → UI | 공격 재현·탐지·경보 생성 | 경보 수신·표시와 지연 증거 제공 |

과거 IT-001은 TC-INT-001, IT-002는 TC-INT-003, IT-003·IT-004는 TC-INT-002의 정상·변조 조건, IT-005는 TC-INT-004로 대응한다. 시나리오를 합쳐 정상/변조 중 한 조건을 잃지 않는다.

산출물: TC별 통합 결과와 동작 영상·스크린샷·필요한 로그 요약. 완료 조건: 공식 TC의 필요한 조건 모두 수행, 미달 원인과 재시험 처리. 장비 부재 시 차단/부분 검증으로 남긴다.

<a id="com-eval-01"></a>
## 6. COM-EVAL-01 — 실험·성능 증거 결합

상태: 재확인 · 주관: 공동 · 선행: COM-INT-01, ECU-EXP-01, IVI-MEAS-01 · 단계: M5, M7

방어 구성·공격·학습 및 평가 조건의 원본은 [ECU-EXP-01](ECU.md#ecu-exp-01), 측정 도구·시계 조건의 원본은 [IVI-MEAS-01](IVI.md#ivi-meas-01)이다. 여기에는 양측 결과의 인수 여부만 기록한다.

- 같은 run의 공격 시작·ECU 상태·CAN 경보·IVI 반영 증거를 묶고 구성·환경·분모가 일치하는지 확인한다.
- TC-EXP-001~005, TC-PERF-001~003 및 관련 NFR을 원천 기준으로 판정한다. 합성 오프라인 결과와 물리 CAN 결과는 별도 표로 구분한다.
- 문서 간 측정 시작/종료 지점이 다르면 결과를 동일 지표로 합치지 않는다. 특히 TC-PERF-001의 제목·측정 설명과 SRS의 UI 반영 기준을 대조해 지점을 명시한다. 기준 변경은 합의가 필요한 후속 작업이다.
- 고정된 성공률을 미리 채우지 않는다. 미달 결과도 환경·원인·후속 조치와 함께 남긴다.

산출물: 채택한 결과 파일·재현 방법의 인수 기록. 완료 조건: 팀원A/B 결과가 같은 실험 조건으로 연결되고 공식 기준과 실측을 구분했다.

<a id="com-review-01"></a>
## 7. COM-REVIEW-01 — 문서·품질 교차 검토

상태: 재확인 · 주관: 공동 · 선행: 양측 QA 과제 · 단계: M6~M7

팀원A는 IVI 파서·인증·표시를, 팀원B는 ECU 프레임·보안·상태 전이를 교차 검토한다. SRS의 필수 FR과 NFR마다 구현·시험·증거를 연결하고 미구현 항목을 남긴다. SDD는 실제 모듈 경계를, TARA는 실험 결과와 한계를, ADR은 실제 채택·전환 결정을 반영한다. 보안 HTML의 연구 제안은 검토 자료이며 자동으로 필수 계약이 되지 않는다.

산출물: 요구사항별 확인 결과, 문서·구현 drift와 처리 내역. 완료 조건: 공식 기준 누락·시험 결과 없는 완료 표시·미지원 명령을 식별하고 조치했다. 커버리지·정적 분석·리뷰 목표는 SRS와 TEST_PLAN을 따른다.

<a id="com-rel-01"></a>
## 8. COM-REL-01 — 공통 작업·마일스톤·릴리즈

상태: 재확인 · 주관: 공동, 팀원B 실행 환경 지원 · 선행: 저장소 설정 및 해당 단계 게이트 · 단계: 단계별 반복

1. 실제 저장소가 준비되면 작업 과제를 Issue와 연결하고 역할별 변경을 PR로 제시한다. 커밋에는 변경 목적을 쓰고 상대가 리뷰한다. 계약 변경은 AGENTS의 변경 게이트를 따른다.
2. PR에는 변경 행동·연결 과제/FR/TC·검증 결과·미검증 범위를 적는다. 복제 템플릿이나 버튼별 사용법은 유지하지 않는다.
3. 단계 완료 시 양측 결과와 미해결 이슈를 검토한다. 필수 기준 미달을 다음 단계로 옮기는 것만으로 완료 처리하지 않는다.
4. 승인된 변경을 통합하고 실제 CI 결과를 확인한 뒤 마일스톤·태그·릴리즈를 연결한다. 기존 v0.N.0/v1.0.0은 과거 계획이며 실제 사용 여부를 저장소 설정 시 확인한다.
5. 릴리즈에 변경 요약·시험 증거·알려진 한계·재현 방법을 연결한다. 실제 비밀·원시 대용량 로그는 첨부하지 않는다.

산출물: PR/리뷰·단계 판정·릴리즈 기록. 완료 조건: 실제 변경과 증거가 연결되고 실패한 필수 검증이 은폐되지 않았다. 이 문서는 Git 생성·푸시·배포 실행을 수행했다는 기록이 아니다.

<a id="com-final-01"></a>
## 9. COM-FINAL-01 — 데모·최종 제출

상태: 재확인 · 주관: 공동 · 선행: COM-REVIEW-01, 양측 FINAL 과제 · 단계: M8

정상 BMS 표시 → Fail-safe 경고 → 보안 방어 구성별 공격·거부/탐지 → 정상 복귀 순서의 데모를 준비한다. 시험을 통과한 입력·CLI만 사용하고, 구성별 실패/차단 현상을 실제 로그와 화면으로 설명한다. 장비 장애에 대비한 검증된 영상은 보조 자료로 표시한다.

| 최종 산출물 | 팀원A | 팀원B | 공동 확인 |
|---|---|---|---|
| 실행·재현 안내 | ECU·보안 실행 조건 | IVI·측정·배포 조건 | 새 환경에서 재현 가능 여부 |
| 공식 문서 | ECU 설계·보안 실험·TARA | IVI 설계·CI·측정 | ICD/SRS/시험 추적·ADR |

리허설에서 준비·시작·전환·복귀 절차를 검증하고 결함을 해결한 뒤 COM-REL-01로 최종 제출 상태를 확정한다. 발표 수사·예상 Q&A 장문은 계획에서 제외하며, 필요한 주장에는 증거를 연결한다.

## 10. 공동 차단 요인과 기록

| 조건 | 담당·조치 | 남겨야 할 한계 |
|---|---|---|
| 계약 불명확·문서 drift | 공동: 영향 식별 후 인터뷰·계약 변경 게이트 | 임의 레이아웃·기준 변경 금지 |
| 상대 구현 지연 | 제공자: 예상 인계 재확인; 인수자: Mock 독립 검증 | 실제 통합 완료로 기록하지 않음 |
| AOSP 부팅/CAN/UI 확보 실패 | 팀원B: IVI-ENV-01의 전환 판단 자료 제출 | Qt 자동 전환·코드 병합 금지 |
| 물리 CAN·장비 부재 | 공동: vcan/단위 검증으로 진행 가능한 범위 수행 | 물리 TC·성능 판정은 차단 |
| IDS·성능·커버리지 기준 미달 | 담당자: 조건·원인·수정·재시험 기록 | 목표 완화·임의 수치 대입 금지 |
| CI 미구현·배포 실패 | 팀원B: 환경·권한·빌드 조건 확인 | 로컬 시험을 CI 통과로 표기하지 않음 |

현재 결과 기록: 없음. 실행 후 `과제 ID / 날짜 / 환경·버전 / 절차·명령 / Pass·Fail·차단 / 증거 / 검토자 / 후속 조치`를 각 주관 과제에 기록한다. 큰 원시 산출물은 제외 경로에 두고 보존할 요약은 공식 문서와 연결한다.
