# 커밋 규칙

Cursor 터미널의 Claude Code·Codex CLI 공용 규칙이다. 공통 정책은 [AGENTS.md](../../../AGENTS.md), 상위 커밋 형식·브랜치·PR 기준은 [공동 협업 규약](../../../plan/detail/common/00_협업_규약.md)을 따른다.

## 메시지 형식

- **한글 1줄**: `type(scope): 간결한 설명`
- CAN·SecOC·IDS 같은 기술명과 코드 식별자는 그대로 사용한다.
- 상세 근거는 PR·작업 기록에 남긴다. 요청하지 않은 `Co-Authored-By`는 추가하지 않는다.

```powershell
# Good — 메시지 예시이며 실제 변경에 맞춰 사용
git commit -m "refactor(bsw): CAN 인코딩 보조 함수 분리"
git commit -m "feat(ui): 배터리 상태 표시 추가"
git commit -m "fix(secoc): 인증 실패 처리 수정"

# Bad
git commit -m "fix stuff"                 # 목적과 영역 불명확
git commit -m "feat(ui): 화면 추가와 CAN 코드 정리" # 독립적인 목적 혼합
```

## 커밋 타입

| 타입 | 용도 |
|---|---|
| `refactor` | 동작 보존 정리·코드 이동 (기존 Tidy First 개념) |
| `feat` | 새 기능 |
| `fix` | 오류 수정 |
| `test` | 시험만 추가·수정 |
| `docs` | 문서 내용·위치·참조 수정 |
| `chore` | 빌드·환경·설정 변경 |

scope는 변경 중심에 맞춰 하나를 고른다. ECU: `bsw`, `bms` / 보안: `secoc`, `ids` / IVI: `hal`, `service`, `ui` / 공통: `icd`, `ci`, `docs`.
공동 규약에 맞춰 기존 `tidy` 대신 `refactor`를 사용한다. 포맷·최적화도 실제 목적에 맞는 위 타입으로 분류한다.

## 커밋 분리 전략 (Tidy First)

1. **먼저 정리:** 요청 범위에서 필요한 독립적 정리만 `refactor`로 분리한다.
2. **기능 구현·수정:** `feat/fix`에 해당 동작의 시험·필수 문서를 함께 담는다.
3. **후속 정리·최적화:** 필요할 때만 별도 목적의 커밋으로 만든다. 성능 향상은 측정 근거로 설명한다.

| 상황 | 판단 |
|---|---|
| 기능과 대응 시험·문서 | 같은 목적이면 함께 커밋 |
| 무관한 정리와 기능 | 분리 |
| 이동과 동작 변경 | 가능하면 분리하되 import·CMake·링크는 이동과 함께 수정 |
| 100줄 이상 변경 | 분리 가능성을 검토하되 줄 수만으로 금지하지 않음 |

분리된 각 커밋의 빌드·참조 관계를 유지한다. 커밋을 나누려고 무관한 정리나 깨진 중간 상태를 만들지 않는다.

## 파일 이동·이름변경

**옛 경로의 삭제와 새 경로의 추가를 같은 커밋에 담는다.** 아래 경로는 실제 이동 파일로 바꿔 사용한다.

```powershell
# Good — 파일 단위로 이동 양쪽을 명시
git add -A -- "옛경로/파일" "새경로/파일"
git diff --cached --name-status -M
git diff --cached

# Bad — 새 파일만 추가하면 옛 경로 삭제가 빠질 수 있음
git add -- "새경로/파일"
```

이름변경은 Git이 내용 유사도로 판단한다. `R100`은 동일 내용의 이동 표시이며 필수 조건은 아니다.
`A`·`D`로 나오면 양쪽 포함 여부와 내용 차이를 확인한다. 이력이 영구 소실됐다고 단정하거나 같은 add를 반복하지 않는다.
디렉토리째 stage하면 무관한 변경도 들어갈 수 있으므로 실제 파일을 명시하는 방식을 우선한다.

## ECU·IVI별 포함·제외 기준

**아래 영역 전체가 아니라 이번 목적에 해당하는 실제 파일만 선택한다.** 상대 담당 폴더를 저장소에서 삭제하거나 ignore하지 않는다.

| 담당·영역 | 포함할 변경 | 제외할 파일 |
|---|---|---|
| ECU | `adaptive_ecu/` 소스·헤더·CMake 설정·`test/` 시험 | `build/`, 바이너리·캐시 |
| IVI | `ivi_platform/`의 프로젝트 소유 HAL·Service·UI 소스·설정·시험 | AOSP 전체 소스, `out/`, APK·자동 생성물·개인 설정 |
| 보안·IDS (양측 공통) | `security/` 소스·시험·의존성·재현 절차·경량 결과 요약 | 학습 모델·대용량 원시 데이터·로그 |
| 문서 (양측 공통) | 관련 `docs/`, `plan/ECU.md`·`plan/IVI.md`와 상세 계획 | `tmp/` 임시 분석·백업 |

IVI 코드가 없으면 현재 존재하는 계획·문서만 대상으로 삼는다. 제외 세부는 [.gitignore](../../../.gitignore)를 따른다. 이미 추적된 파일도 확인하며, 비밀키·토큰은 포함하지 않는다.

## 허용·금지 기준

| 상황 | 허용 | 금지 |
|---|---|---|
| 검토·메시지 추천 요청 | 분석과 제안 | 임의 stage·commit |
| 로컬 커밋 요청 | 지정 범위의 검증·stage·commit | 무관한 변경 포함, 요청 없는 push·병합·태그 |
| 다른 작업이 섞인 파일·stage | 변경 조각과 소유 범위 구분 | 사용자 변경을 임의로 stage·unstage·폐기 |
| Cursor·Claude·Codex 병용 | 같은 작업 트리에서 한 주체만 수정·stage·commit | 같은 index를 여러 주체가 동시에 변경 |
| CAN·SecOC·HAL 계약 변경 | AGENTS의 인터페이스 변경 게이트 적용 | 한쪽 구현·계약만 임의 변경 |
| 검증 실패·미실행 | 원인과 미검증 범위 보고 | 통과·기능 완료로 표시, hook 임의 우회 |

## 커밋 전 자가 점검

- [ ] 한 가지 목적이며 메시지가 실제 변경을 설명하는가?
- [ ] 필요한 소스·시험·문서와 이동 전후 경로가 함께 포함됐는가?
- [ ] 대응 검증을 실행하고 실패·미실행 이유를 구분했는가?
- [ ] staged diff에 요청 밖 변경·비밀·산출물이 없는가?
- [ ] 기존 사용자 작업과 필요한 참조 관계를 보존했는가?

AI 실행은 [SKILL.md](SKILL.md), 사람이 따라 하는 상세 명령·ECU·IVI별 예시는 [commit.md](../../../docs/development/governance/commit.md)를 따른다. 두 문서는 위 커밋 기준을 적용한다.
