# CAN 인증 진단 계약 — diagnostic-v1

2026-11-11 사용자 승인으로 [session-v2](ICD-CAN-SESSION.md)에 포함된 상세 CAN 진단 계약이다. [ICD](ICD.md)와 함께 적용한다. 승인된 형식과 실제 제품 구현/물리 인수 완료는 구분하며 현재 구현 상태는 CHG-029를 따른다.

## 전달 경로와 영향

| ID | 방향 | 역할 | DLC |
|---|---|---|---:|
|0x302|ECU→IVI|ECU 상태·재시작 예고·IDS 사건/관찰·측정|8|
|0x303|IVI→ECU|재시작 확인·실제 수신 거부 근거·측정|8|

초기 설계에서는 이 두 ID의 기존 용도를 발견하지 않았으며, 현재는 승인된 session-v2 제품 코드가 이 문서대로 사용한다. 실제 버스 ID 충돌 검사는 장비 인수 때 별도로 해야 한다. 기존0x100~103/200의 바이트를 재사용하지 않는다. 별도 LAN/TCP/TLS 제품 경로는 없다. PC SSH는 실험 제어/로그 수집용으로 유지한다.

세션 제어0x300/301·현재 상태0x104/105와 함께 ECU/IVI 필터·수신/송신·SecOC/IDS 허용 목록·실험 분석·ICD/SRS/양측 SDD/TEST_PLAN/ADR/TARA에 영향을 준다. 정상 진단 트래픽이 늘어나므로 기존 정상 IF 학습/보정 자료와 실험 결과를 새 계약의 결과로 재사용하지 않는다. 제어/진단 ID도 과다 전송 관찰에서 무조건 제외하지 않는다.

ECU 내부의 Python IDS→C++ CAN 발행자는 소유 PID/UID・신선도・유한 예산을 검사하는 로컬 IPC로 연결한다. 반대 방향의 인증된 IVI 거부 진단은 감독자 소유의 별도 비차단 상속 pipe로 IDS에 전달한다. 로컬 버전/순번/신선도와 소비 검증의 현재 근거는 CHG-029를 따르며 CAN 본문/키/ID를 확장한 것이 아니다. 이는 노드 사이의 제품 전달을 LAN으로 바꾸는 것이 아니다. 공격 Pi3에 장기 키·세션 키·관리 SSH 역할을 주지 않는다. 로컬 송신자의 권한/큐/실패 격리는 별도 제품 구현/검증 대상이다.

## 인증·분할 형식

세션 제어 버전2를 사용하며 역할 키 라벨 `diag-ecu`, `diag-ivi`를 추가한다. 기존6개 역할의 입력/출력은 바뀌지 않는다. 키는 같은 HKDF의 info=`ASCII(role)||T_v2`, 길이32B다. 반대 방향 키로 반사한 메시지를 받아들이지 않는다.

논리 envelope:

| 오프셋 | 길이 | 필드 |
|---:|---:|---|
|0|16|session_id=`SHA256(T_v2)[0:16]`; 공개 교환 식별이며 키 해시가 아님|
|16|4|방향별 message_sequence, BE uint32|
|20|1|아래 메시지 종류1~9|
|21|1|정확한 종류별 본문 길이|
|22|가변|본문|
|22+본문길이|16|인증 태그|

`tag=HMAC-SHA256(K_diag_direction, ASCII("CAPSTONE-CAN-DIAG") || 0x01 || CAN_ID(BE2) || envelope_without_tag)[0:16]`.

CAN 프레임 byte0=`0xD1`, byte1=fragment index0부터, byte2~3=`message_sequence & 0xFFFF` BE, byte4~7=envelope의4B 조각이다. 마지막 조각의 남는 공간은 반드시0이다. 최대 본문104B, envelope142B, 패딩144B/36프레임으로 제한한다. 조각5에서 종류/길이를 읽고 필요한 조각 수를 확정한다. 미완성/잘못된 방향·버전·DLC·index·중복 상충은 인증된 상태를 갱신하지 않는다.

송신 sequence는 세션/방향별로 독립이며 일반 BMS 전역 counter에 섞지 않는다. 소진 시 같은 키로0을 재사용하지 않고 새 인증 세션이 필요하다. 재전송은 이미 만든 동일 envelope/sequence를 재사용한다.

수신은 인증된 sequence의64칸 창을 유지한다. 창 안의 미수신 역순은 전달하고 동일 인증 내용의 중복은 중복 표시로만 전달한다(예: ACK 재응답용). 더 오래된 번호는 재생 거부한다. 같은 sequence의 서로 다른 인증된 내용은 진단 채널 불일치 실패다. 새 세션 없이 창을 초기화하지 않는다. 일반 BMS 수신/ECU 보호 판단을 진단 오류 때문에 멈추지 않는다.

미완성 메시지 수(최대8), 최초 조각 기준 조립 기한, 암호 검증의 시간 창/횟수는 명시적 설정이다. 중복·오류 입력이 기한을 늘리거나 진행 중 조립을 밀어내지 않는다. 실제 송신의 대기열/프레임 예산과 우선순위·유실/기록 처리는 제품 어댑터에 별도로 필요하다. 아래 정적 프레임 수는 버스 점유율·지연 보장이 아니다.

## 공통 자료형

정수는 모두 BE다. 프로세스·사건·재시작·거부 ID는 UUIDv4의16B 원형이다. 문자열 UUID를 wire에 넣지 않는다. session_id는 UUID가 아니다. 모든 reserved는0이고 미지원 코드/길이는 거부한다.

FrameReference44B:

| 상대 오프셋 | 길이 | 의미 |
|---:|---:|---|
|0|1|종류0=없음,1=단일 관찰 프레임,2=원본/인증 후보 쌍|
|1,2|각1|원본/인증 DLC|
|3|1|reserved|
|4,8|각4|원본/인증 raw CAN ID(메타데이터 flag 포함)|
|12|16|관찰 당시 보안 context 식별(session_id), 키 아님|
|28,36|각8|원본/인증 payload|

종류0은 나머지 모두0. 종류1은 인증 측 필드가 모두0이며 원본 DLC0~8, 사용하지 않는 payload 뒤쪽은0이다. 종류2는 원본/인증 DLC8·표준 ID이며0x100/102,0x101/103,0x104/105 중 하나다. context는 “어느 보안 교환에서 관찰했는지”이며 해당 프레임 MAC이 그 세션에서 유효했다는 주장이 아니다. 같은 바이트 반복의 실제 로컬 수신 순번은 노드 기록에 보관하며, 단순 바이트/시각 일치만으로 공격자 신원이나 전체 공격 종료를 주장하지 않는다. DLC8을 넘는 관찰은 이 고정 참조로 잘라서 동일 프레임이라고 표시하지 않는다.

## 2 RestartPlan — ECU→IVI,56B/24프레임

instance16, operation16, 보호 사건 UUID16(해당 없으면0), cause1, next_mode1, attempt1, reserved1, ack_wait_ms4.

cause1=보호 정지 뒤 resume(같은 보호 사건 자동1회),2=명시적 fresh 요청,3=명시적 resume 요청. cause1/3은next_mode2, cause2는next_mode1이다. attempt1~3이며 cause1은1만 허용한다. instance/operation은 필수다. ack_wait_ms는 명시적인 양수이며 실측 없이 운영 기본값으로 고정하지 않는다.

보호 판단은 ACK를 기다리지 않는다. ACK가 없으면 제한 대기 뒤 자동 재시작한다. 같은 operation의 중복 계획으로 대기시간이나 자동 시도 횟수를 재설정하지 않는다. 배선 단절·돌발 종료에는 사전 예고가 없을 수 있으며 이때 “재시작 확정”으로 표시하지 않는다.

## 3 RestartReceipt — IVI→ECU,40B/20프레임

원래 ECU instance16 + operation16 + accepted1(값1) + reserved3 + 수신한 Plan envelope sequence4.

현재 세션·instance·operation·실제 보낸 Plan sequence에 맞는 인증된 응답만 대기를 끝낼 수 있다. 새 ECU가 실행된 뒤 옛 응답이 와도 재시작 로직을 다시 시작하지 않는다.

관찰 중은 window>0·프레임 수>0·quiet=0이다. 종료는 quiet>=5000이며, 관찰 불가는 quiet=0이다. 전송 성공이 공격 분류 정확도를 증명하지 않는다. 서로 다른 유형은 별개 사건이며 source_instance 변경/상태 공백은 종료로 합치지 않는다. 역순 메시지는 source_tick/update revision으로 비교하고 옛 상태가 현재를 덮지 않게 한다.

## 5 RejectionRecord — IVI→ECU,80B/30프레임

IVI instance16 + rejection UUID16 + reason1 + MAC 검증됨1(0/1) + treatment1 + reserved1 + FrameReference44B.

reason:1=메타데이터,2=미지원 ID,3=후보 포화,4=원본 만료,5=인증 만료,6=검증 예산,7=재생,8=번호 앞섬,9=동일 중복,10=본문,11=일반 큐 포화,12=보호 큐 포화,13=인증 상충,14=시계 오류,15=현재 상태 확인 전 입력.

treatment:1=거부,2=검증 대기,3=중복 무시,4=기한 만료,5=채널 실패. reason4/5는treatment4,6은2,9는3,12/13/14는5,나머지는1이다. reason7~13은 실제 유효 MAC이 확인된 결과이며 MAC flag1/현재 context가 있는 쌍 참조를 요구한다. 만료/미완성 후보를MAC_FAIL로 바꾸지 않는다.

IDS 사건과 실제 거부가 유일하게 같은 관찰 후보로 연결될 때만 “관련 데이터의 수신 거부 확인”을 표시한다. 후보가 여러 개거나 단순 해시/시각만 같은 경우는 미확정이다. “공격 노드 송신을 막음/버스 전체 차단 완료”로 표시하지 않는다. Flooding에는 이 완료 문구를 적용하지 않는다.

## 6 Metrics — 양방향,52B/23프레임

source_instance16 뒤에 uint32 9개: window_ms, 관찰 RX 프레임 수, 정상 인증 BMS 쌍 수, 마지막 정상 RX age_ms, 평균 반영 간격_us, 최대 반영 간격_us, 실제 CAN RX error 증가량, 실제 RX drop 증가량, known_mask.

known_mask bit0~6은 순서대로 RX/인증 쌍/age/평균/최대/error/drop이다. bit0은 필수이며 window>0, 나머지 미측정 필드는0xFFFFFFFF다. 알고 있는 필드에unknown 값을 쓰지 않는다.0은 실제 측정0일 때만 쓴다. 오류/drop 수집 불가를0으로 꾸미지 않는다. mask 밖 비트는0이다. 정상 쌍 수는 RX 수를 넘지 않으며 평균/최대가 모두 있으면 평균<=최대다.

CAN ID 방향으로 측정 노드를 구분한다. ECU의 자기 관찰을 IVI의 정상 수신으로 표시하지 않는다. IVI 화면의 다섯 항목은 과다 RX/근거, IVI 정상 인증 수신, 마지막 정상 경과시간, IVI 실제 반영 간격/지연, 실제 error/drop/품질이다. fps를 실제 버스 점유율로 환산하지 않는다.

## 7 ObservationStatus — ECU→IVI,52B/23프레임

IDS source_instance16; health1(1=정상 관찰,2=불확실,3=중단); reason1(0=없음,1=수신 유실,2=입력 오래됨,3=탐지기 오류,4=재시작,5=큐 포화,6=필수 모델 없음); reserved2; source_tick4; source uptime_ms8; window_ms4; 검사 프레임 수4; 실제drop4(모르면FFFFFFFF); healthy_span_ms4; 현재 조건 mask1(Fuzzy/Replay/Spoofing/Flooding=bit0..3); detector revision2; reserved1.

정상 관찰은 reason0,양수window/프레임 수,drop0,healthy_span>=window가 필요하다. 불확실/중단은 reason1~6,healthy_span0이며 “정상 조건 없음”으로 누적하지 않는다. source_tick은1부터 단조 증가한다. source uptime은 다른 호스트 시각과 직접 빼지 않는다.

1초 갱신·3초 상태 손실→불명·5초 연속 정상 관찰 뒤 해당 조건 없음→종료라는 사용자 선택을 적용한다. IVI에서 상태가 끊기면 quiet 누적을 끊고 돌아온 뒤 새 연속 관찰을 확인한다. 이전 source_tick의 늦은 사건/heartbeat가 현재 상태를 되돌리지 못하게 한다. 팝업 닫기는 보안 상태/이력 초기화가 아니다.

|16|16|계산 상태 계보 UUIDv4. fresh에서 새로 발급하고 검증된 checkpoint에 보존|
|32|16|보호 사건 UUIDv4. 아직 사건이 없으면 전부0|
|48|1|현재 위험 상태0~3|
|49|1|현재 위험 사유0~7.0이면 사유 없음이며 다른 값은 현재 상태 계약의 허용 조합을 적용|
|50|1|단계0=사건 없음,1=경고/보호 유지,2=정상 복귀 확인|
|51|1|bit0=같은 계보의 검증된 checkpoint resume. 나머지 reserved0|
|52|4|사건 revision, BE uint32|

단계0은 상태0/사유0/사건UUID0/revision0이다. 단계1은 상태1~3·유효 사건UUID·revision1이상, 단계2는 상태0·유효 사건UUID·revision1이상이다. 단계2의 사유는 현재 상태 계약이 허용하는 정상/복귀 사유만 허용한다. bit0은 사건 존재와 별개로 검증된 복원 계보를 뜻한다. IVI→ECU 방향, 잘못된 UUID/상태 조합/단계/예약 비트/길이는 거부한다.

NORMAL→위험에서 새 사건을 발급하고 같은 연속 위험 구간의 상태/사유 변경은 동일 사건 revision을 올린다. 정상 복귀는 같은 사건의 종료 기록이며 이후 재발은 새 사건이다. 자동 프로그램 복구는 마지막 저장 완료 계보/사건/revision을 이어받지만 인증 키/counter는 복원하지 않고 새 세션을 사용한다. 명시적 fresh는 새 계보이며 이전 사건을 정상 종료로 꾸미지 않는다. 식별자가 없는 구형 checkpoint는 새 계보/연속성 미상으로 구분하고 bit0을 세우지 않는다. revision은 소진 후0으로 순환하지 않는다.

IVI는 현재 인증 세션의 NodeStatus instance·ProtectionStatus instance/계보·현재 STATE가 일치한 뒤 사건을 연결한다. 세션 혼합/누락/상태 불일치·시각 오류는 미확정이며 같은 온도/위험 코드만으로 사건을 합치지 않는다. 미저장 전이/정전 직전 기록과 통신 공백의 완전 보존은 보장하지 않는다. 기존 BMS/보호 판단은 이 진단을 기다리지 않으며 송신 큐/프레임 예산으로 제한한다. 보호 해제/프로그램 재시작·공격 차단 정책을 이 메시지가 변경하지 않는다.

## 9 PhysicalMeasurement — ECU→IVI,80B/30프레임

2026-11-17 사용자에게 기존 BMS8바이트를 유지하고0x302의 종류9로 실측값·미산정·품질을 전달하는 영향을 설명한 뒤 “ㅇㅋ 그렇게 하셈” 승인을 받았다. 기존 종류1~8·키 파생·인증 입력·ID/DLC는 그대로다. 구형 수신기는 종류9를 거부하므로 ECU·IVI·C++/Python 검증기를 함께 갱신한다.

모든 정수는 BE다. 유효비트가0이면 대응 수치 필드는0으로 고정한다. 따라서 미산정SOC와 유효0%는 별개다. 전압·전류는 한 INA변환이므로 두 비트가 함께 켜지거나 꺼진다. 채널 품질2와 대응 실측 유효비트는 일치해야 하고, 정상 값의 나이는FFFFFFFF일 수 없다. 품질4/6의마지막값존재는현재값유효를뜻하지않으며실측화면은무효채널을`--`로표시한다. SOC유효에는 정상 INA입력과SOC근거1또는2가 필요하다. SOH유효와SOH근거1은 함께 사용한다. 취득 순번0은 실측/SOC유효비트0·두 채널 품질1또는3·두 나이FFFFFFFF만 허용한다. 외부 용량시험의SOH는 독립적이다. 용량시험 입력의 존재는 실제 정확도 인증이 아니다.

ECU는 현재 세션이 열린 뒤1초 간격으로 최신 보고를 제안한다. 대기 메시지1개, pump당최대6프레임, 큐 만료는 명시한 diagnostic_assembly_ms다. 세션 변경·만료·송신 실패는 이전 메시지를 버리며 같은 순번으로 다시 만들지 않는다. 1초는 이 선택형 표시 경로의 설계 주기이며 실제 Pi 처리량/지연 보장이 아니다. 취득은 명시한 별도 period_ms이며1초마다 새 측정이 생긴다는 뜻이 아니다.

IVI는 현재 세션·신선한NodeStatus·동일instance·동일설정·취득 순번을 검사한다. 같은 순번의 정상값/추정값 변경, 오류값의 정상 재생, 나이 감소, 설정/근거 혼합과 역순을 거부한다. 같은 순번의 품질 무효화와 증가한 나이 보고는 허용한다. ECU나이에 수신 후 IVI 로컬 경과를 더해 각 채널을 만료시키고, NodeStatus나 보고 자체가 만료돼도 유효표시를 내린다. 이 방식은 서로 다른 호스트 시계를 빼는 종단 지연 측정이 아니다.

`physical` 모드는 이 종류로 표시하며0x100/102에 가짜SOC/SOH나 가상10셀 값을 보내지 않는다. 기존0x104/105는 세션 개방 상태 동기화에 사용하되, NodeStatus의 위험값FF로 실제 셀 보호 판단이 미구성임을 구분한다. IVI는 실측 모드에서 세션의 초기NORMAL을 실제 배터리 안전 상태로 표시하지 않는다. 가상55/60°C 정책·실제 부하 차단·저잔량 보호·checkpoint 자동 복구는 이 메시지 추가만으로 구현/인수된 것이 아니다. 가상/ADS1115 제품 경로와 분리한다.
