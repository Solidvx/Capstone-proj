## 1. 확정 범위와 현재 상태

사용자는 인증 세션 기반 자동 재동기화와 CAN을 통한 세션 메시지 교환을 승인했다. IVI→ECU 제어 메시지가 필요하다는 방향도 승인 범위에 포함된다. 아래의 구체적인 ID·바이트 형식·키 파생·시간 값은 이번에 제시하는 후보이며 아직 확정하지 않았다.

현재 C++ `adaptive_ecu/src/bsw/secoc_module.cpp`와 Python `security/secoc_module.py`는 고정 공유키와 rolling counter를 사용한다. 세션 교환은 구현돼 있지 않다. 이 작업 시점에는 `ivi_platform/` 디렉토리와 Git 메타데이터가 없으므로 IVI 구현·브랜치 상태를 추정하지 않는다.

목표는 재부팅 후 새로운 양측 난수로 세션을 인증하고, 이전 세션 데이터가 새 세션에서 검증되지 않도록 하는 것이다. 이는 캡스톤용 프로토콜 제안이며 표준 SecOC 확장으로 표현하지 않는다. 암호 구성요소의 표준 준수만으로 전체 프로토콜의 안전성이 입증되는 것은 아니다.

## 2. 사전 검증할 후보안 — 상세 계약은 아직 미확정

| 안건 | 제안 | 영향 |
|---|---|---|
| SES-D1 전송 | 0x300 ECU→IVI, 0x301 IVI→ECU, 표준 CAN 데이터 프레임, DLC=8 | ECU 수신 경로·IVI 송신 경로, 양측 필터·IDS 허용 목록 추가 |
| SES-D2 인증 | 양측 16바이트 난수, 16바이트 세션 인증 태그, HKDF-SHA256 세션키 | 기존 공유키는 장기 키로 보관하고 데이터 HMAC에는 파생 키 사용 |
| SES-D3 호환성 | 기존 0x100~0x103의 DLC·배치 유지, 양측 동시 전환, 구형 인증으로 자동 복귀 금지 | wire 배치가 같아도 인증 의미는 비호환; 공식 계약·시험 변경 필요 |
| SES-D4 카운터 | 세션 내 전역 카운터 유지, 소진 시 같은 키로 래핑하지 않고 새 세션 수립 | 기존 ICD의 래핑 규칙 및 래핑 시험 변경 |

기존 프로젝트 문서·소스에서 0x300/0x301 사용은 검색되지 않았다. 실제 연결 장치의 ID 목록과 충돌 여부는 하드웨어 정보 입력 후 재확인한다. 모든 시간은 제안한 목표·설정이며 실측값이 아니다. 공격·버스 장애 중에는 복구 기한을 보장하지 않고 장애 제거 후 복구를 별도로 평가한다.

## 3. CAN 메시지 후보

### 3.1 공통 분할 헤더

8바이트 안에 난수·태그를 모두 넣을 수 없으므로 고정 길이 논리 메시지를 나누어 전송한다. CAN FD·ISO-TP 지원을 새 선행조건으로 요구하지 않는 후보 방식이다.

| 바이트 | 의미 |
|---|---|
| 0 | 상위 4비트 프로토콜 버전=1, 하위 4비트 메시지 종류 |
| 1 | fragment index, 0부터 시작 |
| 2~3 | transfer ID, unsigned 16비트 BE |
| 4~7 | 논리 메시지의 해당 4바이트 |

transfer ID는 조립 식별자일 뿐 인증·재생 방지 수단이 아니다. B가 새 교환마다 선택하고 A가 응답에 그대로 사용한다. wrap·충돌 상황에서도 양측 새 난수와 인증 transcript가 세션을 구분한다.

| 종류 | 방향·CAN ID | 논리 본문 | 프레임 수 |
|---|---|---|---:|
| 0 REQUEST | A→B, 0x300 | 4바이트 모두 0, transfer ID=0 | 1 |
| 1 CHALLENGE | B→A, 0x301 | nonce_B 16바이트 | 4 |
| 2 OFFER | A→B, 0x300 | nonce_A 16바이트 + tag_A 16바이트 | 8 |
| 3 CONFIRM | B→A, 0x301 | tag_B 16바이트 | 4 |
| 4 ACK | A→B, 0x300 | tag_ACK 16바이트 | 4 |

정상 교환은 REQUEST를 제외하면 20프레임이다. 이는 표에서 계산한 프레임 수이며 실제 버스 점유율이 아니다. 실제 CAN에서 arbitration·stuffing·재전송을 포함해 측정한다.

조립은 논리 메시지 종류별 고정 길이와 index 범위를 검사한다. 잘못된 방향·버전·DLC·확장 ID·RTR·error frame은 프로토콜 입력으로 받지 않는다. 동일 index·동일 bytes는 중복으로 무시하며 서로 다른 bytes는 해당 조립을 실패 처리한다. 조각 순서 역전은 bounded buffer로 수용하되, 완성 전 인증 상태·카운터·UI를 변경하지 않는다.

노드별 진행 중 교환은 하나만 유지하고 조립 본문은 메시지별 최대 32바이트로 제한한다. 새 비인증 요청이 진행 중 교환을 교체하거나 기한을 연장하지 못하게 한다. 단계 타이머는 첫 조각 또는 단계 진입 시 시작하며 중복·잘못된 입력으로 재설정하지 않는다.

## 4. 인증·키 파생 후보

양측은 OS의 암호학적 난수원으로 각 16바이트 nonce를 만든다. 운영 중 고정 seed·시각·카운터로 nonce를 대신하지 않는다. 난수원 실패 시 새 세션 수립은 실패 처리한다. 단위시험에서만 명시적 더미 키·nonce를 사용한다.

다음 연결은 raw bytes이며 문자열은 ASCII, NUL 종료 문자는 붙이지 않는다. 역할 이름과 ID 순서는 고정한다.

```text
T = ASCII("CAPSTONE-CAN-SESSION") || version(1B=0x01)
    || ECU_ID(2B BE=0x0300) || IVI_ID(2B BE=0x0301)
    || transfer_id(2B BE) || nonce_B(16B) || nonce_A(16B)

PRK = HKDF-Extract-SHA256(salt=nonce_B || nonce_A, IKM=SharedKey)
K_A   = HKDF-Expand-SHA256(PRK, info=ASCII("offer")   || T, L=32)
K_B   = HKDF-Expand-SHA256(PRK, info=ASCII("confirm") || T, L=32)
K_ACK = HKDF-Expand-SHA256(PRK, info=ASCII("ack")     || T, L=32)
K_DATA= HKDF-Expand-SHA256(PRK, info=ASCII("data")    || T, L=32)

tag_A   = HMAC-SHA256(K_A, T)[0:16]
tag_B   = HMAC-SHA256(K_B, T)[0:16]
tag_ACK = HMAC-SHA256(K_ACK, T)[0:16]

DataMAC = HMAC-SHA256(K_DATA,
          CAN_ID(2B BE) || RollingCounter(4B BE) || Payload(8B))[0:4]
```

HKDF의 Extract/Expand 정의는 [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869)를 따른다. 위 transcript·라벨·메시지 교환은 본 프로젝트 제안이다. 양측 nonce와 역할을 인증에 결합하고 키 용도를 분리하되, 교차 언어 벡터와 상태 전이 공격 시험으로 검토해야 한다.

장기 공유키는 CAN으로 전송하지 않는다. 파생 키도 전송·로그·영구 저장하지 않는다. 인증 비교는 constant-time 연산을 사용한다. 기존 데이터 MAC 4바이트는 유지하므로 세션 태그를 늘렸다고 데이터의 위조 저항이 128비트가 된 것으로 주장하지 않는다. 장기 키 유출·공격자의 버스 점유는 이 설계만으로 해결되지 않는다.

## 5. 상태 전이와 실패·복구

1. B가 시작하거나 복구를 시도하면 새 nonce_B와 transfer ID로 CHALLENGE를 보낸다. A가 먼저 시작하면 REQUEST를 제한된 빈도로 보내 B의 시도를 요청한다. REQUEST 자체로 인증된 상태를 삭제하지 않는다.
2. A는 CHALLENGE에 새 nonce_A를 생성하고 OFFER를 보낸다. 같은 교환의 재전송에는 같은 nonce_A·OFFER를 사용한다. 인증되지 않은 신규 CHALLENGE는 기존 활성 세션을 바꾸지 않는다.
3. B는 현재 nonce_B·transfer ID와 일치하는 OFFER의 tag_A를 검증하고 CONFIRM을 보낸다. 실패하면 데이터 키·카운터를 갱신하지 않는다.
4. A는 현재 pending 교환의 tag_B 검증 성공 시에만 세션을 교체한다. 송신 큐·수신 pending을 세션 경계에서 정리하고 전역 카운터를 0으로 설정한 뒤 ACK를 먼저 큐에 넣는다. 그 후 새 키의 BMS 인증 쌍을 전송한다.
5. B는 ACK를 검증한 후 세션을 교체하고 이전 원본/인증 pending·수신 카운터를 지운다. 새 세션에서 완전한 BMS 인증 쌍을 검증해야 UI stale을 해제한다. ACK만으로 통신 정상으로 표시하지 않는다.
6. ACK 유실 시 B는 같은 CONFIRM을 재전송한다. A는 완료 교환의 ACK를 5초 동안 재전송할 수 있게 보관하되 **중복 CONFIRM으로 키·카운터를 다시 초기화하지 않는다**. 그 뒤에는 새 교환을 요구한다. ACK 대기 중 도착한 새 세션 BMS는 폐기하고 다음 정상 주기의 쌍을 기다린다.
7. 각 노드의 세션 교체는 해당 노드의 키·카운터·pending을 한 번에 바꾸는 로컬 동작이다. 네트워크를 통한 양측의 동시 commit을 가정하지 않는다. ACK 유실·교체 도중 재부팅·늦게 도착한 구세션 프레임을 반드시 시험한다.

### 5.1 활성 세션과 복구 후보의 분리

활성 세션과 pending handshake를 별도로 관리한다. 인증 실패·REQUEST·CHALLENGE만으로 활성 키나 카운터를 초기화하지 않는다. 새 교환 실패 시 기존 세션이 아직 유효하면 유지한다. 상대가 재부팅했거나 CAN 장애로 유효 BMS가 없으면 기존 300ms stale 정책을 적용한다.

활성 세션이 없거나, B가 300ms 동안 유효 BMS를 받지 못한 경우 자동 복구 시도를 예약한다. 후보 교환은 위 타임아웃·횟수 제한을 따르며 무한한 즉시 재시도를 하지 않는다. 인증되지 않은 REQUEST 처리도 최대 1초에 1회로 제한한다. CAN 점유 공격 중에는 가용성을 보장할 수 없으며 CPU 사용량·큐 크기·복구 트래픽을 제한하는 것이 검증 대상이다.

### 5.2 카운터와 인증 데이터

0x100/0x102 및 0x101/0x103은 기존처럼 한 송신 세션의 전역 counter를 공유하고 송신 순서를 직렬화한다. 새 세션 첫 수신 counter 후보 범위는 0~99, 이후에는 증가량 1~100이다. 범위 밖 프레임은 MAC이 유효해도 기준을 되돌리지 않는다.

같은 세션에서는 0xFFFFFFFF 뒤에 0을 재사용하지 않는다. 소진 시 인증 데이터 송신을 멈추고 새 세션을 수립한다. 새 세션 실패 시 BMS 계산·ECU 로컬 Fail-safe는 계속 수행하되 인증 송신 재개는 보류한다. IVI는 마지막 유효값과 stale을 표시한다. 보안 OFF 실험으로 자동 전환하지 않는다.

IDS_Alert 0x200은 현재 ICD의 비인증 참고 경보 범위를 유지한다. 새 세션 메시지를 BMS 데이터나 IDS 공격 건수로 잘못 계수하지 않도록 탐지기·측정기 입력 분류를 수정한다. Flooding 검사에서 세션 ID를 무조건 제외하지 않는다.

## 6. 실제 하드웨어 인수 계획

아래 SES-V 번호는 이 설계안 내부의 검토 항목이다. 공식 TC 번호는 승인 후 TEST_PLAN에 등록하고 기존 TC-SEC/TC-INT와 추적한다.

| 항목 | 실행·관측 | 합격 조건 |
|---|---|---|
| SES-V1 | 더미 키로 Python·ECU C++·IVI 코어 transcript/HKDF/태그 벡터 비교 | byte 단위 일치, RFC HKDF 벡터도 통과 |
| SES-V2 | 변조·반사·이전 handshake·이전 데이터 재생 | 시험 입력이 새 세션 활성화·데이터 반영·counter reset을 유발하지 않음 |
| SES-V3 | 모든 단계의 유실·중복·순서 역전·fragment 혼합·잘못된 DLC | 메모리 상한 유지, 인증 실패 시 기존 상태 보존, 중복 완료에서 재초기화 없음 |
| SES-V4 | A 단독·B 단독·양측 동시 재부팅, ACK 직후 재부팅 | 자동 재수립, 새 인증 BMS 후 stale 해제, 구세션 입력 거부 |
| SES-V5 | counter 소진·100 초과 유실·난수원 실패·키 불일치 | 같은 키의 counter 재사용 없음, 실패 표시와 bounded retry, 자동 보안 해제 없음 |
| SES-V6 | RPi4 두 대·실제 CAN에서 각 재부팅 유형 30회 | 서비스·CAN 준비부터 첫 유효 BMS까지 최대 5초 목표, 실패·누락 포함 전 시행 보고 |
| SES-V7 | bus-off·케이블 분리·Flooding 후 장애 제거 | 장애 중 stale·기존 ECU 로컬 동작 확인, 복구 시간 별도 측정, 메시지 폭주 없음 |

단위 상태 머신→vcan 교환→실제 CAN 순으로 진행한다. vcan에서 얻은 시간·부하는 실제 버스 성능으로 보고하지 않는다. 대상 Android의 CAN 송신 권한·SocketCAN 지원, 양측 필터와 실제 모듈 사양을 먼저 확인한다. SocketCAN 프레임·필터·오류 처리의 근거는 [Linux 커널 문서](https://docs.kernel.org/networking/can.html)다.

복구 시간의 시작은 전원 인가 시각이 아니라 양측 서비스와 CAN 준비가 확인된 시점으로 정의한다. 전원 인가부터 UI까지의 부팅 시간은 별도로 기록한다. 공통 관측 장치 또는 오차가 검증된 시계로 측정하고 run/boot 식별자·원시 CAN 로그·세션 결과·첫 유효 BMS 수신 증거를 남긴다. 키와 파생 키는 증적에 포함하지 않는다.

## 7. 승인 후 계획 반영 순서

1. 사용자 I-1=B에 따라 후보의 상태 머신·유실/재생 시험·대상 환경 검토를 선행한다. 양측 전환·ACK 유실·오래된 메시지·counter 수명·재시도 상한의 실패 사례를 검토하고 결과와 수정안을 제시한 후 SES-D1~D5를 확정한다. 하드웨어·Android 빈칸은 유지한다.
2. 공동 M1에서 ICD 변경안을 정리한다. CAN ID·방향·분할 형식·키 의미·counter 규칙·stale 구조체를 변경 전후로 대조한다. SRS·양측 SDD·TEST_PLAN·ADR·TARA의 영향 항목을 함께 검토한다.
3. ECU M3는 세션 수신/응답·키 수명·송신 직렬화·로컬 Fail-safe 독립성을 구현할 과제로, IVI M3는 challenge·세션 검증·stale 전달·재연결을 구현할 과제로 구체화한다. 보안 담당은 Python 참조와 replay/fragment 공격 벡터를 제공한다.
4. 공식 계약·구현·시험은 프로젝트 인터페이스 변경 게이트에 따라 동기화한다. 이 계획 편집만으로 실제 구현을 변경하지 않는다.
5. 공동 통합시험·IDS ablation·CI·데모의 protocol version과 방어 구성을 명시한다. 무방어/기존 고정키 결과를 새 세션 보안 결과와 합쳐 평균내지 않는다.
6. 양측 동시 배포와 세션 수립 smoke test를 통과해야 통합 완료다. 구버전 혼합 배포는 실패로 표시하며 보안 OFF 또는 고정키 방식으로 자동 downgrade하지 않는다.
7. 이후 `Plan/` 병합 시 과거 고정키 재동기화 설명을 역사 자료로 식별하고, 승인된 새 계약과 실행 과제를 기준으로 대응표를 갱신한다.

## 8. 미완료 및 검토 한계

이 문서는 상태 전이·바이트 배치·검증 방법을 검토하기 위한 제안이다. Python 논리 모형의 제한된 사전 검증은 §10에 기록했다. 전체 프로토콜 상태 머신 검증, 교차 구현 시험, 실제 장비 인수는 아직 완료하지 않았다. SES-D1~D5 승인 이후에도 시험에서 발견한 계약 변경 사항은 다시 보고한다. 이전 계획 개선안의 BMS·ADC·측정·추적성 등 독립 항목은 별도 잔여 작업으로 유지하며 이 문서 작성으로 전체 plan 개선을 완료 처리하지 않는다.


## 9. 사전 검증 게이트 — 사용자 I-1=B

이 단계는 최종 제품 구현의 시작이 아니라 후보 프로토콜을 확정하기 위한 검증 과제다. ECU·IVI 담당은 동일 상태 전이표와 더미 입력을 사용해 세션 확정 전 데이터 차단, 양측 각각의 전환 시점, 중복 확인의 counter 불변, 구세션 거부, 오류/유실 시 기존 상태 보존을 검토한다. 상태 머신 하네스·교차 벡터 결과가 나오기 전에는 세부 형식이나 복구 목표의 검증 완료를 주장하지 않는다.

실장비 지원·시계/부하·복구 시간 검증은 사용자가 보류한 장비·Android 입력이 선행된다. 센서 오류 별도 전달(I-2=B) 중에도 통신은 유지되므로 '유효 BMS 없음'이 무조건 peer 재부팅을 의미하지 않도록 세션 재수립 trigger를 함께 검토한다. 센서 품질 상태와 통신 timeout을 구분하지 못하면 재인증 반복이 생길 수 있으므로 두 계약의 결합이 새 검토 조건이다. 필요한 trigger 변경은 후보 수정안으로 제시하며 임의 확정하지 않는다.


### Q-1=B 확정 방향과 후보 검증의 연결

센서 품질은 별도 상태 프레임 대신 기존 BMS 예약 영역에 담는 방향으로 결정됐다. 구체적인 비트 배치는 아직 미확정이며 기존 ICD의 예약값은 변경하지 않았다. 후보 사전 검증에는 동일 BMS payload의 값·품질이 함께 인증되는 경우를 포함한다. 인증된 센서 오류 payload의 수신과 정상 센서 측정의 부재를 구분하고, Q-3의 3회 복구를 세션 인증 성공으로 대체하지 않는다. §9의 trigger 검토는 유지하며 센서 오류만으로 재인증을 반복하는 설계를 채택하지 않는다.

### 결과가 드러낸 잔여 설계 조건

1. §5.1의 `유효 BMS`는 후보 수정 시 **형식·MAC·counter 검증을 통과한 BMS 통신**으로 명확히 정의해야 한다. 정상 센서값이 없다는 이유만으로 재인증하지 않는다. 이는 합성 반례와 Q/R의 상태 분리 결정으로 뒷받침되며 최종 세션 계약 검토에 포함한다.
2. 최초 조각/단계 진입 타이머, 단계 재전송, 전체 handshake 실패 기한, 5초 backoff의 관계를 실제 스케줄러 모형으로 검토해야 한다. 현재 모형은 수동 호출이며 bounded retry 전체를 실행하지 않았다. 단계당 3회×여러 단계가 정상 무손실 5초 목표와 같다고 계산하지 않는다.
3. 인증되지 않은 신규 CHALLENGE가 진행 중 교환을 교체하지 않는 규칙과 만료 뒤 새 교환 허용 경계를 명세해야 한다. 현재 모형의 단순 메서드는 스케줄러·wire 입력 처리기를 대신하지 않는다.
4. 데이터가 B에 인수되기 전 sender counter가 초기 허용 범위 0~99를 벗어나는 상황도 검토한다. ACK 유실 중 BMS와 Fail-safe가 같은 전역 카운터를 소비하므로 시간만으로 최초 counter 범위가 충분하다고 단정하지 않는다.
5. 노드 단독/동시 재부팅, 중복 완료 뒤 새 교환, 조각 자원 고갈, 데이터/제어 큐 경쟁, 이전 세션 pending 폐기는 후속 모형과 교차 구현·vcan 시험에 남아 있다. 하드웨어 목표와 장비별 CAN 권한은 사용자 후속 입력 뒤 검증한다.

### 후보 수정 전 결정과 후속 검증

ACK 이전 카운터 소진의 해결 방향은 [질문리스트](../governance/의사결정_기록.md#part1-questions)의 S-6에서 인터뷰한다. 수신 허용 범위를 임의로 넓히거나 같은 키에서 카운터를 초기화하지 않는다. 답변 전에는 메시지 종류·방향·길이·인증 입력·공식 ICD를 변경하지 않는다. S-6 선택은 수정 후보를 검토할 방향이며, 검증 전 최종 계약 승인으로 취급하지 않는다.

다음 후보 검증에는 아래 항목을 모두 포함해야 한다.

1. 하나의 이벤트 스케줄러에서 단계 진입·최초 조각·완성·타임아웃·재시도·5초 backoff를 연결한다. 이번 모형은 실패 뒤 다음 허용 시각만 산출하며 반복 재시작까지 실행하지 않았다.
2. ACK 이전 데이터 카운터 경계 99/100, BMS와 Fail-safe 동시 송신, ACK/후속 확인 유실을 결합한다. 실패 시 stale 유지와 ECU 로컬 판단 지속을 확인한다.
3. 재부팅 탐지부터 이전 pending 폐기·새 nonce 생성·새 키 확정·첫 인증 데이터까지 자동 경로를 구현한 모형으로 재검증한다. 시험 코드의 강제 새 교환을 자동 복구의 증거로 쓰지 않는다.
4. 미인증 새 CHALLENGE와 오래된 캐시 응답의 우선순위, 타이머 연장 금지, 조각별 유실·재정렬·동시 입력을 실제 dispatcher 경계에서 검증한다.
5. 승인된 수정 후보를 양측 독립 구현과 교차 벡터로 대조한 뒤 vcan·실제 CAN 검증을 수행한다. 정상 무손실 목표와 장애 중 실패 종료·장애 제거 후 복구 시간을 별도 기록한다.

판정: **2차 제한 모형 검토 수행 완료, SES-D1~D5 최종 확정 및 세션 인수는 보류.** plan의 기존 구조와 Plan은 유지한다. 이 절은 §10의 후속 증거이며 전체 상태 머신 검증 완료로 읽지 않는다.


## 12. S-6=A 확인 — 수신 준비 확인 후보 검토

사용자는 인증된 IVI 수신 준비 확인 뒤 ECU가 새 세션 데이터를 송신하는 후보를 검토하도록 선택했다. 추가 조건은 비어 있다. 이는 SES-D1~D5나 새 wire 형식의 최종 승인이 아니다. §5의 기존 ACK 직후 송신 후보는 §11의 반례가 있는 비교 대상으로 유지하고, 아래 수정 후보를 후속 검증한다.

| 주체·상황 | 수정 후보의 필수 동작 | 확인할 실패 경계 |
|---|---|---|
| ECU가 CONFIRM 검증 | ACK 송신 후 새 세션 데이터 송신을 대기 | 대기 중 데이터 카운터를 소비하지 않음; 로컬 BMS·Fail-safe 판단은 계속 |
| IVI가 ACK 검증 | 해당 교환에 결합된 인증된 수신 준비 확인을 송신 | 이전 세션·다른 교환의 확인으로 새 송신을 열지 않음 |
| ECU가 준비 확인 검증 | 새 세션 데이터 송신 허용 | 중복 확인은 재초기화·카운터 리셋·중복 작업 생성으로 이어지지 않음 |
| 준비 확인 유실·지연 | 제한된 재시도와 실패 종료가 필요 | 반복 횟수·전체 기한·캐시 만료·backoff를 결합한 모형으로 검증 |
| 대기 중 위험 상태 변화 | 로컬 판단 유지, IVI 통신 상태를 센서 상태와 분리 | 대기 이벤트 보존/전송 순서·오래된 위험 상태 처리 정책은 후보 구체화 후 인터뷰 |

준비 확인의 메시지 종류·길이·역할별 인증 입력과 재전송 정책은 아직 미확정이다. 별도 후보로 영향표를 작성하고 사용자에게 질문한 뒤 변경한다. 첫 데이터 자체의 대량 유실, 준비 확인 직후 재부팅, 동시 교환, 최초 카운터 범위 이탈은 여전히 검증해야 한다. 추가 확인 단계가 생기므로 기존 20프레임·4단계·복구 시간 산정을 그대로 재사용하지 않는다. 공식 ICD와 제품 소스는 이번 답변으로 변경하지 않았다.



## 13. 수신 준비 확인 상세 후보 — 계약 적용 전 검토

2026-09-07 S-6=A에 따라 검토용 후보를 구체화했다. 아래는 현재 ICD나 구현이 아니며 §3~5의 최초 후보를 조용히 대체하지 않는다. §10~11 시험 결과도 이 수정 후보의 검증 결과로 재사용하지 않는다.

### 메시지·인증 영향안

| 항목 | 기존 후보 | 수정 검토안 | 영향 |
|---|---|---|---|
| 프로토콜 버전 | 1 | 2 | 수신 준비 없이 송신하는 구후보와 구분. 자동 downgrade 금지. 모든 교환 메시지의 헤더 및 transcript version을 함께 변경 |
| 준비 확인 READY | 없음 | 종류 5, IVI→ECU 후보 0x301, DLC=8, tag_READY 16B를 4조각 | header byte0=0x25, byte1=0~3, byte2~3=현재 transfer ID BE, byte4~7=태그 조각 |
| 역할별 키 | offer/confirm/ack/data | 기존 라벨에 ready 추가 | `K_READY=HKDF-Expand(PRK, ASCII("ready") \|\| T_v2, 32)`; `tag_READY=HMAC-SHA256(K_READY,T_v2)[0:16]`. T_v2는 §4 transcript의 version만 0x02로 변경. 다른 역할 태그를 READY로 사용하지 않음 |
| 정상 메시지 수 | REQUEST 제외 20프레임 | REQUEST 제외 24프레임 | 4+8+4+4+4의 정적 합계. 실제 시간/버스 점유율이 아님 |
| 기존 BMS 인증 | 0x100~0x103 payload 배치 | 배치는 유지하되 v2 transcript로 파생한 키 사용 | 전체 태그 벡터를 새로 계산하고 Python/C++/IVI를 교차 검증해야 함 |

### 상태 전이와 재전송 검토안

1. ECU는 현재 pending CONFIRM을 검증한 뒤 새 키를 준비하고 ACK를 송신한다. 새 세션 데이터 송신은 READY 검증까지 닫아 둔다. 기존 세션 처리와 전환 시점은 §5 비교표와 함께 시험하고, 실패 시 이미 쓴 키/카운터로 되돌리는 경로를 만들지 않는다.
2. IVI는 ACK 검증 후 새 키의 데이터 수신을 준비하고 READY를 송신한다. READY 전송 사실만으로 stale을 해제하지 않는다. 새 세션의 완전한 인증 BMS 수신을 확인하며 센서 오류 상태 수신과 통신 단절을 구분한다.
3. ECU가 현재 교환의 READY를 완전히 검증한 경우에만 송신을 허용한다. 중복 READY는 키/카운터 초기화나 대기 이벤트 중복 전송을 유발하지 않는다. 이전 교환·다른 방향/버전·다른 역할의 태그는 허용하지 않는다.
4. READY 유실에 대비해 ECU의 ACK 재전송에 IVI가 같은 READY로 응답하는 후보를 검토한다. 동일 ACK/READY는 재시도 횟수·전체 교환 기한·캐시 만료를 연장하지 않는다. 기존 1초/3회/5초 캐시는 확정값이 아니며 추가 단계의 최악 일정과 함께 재검증한다. 무한 대기는 허용하지 않는다.
5. IVI는 첫 인증 데이터 수신 전 복구 대기 상태를 유지한다. ECU는 READY 이후 데이터 유실 여부를 READY만으로 알 수 없으므로 첫 데이터 100개 이상 유실·READY 직후 재부팅에 대한 새 교환 경로가 계속 필요하다. 신규 CHALLENGE/REQUEST가 기존 pending을 덮어쓰거나 타이머를 갱신하지 못하게 한다.
6. 실패 시 ECU 로컬 계산/위험 판단은 계속하고 인증 송신은 상태에 따라 보류한다. S-10=A에 따라 준비 완료 후 현재 위험 상태를 한 번 인증 전달하고 과거 전이는 ECU 진단 기록으로 남기는 방향을 적용한다. wire 형식·필드 의미는 아래 후속 계약 과제로 남긴다. 작업 회수 실패나 공유 키 유출을 세션 재교환으로 해결했다고 간주하지 않는다.

### 필수 검증과 아직 미결인 조건

- 새 버전 모든 역할의 더미 벡터, READY 태그 변조·다른 역할 반사·이전 세션 재생·조각 혼합을 검증한다. 기존 v1 벡터와 v2를 섞지 않는다.
- 하나의 스케줄러에서 ACK/READY 유실·중복·역전과 캐시 만료, 단계 진입/조립/전체 기한을 실행한다. 단계당 3회가 전체 몇 회인지와 실패 후 재시도 기한을 명시한다. 검증 전 5초 복구 목표를 보장하지 않는다.
- READY 이전 카운터가 증가하지 않는지, 최초 송신·중복 READY 이후 카운터와 commit 횟수가 유지되는지 확인한다. 변조·미인증 입력이 송신 게이트를 열지 못해야 한다.
- ECU/IVI/양측의 각 전환 경계 재부팅, 구교환 완료 캐시와 신교환 pending 충돌, 이전 작업의 늦은 입력을 결합한다. 시험 코드가 새 교환을 강제로 시작한 결과를 자동 복구로 표시하지 않는다.
- **미결:** 기존 세션에서 새 세션으로 전환하는 동안의 정확한 송신 경계, 단계/전체 타이머 및 캐시 기한, S-10=A 상태 동기화의 필드 의미·유실 복구를 확정해야 한다. 후보 메시지·인증 입력 변경의 공식 ICD·SRS·양측 SDD·TEST_PLAN·ADR·TARA·필터/IDS 영향표는 후보 검증 후 승인 단위로 제출한다.

### S-10 위험 상태 재전달의 계약 영향

연결 대기 중 위험 상태가 변하면 ECU 로컬 판단은 유지되지만 IVI가 전이를 받지 못할 수 있다. 기존 0x101은 event 통보다. 준비 완료 시 현재 상태를 한 번 재전달하려면 기존의 전이 시 송신 조건에 세션 재수립 시 상태 동기화 조건을 추가하는 계약 검토가 필요하다. payload를 그대로 쓰더라도 송신 의미가 달라진다. 과거 전이를 현재 사건처럼 순서대로 재생해서는 안 된다.

S-10=A 후보는 준비 완료 후 현재 위험 상태/그 상태에 대응하는 사유를 한 번 인증해 전달하고, 그동안의 전이 이력은 ECU 진단 증거로 남긴다. 사유 없는 초기 상태의 표현·전달 순서·중복 준비 확인의 1회성도 함께 검증한다. S-10=B 후보는 현재 상태와 별도로 대기 중 사건 이력을 IVI가 구분해 표시하도록 전송한다. 사건 순서/식별·과거 표시·큐 상한/넘침·현재 상태 갱신 분리가 추가로 필요하다. 어떤 안도 이번 문서만으로 적용하지 않는다.



## 14. S-10=A 반영 — 현재 위험 상태 동기화

사용자 답변 A, 추가 조건 없음. 연결 준비 완료 후 현재 위험 상태를 한 번 인증해 IVI에 전달하며, 연결 대기 중 전이 이력은 ECU 진단 자료로 남긴다. 과거 사건을 현재 경고처럼 순차 재생하지 않는다. 이 방향 승인은 현재 0x101의 필드 의미나 새 메시지 형식까지 확정한 것은 아니다.

| 연결 대기 중 상태 | 준비 완료 후 기대 표시 | ECU 진단 기록 |
|---|---|---|
| NORMAL 유지 | 현재 NORMAL | 동기화 시점·결과 |
| NORMAL→WARNING 유지 | 현재 WARNING | 원래 전이와 동기화 결과 |
| NORMAL→WARNING→NORMAL | 현재 NORMAL; 지난 WARNING을 신규 현재 경고로 표시하지 않음 | 두 전이 이력 |
| WARNING→CRITICAL 또는 SHUTDOWN | 현재 도달한 위험 상태 | 기존 전이 규칙대로 발생한 이력 |
| 센서 오류/회복 중 | 마지막 유지한 위험 상태와 별도 센서 품질 표시 | 관측 부재·상태 유지 근거; 정상 복귀를 추정하지 않음 |
| 인증 동기화 메시지 유실 | 동기화 수신 성공을 주장하지 않음 | 송신/수신 증거와 실패/후속 복구 |

한 번 동기화는 논리 상태 갱신의 1회성을 뜻한다. ACK/READY 중복 때문에 동일 상태를 새 전이로 반복 처리하지 않는다. CAN 송신 성공만으로 IVI 상태 인수를 확인한 것으로 간주하지 않는다. 동기화 메시지 유실 시 확인·재전송·새 교환 중 어떤 경로를 사용할지는 전체 상태 머신의 후보 검증에 포함한다. 동기화와 실제 신규 전이가 경합하면 상태를 일관되게 취득·직렬화하여 오래된 상태가 최신 상태를 덮어쓰지 않는지 검증한다.

### 기존 0x101 필드와의 차이

ICD §1.3은 PrevState/NewState, 전이 Reason, SOC_AtEvent/Temp_AtEvent를 정의한다. 새 부팅 이후 전이 없이 NORMAL인 경우에는 실제 이전 전이 사유가 없고, 현재 상태 동기화는 전이 사건 자체가 아니다. 따라서 PrevState=NewState 또는 Reason=0을 임의 지정하거나 현재 측정값을 과거 전이 시점 값처럼 쓰지 않는다. 예약 바이트도 승인 없이 동기화 표시로 사용하지 않는다.

후속 변경안에는 동기화 식별·상태/사유 부재·현재 값과 사건 값의 구분, 최초 표시와 전이 알림의 차이, 중복/유실·경합 처리, 원본/인증 쌍과 카운터 소비를 명시한다. 0x101 확장과 별도 메시지 중 선택할 구체안을 영향/검증 결과와 함께 제시한 뒤 인터뷰한다. 현재 단계에서는 새 ID·Reason·필드 코드를 정하지 않는다.

### S-11 메시지 형식의 구체 후보

**A 후보 — 별도 상태 쌍:** 원본 `0x104`·인증 `0x105`, Node A→B, 각 DLC=8. 현재 조사한 ICD·제품 소스에서 이 ID 용도는 확인되지 않았으나 실제 버스 충돌은 장비 정보 후 재확인한다. 원본 byte0=현재 Fail-safe 상태(0~3), byte1=사유 존재(0/1), byte2=마지막으로 현재 상태에 진입한 사유(존재 시 기존 1~7), byte3~7=0 후보다. 사유 부재 시 byte2=0은 이 새 메시지 안에서만 정의한다. 초기 NORMAL은 사유 없음으로 표현한다. 현재 SOC/온도는 0x100에서 받으며 과거 전이 시점 값과 섞지 않는다. 상태·사유 조합, 미지원 값·예약값을 검증하고 센서 품질을 정상으로 추정하지 않는다.

0x105는 기존 형태의 MAC4B+counter4B 후보이고 MAC 입력은 원본 ID `0x0104` BE || 전역 counter BE || payload8이다. 데이터 키는 세션 v2 파생 키를 쓰며 0x100/101과 동일 전역 counter/직렬화 경계를 공유한다. 이는 새 인증 대상 추가이므로 현재 ICD를 수정한 것으로 취급하지 않는다. 0x101/103은 실제 전이 사건으로 유지한다.

**B 후보 — 기존 전이 쌍 확장:** 0x101/103을 유지하고 예약 byte5를 종류(0 전이/1 동기화), byte6을 사유 존재, byte7=0으로 확장하는 후보다. 동기화에서는 PrevState=NewState=현재 상태, 사유 부재 시 Reason=0, SOC_AtEvent/Temp_AtEvent는 의미 없음으로 별도 정의해야 한다. 기존 소비자가 동기화를 전이로 오인할 수 있으므로 양측 parser·HAL/Service·시험을 동시 전환해야 한다. 단순 예약값 사용이나 무변경 호환으로 주장하지 않는다.

두 안 모두 S-10=A의 현재 상태 전달 방향을 구현하며 과거 이력을 IVI에 전송하는 선택으로 바꾸지 않는다. 초기 상태·사유 부재를 기존 Reason 코드에 임의 대입하지 않는다. S-11=A로 별도 상태/인증 쌍을 선택했으며 B는 비교 대안으로만 보존한다. 선택한 후보의 상세 형식과 전체 프로토콜을 검증한다.

### S-12 상태 수신 확인의 구체 후보

**A 후보 — 인증된 상태 수신 확인:** IVI가 현재 세션의 상태 메시지 인증·상태 반영을 마친 뒤 해당 메시지에 결합된 확인을 보내는 방안이다. 후보 handshake 종류 6, 0x301, 20B 본문(counter4B BE+tag16B), 5조각이다. 별도 `state-receipt` 역할 키와 `T_v2 || 원본CAN_ID(2B BE) || counter(4B BE) || payload(8B)`에 대한 16B HMAC으로 확인을 결합하는 후보를 검토한다. READY·이전 상태·다른 counter의 확인으로 새 상태 전달 성공을 오인하지 않는다. 정확한 형식은 S-11 선택 결과와 함께 검증한다.

송신자는 현재 동기화 건의 제한된 재시도 목록과 확인을 연결한다. 재시도마다 새 전역 counter를 소비하는 경우에도 동일 현재 상태를 새 전이 알림으로 만들지 않는다. 이미 바뀐 상태에 대한 오래된 확인이 최신 동기화를 완료시키지 않도록 버전/소유 경계를 정한다. 확인 유실·최대 재시도 소진·부팅 경계·실제 전이와 경합을 검증하고, 실패 시 상태 미확인으로 보고한다. 일반 데이터 수신과 위험 상태 동기화 완료는 별도 조건이다.

**B 후보 — 횟수 제한 반복 송신:** 인증된 현재 상태를 미리 정한 횟수만큼 보내고 IVI 수신 확인은 추가하지 않는다. ACK 없는 송신으로 실제 수신 완료를 증명할 수 없으므로 ECU는 ‘송신 시도 완료’까지만 보고한다. IVI 상태 미확인과 정상 BMS 수신을 구분해야 하며 누락 시 새 동기화 유발 조건이 필요하다. 반복 횟수·기한은 자동으로 정하지 않는다.

S-12=A라도 버스 공격 중 전달 보장은 아니다. 상태를 확인하지 못한 경우의 실패 표시·다음 교환 정책과 일반 데이터 진행 조건을 전체 상태 머신에서 검증해야 한다. 두 질문은 검토할 방향 선택이며 SES-D1~D5/추가 ID·키 입력·타이머의 최종 승인이나 제품 구현 지시로 확대하지 않는다.

|---|---|---|
| CHALLENGE/OFFER/CONFIRM/ACK/READY/상태 원본/상태 인증/RECEIPT 각각 최초 0 또는 1회 유실 | 256개 모두 교환 완료; 최대 4,007 tick | 선택한 유실 조합에서만 관찰. 실제 성공률·복구 시간·최악 지연 보장 아님 |
| 위 8개 메시지별 지속 유실 | 8개 모두 제한 내 실패 | 실패 후 자동 새 교환 스케줄러는 포함하지 않음 |
| RECEIPT 유실 후 재전송 | 상태 반영 1회, 확인 뒤 완료 | 불변 snapshot 조건. 실제 전이 경합은 미포함 |
| 다른 역할·payload·이전 epoch의 receipt | 거부 | 제한 HMAC 입력 대조. 모든 wire 공격 검증 아님 |
| 논리 경계 6곳 재부팅 주입 | 해당 교환 폐기, 명시적으로 시작한 새 epoch 교환 성공·구확인 거부 | A/B 독립 재부팅 탐지·자동 복구를 구현한 것이 아님 |

### 남은 모델 격차와 다음 검증 순서

1. 현재 중앙 `accepted` 집합은 양측 진행을 알고 있다. 제품은 이를 공유할 수 없으므로 다음 모형에서는 A/B 각각의 상태·타이머·캐시·재부팅 세대를 분리한다. 한 노드의 완료/실패가 상대에 자동 전달되지 않게 한다.
2. 원본/인증을 따로 유실시키지만 모형은 원본에 내부 counter를 붙여 조립한다. 실제 0x104 원본에는 counter가 없으므로 이 편의를 제거하고, bounded 원본/인증 pending에서 실제 MAC으로 대응을 확인해야 한다. 부분 메시지·조각 역전·충돌·만료·메모리 상한을 검증한다.
3. 아직 시험하지 않은 상태 변경 경합과 정상 BMS/전이 메시지의 전역 counter 경쟁을 포함한다. S-13/14의 사용자 정책을 적용하기 전 시험용 불변 snapshot·일반 송신 대기 가정을 제품 결정으로 사용하지 않는다.
4. 독립 노드 부팅·타임아웃→새 nonce 교환을 자동화하고 재시도 소진 이후 backoff·이전 캐시와 새 pending·난수 실패를 연결한다. 현재 시험의 명시적인 새 Chain 생성은 자동 복구 증거가 아니다.
5. 위 모델이 통과한 뒤 교차 언어 벡터와 실제 parser/큐 경계를 확인한다. vcan·실장비는 별도 인수다. 공식 CAN/키/시간/HAL 계약은 후보 근거와 영향표를 검토한 후 갱신한다.

현재 판정은 **전체 논리 메시지 연결 시험 수행 완료, 양측 독립 프로토콜/실장비 인수 보류**다. 결과를 완성된 세션 구현이나 검증된 보안 프로토콜로 설명하지 않는다.

### S-13·S-14의 결정 지점

S-13은 상태 receipt 이전 일반 BMS 송신을 대기할지, 계속하되 IVI의 위험 상태 미확인을 따로 표시할지 선택한다. 전자는 대기/실패 시 마지막 값·stale 유지와 로컬 계산 지속, 후자는 새 값과 위험 상태 미확인 동시 표시·HAL 계약 검토가 필요하다. READY 이전 새 세션 송신 금지 결정은 둘 다 유지한다.

S-14는 확인 대기 중 상태가 바뀌면 최신 snapshot을 새 counter로 보내고 이전 확인은 완료 판정에서 제외할지, 기존 snapshot의 확인/실패를 마친 후 최신 상태를 보낼지 선택한다. 전자는 미확인 최신 건의 소유·이전 receipt 거부·전체 기한 연장 금지가 필요하고, 후자는 이전 상태 대기로 최신 위험 전달이 늦어질 수 있다. 어느 안도 로컬 판단을 중단하거나 기존 전이 규칙을 변경하지 않는다. 구체한 재전송 수치·새 UI/HAL 필드·공식 계약은 아직 미확정이다.



## 18. S-13=A·S-14=A — 송신 게이트와 최신 상태 우선

두 답변 모두 A이며 추가 조건은 비어 있다. §17의 일반 데이터 대기는 이제 선택된 정책이고, 불변 snapshot 가정은 최신 상태 우선 정책으로 보완해야 한다. 이전 중앙 모형 결과는 상태 변경 경합 검증 완료의 증거가 아니다. 아래 정책을 독립 노드 모형과 후보 계약에 반영한다.

1. READY가 인증됐더라도 최신 현재 상태에 대한 receipt가 확인되기 전에는 새 세션의 일반 BMS 데이터 송신을 대기한다. 로컬 BMS 계산·위험 판단·과거 전이 진단 기록은 계속한다. 대기/실패 중 IVI는 마지막 값과 통신 대기/단절 표시를 유지하며, 별도로 인증된 현재 위험 상태가 도착하면 그 상태는 반영한다. 오래된 마지막 값이 현재 정상 측정인 것처럼 표시하지 않는다.
2. 상태 확인 대기 중 ECU의 실제 위험 상태가 바뀌면 미확인 최신 건을 갱신한다. 새 전역 counter로 최신 상태를 인증 송신하고 이전 상태의 receipt는 최신 동기화 완료로 인정하지 않는다. 과거 이벤트를 현재 사건처럼 순서대로 재생하지 않는다.
3. 최신 건의 식별은 세션·원본 ID·counter·payload와 내부 세대에 연결한다. WARNING→NORMAL→WARNING처럼 payload가 다시 같아져도 첫 WARNING의 늦은 확인이 마지막 WARNING의 완료를 열지 못해야 한다. 동일 최신 건의 재시도와 새로운 상태 변경은 구분한다.
4. 현재 receipt 검증과 상태 변경 처리를 같은 소유 경계에서 직렬화한다. 일반 송신을 열기 직전에 그 receipt가 여전히 최신 상태를 가리키는지 확인한다. 이전 확인 처리와 최신 상태 게시가 경합하여 구상태 기준으로 열리지 않도록 시험한다. 실제 전이 직렬화와 counter를 별개로 초기화하지 않는다.
5. 상태 변경이나 중복 입력이 전체 교환 기한을 연장하거나 재시도 예산을 무한히 새로 부여하지 못하게 한다. 최대 송신/대기 예산의 구체 수치는 미확정이며 기존 시험 상수를 제품 설정으로 채택하지 않는다. 상한에 도달하면 실패와 후속 복구 조건을 기록하고 무한 대기하지 않는다.
6. 최신 상태 receipt 확인 뒤 일반 데이터를 재개한다. IVI 통신 stale 해제는 실제 새 세션 BMS 인증 쌍 수신으로 확인한다. receipt·상태 반영만으로 센서 품질이나 SOC 정확도까지 정상 복귀한 것으로 판단하지 않는다. 정상 송신 재개 이후 실제 새 전이는 기존 전이 통보 경로로 처리하며, 매 전이마다 재연결 게이트를 다시 닫는 정책을 추가하지 않는다.

| 입력/순서 | 기대 결과 |
|---|---|
| READY 성공, STATE/RECEIPT 유실 | 일반 BMS 차단; 로컬 계산 지속; 제한 소진 시 실패 |
| WARNING 송신→CRITICAL로 변경→WARNING receipt | 일반 송신은 계속 차단; CRITICAL 건만 최신으로 관리 |

정책 방향은 승인됐지만 큐/타이머·조립·독립 노드 재부팅·HAL 매핑·공식 ICD 전환은 아직 완료하지 않았다. 추가 UI 필드나 새로운 CAN 값은 이 문서 반영만으로 생성하지 않는다.



## 19. 독립 ECU·IVI 상태 동기화 모형 결과

S-13=A·S-14=A를 반영해 `python tmp/independent_state_review.py`를 실행했다. 시험 8개, 실패 0·오류 0. 결과 `tmp/independent_state_result.json`, 소스 SHA-256 `77d6a1633fd1547882081e679b6bef7f7f16df83f4f5777525bdcde545b21be6`. 더미 공유 키 00~1f와 결정적 시험 nonce만 사용했다. 제품 코드와 공식 ICD는 변경하지 않았다.

### 이전 중앙 모형과 달라진 부분

ECU와 IVI는 각각 로컬 상태를 소유하고 상대 객체나 공유 `accepted` 집합을 읽지 않는다. ECU가 만든 메시지 바이트를 외부 시험 루프가 IVI로 전달하고, IVI가 만든 receipt 바이트만 ECU로 전달한다. 시험용 컨텍스트를 양측에 미리 주어 READY 이후부터 시작한다. 정상 일반 데이터의 실제 전송은 포함하지 않고 송신 허용 상태 OPEN을 검증한다.

상태 원본은 counter 없는 payload 8B, 인증은 MAC4B+counter4B다. IVI는 보관 중인 원본과 인증의 MAC을 대조하여 쌍을 찾는다. 이전 모형처럼 원본에 내부 counter를 붙여 주지 않는다. 수신 확인은 세션 transcript·원본 ID·counter·payload에 결합한 20B 논리 메시지다. 이 receipt의 CAN 분할/조립은 아직 포함하지 않았다.

| 시험 | 결과 | 의미·한계 |
|---|---|---|
| 원본/인증/receipt 각각 앞선 0~3회 유실 | 64조합 중 OPEN 14·제한 내 실패 50 | 의도적으로 택한 유실 조합 결과이며 실제 성공률 아님 |
| 원본 먼저/인증 먼저, 원본 8바이트 각각 변조 | 정상 순서 2가지 인수, 변조 입력은 미반영 | 8B 프레임만 처리; 실제 CAN flags·드라이버 미검증 |
| WARNING→CRITICAL 및 WARNING→NORMAL→WARNING | 이전 receipt로 OPEN 불가, 최신 건 확인으로만 OPEN | 상태 변경 세대별 pending 폐기와 counter 결합 확인 |

| 새 컨텍스트로 명시적 재기동 | 구 receipt/구 프레임 거부, 새 상태 인수 | 자동 부팅 탐지·nonce 교환은 시험 코드가 대신했으므로 자동 복구 검증 아님 |

**시험용 가정:** READY 성공·새 키 전달 완료를 시작 조건으로 놓았다. 재시도 간격 10 tick, 총 송신 예산 3회, 동기화 기한 30 tick, 원본/인증 각각 최대 4개·보관 5 tick, 가득 차면 가장 오래 보관한 항목 축출이다. 이는 동작을 실행하기 위한 임시 값/정책이며 승인된 제품 상한이 아니다. 최신 상태는 다음 허용 송신 시각에 보내며 변경마다 무제한 즉시 송신하지 않는다. 하나의 호출 안에서 상태 변경 또는 receipt 처리/송신 허용을 직렬화한다. 실제 스레드 경합과 독립 시계 편차는 미포함이다.

### 승인된 정책과 모형 선택의 구분

- S-13/A의 일반 송신 대기, S-14/A의 최신 건 우선, 이전 확인 거부·전체 기한 연장 금지는 사용자 결정이다. 이번 모형에서 해당 조건의 제한된 실행을 확인했다.
- 저장 용량·만료·축출·송신 간격·예산의 숫자는 아직 선택되지 않았다. 오래된 원본 축출로 정상 입력이 사라지는 과부하 시나리오도 후속 검증 대상이다. 모형 상수를 공식 기본값으로 복사하지 않는다.
- 모형의 상태/사유 검사에는 byte 범위·예약값·사유 존재만 포함된다. 상태별 Reason 조합 전체, HAL 의미, 새 경고 알림 정책의 실제 구현을 검증한 것은 아니다.
- 키 파생은 명시적 테스트 문맥을 사용한다. 같은 소스의 시험 도우미가 두 노드 키를 만들어 주므로 독립 암호 구현 교차 검증으로 계산하지 않는다.

### 다음 실행 단위와 종료 기준

1. READY 이전 CHALLENGE/OFFER/CONFIRM/ACK/READY를 A/B 로컬 상태·타이머·캐시로 분리하여 이 동기화 모형에 연결한다. 공유된 상대 성공 여부를 도입하지 않는다.
2. receipt의 실제 5조각 헤더·순서/중복·충돌·만료·버전/방향/transfer 검증을 연결한다. 상태 인증의 8B 프레임과 handshake 조각을 구분한다.
3. 노드 각각/양측 재부팅과 peer 침묵을 자동 감지→기존 pending 무효화→새 nonce 교환→상태 확인까지 실행한다. 실패 후 backoff·구캐시·새 pending 경합을 포함한다.
4. 일반 BMS/전이/상태의 전역 counter 경쟁, 상태 변경과 receipt의 두 직렬 순서, 큐 상한/카운터 창·소진을 결합한다. 송신 OPEN 이후도 검증하며 READY만으로 전체 완료로 간주하지 않는다.
5. 결과를 통과/실패/미검증 표로 고정한 뒤 필요한 시간·용량·계약/HAL 선택안을 모아 최종 검토한다. 같은 사용자 방향을 다시 묻지 않는다. 자동 재부팅 복구·조각 처리·전체 키 수명 미검증이 남으면 최종 세션 인수를 통과시키지 않는다.

**현재 판정:** READY 이후 상태 동기화의 독립 노드 모형 검토 수행 완료. 전체 프로토콜·제품·실장비 인수는 보류다. 이번 검증으로 새 정책 결정을 추가하지 않았으며 질문리스트의 사용자 답변은 변경하지 않았다.



## 20. RECEIPT CAN 조각 조립 검토 결과

`python tmp/receipt_fragment_review.py` 실행: 시험 8개, 실패 0·오류 0. 결과 `tmp/receipt_fragment_result.json`, 모형 SHA-256 `5ac7933ea1f100ca81f90bc708b0d4dbc0458eaca37e65a3e89168d5408179ff`. §19의 독립 ECU/IVI 모형을 가져와 IVI의 완성된 receipt를 후보 형식의 5개 CAN 프레임으로 나누고, 조립된 결과만 ECU 인증 함수로 전달했다. 실제 키·제품 코드·장비를 사용하지 않았다.

후보 형식은 0x301, DLC=8, header byte0=0x26, index=0~4, transfer ID BE, 데이터 4B다. 확인 본문 20B(counter4+tag16)를 완전히 조립해야 ECU가 검증하며, 부분 조각으로 송신 허용 상태를 바꾸지 않는다. 조립 버퍼는 한 논리 메시지 20B다. 시험용 수명 5 tick은 공식 설정이 아니며, 동일 조각이 들어와도 최초 deadline을 연장하지 않는다.

| 검증 | 관찰 결과 |
|---|---|
| 조각 순서 5! = 120가지 | 완성 전 SYNC 유지, 정상 조립·인증 후 OPEN |
| 조각 하나씩 누락 5가지 | 미완성 유지, 만료 시각의 마지막 조각으로도 완료하지 않음 |
| 잘못된 ID·extended/RTR/error·길이·버전·종류·index·transfer 9가지 | 조립에 반영하지 않음 |
| 본문 20바이트 각각 변조 | 조립될 수 있어도 인증 실패, OPEN 금지 |
| 동일/상충 조각 중복 | 동일 조각으로 기한 연장 없음, 상충 조각은 해당 조립 실패·버퍼 폐기 |
| 동일 transfer의 서로 다른 재시도 receipt 조합 30가지 | 혼합 본문 인증 거부, SYNC 유지 |

모형은 실제 CAN 플래그를 boolean 입력으로 검사한다. 커널 수신 프레임을 읽은 것이 아니며, READY 이전 교환과 자동 reboot/재시도 dispatcher는 여전히 없다. 마지막 항목의 명시적 새 조립기 생성은 자동 회복 증거가 아니다. 시험 통과에는 안전한 거부와 문제 재현이 포함된다.

### 같은 교환 내 여러 receipt의 식별 문제

같은 transfer ID에서 재시도마다 counter가 달라지면 receipt 본문이 달라진다. counter는 본문의 첫 조각 안에 있고 나머지 조각에는 없다. 따라서 조각 순서가 역전되면 헤더만으로 모든 조각의 재시도 소속을 알 수 없다. 최종 HMAC은 혼합 본문을 거부하지만, 그 사실만으로 정상 교환의 진행 가능성이 보장되지는 않는다. 확인된 반례는 이전 첫 조각이 새 조립에 들어가 새 첫 조각과 충돌하는 경우다.

다음 독립 스케줄러는 실패/만료 이후 다음 허용 조립 시각을 노드 로컬 상태로 관리하고, 중복·변조 입력이 그 시각이나 전체 교환 기한을 연장하지 못하게 해야 한다. 아직 조립 재개 정책을 제품 계약으로 확정하지 않는다. 정상 네트워크에서도 재시도/지연 조각만으로 예산 소진이 일어나는지 함께 관측한다.

이를 해결할 후보 비교는 두 방향으로 제한한다. 첫째, 현재 wire 후보를 유지하고 송신 직렬화·확인 캐시·조립 만료/재개·제한된 재시도로 진행 조건을 검증한다. 둘째, 모든 조각에서 확인 시도를 구분할 수 있도록 헤더/식별 방식을 변경하는 영향안을 검토한다. 후자는 헤더·프레임 수·transcript/확인 결합까지 재검토가 필요하므로 임의 적용하지 않는다. 지금은 반례와 필수 검증 조건만 기록하고, 비교 근거를 모은 후 필요한 변경을 묶어 인터뷰한다.

### 미완료 범위의 우선순위

1. READY 이전 A/B 독립 상태·타이머·캐시를 연결한다. 새 교환 ID와 nonce의 로컬 생성·확정 시점을 명시하고 상대 완료를 공유 변수로 읽지 않는다.
2. 실패 조립 재개와 receipt 재전송을 자동화하여 이번 지연 조각 반례와 최초/반복 유실을 실행한다. 정상 회복·제한 내 실패·CPU/메모리/송신 예산을 분리해 보고한다.
3. 한쪽/양측 reboot·침묵 후 자동 새 교환, 구캐시/새 pending, 일반 BMS/전이 counter 경쟁·소진을 결합한다.
4. 그 결과로 시간/자원 상한 및 식별 방식의 구체 변경안을 정리하고 공식 계약/HAL·양측 시험 영향을 검토한다. 실장비 값은 하드웨어 정보를 받은 후 별도 확인한다.

**판정:** receipt 조립과 인증 연결의 제한 모형 검증 수행 완료. 자동 교환·재부팅 복구·실제 CAN 인수는 보류다. 이번 결과로 새로운 CAN 형식·상수를 확정하지 않았다.

### 시험 가정 — 제품 정책으로 채택하지 않음

READY 이전 교환은 CAN 조각이 아닌 완성 논리 메시지를 1 tick 뒤 전달한다. 각 단계 송신 간격 10 tick·최대 3회, 로컬 시도 기한 40 tick, 실패 후 대기 5 tick, 전체 관찰 240 tick이다. 단계 변경·중복 입력은 최초 시도 기한을 늘리지 않는다. B는 로컬 대기가 끝나면 새 CHALLENGE를 시작하고 A는 REQUEST를 송신한다. 이 모형의 REQUEST는 B의 pending을 교체하지 않는다.

READY 캐시는 같은 제한된 시도 안에서 주기적으로 재송신한다. 데이터 단계로 연결하지 않았으므로 B의 READY 이후 캐시도 40 tick 시도 기한에 종료된다. **이 동작을 운영 중인 정상 세션의 주기적 강제 종료 정책으로 사용하면 안 된다.** 실제 후보의 ACK 중복 응답·캐시 수명·세션 활성 전환을 별도로 연결해야 한다.

nonce는 노드별 시험 일련번호/재부팅 횟수로 만든 결정적 더미다. 실제 난수 생성기나 전원 단절 후 nonce 유일성을 검증하지 않았다. transfer ID는 7로 고정하여 새로운 transcript의 인증 분리만 사용했다. ID 할당·재사용·소진 및 구조각 경합은 미검증이다.

receipt 조립 재개는 별도 모형에서 ECU 송신 슬롯 0/10/20 tick에만 수행한다. 외부 입력으로 재개 시각을 옮기거나 전체 기한을 늘리지 않는다. 조립 수명 5 tick, 단일 20B 버퍼다. §20의 수동 재생성 한계는 이 제한 실험에서 자동화했지만, 모든 지연·역전·혼잡에서의 회복을 증명한 것은 아니다. CPU 실행 시간·실제 메모리 사용량·CAN 점유율은 측정하지 않았다.

### 다음 작업과 승인 경계

1. 독립 READY 이전 모형과 §19~20의 STATE/RECEIPT를 하나의 수신 경로로 연결한다. 논리 메시지 전체 전달 가정을 실제 후보 조각 조립으로 바꾸고 READY 캐시의 종료/중복 응답과 세션 활성 전환을 확인한다.
2. 같은 실행에서 최신 상태 변경, 조각 지연/역전, 한쪽 재부팅, 구세션 조각을 주입한다. 일반 BMS·상태 전이의 공유 counter 경쟁/소진도 연결한다. 이 결합 시험 전에는 부분 결과를 전체 세션 통과로 합산하지 않는다.
3. 현재 헤더 유지 시 필요한 캐시·직렬화·기한 조건과 조각별 식별 확장 시 영향을 비교하여, 미확정 정책과 상수만 질문리스트에 모아 인터뷰한다. 시험 가정을 사용자 선택 없이 공식 계약으로 승격하지 않는다.

**현행 판정:** 로컬 타이머에 의한 논리 교환 복구와 receipt 자동 재개 제한 검증은 수행했다. 전체 CAN 세션·제품·실장비 인수 및 6번 전체 정합성 심사는 계속 보류다. 공식 ICD와 승인된 사용자 정책은 변경하지 않았다.

### 결합한 수신 흐름

활성 데이터 상태는 handshake 캐시와 분리했다. 미인증 CHALLENGE로 활성 키/counter를 초기화하지 않고 별도 pending을 시작한다. A의 CONFIRM 인증 성공에서 구세션 송신을 닫고 새 READY 후 동기화를 시작하는 경계는 **비교용 후보**다. 이 정확한 전환 시점·캐시 정책을 이번 검사로 공식 계약으로 확정하지 않는다. 정상 데이터 수명은 기존 시험용 40 tick 캐시 만료에 의해 종료되지 않는다.

| 정상 전체 프레임 경로 | 상태 적용·receipt 이후 일반 BMS 수신, 불필요한 세션 재생성 없음 |
| handshake/receipt 각 조각 및 상태 원본/인증의 첫 유실 | 31개 경우 실행 구간 내 복구·새 BMS 수신. 재시도를 포함하며 실측 성공률이 아님 |
| A/B/양측 재부팅 | tick 1~8/25/60 × 3 = 30개 경우 자동 재교환·새 BMS 수신. 유한한 선택 시점의 시험이며 모든 동시성 증명은 아님 |
| 상태 적용과 receipt 도착 사이 최신 상태 변경 | 이전 확인으로 재개하지 않고 최신 상태 확인 후 재개 |
| 새 세션에 구세션 BMS/전이/현재 상태·receipt 입력 | 수신 counter/반영 건수/현재 상태와 ECU 송신 counter/게이트 보존 |
| 전역 counter 공유·소진 경계 | BMS/전이에 연속 번호 사용, 최대값 사용 뒤 동일 키의 다음 송신 차단. 소진 후 자동 새 세션 전체 경로는 이 경계 검사에 포함하지 않음 |
| 중복 counter·증가량 101 | MAC이 유효해도 수신 기준을 되돌리지 않음 |
| 매 수신 배치를 완전히 역순으로 전달 | 전이는 수용하면서 BMS는 계속 폐기, stale 기반 재교환 반복. 해결되지 않은 진행 가능성 반례 |

조립은 후보 종류별 고정 길이와 방향·버전·index를 검사하되, transfer ID=7/REQUEST=0 고정이다. 10 tick 고정 슬롯에서 자동 재개하는 시험 정책이며 실제 단계별 수신 기산점·ID 할당을 구현하지 않았다. 논리 메시지 최대 32B, 정상 실행의 조립 보관 데이터 상한 단언 A 68B/B 52B, 데이터 후보 목록 최대 24건을 확인했다. 이는 실제 런타임 메모리나 공격 입력 전체의 자원 상한 증명이 아니다.

raw/auth 후보 만료 5 tick·ID당 최대 4건, B의 유효 BMS 미수신 30 tick 후 재교환, 일반 송신 간격 4 tick 등은 모두 시험값이다. BMS와 전이를 매번 함께 생성하는 것은 counter 경합 부하이며 실제 Fail-safe가 매 주기 전이한다는 뜻이 아니다. 실제 CAN arbitration/프레임 직렬화/송신 실패/OS 지연·플래그·C++/Android/HAL·운영 난수원·전체 상태/사유 의미 검증은 미실행이다. 역순 주입은 소프트웨어 지연을 포함한 적대적 수신 순서 조건이며 물리 CAN에서 같은 순서가 필연적이라고 주장하지 않는다.

### S-15 인터뷰가 필요한 이유 — 큰 번호가 먼저 오면 작은 번호가 버려짐

예: BMS 번호 10, 나중에 생성된 전이 번호 11. IVI가 11을 먼저 인증·반영하면 전역 마지막 번호가 11이 된다. 이후 도착한 10은 진짜 메시지여도 현행 엄격 증가 규칙에 따라 폐기된다. 같은 배치 역전이 반복되면 새 전이만 수신하고 배터리 값은 갱신되지 않는다. 인증된 전이 수신으로 BMS stale을 해제해 숨기면 기존 통신/센서 구분 및 BMS 신선도 요구와 충돌한다.

검토 방향 A는 인증된 완성 쌍을 제한된 대기열에 잠깐 모아 counter 순으로 반영하는 방식이다. 대기 상한·빈 번호를 건너뛰는 조건·위험 전이 추가 지연·세션 경계 폐기를 검증해야 한다. 이미 반영한 counter를 뒤로 돌리거나 미인증 값을 화면에 보내는 방식은 아니다. 방향 B는 현행 즉시 반영/늦은 번호 폐기를 유지하고 송신·수신 큐와 정상 BMS 도달 조건을 강화하는 방식이다. B에서는 역전된 개별 BMS의 손실을 허용하되 다음 BMS가 정해진 기한 내 도달함을 별도 입증해야 한다. 아직 어느 방향도 적용하지 않았다.

영향은 ICD 수신 절차·수신 창/timeout 설명, ECU 송신 직렬화, IVI raw/auth 매칭과 HAL 전달 시점, Python 참조/교차 시험, SRS 지연/통신 신선도 및 TEST_PLAN 추적이다. CAN ID·기존 데이터 배치·전역 counter를 새 결정 없이 변경하지 않는다.

### S-16 인터뷰가 필요한 이유 — receipt 조각 식별

§20~21의 같은 transfer에서 이전 receipt 조각이 새 receipt와 섞이는 문제는 독립적으로 남아 있다. 현재 형식 유지와 제한 재시도는 일부 정상 회복을 확인했으나 반복 간섭의 가용성을 보장하지 않는다. 모든 조각에 확인 시도 식별자를 추가하는 방향은 혼합을 더 일찍 걸러낼 수 있지만, 한 프레임의 데이터 공간·프레임 수·인증 결합·ID 재사용 규칙이 달라질 수 있다. 식별 확장도 공격자가 버스를 점유하는 상황을 해결하지 않는다.

두 방향의 선택·구체 시간/자원 값과 운영 전환/HAL 계약은 질문리스트와 후속 영향안에서 처리한다. **현재 결론:** 전체 후보 프레임 경로의 제한 검토는 수행했으며, counter 역전 반례와 receipt 식별/재시도 정책이 남아 세션 상세 인수는 보류다. Plan 융합·재검사는 사용자 지시에 따라 이번 작업에 포함하지 않는다.

질문리스트의 사용자 답변은 두 항목 모두 A, 추가 조건 없음이다. S-15는 인증된 데이터를 제한된 시간/개수의 대기열에서 counter 순서로 반영하는 방향, S-16은 현재 receipt 조각 형식과 제한된 조립 폐기·재개·재시도를 유지하는 방향이다. 아래는 선택 방향을 구체화한 검토이며 미정 숫자·포화 처리·정확한 운영 전환까지 승인됐다는 뜻은 아니다.

### 수신 절차 후보와 시간의 의미

1. 원본/인증을 제한된 pending에서 MAC으로 결합하고 형식·counter 창을 검증한다. 인증된 완성 쌍만 정렬 큐에 넣는다. 원본이나 MAC 실패만으로 HAL/UI·counter를 바꾸지 않는다.
2. 시험에서는 최초 입장부터 2 tick, 최대 8건이다. 같은 counter가 다시 오면 기한을 갱신하지 않는다. 포화 시 신규 건을 거부하는 조건으로 시험했다. 같은 counter의 상충된 유효 쌍·포화 시 위험 전이 보존은 별도 정책/시험 대상으로 남긴다.
3. batch 기한에 counter 오름차순으로 반영한다. 각 건의 반영 직전에 마지막 반영 counter와 증가량을 다시 검사한다. 누락 번호를 무한히 기다리지 않으며 이미 반영한 번호를 되돌리지 않는다. 기한 이후 더 작은 번호가 오는 경우의 손실은 여전히 가능하다.
4. STATE receipt는 정렬 큐 입장이 아닌 **현재 상태 반영 후** 생성한다. 세션 교체/재부팅에서 구세션의 미반영 큐·수신 pending을 폐기한다. 현재 상태 확인과 일반 송신 게이트는 S-13/S-14를 유지한다.
5. 정상 BMS 인증 쌍의 수신 시각과 정렬 후 반영 시각을 분리한다. 모형도 정렬 flush 시각으로 수신 시각을 새로 쓰지 않는다. 중복·전이 메시지 수신으로 BMS 통신 신선도를 연장하지 않는다. 센서 오류/정상 품질 판정과 통신 수신은 기존 구분을 따른다.

2 tick을 2ms나 공식 대기 상한으로 변환하지 않는다. 정렬 대기 시간은 CAN 수신→UI 반영 구간에 포함된다. NFR-PERF-001/TC-PERF-001의 평균 50ms 이하·최대 100ms 이하를 완화하거나 타이머 시작을 정렬 이후로 옮겨서는 안 된다. 수신·인증 완료·큐 입장·반영·HAL·UI 시각을 따로 수집하고 전체 원래 구간을 판정한다. 기존 UI 보간/장식 지연 금지와 함께 적용한다.

### 남은 구체화와 종료 조건

이제 S-15/S-16의 큰 방향은 다시 묻지 않는다. 남은 것은 (a) 정렬/조립/교환/캐시 기한·용량의 근거, (b) 포화와 상충된 인증 입력·위험 전이의 처리, (c) 활성/후보 세션 전환·HAL 현재 상태/이벤트 매핑, (d) 모든 후보 ID/형식과 공식 전환 영향의 확정이다. 상수는 대상으로 삼을 OS·장비와 부하 조건의 근거 없이 채우지 않는다. 필요한 선택은 수치·영향·한계를 구체화한 뒤 인터뷰하며 빈 추가 조건으로 승인받았다고 하지 않는다.

**판정:** 답변 반영·기존 counter 역순 반례의 제한 재검증·계약 영향표 작성 완료. 제품/실장비·전체 계약 인수와 네 기준 최종 심사는 계속 보류다. Plan 융합·재검사는 제외 범위를 유지한다.



## 24. 큐 예외 정책과 운영 수치 확정 절차

S-15=A 정렬과 S-16=A 기존 receipt 형식은 유지한다. 이번 검토는 §23에서 명시적으로 남긴 큐 포화·상충 입력을 구체화하고, 운영 수치를 임시 tick과 분리하는 단계다. 공식 ICD·제품 소스는 변경하지 않는다.

### 미확정 시험 정책의 결과 재현

### S-17 — 포화에서 위험 전이를 다루는 후보

A: 총 큐 용량 안에서 전이/현재 상태 동기화용 공간을 예약한다. BMS는 일반 구역 한도를 넘겨 점유하지 못한다. 예약은 **저장 공간의 구분**이며 반영 순서는 여전히 전역 counter 순서다. 위험 상태 구역까지 차면 조용히 정상 처리하지 않고 수신 실패 표시·제한 재동기화로 전환하는 후보로 검토한다. 예약량·일반 데이터 포화 처리·늦은 번호/누락과의 결합은 선택 후 구체화한다.

B: 구역을 나누지 않고 인증 정렬 큐가 넘치면 해당 수신 세션을 실패로 처리한다. 미반영 큐를 폐기하고 현재 값/경고를 보존한 채 통신 실패 표시·제한 재동기화로 전환하는 후보로 검토한다. 모든 과부하를 실패로 드러내기 쉽지만 일시적 BMS 집중에도 새 값 표시가 중단될 수 있다.

둘 다 ECU 로컬 Fail-safe를 바꾸지 않으며 미수신 위험 상태를 알았다고 표시하지 않는다. 인증된 통신 실패 표시와 실제 배터리 SHUTDOWN 판단을 구분한다. 총 자원 상한·반복 실패 backoff는 필요하며 무한 큐나 무한 즉시 재시도는 후보가 아니다. 사용자 선택 전 제품 정책으로 적용하지 않는다.

### S-18 — 같은 번호의 인증된 상충 본문 후보

여기서 비교 대상은 **아직 반영 전 정렬 큐에 있는 동일 세션·counter**다. 동일 ID·동일 본문은 일반 중복 처리한다. ID 또는 본문이 다른데 각 MAC이 유효한 경우만 상충이다. 이미 반영한 과거 번호는 기존 재생 거부를 따르며 이를 비교하려고 무제한 과거 본문을 저장하지 않는다.

A: 상충을 발견하면 해당 수신 세션을 불일치 실패로 처리하고 미반영 큐를 폐기한다. 기존 표시값/경고를 유지하면서 오류·제한 재동기화를 수행한다. 새 세션이 된 사실만으로 장기 키 노출이 해결됐다고 하지 않는다.

B: 먼저 대기열에 들어온 건을 유지하고 뒤의 상충 건을 거부·진단 기록한다. 통신은 이어가지만 먼저 온 본문이 올바르다고 판별한 것은 아니다. 동일 counter에 정상 상태와 위험 상태가 엇갈리면 도착 순서에 따른 결과를 감수해야 한다.

영향은 IVI 인증 큐·실패 표시/재동기화·진단, ECU 송신 직렬화와 번호 유일성, Python 참조, TC-SEC-003/TC-INT-002/003 및 TARA 원인 분석이다. 오류 표시를 위해 CAN Reason 코드나 HAL API를 이번에 신설하지 않는다. 표시 전달 경로의 상세 변경은 공식 영향안에서 검토한다.

### 세션 전환 시점 — S-19 후보

### HAL의 사유 부재 표현 — S-20 후보

현재 ICD의 `VehicleData.failSafeReason`에는 사유 존재 여부가 명시돼 있지 않다. 새 상태 후보 0x104에는 사유 존재 byte가 있으므로 HAL에서도 이를 잃지 않아야 한다. 다음은 전환안이며 현재 ICD를 임의 변경하지 않는다.

A: 기존 HAL `failSafeReason=0`을 ‘현재 상태의 사유 정보 없음’으로 정의하고 존재 시 기존 1~7을 전달한다. 이는 HAL 해석 확장이며 **기존 0x101 Reason=0을 허용하는 변경이 아니다.** B: HAL 끝에 별도 `bool failSafeReasonPresent`를 추가하여 유무를 표시하고, false일 때 reason은 해석하지 않는다. B는 생성 인터페이스·직렬화/Parcelable·Mock의 추가 필드 전환이 필요하다. 승인된 stale/sensorState 필드와 같은 전환 단위로 비교한다.

현재 상태 동기화는 기존 데이터 snapshot 콜백으로 현재 상태를 갱신하고 가짜 `onFailSafeTransition` 사건을 만들지 않는 계획으로 연결한다. 실제 인증 전이만 기존 전이 콜백을 사용한다. 최초 BMS 수신 전 숫자들은 미수신/품질 미확정 표시를 유지하고 사유 없음에서 배터리 정상이나 센서 정상을 추정하지 않는다. snapshot 반영 뒤 receipt 생성 원칙은 유지한다. 후보 필드/API의 공식 반영은 선택과 계약 영향 검토 후 수행한다.

후보 CAN ID/버전/조각·키 파생·HAL 확장과 시간/자원 값은 계획 검토 산출물이다. S-19/S-20 선택 및 장비별 ID 충돌·운영 수치 근거를 확인한 뒤 명시적인 상세 계약 전환 단위로 검토한다. 제품 C++·Python·IVI 및 시험이 현재 계약을 사용하는 동안 계획만으로 호환 구현이 있다고 표시하지 않는다. 위험 점수나 실제 성능 합격을 모형 결과로 채우지 않는다.


## 26. S-19=A·S-20=A 확정 방향과 인수 조건

사용자 서면 답변은 두 항목 모두 A이며 추가 조건은 없다. §25의 A/B 비교는 검토 이력이고 현행 선택은 이 절이다.

- ECU: 새 CONFIRM 인증 성공 시 구세션 일반 인증 송신을 닫고 미전송 구세션 큐를 폐기한다. ACK→READY→최신 STATE의 인증 RECEIPT 완료 전 새 일반 BMS를 보내지 않는다. 로컬 계산은 계속하며 실패해도 이전 키/counter로 돌아가지 않는다.
- IVI: HAL failSafeReason=0은 사유 정보 없음, 1~7은 기존 사유를 뜻하는 목표 해석으로 선택했다. 별도 존재 여부 필드는 추가하지 않는다. 기존 CAN 0x101의 Reason=0 허용으로 확대하지 않는다.
- 현재 상태 snapshot 갱신은 새 전이 사건을 만들지 않으며 사유 없음에서 정상 상태를 추론하지 않는다. 최초 BMS 미수신·센서 품질 표시는 독립적으로 유지한다.

검증 과제: 위조 CONFIRM에는 구세션 유지, 정상 CONFIRM 직후 송신 차단, READY 유실·지연, 최신 receipt 전 차단, 구세션 큐 잔류/커널에 이미 제출된 프레임과 새 세션 경합, 실패 후 counter 재사용 금지를 시험한다. HAL은 사유 없음과 1~7, 미수신/오류 상태 동시 표시, 가짜 전이 콜백 부재를 시험한다.

기존 결합 모형의 CONFIRM→READY 경계에서 active를 닫는 구현은 선택과 일치한다. 실제 송신 큐/커널 drain과 Android HAL/UI는 모형에 없으므로 검증 완료가 아니다. ICD·양측 SDD·SRS·시험·제품 코드의 상세 전환 단위는 미완료이며 후보 CAN 형식·운영 상수 전체를 이번 답변으로 승인했다고 보지 않는다.

## 27. 세션 상세 계약 전환 영향과 적용 순서

이 절은 현행 ICD를 변경하는 승인이 아니라 전환 검토 목록이다. §3~5의 버전 1·ACK 직후 일반 송신·초기 1초/3회/5초 설정은 최초 후보 이력이다. 현행 검토 대상은 §13의 v2와 §15~26의 사용자 선택을 결합한 후보이며 초기 후보의 숫자·벡터를 그대로 운영 설정으로 쓰지 않는다.

### 후보 형식의 읽기 순서와 정적 개수

- REQUEST~READY 헤더·transcript는 버전 2를 함께 사용한다. §4의 v1 더미 태그는 v2 교차 벡터가 아니다.
- §13: CHALLENGE 4 + OFFER 8 + CONFIRM 4 + ACK 4 + READY 4 = 24프레임(REQUEST 제외).
- §15: STATE 원본/인증 2 + RECEIPT 5를 더하면 최초 상태 동기화까지 31프레임이다. REQUEST가 있으면 32프레임이며 재시도·일반 BMS·CAN 재전송은 제외한 정적 합계다. 실제 지연이나 성공률이 아니다.
- 후보 ID 네 개(0x104/105/300/301)는 현행 ICD 할당표에 없다. 제품과 실제 USB-CAN 주입 설정·버스 로그의 충돌 검사는 따로 수행한다.

### 전환 작업 순서와 멈춤 조건

1. 계획 단계: 사용자 결정·후보·현행 계약의 차이를 이 표에서 검토한다. 모호한 동작은 인터뷰하고 아직 없는 수치는 §24의 측정 과제로 관리한다.
2. 상세 승인 준비: CAN ID/헤더/모든 논리 본문·transcript·counter·HAL 해석·오류 처리를 하나의 변경안으로 제출한다. I-1=B의 교차 벡터/상태 검증·대상 지원 증거를 제시하며 부족하면 최종 계약 승인을 요청하지 않는다.
3. 승인 후 공식 문서 전환: ICD를 먼저 갱신하고 SRS·양측 SDD·TEST_PLAN·ADR·TARA의 같은 의미를 동기화한다. 현재 문서의 수정만으로 제품 호환성을 주장하지 않는다.
4. 구현 전환: ECU/C++·Python 참조·IVI 코어/HAL·Mock·IDS/측정 도구를 같은 계약 버전으로 준비한다. 실제 파일이 없는 IVI는 신규 구현 과제다.
5. 검증·배포: 독립 벡터→상태/조립 단위시험→vcan→실장비→양측 동시 배포 순서로 인수한다. Android 정보가 없으면 대상 빌드/권한 단계는 착수 보류한다.

**현재 미완료:** 상세 형식의 최종 승인, S-22=A 포화의 실장비 인수, 시간/큐 수치, 커널 송신 경계, 독립 C++/IVI 벡터, Android 후보 빌드와 실제 버스 검증. Android 환경 인터뷰는 종료됐고 서버 주 빌드 배치는 확정됐다. 현재 소스의 unsigned delta와 ICD의 단순 증가 표현 차이도 전환 시 명시적으로 해소한다. 계획 검토를 위해 현행 ICD·제품 소스를 조용히 수정하지 않는다.

## 28. S-22=A 및 운영 수치 인수 관리

최신 승인 범위와 남은 증거는 §29를 함께 따른다.

### S-22=A 일반 BMS 구역 포화 처리

사용자 답변 A, 추가 조건 없음. 일반 BMS 구역만 차면 기존 대기 건을 유지하고 신규 BMS를 거부하며 진단에 남긴다. 위험 메시지 예약 공간을 빌려 쓰거나 해당 포화만으로 즉시 재연결하지 않는다. 기존 counter 순서·윈도우·통신 timeout·실패/복구 조건은 유지한다. 거부된 값을 화면의 새 정상 측정값으로 표시하지 않는다. 지속 누락으로 정상 인수가 불가능하면 기존 실패/복구 규칙을 적용한다. S-17의 위험 구역 포화와 S-18의 인증 상충은 세션 실패 정책을 유지한다.

일반 구역 6건·위험 2건은 모형 값이며 운영 용량 승인으로 확대하지 않는다. 인수 시험은 일반 구역 경계 전/정각/초과, 반복 포화 후 정상 수신 회복, 위험 메시지 보존, counter 공백과 timeout, 미반영 값/UI 시각 및 진단 누락을 포함한다. 모형 검증은 실제 UI·커널·SPI 지연 인수를 대신하지 않는다.

### 수치 승인에 필요한 증적 — §24 측정 목록의 수행 기준
