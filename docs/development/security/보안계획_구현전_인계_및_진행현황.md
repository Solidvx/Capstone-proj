# 보안 계획 구현 전 인계·진행 현황

> **현행 계획 편입 완료 — 2026-09-09:** [현행 공동 인계](../../../plan/detail/common/01_연계_의존성.md#security-integration)에 따라 ECU/IVI 상위 및 상세·공동 계획 18개 문서에 최신 실행 조건을 실제 편입했다. 계획 문서 정돈은 완료했으며 제품 구현·시험은 수행하지 않았다.

> **최종 범위·판정:** [§11 계획·설계 마감](#planning-complete)이 최신 진행 기준이다. 이전의 장비·운영값 미확정은 실행 인수 조건이며 이번 문서 설계 완료의 대기 사유가 아니다. 제품 구현은 진행하지 않았다.

기준일: 2026-09-09. 범위: 원자료 보안 방식 차용 및 Q2 인증 이벤트 전달의 **실제 기능 구현 이전 준비**.

## 1. 판정

**현재 환경에서 가능한 설계·수행 계획·모형 검증·인계 자료 정리는 마쳤다. 실제 장비 적용 가능성, 운영값, 상세 계약의 확정은 미완료이므로 ‘구현 착수 조건 전체 충족’으로 판정하지 않는다.** 제품 기능 구현은 시작하지 않았다.

이 문서는 기존 자료를 반복 확장하기 위한 계획이 아니라 다음 담당자가 읽을 최종 인계 색인과 미결 목록이다. 구현 이전에 실측 불가능한 성능은 구현 이후 파일럿에서 확정하도록 구분했다. 모든 실측이 있어야 첫 코드를 작성할 수 있다는 순환 의존은 만들지 않는다.

## 4. 과제별 구현 인계

아래 P 번호는 이 문서의 작업 묶음 색인이며 새 공식 FR/TC 또는 별도 단계가 아니다. 기존 M3~M6와 공동 인수를 유지한다.

| 묶음 | 기존 단계/담당 | 입력→출력 | 실패·인수 조건 |
|---|---|---|---|
| P1: N01 보안 시작 | ECU M3 + IVI M3/M4 | 실제 실행 설정·키 로드 결과→양측 보안 활성 증거 | 일반 경로 key/config 오류는 실패, C0는 명시적 우회. OFF를 성공으로 표시하지 않음 |
| P2: N02 입력 계보 | ECU M3/M4 | profile/source_mode·hash·seed·단위→정상/결함/공격을 구분한 입력과 라벨 | drift/jump/freeze/plausibility 보완, 정상 고정값과 freeze 공격 구분 |
| P3: N03 IDS 근거 | ECU M4 | raw/Rule/Spec/필수 IF·인증 진단→개별 Findings | source·reason·expected/observed·unit·rule/model version, 없는 IF 기여도 생성 금지 |
| P4: N04/N05·Q1 공격 도구 | ECU M4 + 공동 시험 | 허용 대상/상한/격리 확인→정상 실행·실제 주입·복구 기록 | 사전 거부는 송신 0건. A5 sender 중단, A6 중단 후 위장, 예외 시 재개 결과 확인 |
| P5: Q2·Q4 수신/전달 | IVI M3 + ECU M4 | 기존 verifier 결과→worker→collector→IDS 진단 | Q4 pending 보존. 양측 인증·연결/순번·유한 큐·장애 격리, UI/ECU 안전 비차단 |

| P7: N08 증거 설명 | ECU M6 + 공동 발표 | 원자료→방법→실제 모듈→시험→증거 | 목표/실측/외부 결과 구분, 무결성·freshness를 CAN 암호화로 표현하지 않음 |

### 현재 소스에서 주의할 차이

[ECU main](../../../adaptive_ecu/main.cpp)의 secoc_enabled 기본값은 false이며 --secoc on일 때 활성화된다. 일반 실행/배포에서 명시적 ON을 인수한다는 N01 계획과 기본 동작을 구분한다. 이번 작업은 기본값을 수정하지 않았다. 인자 값 검증과 양측 키 오류 동작은 구현 시 함께 검토한다.

[traffic_gen.py](../../../security/attacks/traffic_gen.py)는 라벨이 있는 합성 트래픽 생성기다. 이를 실제 CAN 공격 CLI·중단/복구 도구가 구현됐다는 근거로 쓰지 않는다. 온라인 진입점과 alerter도 실제 파일/호출 관계를 확인해 하나로 정하고 예정 이름을 중복 구현하지 않는다.

P1~P4·P6/P7의 상세 절차는 각각 [ECU M3](../../../plan/detail/ecu/M3_EKF_Failsafe_SecOC.md#security-adoption), [ECU M4](../../../plan/detail/ecu/M4_IDS_공격_물리통합.md#security-adoption), [ECU M5](../../../plan/detail/ecu/M5_Ablation.md#security-adoption), [발표·제출](../../../plan/detail/common/03_발표_제출.md#security-adoption)에 이미 있다. 제품 실행 결과는 아직 채우지 않았다.

## 5. 구현 순서와 의존성

1. 대상 profile·실제 실행 환경·주 진입점을 확정하고 기존 공식 계약의 적용 버전을 인계한다.
2. P1/P2의 설정·계보와 P3/P4의 로컬 입력/사전 거부/복구 조건을 구현한다. Q2 장비가 없어도 이 부분은 후속 구현 지시 후 독립 수행 가능하다.
3. P5는 후보 2의 message validator·Node B producer·Node A receiver·IDS consumer 순으로 단위 시험을 작성한다. 제품 parser는 문서 모형을 그대로 복사하지 않는다.
4. 유한 큐·부팅/종료·worker 세대 전환·TLS/권한을 연결한다. 테스트 범위 설정과 운영 설정을 분리한다.
5. [공동 통합시험](../../../plan/detail/common/02_통합시험.md#security-adoption)에 따라 실제 verifier→IDS 소비와 기존 CAN/UI 회귀를 확인한다.
6. 운영 파일럿 후 설정을 고정하고 P6 공식 평가를 수행한다. P7에 동일 run 증거를 인계한다.

이 목록은 착수 후 작업 순서이며 이번에 실행한 단계가 아니다. 모델/threshold calibration과 최종 평가 입력을 분리하고 결과를 보고 수치를 다시 조정하지 않는다.

## 6. 설정 확정 기록 — 값과 근거를 함께 작성

빈칸은 승인/기본값이 아니며 미확정이다. 실제 주소·키는 이 표 대신 비공개 배포 설정으로 관리하고 본 문서에는 식별용 설정 버전/증거 위치만 남긴다.

| 설정 | 구현 전 정할 내용 | 구현 후 파일럿에서 정할 내용 | 현재 값/근거 |
|---|---|---|---|
| profile·schema revision | 해석할 CAN 계약·후보 2 채택 여부·호환 거부 | 적용 빌드 회귀 확인 | 미확정 |
| TLS/신원 정책 | 양측 인증·허용 peer 매핑·인증서 배포/갱신·0-RTT 미사용 후보 | 대상 플랫폼 handshake/키 권한·재시작 | 미검증 |
| 메시지/문자열 상한 | schema 최대 정상 메시지와 거부 정책을 기준으로 테스트 설정 작성 | 실제 메모리/CPU·버스트·악성 길이 거부 확인 | 모형 limits만 존재, 운영값 없음 |
| producer/receiver/FIFO 큐 | 모든 대기 단계의 소유자·상한·포화 정책 | 실제 생성/소비량·지연·drop 기반 용량 | 미확정 |
| source/consumer age | 각 노드 시계·정각 의미·expired 처리 | 실제 분포와 기존 성능 기준 내 허용값 | 미확정 |
| heartbeat/status/준비/read 기한 | 기산·종료 조건·부분 read의 전체 기한 | 느린 peer·정상 부하·재시작 측정 | 미확정 |
| 재연결 | 간격/최대 시도·동시 연결·복구/실패 표시 | 실제 단절 조건과 CPU/로그량 측정 | 미확정 |
| attack rate/duration | 격리·사전 거부·정상 sender 제어 범위 | 공식 flood 강도와 버스 조건 양립 확인 | 미확정 |
| A5/A6·진단 임계 | 사건 정의·분모·calibration/평가 분리 | pilot 반복/강도·진단 임계 결정 | 미확정 |
| 자원/시간 계측 | 원본 필드·단위·시계·측정 종료점 | 관측값·측정 오버헤드 | 미실측 |

확정 기록 양식: **대상 / 선택값·단위 / 근거 run·환경 / 정상·경계·초과 결과 / 담당 / 합의일 / 적용 버전 / 미검증 한계**.

## 7. 장비 적용 가능성 확인 인계

| 담당 | 확인 순서 | 제출할 증거 | 실패 시 처리 |
|---|---|---|---|
| ECU | 대상 Ubuntu/Python/OpenSSL 버전과 TLS 1.3 지원, 제한된 listener·키 읽기 권한 | 버전·허용 정책·비밀 제외 로그 | 로컬 Windows 결과로 대체하지 않음 |
| IVI | 고정 Linux 이미지·Qt/OpenSSL 버전·TLS 링크 가능성·대상 서비스 계정의 소켓/파일 권한 | 최소 빌드 로그·허용/거부 접근 결과 | 적용된 OS 접근 통제/인증 검증을 끄지 않음 |
| 공동 | 양측 유선 연결과 상호 인증, 잘못된 peer/인증서 차단 | 정상/거부 handshake·재시작·시계 준비 기록 | 평문 자동 전환 금지, 수단 재검토 |
| 공동 | 인증서 유효기간/갱신·분실·권한 오류 | 재현 절차·상태/복구 결과 | 실제 키·장비 주소는 공개 로그에서 제외 |

위 확인은 제품 IDS를 만들지 않고 플랫폼의 최소 가능성 시험으로 먼저 수행할 수 있다. 현재 세션에는 실행 가능한 장비 연결이 없어 수행하지 않았다. 장비 보유 여부나 서버 사양 답변을 다시 요구하지 않고 실행 담당의 실제 결과를 기다리는 항목이다.

## 8. 구현 전 리뷰에서 남겨둘 주의점

- q2_validation은 제한 모형이다. 소비 결과 리스트·직렬 함수·신원 stub을 제품의 유한 로그/스레드/TLS 보장으로 간주하지 않는다.
- 같은 event/state 형식 검사는 준비됐지만 실제 양방향 stream, Node B 상태 머신, 큐/송신 FIFO 동시성은 아직 구현·시험 대상이다.
- producer ready 경계에서 이전 worker의 세대 검사와 offer 원장 갱신은 하나의 정의된 순서로 처리해야 한다. snapshot/FIFO 순서를 바꾸는 최적화는 새 반례 검증이 필요하다.
- 같은 producer_epoch에서 profile/verifier 변경을 단순 새 연결로 숨기지 않도록 제품 정책을 정한다. 설정 변경 시 새 epoch를 권장하고 마지막 기억값만 있는 모형의 장기 재생 방지 한계를 보존한다.
- 인증된 Node B의 악의적 고순번/허위 status는 endpoint 신뢰 문제다. TLS와 형식 검사가 내용의 진실을 보증하지 않는다.
- event 결과 발생 전과 발생 후의 장비 오류, source age 초과와 연결 프로토콜 오류를 제품 reason/복구 정책에서 구분한다. 임의 새 HAL reason이나 0x200 공격 타입을 추가하지 않는다.

이 목록은 아직 재현하지 않은 제품 결함 보고가 아니라 구현 리뷰의 필수 확인 사항이다.

## 9. 상세 계약 검토 묶음

후보 채택 때 한 번에 검토할 대상:

| 대상 | 제시한 후보 | 변경 범위/승계 조건 |
|---|---|---|
| 통신 수단 | 별도 유선 IP + 상호 TLS | CAN ID·DLC·방향 변경 없음. 별도 진단 계약 위치 확정 |
| 메시지 | 후보 2의 5종, 11개 집계 필드 | 실제 profile·운영값·동시성 정책과 함께 버전 고정 |
| IDS | 기존 raw/필수 IF 유지, 인증 진단 별도 소비 | 새 IF 특징/공격 타입/UI 계약 자동 추가 없음 |
| 신뢰/장애 | endpoint 인증·순번/epoch·유한 큐·가용성 분리 | TARA에 endpoint 침해·망 가용성·인증서 잔여 위험 반영 |
| 공식 문서 | ICD·SRS·양측 SDD·ADR·TARA·TEST_PLAN 영향 | 승인된 범위만 동기화, 기존 Q1~Q4 답변 재질문 없음 |

현재는 검토할 후보가 준비됐다는 상태다. 공식 인터페이스 전환은 AGENTS의 HARD RULES·Default Workflow에 따라 상세 영향과 승인 후 처리한다. 이번 요청의 구현 전 종료 경계를 넘어 제품 변경이나 공식 계약 채택을 수행하지 않는다.

## 11. 사용자 범위 확정 후 계획·설계 최종 마감

사용자가 원하는 종료 범위는 **제품 구현·장비 시험 없이 구현 전 계획·설계를 완성하는 것**이다. 따라서 §1·2·10의 ‘장비 증거/운영값/계약 채택 미완료’는 계획 미완료 사유가 아니라 실행 착수·배포 인수 조건으로 분류한다. 그 조건이 실제로 충족됐다는 뜻은 아니다.

### 11.1 계획의 기준과 문서 읽는 순서

1. 공식 계약·요구·시험은 기존 ICD/SRS/SDD/TEST_PLAN을 우선한다.
2. [공동 선택 기준](../../../plan/detail/common/00_협업_규약.md#security-adoption)은 Q1~Q4 선택과 현행 적용·제외 범위를 관리한다.
3. 기존 ECU/IVI/공동 계획은 담당별 실행 과제와 증거를 관리한다.
4. 본 문서는 전체 보안 계획의 인계·진행 상태 정본이다.
5. Q2 상세는 [메시지·상태 규약 §10](인증이벤트_메시지_상태규약.md#planning-final)의 실행 정책을 포함해 읽는다. 전달 설계안→최초 모형→후보 2는 발전 이력이고, 앞 문서의 단순 요약으로 최신 규칙을 덮어쓰지 않는다.

새 통신은 **유선 IP+상호 TLS를 계획상 우선 적용안**으로 둔다. 적용 가능성 시험 실패 시 근거와 영향으로 대안을 검토하며 추가 CAN 메시지·평문·사후 로그 방식으로 자동 전환하지 않는다. 실시간 전달 Q2=B를 포기하려면 별도의 범위 판단이 필요하다.

### 11.2 실측값을 비워 두어도 실행 가능한 확정 절차

| 항목 | 결정 절차 | 담당·시점·실패 시 조치 |
|---|---|---|
| 메시지·문자열 상한 | 허용 필드의 최대 길이로 최대 정상 encoding 크기를 계산하고 bounded parser 거부값과 함께 설정 | 양측, parser 구현 착수. 정상 최대 메시지를 담지 못하면 구조/예산 재검토 |
| 큐 용량·bytes | 허용 메모리 예산과 최악 정상 이벤트 크기로 상한을 산출. 관찰 생성률×허용 대기 동안의 건수와 비교 | 양측, 첫 통합 파일럿 전 후보 고정. 양립 불가면 요약/부하 정책 재검토 |
| status·read/write·재연결 기한 | 기산점·정각 정책을 규약대로 적용하고 설정으로 주입. 정상 부하와 느린 peer 양쪽 측정 | 양측, 통합 파일럿 후 운영 확정. 미달 시 기준을 낮추지 않고 병목/운용 범위 수정 |
| 독립 timer·Rule/진단 임계 | ICD에서 직접 정해진 기준은 그대로 사용. 신규 기준만 정상 calibration과 결함/공격 파일럿으로 결정 | ECU, 최종 평가 전에 고정. 정상 profile 변화는 별도 버전으로 관리 |
| A5/A6 반복·강도 | 실제 중단/복구가 재현되는지 pilot 확인 후 반복/강도·기대값·실험 시간 산정 | ECU+공동, 공식 평가 전. 기본 1,200 시행과 대체/합산 금지 |
| 지연·CPU/RSS·모델 크기 | 측정 지점·단위·분모를 먼저 고정하고 동일 run 원본으로 계산 | 양측 M5. 미계측은 N/A+사유, 외부 수치를 채우지 않음 |

위 계산은 설정 산출 절차이며 수치 성능을 예측한 것이 아니다. 단위/호스트 시험의 가상 limits와 운영 파일럿 설정은 다른 profile로 둔다. 운영 profile은 필수값 누락·비양수·상호 모순이면 시작을 거부하고 더미 limits로 조용히 대체하지 않는다.

### 11.3 IDS·공격·평가 계획의 최종 경계

- IF는 기존 raw 특징과 필수 인수를 유지한다. Q2는 최초에는 별도 인증 진단 채널로 소비하며 IF 특징 확장/재학습을 필수로 추가하지 않는다.
- 개별 검출 결과와 결합 판정은 별도 출력한다. 결합 논리는 calibration 단계에서 문서화·동결하고 시험 데이터로 최적화하지 않는다. 미지원 진단을 기존 0x200 type에 억지로 매핑하지 않는다.
- 진단 채널이 없으면 정상 인증으로 가정하지 않는다. raw 도착, 인증된 유효 수신, IDS 판단, 안전 전이, UI 표시를 각각 기록한다.
- 공격 도구는 구성 검증→허용 대상/격리 확인→송신 준비→실제 주입→중지→sender 재개 확인 순으로 수행한다. 오류는 finally 성격의 복구 경로로 모으되 재개 시도와 재개 성공을 분리한다. 물리 상태가 불명확하면 다음 시행을 시작하지 않는다.
- 데이터 인계의 공통 키는 run/trial/profile/source_mode·입력/설정/모델 hash와 시계 정의다. Findings는 그 키와 규칙/모델 버전·기대/관측·단위·사유를 참조한다. 키/원본 MAC/불필요한 payload를 새 진단에 넣지 않는다.
- 공식 평가·정상 FPR·보조 A5/A6·결함 입력 시험을 분리한다. INVALID 재수집은 원장에 남기고 미탐을 INVALID로 제외하지 않는다.
- 제출에서는 원자료→방법→실제 모듈→시험→증거를 연결한다. 아직 없는 모듈은 예정, 검증하지 않은 항목은 미검증으로 표시한다.

### 11.4 계획 완료 심사표

| 검토 항목 | 결론 | 근거 |
|---|---|---|
| 원자료 우선순위·추적 | 정리 완료 | 발표자료 우선 대조 이력. 현행 적용·제외 범위와 담당은 [공동 규약](../../../plan/detail/common/00_협업_규약.md#security-adoption)과 [과제 매핑](../../../plan/detail/common/01_연계_의존성.md#security-adoption) 참조 |
| 사용자 선택 | 반영 완료 | Q1=A·Q2=B·Q3=A·Q4=A 원문 보존 |
| 현행 구조·계약 보존 | 반영 완료 | 기존 단계·Node A IDS·필수 IF·CAN/HAL 계약 유지 |
| 담당·순서·인계·인수 | 정리 완료 | P1~P7 및 기존 단계별 추가 조건 |
| Q2 메시지·양측 상태·장애 처리 | 설계안 정리 완료 | 후보 2 + §10 Node B/큐/FIFO/기한 보완 |
| 실측 미정값 | 결정 절차 정리 완료 | 담당·시점·근거·실패 처리 정의, 값은 실행 때 기록 |
| 검증·한계 | 구분 완료 | 기존 18/12 모형 결과와 미실행 제품 인수 시나리오 분리 |

| 코드·실장비 작업 | 이번 범위에서 제외 | 제품 변경·네트워크 배포·장비 시험 미수행 |

**최종 판정: 요청된 보안 방식 차용과 Q2의 구현 전 계획·설계 문서 작업을 마감한다.** 무결점 보장이나 전체 프로젝트 구현 완료 선언은 아니다. 이후 실제 환경에서 반례·제약이 발견되면 변경 근거와 영향받는 계약·시험을 함께 갱신한다. 다음 단계는 사용자 구현 지시가 있을 때 실행하며, 현재 남은 항목은 위에 명시한 실행·검증·채택 절차다.
