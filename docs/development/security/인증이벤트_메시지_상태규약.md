## 1. 이번에 완성한 범위

[전달 설계안](인증이벤트_전달_설계안.md)의 통신 후보를 바탕으로 hello/challenge/ready/event/status **5종 메시지의 필수 필드·타입·의미**, 연결 단계, 순번·누적 집계·유실 처리를 정리했다. [사전검증](인증이벤트_전달_설계안.md#delivery-precheck)의 부분 event 모형에서 한 단계 확장한 검토용 규약이다.

[필드 명세](../q2_validation/protocol_schema.json)와 [메시지 예시 5개](../q2_validation/protocol_fixtures.json)를 양측이 같은 의미로 읽는 공통 자료로 둔다. 필드 명세 JSON은 이 검증 도구가 사용하는 간단한 타입 표이며 표준 JSON Schema 문법이라고 주장하지 않는다. [독립 모형](../q2_validation/protocol_model.py)은 데이터 검사와 Node A 상태를, [시험](../q2_validation/test_protocol.py)은 고정 예시·변형 입력·경계 순서를 확인한다.

기존 문서의 hello→ready→event 구상을 **hello→challenge→ready→최초 status→event/status**로 구체화했다. wire version=1은 아직 배포 전인 후보 값이고 기존 부분 모형과의 호환성 보장은 없다. 후보 revision을 별도로 식별하고 승인·배포 때 양측 버전을 함께 고정한다.

## 2. 표현 규칙과 메시지 구성

길이 접두부 4바이트 unsigned big-endian + UTF-8 JSON 객체 후보를 유지한다. 종류별 필드는 모두 필수이고 선언되지 않은 필드는 거부한다. 선택적 정보도 필드를 생략하지 않고 허용된 null로 표시한다. 중복 키·잘못된 UTF-8·비유한 수·배열/중첩 객체·잘못된 타입·지원하지 않는 종류/버전은 연결 오류다.

식별자 문자열은 ASCII 영문/숫자/밑줄/점/하이픈만 허용한다. uint64는 선행 0 없는 십진 문자열이며 0은 "0", 음수·소수·숫자형 JSON·범위 초과를 거부한다. CAN ID·counter는 각각 11bit/uint32 범위 JSON 정수이고 bool을 정수로 인정하지 않는다. 이 필드는 진단용이며 CAN 배치를 변경하지 않는다.

| 모든 메시지의 공통 필드 | 의미 |
|---|---|
| version, kind | 후보 버전과 메시지 종류 |
| node_id | 보고를 생산하는 Node B의 논리 신원. challenge에서도 대상 Node B를 뜻함 |
| producer_epoch | verifier 실행 세대. OS 부팅 ID나 CAN 인증 세션 ID와 다름 |
| contract_profile, verifier_version | 결과를 해석할 계약 profile과 verifier 버전. 연결 중 변경 금지 |
| connection_id | hello에서만 null, 나머지는 Node A가 해당 인증 연결에 발급한 값 |

| 종류 | 방향 | 추가 필수 필드 | 역할 |
|---|---|---|---|
| hello | B→A | 없음 | 허용 신원·epoch/profile/verifier를 제시 |
| challenge | A→B | 없음 | hello 정체성을 그대로 되돌리고 새 connection_id를 바인딩 |
| ready | B→A | cutoff_seq + 아래 집계 필드 11개 | 이전 큐 폐기 후 새 관측 구간의 기준값 제시 |
| event | B→A | event_seq, raw_id, auth_id, counter, counter_trusted, decision, reason, event_mono_ns, emit_mono_ns | 검사 결과 1건 |
| status | B→A | status_seq, snapshot_mono_ns + 집계 필드 11개 | producer 진단 원장의 일관된 snapshot |

숫자/문자열/메시지/큐·기한 상한은 명세 JSON의 **시험 전용 limits**로 검사한다. 실제 운영값이 아니다. 제품값은 파일럿 근거와 합의가 필요하다. profile의 TEST_FIXED_V1/TEST_C0와 TEST_NODE/CONN/EPOCH는 재현용 더미다. 실제 신원·주소·비밀을 포함하지 않는다.

## 3. 결과와 신뢰 의미

| decision | 허용 reason | 정보 제약 |
|---|---|---|
| ACCEPTED | VERIFIED | raw/auth 쌍·counter 존재, counter_trusted=true. 실제 검증과 기존 상태 commit 후 생성 |
| REJECTED | MAC_MISMATCH, COUNTER_REJECT | 검사 입력 존재, counter_trusted=false. counter를 신뢰된 ECU 값으로 사용하지 않음 |
| NOT_EVALUATED | RAW_EXPIRED, RAW_REPLACED, ORPHAN_AUTH, FORMAT_INVALID, CONFIG_ERROR | 수행하지 않은 검사 결과를 추정하지 않음. counter_trusted=false |
| BYPASSED | SECURITY_DISABLED | C0 profile에서만 허용. raw 존재, auth/counter=null, counter_trusted=false |

RAW_EXPIRED/RAW_REPLACED는 raw만, ORPHAN_AUTH는 auth만 관측한 경우다. raw가 없으면 raw_id=null로 표시하고 auth ID에서 raw가 실제 수신됐다고 추정하지 않는다. auth 없이 counter를 채우지 않는다. 완성된 raw/auth 쌍은 profile의 허용 매핑과 일치해야 한다. 미지원 번호나 형식 때문에 매핑할 수 없는 입력은 FORMAT_INVALID에 해당 ID를 null로 보내며 원본 세부사항은 별도의 제한된 로컬 진단에 남긴다.

counter_trusted는 이 이벤트의 모든 수신 검증이 성공했는지를 뜻한다. COUNTER_REJECT가 MAC 실패를 증명하는 것은 아니다. C0의 모든 결과는 BYPASSED로 집계하고 secure profile에서는 BYPASSED를 거부한다. 같은 원본에 여러 auth가 오면 검사 시도별 결과가 될 수 있으므로 프레임 수·시행 탐지율과 분모를 섞지 않는다.

본 규약은 [ICD](../../ICD.md)의 현행 counter/pending/commit을 변경하지 않는다. 승인된 다음 목표·세션 후보는 profile의 별도 의미·매핑을 준비해야 한다. IF 특징 수·모델과 0x200 형식도 유지한다.

## 4. 누적 집계와 보존식

ready/status의 **11개 집계 필드**는 다음과 같다. 모든 누적값은 producer_epoch 범위이고 status는 최신 snapshot 하나로 교체할 수 있다.

| 필드 | 정의 |
|---|---|
| generated_total | 결과를 생성해 event_seq를 부여한 총수. event_seq는 1부터 시작 |
| accepted_total, rejected_total, not_evaluated_total, bypassed_total | 생성 결과의 decision별 총수 |
| offered_total | 이벤트를 송신 직렬화 FIFO로 넘긴 총수. 송신 완료·수신·IDS 소비 성공과 다름 |
| overflow_total | 송신 전 유한 큐 초과로 폐기한 총수 |
| expired_total | 송신 전 나이 초과로 폐기한 총수 |
| reset_total | 재연결/종료 경계에서 아직 FIFO에 넘기지 않은 큐를 폐기한 총수 |
| queue_depth | 아직 FIFO에 넘기지 않은 현재 대기 건수. 누적값이 아님 |
| last_offered_seq | 마지막으로 FIFO에 넘긴 event_seq. 한 번도 없으면 0 |

검사할 두 보존식:

```text
generated_total =
  accepted_total + rejected_total + not_evaluated_total + bypassed_total

generated_total =
  offered_total + overflow_total + expired_total + reset_total + queue_depth
```

하나의 사건은 송신 전 폐기 사유 중 하나에만 속한다. 이미 FIFO로 넘긴 이벤트의 뒤늦은 전송 실패는 offered_total에 남고 overflow/expired/reset에 다시 더하지 않는다. 연결 내 FIFO는 순서대로 event/status를 직렬화하고 status snapshot과 그 앞의 offer 순서가 뒤집히지 않게 한다. 현재 모형은 이 직렬화 순서를 입력 전제로 두며 실제 worker의 동시성 증명이 아니다.

status_seq는 connection별 1부터 증가하며 최신 snapshot으로 교체할 수 있으므로 순번 gap 자체는 이벤트 유실이 아니다. 중복/역순은 가용성 시각을 갱신하지 않고 무시한다. 새 status의 누적값·last_offered_seq·snapshot 시각은 뒤로 갈 수 없다. queue_depth만 증감할 수 있다. event를 관측한 뒤 그보다 작은 last_offered_seq가 오는 것은 snapshot 순서 위반이다.

Node A는 receiver_overflow/receiver_expired/receiver_reset을 **별도 로컬 원장**으로 기록한다. producer 폐기 총수·수신 순번 gap·수신 후 폐기를 더해서 정확한 총유실이라고 부르지 않는다. gap과 producer 보고는 같은 사건을 가리킬 수 있다. 정확한 대조는 epoch+event_seq 기준 증거가 있을 때만 수행한다.

이전 후보의 interval_start/end와 구간별 결과 수는 wire에서 제외하고 누적 snapshot 차이로 계산하도록 단순화했다. 구간은 Node B의 snapshot 시각을 사용한다. 여러 status가 교체돼도 두 정상 누적값 간 차이는 계산할 수 있지만 세부 사건 시각과 해당 구간 전체 로그가 복원되는 것은 아니다.

## 5. 연결 상태 전이

Node A의 상태와 Node B의 수행을 함께 정의한다. 상태는 통신/진단 경로의 상태이며 CAN freshness·배터리 안전 상태가 아니다.

| Node A 현재 상태 | 입력·조건 | Node A 처리/다음 상태 | Node B 수행 |
|---|---|---|---|
| DISCONNECTED | 허용 peer와 인증 연결 완료 | WAIT_HELLO, 전체 준비 기한 시작 | hello 전송 |
| WAIT_HELLO | 유효 hello | 신원·profile·버전 결속, challenge 발급, WAIT_READY | challenge의 대상/epoch/profile/버전 확인 |
| WAIT_READY | 유효 ready | cutoff·누적 기준 저장, WAIT_STATUS | ready 다음에 최초 status를 event보다 먼저 직렬화 |
| WAIT_STATUS | 유효 최초 status | ACTIVE로 전환 | 이후 event/status 전달 |
| ACTIVE | 유효 신규 event | 순번·나이 검사 후 유한 소비 큐에 추가 | producer 원장/순서 보존 |
| ACTIVE | 유효 신규 status | 누적/순서 검산·가용성 갱신 | 최신 snapshot 전달 |
| ACTIVE | 같은 연결의 중복/역순 event/status | 소비·가용성 갱신 없이 무시 | 재전송 성공으로 해석하지 않음 |
| 준비 상태 | 전체 준비 기한 도달 | 연결 종료, DISCONNECTED | 제한된 재연결 절차 |
| WAIT_STATUS/ACTIVE | heartbeat 또는 status 기한 도달 | 연결 종료, 대기 큐 폐기, DISCONNECTED | 새 인증 연결과 새 ready |
| 연결 중 | 형식/신원/epoch/profile/상태 순서·누적 불일치 | 연결 종료. 거부 입력으로 기준값 갱신 금지 | 원인 기록·재연결 제한 |
| 연결 중 | 같은 peer의 새 중복 연결 | 새 연결 거부, 기존 연결 보존 | 기존 연결 종료/만료 후 재시도 |

준비 기한은 hello가 도착해도 연장하지 않는다. ACTIVE는 event가 계속 와도 새 status가 일정 기간 없으면 종료한다. 누적 집계 검증을 영구히 회피하지 못하게 하기 위한 후보다. 각 기한 정각은 만료로, event source/consumer age 정각은 허용·초과는 폐기로 정의했다. 숫자는 시험 전용이다.

새 TLS 연결은 이전 connection_id를 재사용하지 않는다. 현재 모형에서는 TEST_CONN을 직접 공급하므로 난수 생성·TLS 바인딩은 미검증이다. Node B 측은 handshake 완결·challenge 검증 전 event 전송을 금지한다. 실제 Node B 상태 머신 코드는 아직 없고 아래 검사는 Node A 모델과 producer 원장에 한정된다.

## 6. ready 경계와 재시작

Node B는 challenge 수락 뒤 이전 worker의 세대 토큰을 폐기하고, producer의 짧은 임계 구역에서 아래를 하나의 경계로 처리하는 후보를 적용한다.

1. 아직 FIFO에 넘기지 않은 큐를 reset_total로 이동한다.
2. generated_total을 cutoff_seq로 snapshot한다.
3. queue_depth=0인 ready baseline을 만든다.
4. 새 세대에 대해 cutoff 이후 결과만 enqueue한다.
5. 새 연결은 ready→최초 status→event/status 순서로 직렬화한다.

기존 worker에 이미 넘긴 건은 새 연결로 재전송하지 않는다. producer의 실제 검사 commit을 네트워크 대기로 막지 않는다. 세대 토큰 확인/큐 전환을 같은 임계 구역으로 만들고 테스트에서 ready 전후 생성·enqueue·worker offer 경쟁을 따로 확인해야 한다.

모형은 두 번의 generate와 하나의 원자적 ready의 가능한 순서 3개를 열거해 ready 전 건은 폐기, 후 건은 보존되는지 확인했다. 이 검사가 실제 스레드 경쟁·lock 시간·비차단 동작을 증명하지는 않는다.

같은 epoch 재연결에서는 누적값·event_seq를 초기화하지 않는다. Node A가 이전 epoch 기준을 메모리에 보유하면 기준값 감소나 이미 본 순번보다 작은 cutoff를 거부한다. 새 verifier 실행은 새 epoch를 사용한다. Node A 재시작으로 메모리 이력이 없을 때는 새 인증 연결/ready 기준을 시작하며 과거 모든 epoch의 재생 방지를 증명했다고 주장하지 않는다.

uint64 소진은 래핑하지 않고 producer 진단 세대를 새로 시작한다. 이는 CAN SecOC counter나 인증 세션을 초기화하라는 명령이 아니다. 실제 epoch 식별·충돌 방지·재연결 빈도 상한은 제품 배포 조건으로 확정한다.

## 7. 가용성·손실·시각 해석

- 최초 status 전이나 연결 종료 상태는 UNAVAILABLE이다.
- 정상 상태 보고를 받은 연결은 AVAILABLE이다. 이것은 진단 채널 관측 가능성을 뜻하며 BMS가 새로 수신됐다는 뜻이 아니다.
- 현재 연결의 event gap·producer 폐기 증가·consumer 폐기는 INCOMPLETE를 만든다.
- status의 last_offered_seq가 아직 관측하지 않은 event까지 넘어가면 누락으로 기록하고 그 이하의 뒤늦은 event를 실시간 소비하지 않는다. 단일 FIFO 순서 가정에 따른 규칙이다.
- 현재 연결의 INCOMPLETE는 해당 연결 동안 유지한다. 새 연결은 새 관측 구간으로 시작할 수 있으나 history_loss와 이전 구간 원장은 남긴다. ready 이전의 관측되지 않은 구간은 초기 기준 구간으로 기록한다.
- status만 계속 와도 CAN 미수신을 정상으로 바꾸지 않는다. Node B 자체가 침해된 경우의 허위 보고는 이 모형으로 해결되지 않는다.

source age는 Node B의 emit−event로, consumer age는 Node A의 소비−수신으로 검사한다. 서로 다른 노드의 monotonic 값을 직접 빼지 않는다. 같은 Node A 시계가 뒤로 가면 모형은 연결을 종료한다. 실제 시계 정렬 오차·TLS/네트워크 지연·전체 실시간 성능은 별도 측정이다.

이번 실행에서 신규 규약 모형 **18개 검사 통과**, 기존 부분 모형 **12개 검사 통과**를 확인했다. 기존 14개 고정 입력은 그대로 보존했다. 두 모형의 일부 검사가 중복되므로 30개의 서로 다른 공식 인수 항목으로 해석하지 않는다.

## 9. 이번 단계 이후 필요한 실행

규약 초안과 재현 자료는 준비됐다. 다음에 필요한 것은 문서 항목의 반복 추가가 아니라 다음 외부·구현 증거다.

1. 실제 양측 유선 연결과 선택 AOSP에서 TLS/권한 지원을 확인한다.
2. 시험 전용 limits를 실제 생성량·메모리·지연 근거로 운영 후보값에 대입한다.
3. 이 규약과 [설계안의 영향 목록](인증이벤트_전달_설계안.md)을 기준으로 상세 계약을 검토·확정한다.
4. 확정 후 양측 producer/receiver/IDS 소비와 공식 문서·시험을 동기화한다.

설계 자료만으로 수단 채택·운영값 승인·제품 구현을 완료 처리하지 않는다. 이번 작업에서 공식 ICD/SRS/양측 SDD/TEST_PLAN·제품 코드·기존 사용자 답변은 변경하지 않았다.

## 10. 구현 전 설계 마감 — 실행 정책 보완

이 절은 후보 2를 제품으로 채택했다는 선언이 아니라 **설계 문서에서 정할 수 있는 남은 정책을 보완한 권고안**이다. 앞 절의 실장비·운영값 확인은 실행 단계의 인수이며 계획 완료의 대기 조건이 아니다. 보완 정책은 아래 기존 모형이 전부 검증한 내용으로 확대하지 않는다.

### 10.1 Node B 송신 상태와 종료

| 상태 | 허용 행동 | 전환·실패 처리 |
|---|---|---|
| STOPPED | 설정/profile/키 권한 점검 | 유효 설정에서 CONNECTING. 오류는 CONFIG_ERROR 로컬 진단, 평문 전환 없음 |
| CONNECTING | 제한된 연결·양측 인증 | 성공 시 hello 송신 후 WAIT_CHALLENGE. 기한/인증 실패는 BACKOFF |
| WAIT_CHALLENGE | 현재 TLS stream의 challenge 1개 수신 | version·node·epoch·profile·verifier 일치와 비어 있지 않은 connection 확인. 불일치/중복/기한 초과는 연결 종료 |
| PREPARE | 세대 변경·기존 큐 폐기·ready baseline 작성 | ready→최초 status 순서를 예약하고 STREAMING. 준비 중 만든 이벤트는 cutoff 뒤 큐에 남김 |
| STREAMING | 순번 순 event·최신 status를 단일 writer로 직렬화 | 부분 write는 같은 메시지의 남은 바이트만 진행. 전체 write 기한 초과·프로토콜 오류는 BACKOFF |
| BACKOFF | 로컬 상태 기록, 상한 있는 재시도 예약 | 누적 시도 한도 소진은 STOPPED와 운용자 복구 필요 표시. 정상 유지 구간을 충족한 뒤에만 실패 횟수 초기화 |
| STOPPING | 새 송신 금지·취소 신호·유한 종료 대기 | queue 정산·worker 종료 확인 후 STOPPED. join 기한 초과는 종료 실패, 성공으로 표시하지 않음 |

STREAMING은 Node B가 송신 준비를 마쳤다는 뜻이며 Node A 소비 확인 상태가 아니다. 최초 status 이후 별도 ACK는 추가하지 않는다. 전달 성공 증거는 Node A의 receiver/consumer 기록에서 확인한다. 네트워크 장애 시 verifier와 기존 UI는 계속 동작한다. 종료 취소는 blocking I/O를 깨울 수 있어야 하며 단순 플래그만으로 thread 종료를 보장하지 않는다.

### 10.2 큐·원장·status의 소유권

| 경계 | 소유자·상한 정책 | 포화·종료 시 기록 |
|---|---|---|
| verifier→event 대기 큐 | producer 임계 구역에서 결과 순번·원장을 갱신. 새 결과를 추가할 공간 없으면 신규 건 거부 | overflow_total 증가. 기존 대기 순서 보존 |
| 대기 큐→직렬화 FIFO | 단일 writer만 offer. FIFO 공간 없으면 대기 큐에 남겨 다른 스레드를 막지 않음 | offer 전 age 초과는 expired_total, 세대 전환은 reset_total |
| 직렬화 FIFO | 메시지 수와 bytes를 함께 제한. ready/status용 제어 예약 공간 확보 | offer 후 실패는 offered_total 유지, 연결 불완전 증거로 추적 |
| 최신 status 슬롯 | 아직 FIFO에 넣지 않은 후보 snapshot 하나만 교체 | 교체 자체는 event drop 아님. 임의 무한 status 큐 없음 |
| Node A receiver→consumer | 유한 큐, 신규 건 거부·소비 나이 제한 | receiver_overflow/expired/reset을 producer와 별도 기록 |
| 로그·소비 증거 | bounded ring 또는 회전 파일과 용량 한도 | 로그 손실을 별도 표시. 로그 실패로 verifier 대기 금지 |

status는 **실제 FIFO 삽입 시점**의 원장을 일관되게 snapshot한다. 그 snapshot보다 앞선 offer는 반드시 먼저 직렬화한다. 나중에 만들어진 snapshot을 기존 FIFO 앞자리로 덮어쓰지 않는다. 대기 중인 status 교체와 FIFO 삽입을 구분하면 오래된 snapshot이 후속 event 뒤에 도착하는 모순을 피할 수 있다. status deadline이 다가오면 새 event offer를 일시 멈추고 예약 제어 공간을 사용한다. 그래도 전체 write/status 기한을 넘기면 연결을 닫는다.

### 10.3 설정 변경·기한·오류의 경계

- profile/verifier/검증 의미 변경은 새 producer_epoch와 새 연결을 요구한다. 같은 epoch에서 의미 변경을 숨기는 재연결은 금지한다. 공식 CAN 계약 전환은 별도 승인 절차를 유지한다.
- 길이 prefix의 첫 바이트부터 본문 완성까지 하나의 전체 read 기한을 둔다. 바이트가 조금씩 도착해도 기한을 연장하지 않는다. TLS handshake 기한, 애플리케이션 준비 기한, read/write 기한은 서로 구분한다.
- parser 오류·신원/profile/epoch 불일치·누적 원장 모순은 연결 종료다. 유효한 중복/역순 메시지는 소비·가용성 갱신 없이 무시한다.
- Node B 송신 전 age 초과는 producer expired, Node A 소비 전 age 초과는 receiver expired다. wire에 이미 source age 한도 위반이 들어온 경우는 협약 위반으로 연결 종료한다. 이 셋을 같은 MAC 실패 reason으로 합치지 않는다.
- 같은 epoch의 마지막 관측 기준은 한 노드의 최근 실행 세대 정보로만 제한 보존한다. 무한 epoch 캐시를 만들지 않는다. 과거 모든 epoch·침해된 peer에 대한 영속 재생 방지는 보장 범위 밖이다.
- event/status 순번이나 누적 원장이 소진되기 전에 새 진단 epoch로 전환한다. 기존 CAN counter·BMS 안전 상태는 초기화하지 않는다.
- 노드 인증서 갱신은 승인된 trust 목록을 준비→교차 확인→새 연결 검증→이전 자격 제거 순으로 수행한다. 키를 공유 로그로 전달하지 않는다. 실패 시 유효한 기존 자격으로 복귀 가능한지 확인하고, 불가능하면 진단 채널을 중단한다.

### 10.4 추가 구현 인수 시나리오

| 로컬 ID | 입력/교차 조건 | 기대 결과 |
|---|---|---|
| Q2-P01 | ready 직전/도중/직후 생성과 이전 worker offer | cutoff 전 자료 재전송 없음, 세대 검사·원장 보존식 성립 |
| Q2-P02 | event FIFO가 가득 찬 상태에서 status deadline | 제어 공간과 순서 보존, 무한 대기 없이 기한 실패 진단 |
| Q2-P03 | 오래된 status 대기 중 새 event offer·snapshot 교체 | 삽입 순간 snapshot 기준과 stream 순서 일치 |
| Q2-P04 | prefix/body의 느린 부분 입력·부분 write·취소 | 전체 기한 연장 없음, 잘못된 이어붙이기/종료 hang 없음 |
| Q2-P05 | 같은 epoch에서 profile/verifier 변경 | 새 epoch 전환 요구, 혼합 해석 없음 |
| Q2-P06 | 반복 인증 실패·잠깐 연결 후 즉시 단절 | backoff/시도 예산 유지, 무한 재접속/로그 폭증 방지 |
| Q2-P07 | 로그 공간 부족·consumer 지연·종료 경쟁 | drop 구분, verifier/UI 비차단, join 결과 확인 |
| Q2-P08 | 인증서 갱신/만료·신뢰 제거·로컬 시각 준비 실패 | 검증 비활성화 없이 허용된 연결만 유지 |

Q2-P는 후속 제품 인수를 위한 시나리오이며 이번 실행에서 통과한 테스트가 아니다. 기존 Q2-D와 대응되는 동시성·배포 보강이며 공식 TC 번호를 추가하지 않는다.
