### 1. 결론과 적용 원칙

**현재 구조는 유지할 가치가 있다. 그러나 내용은 추가 개선이 필요하며, 그대로 최종 실행계획으로 확정하거나 Plan과 단순 합치면 안 된다.**

상위 계획 2개와 ECU·IVI·공동 상세의 역할 구분은 적절하다. 최근 보완으로 인증 보류 흐름, 실험 성공·차단·탐지의 분리, 공식 측정 구간, CI 단일 참조, 미구현 상태 구분이 개선됐다. 하지만 그 변경이 상위 표·상세 코드·최종 체크리스트까지 일관되게 반영되지 않았다. 특히 실제 장비 실행에는 입력 전압 범위, 실행 계정의 키 접근, Android 보드 지원·배포, 물리 CAN 복구와 증적 수집을 구체화해야 한다.

이번 개선안은 이전 [초기 계획 검토 요약](../governance/의사결정_기록.md#decision-development-review)의 PLN-01~10을 유지해 현 상태를 재평가하고, 추가 발견 사항을 PLN-11~18로 구분한다. 이전 보고서의 “미정의 요구사항 ID”, “음수 지연 하나로 PASS” 등의 주장을 현재도 그대로 성립하는 것으로 복사하지 않았다.

### 4. 기존 항목의 재평가와 개선 방향

#### PLN-01 — 인증 상태 전이를 완료 조건까지 연결

[IVI M3](../../../plan/detail/ivi/M3_HAL_Service_대시보드.md) §3.2의 pending→검증→commit→callback 방향은 유지한다. 다만 §4의 “0x100 수신 시 콜백”은 인증 모드를 생략해 다시 잘못 해석될 수 있다. 두 인증 쌍 `0x100/0x102`, `0x101/0x103`의 성공·실패·누락·교차 수신·만료를 표로 정의하고, 수신 데이터·카운터·stale 시각 중 무엇을 언제 갱신하는지 명시한다.

**완료 조건:** 인증 ON에서는 유효한 쌍만 한 번 반영한다. MAC 오류·DLC 오류·짝 유실·중복으로 UI와 Fail-safe 상태가 바뀌지 않는다. 인증 OFF 시험은 별도 모드와 증적으로 구분한다. 재동기화는 PLN-11에 따라 별도 승인·검증한다.

#### PLN-02 — 정정된 실험 의미를 실제 하네스까지 연결

[ECU M5](../../../plan/detail/ecu/M5_Ablation.md) 95~110행의 독립 관측·공격별 정의는 개선됐다. 그러나 134행의 `ReceiverModel` 기반 예시와 §3.5의 `--channel vcan0` 실수신 판정 사이를 연결하는 receiver·실행 감독·이벤트 수집 계약은 부족하다. Config 전환 시 송신기뿐 아니라 수신 verifier 모드·IDS·카운터·기준 상태도 초기화해야 한다.

[ECU M4](../../../plan/detail/ecu/M4_IDS_공격_물리통합.md) 307행은 `security/analysis/measure_can_secoc.py`로 fps·버스 점유율을 확인하도록 한다. 실제 [해당 도구](../../../security/analysis/measure_can_secoc.py)는 버스에 접속하지 않고 비트 수·부하를 계산하며 HMAC 실행 시간을 재는 도구다. **실제 CAN 점유율 측정 근거가 아니다.** vcan 역시 실제 비트레이트·중재·배선 부하를 재현한 것으로 취급하지 않는다.

**개선:** trial 시작·수집 준비·정상 기준·공격 주입·종료·cooldown·실패 정리를 런북으로 작성한다. `run/config/attack/trial/seed/environment`와 원본 로그 연결, 기대한 정상 프레임 수·수용 수·거부 수·실패 사유를 정의한다. 시행 성공률과 프레임 수용률, 윈도우 탐지율은 각각의 분모를 표시한다. vcan은 논리 검증, 물리 버스 부하·전달 지연은 실장비 검증으로 분리한다.

**완료 조건:** 1,200행뿐 아니라 12개 구성·공격 조합의 유일한 100시행, 조건별 입력 일치, missing/invalid/미탐지 처리, 실제 수신 증거를 확인한다. “1,200×3초≈1시간”은 순수 공격 시간 하한이며 준비·안정화·재시도·물리 시험을 포함한 일정으로 쓰지 않는다.

#### PLN-03 — 분석 코드가 불완전한 데이터를 합격시키지 않게 수정

[IVI M5](../../../plan/detail/ivi/M5_성능_UI개선.md)의 현재 코드 블록을 추출해 합성 입력으로 실행했다. 기존 음수·표본 부족 검사는 추가됐으나 다음 문제가 남았다.

| 재현 입력 | 현재 결과 | 개선 조건 |
|---|---|---|
| 유효 1,000쌍 + 짝 없는 1건 + 중복 1건 | TC-PERF-001 PASS, 종료 0 | 공동 §6의 손실 시 PASS 보류 규칙을 코드에도 적용 |
| 1쌍 + `--min-samples 1` | TC-PERF-001 PASS, 종료 0 | 공식 TC 최소 표본 하향 금지; 소규모 디버그는 별도 비공식 모드 |
| 주기 100ms 95개 + 111ms 5개 + 파싱 불가 1줄 | TC-PERF-002 PASS, 종료 0 | 허용 범위 이탈·손상 로그를 공식 합격으로 처리하지 않음 |

근거는 M5 102·159행의 범위 내 95% 기준, 245~256행의 seq만 사용한 중복 처리, 284행의 최소 표본 덮어쓰기, 286~305행의 incomplete 집계다. 공동 통합시험은 개별 간격 90~110ms와 손실 시 보류를 규정하므로 명백한 내부 불일치다.

**개선:** `run_id/boot_id/sample_id`·stage·정수 시각과 manifest를 입력 계약으로 사용한다. 누락·중복·역행·수집 손상은 INVALID, 유효 측정이 기준을 벗어나면 FAIL, 미실시는 NOT_RUN으로 구분한다. 공식 기준값은 옵션으로 낮추지 못하게 한다. 분석기 회귀 시험에 위 세 사례와 정상·경계·혼합 CAN ID·재부팅을 포함한다.

#### PLN-04 — 정본 측정표와 모든 예시·체크리스트를 동기화

[공동 통합시험](../../../plan/detail/common/02_통합시험.md) §6 및 IVI M5 §3.2는 TC-PERF-001=T1→T4, TC-IVI-008=T2→T3으로 정리됐다. 하지만 M5 앞부분의 예전 정의와 §4의 T0→T1 실행 예시·판정표가 남아 있다. [IVI M6](../../../plan/detail/ivi/M6_문서_Coverage.md) 41·68행은 TC-PERF-003을 화면 표시까지라고 설명하지만 현재 TEST_PLAN은 `0x200` 수신까지다.

**개선:** 공식 측정표는 공동 §6 한 곳에 두고 세부 도구·완료표가 이를 참조하게 한다. M6는 공격 실제 주입→0x200 수신과 공격→배너를 별도 열에 기록한다. 수집기를 공격보다 먼저 준비하고 양 노드 로그를 분석 호스트로 모으는 절차를 추가한다. 두 노드의 단조 시계를 직접 빼지 않는다.

**완료 조건:** 같은 TC를 검색했을 때 시작·종료 이벤트·표본 수·평균/최대/P99·단위가 동일하다. NTP 설정만으로 시계 오차가 없다고 가정하지 않는다.

#### PLN-05 — 병합 전에는 두 계획의 역할을 명확히 표시

루트 안내가 plan으로 연결된 점은 유지한다. 다만 `Plan/`을 곧 삭제할 불필요 파일로 취급하지 않는다. [Plan/Common](../../../plan/_archive/plan_20260908/Common.md.txt) 10~16행의 단일 상태 관리·재확인·요구 우선순위와 역할 계획의 안정적인 과제 ID는 병합 가치가 있다.

**개선:** plan은 현재 상세화 대상, Plan은 향후 병합할 비교 원문으로 명시한다. 병합 때의 과제 대응·충돌 처리 방법은 §6을 적용한다. 비교·인수 완료 전 원문 이동·삭제는 하지 않는다.

#### PLN-06 — ID 언급을 실제 검증 연결로 발전

잘못된 FR 범위는 일부 정정됐고 NFR 연결도 추가됐다. 이전 보고서의 전체 누락 수치를 재사용하지 않는다. 다음 단계는 `FR/NFR → 담당 과제 → TC 본문 → 증적`의 의미상 연결이다. `Plan/ECU.md`, `Plan/IVI.md`의 요구사항 연결표를 병합 입력으로 활용한다.

**완료 조건:** 각 필수 요구에 담당 단계·구현 대상·TC·증적·미실시 사유가 연결된다. 공식 TC가 일부 범위만 다루면 별도 하위 시험 조건을 명시하며 새로운 공식 ID를 임의로 만들지 않는다. 코드 존재·계획상의 체크박스를 시험 통과로 바꾸지 않는다.

#### PLN-07 — 상위·상세·정본의 모델과 범위를 통일

[ECU 상위](../../../plan/ECU.md) 77행은 선형·2.6Ah 구현에 맞춰 SDD를 정정하라고 하지만, [ECU M3](../../../plan/detail/ecu/M3_EKF_Failsafe_SecOC.md) 90~92행은 3차·50Ah 구현을 요구한다. 공동 의존성 114행에는 선형 모델이 남았다. M3 90행은 호출부 전압 나눗셈을, 119·148행은 update 내부 나눗셈을 제시해 **이중 변환 위험**도 있다.

또한 M3 §3.11은 ADS1115 필수, §5는 선택으로 표현한다. TC-BMS-001 본문과 §4의 100 step, Watchdog의 “3회 연속 실패”와 “3회 초과”도 다르다. 현재 ICD에 0x07이 추가된 사실과 오래된 코드 목록도 동기화해야 한다.

**개선:** 승인된 모델·용량·팩/셀 단위를 한 곳에서 정하고 API 입력 단위를 명시한다. 팩→셀 변환은 호출부 또는 estimator 중 한 곳에서만 한다. 50Ah는 시뮬레이션 설정인지 실제 확보한 팩인지 구분한다. 직렬수 10만으로 50Ah 용량이 증명되는 것은 아니다. Watchdog는 감지·재시작 시도·실패 집계·복구 성공 초기화·최종 WARNING을 상태도로 정리한다.

**완료 조건:** 상위 방향·상세 구현 과제·공식 입력·완료표가 일치한다. 원문과 구현의 차이를 기록한 뒤 필요한 승인 근거를 연결한다.

#### PLN-08 — 빌드 가능과 대상 런타임 실행 가능을 구분

[IVI M1](../../../plan/detail/ivi/M1_AOSP_Docker_CI.md) §3.5와 [CI 참조](../../../plan/detail/ivi/ref_CI파이프라인_명령모음.md)에는 누락됐던 빌드·서비스·QEMU 인수 과제가 추가됐다. 이를 유지하되 미검증 Dockerfile·toolchain 예시, CICD_SPEC의 옛 실행 경로와도 맞춰야 한다.

**개선:** 산출물 표에 `host Linux core / Node A Ubuntu ARM64 / Node B Android HAL·framework·app / 승인 시 Qt 대안`을 나눈다. 같은 ARM64라도 Linux용 라이브러리·실행파일을 Android 산출물로 인수하지 않는다. HIDL 코드 생성·등록·VINTF·init·권한·앱 접근은 대상 AOSP 빌드의 smoke test로 확인한다. AOSP 공식 문서도 서비스 등록·접근 절차를 구분한다. [AOSP HIDL 서비스](https://source.android.com/docs/core/architecture/hidl/services)

**완료 조건:** 깨끗한 checkout에서 도구·SDK·JDK·sysroot·라이브러리 버전과 artifact를 재현한다. container에서 configure한 테스트의 경로·동적 loader·QEMU 런타임·gcov 버전이 실제 실행과 맞는다. 시험 0개·coverage 자료 없음·대상 기기 시험 미실시는 합격시키지 않는다.

#### PLN-09 — 데모 입력 파일과 전이 경로를 하나로 확정

공동 통합시험은 `failsafe_demo.csv`, ECU M3 §3.12는 `battery_profile_demo.csv`를 생성하도록 한다. ADS1115 주 경로와 CSV 백업도 역할 문서·최종 데모에 전파해야 한다.

**개선:** 준비물·실행 모드·파일명·초기 상태·입력 유지시간·기대 전이·증적을 공동 데모 표 한 곳에 정리한다. SOC 5.0%는 `<5%` 조건을 충족한다고 단정할 수 없으므로 임계 바로 아래·같음·위의 경계 시험을 분리한다. 가변저항 입력은 알고리즘 수렴시간을 실제 측정하고 계획상의 약 5초를 실측으로 발표하지 않는다.

**완료 조건:** 정해진 파일·명령으로 WARNING→CRITICAL→인증 이벤트→화면이 재현된다. 프레임 직접 주입은 IVI 단독 시험으로 구분한다. 모델 정확도용 데이터는 PLN-17에 따라 별도 준비한다.

#### PLN-10 — 중복 감소와 실제 진행 관리

CI 전문을 단계별 복사본에서 단일 참조로 바꾼 방향은 유지한다. 반면 최종 측정 표·모델 수치·데모·릴리즈 절차는 여전히 여러 파일에 반복된다. 상위 진행표가 비어 있어 현재 착수 가능한 작업도 명확하지 않다.

**개선:** 상위에는 요약·링크·단계 상태만, 상세에는 수행 절차와 고유 인수 조건만 남긴다. 공통 수치를 수정하면 참조 문서를 검증하는 체크를 둔다. 담당 역할·선행 과제·예상 기간의 산정 책임·차단 사유·증적 위치를 채우되 실제 날짜나 완료 상태는 확인 없이 넣지 않는다. 공동 태그·릴리즈 생성자는 한 명으로 정하고 양측 승인 뒤 한 번 수행한다.

### 5. 추가 발견 사항과 하드웨어 실행 보강

#### PLN-11 — SecOC 재동기화와 Replay 방어의 충돌

**근거:** [IVI M3](../../../plan/detail/ivi/M3_HAL_Service_대시보드.md) 600~605행은 MAC이 유효하면 윈도우 밖의 과거 counter를 새 기준으로 저장한다. 반면 실제 [Python SecOC](../../../security/secoc_module.py)와 [C++ SecOC](../../../adaptive_ecu/src/bsw/secoc_module.cpp)는 윈도우 밖 값을 거부하며 기준을 바꾸지 않는다. ICD의 재부팅 재동기화 설명 자체와 Replay 요구의 관계도 명확하지 않다.

문서 알고리즘의 상태 전이를 계산하면 현재 기준 1000에서 과거의 유효한 counter 10을 재생했을 때 거부하면서 기준이 10으로 내려가고, 이어 과거 counter 11을 재생하면 수용된다. **계획 예시의 논리적 문제를 확인한 것이며, 없는 IVI 구현의 실장비 취약점을 재현한 것은 아니다.**

**개선:** 정상 운전·수신기 최초 기동·송신기 재부팅·래핑·윈도우 초과를 별도 상황으로 정의한다. MAC 유효성만으로 “송신기가 재부팅했다”는 사실을 판단하지 않는다. 운영자 재동기화·지속 카운터·인증된 세션 등 선택지의 구현비용·ICD 영향·재부팅 시 동작을 인터뷰 후 결정한다. 공통 카운터의 두 메시지 스트림 순서도 인수한다.

**완료 조건:** 과거의 정상 MAC 프레임을 연속 재생해도 기준값을 되돌려 수용하지 않는다. 정상 재부팅·래핑은 합의한 복구 절차로 동작하며 양측 구현·시험이 같은 규칙을 쓴다.

#### PLN-12 — 실제로 전송 가능한 CAN 시험 벡터로 정정

**근거:** [공동 통합시험](../../../plan/detail/common/02_통합시험.md) 201·225·228행의 아래 payload는 각각 9바이트다. 기대 출력·ICD는 8바이트다. Classic CAN용 cansend 데이터는 최대 8바이트 형식이므로 현재 예시는 정상 송신 벡터로 사용할 수 없다. [can-utils cansend 원문](https://github.com/linux-can/can-utils/blob/master/cansend.c)

| 현재 값 | 길이 | 의도한 8바이트 정정 후보 |
|---|---:|---|
| `C83C10680014410000` | 9B | `C83C106800144100` |
| `963C1068FFEC410000` | 9B | `963C1068FFEC4100` |
| `963C10680014820000` | 9B | `963C106800148200` |

같은 문서 96·105행 등의 4바이트·역방향 예시는 물리 smoke test로는 사용할 수 있지만 공식 ICD 데이터 시험과 구분해야 한다. 특히 Node B→A의 0x200은 정식 IDS 방향이 아니다.

**개선:** 테스트 벡터를 길이·필드·방향·예상값으로 기계 검사한다. 물리 smoke, parser 단위, 인증 통합의 실행 모드를 분리한다. 애플리케이션을 종료한 smoke에서 쓰는 임시 프레임을 ICD 합격 증거로 인수하지 않는다. SecOC ON 화면 검증에는 올바른 인증 쌍이 필요하다.

**완료 조건:** 모든 정상 계약 벡터는 8바이트이며 parser·실제 cansend 수신·기대 해석이 일치한다. 잘못된 DLC는 별도의 거부 시험이다.

#### PLN-13 — ADS1115 전압 범위와 설정을 배선에 맞춤

**근거:** [SDD-ECU](../../SDD-ECU.md) 485~496행은 FSR=2.048V, raw 26400, 0~3.3V 입력, 0~2.048V 매핑을 혼용한다. 식으로 계산하면 raw 26400은 1.65V다. ECU M3 §3.11은 3.3V 전원과 가변저항을 제시하면서 2.048V 스케일을 사용한다. 가변저항 양끝·와이퍼 연결과 PGA 설정을 정하지 않으면 전체 회전 구간이 의도한 값에 대응하지 않는다.

TI 데이터시트는 PGA별 full-scale과 입력 전압의 전원 제한을 별도로 규정한다. 따라서 공급전압과 ADC 변환 full-scale을 같은 값으로 취급하면 안 된다. [ADS1115 데이터시트](https://www.ti.com/lit/ds/symlink/ads1115.pdf)

**개선:** 실제 배선을 확인해 0~3.3V 입력을 수용할 PGA·스케일을 선택하거나 입력을 선택 FSR 안으로 제한한다. 설정 레지스터의 MUX·PGA·변환 모드·data rate, 바이트 순서, 변환 완료·timeout, I2C 오류·미연결 처리, 포화·음수 raw 처리를 명시한다. 전압계와 비교할 교정 지점을 정하고 raw→ADC V→가상 팩 V 변환을 표로 기록한다.

**완료 조건:** 최소·중간·최대 입력과 경계값이 포화 없이 기대 매핑에 대응한다. `i2cdetect`에 주소가 나오는 것만으로 센서 기능을 합격시키지 않는다. 실제 팩 전압을 ADC 핀에 연결하는 시험으로 오해되지 않게 **가변저항 기반 가상 배터리 입력**임을 명시한다.

#### PLN-14 — 키 파일을 읽을 수 있는 실제 서비스 실행 구성

**근거:** [IVI M4](../../../plan/detail/ivi/M4_대시보드_Alert_배포.md) 278행은 `User=deploy`로 ECU를 실행한다. [공동 키 배포](../../../plan/detail/common/02_통합시험.md) 121~133행과 ICD는 키를 `root:root`, 400으로 두며, [main.cpp](../../../adaptive_ecu/main.cpp) 78행은 기동 때 직접 키를 읽는다. 현재 예시에 별도 자격·전달 수단이 없어 deploy 계정이 해당 키를 읽는 경로가 성립하지 않는다.

Health Check 362~365행은 `systemctl is-active`만 확인한다. CAN·센서·키·IDS·IVI 데이터 경로가 실패해도 프로세스만 살아 있으면 통과할 수 있다. 서비스가 참조하는 CSV·IDS 모델·의존 라이브러리 배포도 artifact에 포함해야 한다.

**개선:** 서비스 실행 사용자, 키 접근 수단, CAN/I2C 권한, 파일·디렉토리 소유자, Node별 기동 순서를 정합시킨다. ICD 키 권한을 바꾸거나 다른 키 전달 경로를 도입하는 선택은 승인 후 관련 문서에 반영한다. 프로세스 alive와 기능 readiness를 구분하고 기동 후 새로운 정상 CAN·인증·센서·경보 경로를 확인한다.

**완료 조건:** 재부팅 후 별도 수동 sudo 없이 승인된 서비스 구성으로 기동한다. 키 미배치·손상, can0 미준비, ADC 미연결, 모델 누락, 이전 artifact로 rollback을 시험하며 기능 실패를 PASS로 표시하지 않는다.

#### PLN-15 — Android RPi4 보드 지원과 설치 절차를 재현 가능하게 확정

**근거:** [IVI M1](../../../plan/detail/ivi/M1_AOSP_Docker_CI.md) 130~143행은 AOSP 태그를 지정하지만 [M2](../../../plan/detail/ivi/M2_HALMock_PlanAB.md) 182·186행은 device-tree 저장소와 lunch target을 자리표시자로 둔다. “SD 카드 플래시”만으로는 이미지 조합·파티션·커널·DT·펌웨어를 재현할 수 없다. `ip link show can0`은 앱 또는 HAL의 실제 접근을 증명하지 않는다.

**개선:** 사용 장비 revision, AOSP·보드 manifest URL/revision, 커널·DT overlay·vendor 의존성, lunch target, flash 도구·대상 이미지·복구 이미지를 한 세트로 기록한다. Android 커널의 CAN·MCP2515·SPI 지원과 HAL 권한·SELinux·서비스 기동을 실제 양노드 송수신으로 검증한다. M2 판단을 홈 화면·adb·인터페이스 존재에서 **실제 HAL 접근·샘플 데이터·앱 설치 주기**까지 발전시킨다.

빌드 자원도 실제 선택한 Android 13 트리 기준으로 측정한다. 현재 AOSP 공식 안내는 최신 릴리즈에 400GB 저장공간·64GB RAM을 제시한다. 이를 Android 13의 확정 최소치로 소급하지는 않되, 계획의 200GB·16GB가 검증된 충분 조건이라고 단정해서도 안 된다. [AOSP 빌드 환경 요구](https://source.android.com/docs/setup/start/requirements)

**완료 조건:** 다른 사람이 같은 manifest·이미지 절차로 기동하고 물리 CAN payload를 HAL→앱으로 전달한다. 실패 시 로그·원인·남은 작업량을 근거로 기존 Plan A/B 결정 절차를 적용한다. 검토 단계에서 플랫폼을 임의로 전환하지 않는다.

#### PLN-16 — 물리 CAN 인수와 복구를 단계화

**근거:** [공동 통합시험](../../../plan/detail/common/02_통합시험.md) §3은 VCC “3.3V 또는 5V, 모듈 확인”과 양측 SPI 배선을 제공한다. 그러나 구체 모듈·transceiver·logic level, 버스 기준 접지/절연, 전원·전류 여유·냉각, controller loopback 해제, bus-off 복구 조건은 하나의 인수 절차로 연결돼 있지 않다.

Raspberry Pi GPIO는 3.3V 신호를 전제로 하므로 모듈의 전원 핀 선택만으로 SPI MISO·INT 신호 호환을 보장하지 않는다. 부품명·회로·레벨 변환 유무를 확인해야 한다. [Raspberry Pi 전압 사양](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#voltage-specifications)

SocketCAN에는 로컬 loopback과 error/bus-off 상태·restart 기능이 있다. 같은 노드에서 캡처한 송신 프레임을 상대 수신 증거로 오인하지 말고, 인터페이스 UP뿐 아니라 CAN 상태·오류·드롭·재시작을 기록한다. [Linux SocketCAN](https://docs.kernel.org/networking/can.html)

**개선:** 부품·전원 확인 → 무전원 배선·종단 확인 → 각 노드 드라이버·클록·핀·비트레이트 확인 → controller loopback 시험 → loopback 해제 → 상대 노드 수신 → 인증 통합 → 재부팅·통신 단절·bus-off 복구 순서로 런북을 보강한다. 양쪽 120Ω 병렬의 예상 약 60Ω은 전원 OFF에서 확인하는 단순 회로 점검이며 모듈 회로·측정 조건도 기록한다.

**완료 조건:** 수신 증거가 상대 노드에서 나오고, 정상 시험 중 오류 증가 여부를 확인한다. 단절·복구 시 stale와 정상 복구, 재시작 횟수·복구 시간의 실측이 연결된다. vcan은 단일 Linux 호스트의 논리 버스이며 서로 다른 장비의 vcan0가 자동 연결된 것으로 쓰지 않는다.

#### PLN-17 — 데모용 전압 램프를 정확도 검증 데이터로 대체하지 않음

**근거:** [ECU M3](../../../plan/detail/ecu/M3_EKF_Failsafe_SecOC.md) §3.12는 42→30.8V 램프 생성기를 데모와 TC-BMS-002용 36,000행 생성에 같이 사용한다. 공식 TEST_PLAN의 TC-BMS-002는 NASA 기반 1시간 프로파일과 기준값 대비 EKF·쿨롱 비교를 요구한다. 가변저항이나 임의 전압 램프는 상태 전이 입력으로 유용하지만 실제 SOC 정답이나 독립 정확도 근거는 아니다.

**개선:** 데모 벡터, 모델 단위시험 벡터, 정확도 평가 데이터 세트를 분리한다. 평가 자료에는 출처·라이선스·원본 hash·전처리·단위·샘플링·reference SOC 산출법·초기조건·노이즈·학습/평가 분리를 기록한다. 원 데이터에 정답 SOC가 없으면 참조 산출 방법과 한계를 명시한다. 동일 OCV 식으로 만든 입력과 같은 식의 추정값 비교를 실배터리 정확도 증명으로 발표하지 않는다.

**완료 조건:** 데모는 결정적인 전이를, TC-BMS-002는 독립 기준값 대비 1시간 RMSE·최대 오차와 동일 입력 비교를 증명한다. 합성 곡선·추정 수렴시간은 목표·예시·실측을 구분한다. 데이터 조건 변경이 필요하면 공식 시험 변경 근거와 승인을 남긴다.

#### PLN-18 — 실제 UI 상태와 경보 수명주기를 시험

**근거:** [IVI M5](../../../plan/detail/ivi/M5_성능_UI개선.md)의 SocGauge는 300ms 애니메이션을 사용하고 설명은 T4를 애니메이션 시작으로 잡는다. 동시에 공동 측정은 화면 그리기 완료를 요구한다. AlertBanner는 attackType만으로 effect를 재실행하므로 같은 유형의 새 경보가 반복될 때 표시 갱신·자동 숨김의 의미가 불명확하다. `stale` 전달은 ICD §2.5 설명과 §3 HIDL 선언에 여전히 차이가 있다.

**개선:** 값 수신·StateFlow 갱신·첫 실제 그리기·애니메이션 완료를 구분하고 공식 T4를 합의한 이벤트로 계측한다. 단순 함수 호출을 화면 반영으로 대체하지 않는다. SOC 색상 경계·SHUTDOWN/CRITICAL 표시·동일 유형 반복 경보·다른 경보 교체·정상 복귀·인증 오류·통신 단절·앱 재기동을 시나리오로 정의한다. 경보 자동 해제는 공격 종료 판정인지 표시 시간 만료인지 명확히 한다.

**완료 조건:** 같은 공격이 지속되는 동안 경보가 이유 없이 사라지거나, 과거 경보가 새 경보를 지우지 않는다. 통신 단절을 정상 배터리 값으로 오인하지 않으며, stale의 외부 전달 방식은 ICD 승인·양측 동기화 후 구현한다.

### 8. 실제 개선에 앞서 확정할 사항

이번에는 개선안만 작성하므로 다음 사항을 임의 결정하지 않았다. 후속 개선 단계에서 중복 질문 없이 번호를 붙여 인터뷰하고 답변을 결정 기록에 연결한다.

1. 실제 장비 명세: MCP2515 모듈/트랜시버·전압·클록, ADS1115 배선·입력 범위, 디스플레이·전원·저장장치.
2. 모델의 적용 범위: 10직렬·50Ah가 시뮬레이션 기준인지 실제 팩 기준인지, OCV 데이터와 정확도 평가 자료의 출처.
3. ICD 미결정: stale 전달 방식, 송신기 재부팅을 구분할 SecOC 재동기화 절차와 보안 가정.

### 5. 남은 순서

아래 순서는 이 보고서 작성 당시 목록이다. 사용자 요청 1·2번에 대한 분류·처리 결과는 §6을 우선한다. 최종 인수 판정은 별도 단계다.

2. M6~8의 보고·재현·제출 증거와 일정 의존성의 잔여 충돌을 확인한다.
3. 새 정책 판단이 필요한 결함만 종합 인터뷰하고 답변을 반영한다. 이미 답한 항목이나 근거 없는 운영값을 재질문하지 않는다.
4. 재검사 후 이 보고서의 기준별 잔여 사항을 갱신하고 plan 완성 여부를 판정한다.
5. 완성 후 사용자 명시 지시가 있을 때 Plan의 유효 내용 대조·통합·재검사를 진행한다. 현재는 통합하지 않는다.

### 4. 검증과 다음 인계

재현 명령은 `python tmp/validate_scope12.py`, `python tmp/check_scope12_examples.py`다. 첫 검사는 활성 24문서와 이번 보고 문서의 로컬 링크·앵커·ID 존재·코드 펜스·Python 문법, 변경 전후 해시를 검사한다. 두 번째는 M6 문서에서 추출한 지표 검증 함수의 경계값과 CMake 등록/시험 파일을 검사한다. 상세 출력과 파일별 코드 블록 목록은 `tmp/plan_review_20260908_scope12/validation.json`, `example_checks.json`에 둔다.

검증 결과: 활성 plan 24개와 보고서 2개에서 로컬 링크 485회·앵커/ID 존재·펜스 검사 오류 0건, Python 블록 15개 문법 검사 통과. 문서 함수 경계값 12개 통과, CMake 등록 13종과 시험 파일 존재 및 문서 목록 일치 확인. 코드 블록 목록은 총 277개이며 이 수는 런타임 시험 통과 수가 아니다. 변경 전후 해시 대조에서 제품 소스·공식 계약의 변경은 없었다. 검증 스크립트의 Windows 경로 구분자 처리 오류를 수정한 뒤 재검사했다.
