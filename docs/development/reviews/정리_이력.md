### 8. 추가 개선 계획 — Plan을 ECU·IVI 두 파일로 통합

추가 검토일: 2026-09-05. **이번 요청의 산출물은 통합 계획이며, 실제 Plan 파일의 통합·삭제는 아직 수행하지 않았다.**

목표는 `Plan/` 아래에 `ECU.md`와 `IVI.md` **두 파일만** 남기고, 이 두 문서를 담당자별 프로젝트 진행 기준으로 사용하는 것이다. INDEX, 공동 계획, 연계 분석, 별도 최종판, 하위 보관 폴더는 남기지 않는다. 기존 내용을 단순히 두 파일에 이어 붙이지 않고 작업 단위로 재편한다.

이 목표는 앞선 CLN-03·CLN-04의 후속 방안을 구체화한다. 특히 CLN-04의 ‘파일 역할 유지’ 권고는 **필요한 역할만 두 계획에 흡수하고 별도 파일은 폐지**하는 방향으로 대체한다. 7절의 목록·크기는 최초 조사 기록이며, 통합 후 구조를 나타내지 않는다.

#### 8.1 최종 구조와 문서 경계

```text
Plan/
├── ECU.md    # Node A 개발·보안·실험 및 ECU 인계 과제
└── IVI.md    # Node B 개발·표시·측정 및 통합 운영 과제
```

두 계획은 ‘누가, 어떤 순서로, 무엇을 만들고, 어떤 근거로 완료하는가’를 설명한다. CAN 바이트 레이아웃·SecOC 규칙·HAL API는 `docs/ICD.md`, 요구사항은 `docs/SRS.md`, 설계는 양측 SDD, 시험 절차·합격 기준은 `docs/TEST_PLAN.md`, 채택 결정은 `docs/ADR.md`를 참조한다. 공식 문서를 없애거나 계획 문서가 계약을 재정의하지 않는다.

계획의 진입 링크는 루트 `README.md`에 두 개만 제공하는 방안을 권고한다. 별도 `Plan/README.md`나 대체 INDEX는 만들지 않는다. 이 보고서도 통합 과정을 검토하는 기록일 뿐 세 번째 운영 계획으로 사용하지 않는다.

`docs/ROADMAP.md`에 남은 상세 일정·체크리스트를 계속 병행 갱신하면 두 파일 체계가 성립하지 않는다. 실제 통합 시 유효한 일정·고유 위험·미팅 기록을 대조하고, 진행 과제는 두 계획에 흡수한다. ROADMAP은 이전 일정 기록임을 표시하고 활성 계획 두 개로 연결하도록 전환하는 안을 권고한다. 기존 기록은 보존하되 별도 실행 기준으로 유지하지 않는다. 관련 Source of Truth 안내도 함께 정리하며 ICD 등 공식 계약의 우선순위는 바꾸지 않는다.

예를 들어 ECU 계획에는 ‘더미 키 기반 SecOC 벡터 생성·전달’ 과제를 한 번 정의하고, IVI 계획에는 ‘전달받은 벡터로 인증기 검증’이라는 별도 과제를 둔다. 벡터 생성 절차·진행률을 IVI 문서에 복사하지 않는다. 통합 시험 전체의 결과는 IVI 측 통합 과제 한 곳에서 관리하고 ECU 측 준비 상태는 ECU 과제 링크로 확인한다.

계획용 ID는 `ECU-SEC-01`, `IVI-SEC-01`, `IVI-INT-01`처럼 역할·영역별로 부여하는 안을 권고한다. 이는 새 계획을 작성할 때 사용할 **제안 ID**이며 공식 FR·TC·ADR ID를 대체하지 않는다. 상호 링크에는 고정 앵커를 사용하고 제목 수정으로 링크가 끊기지 않도록 한다.

#### 8.4 두 파일의 권장 목차와 필수 범위

목차의 틀은 맞추되, 내용을 같은 길이로 맞추거나 공통 문장을 반복하지 않는다.

| 7. 최종 인수 | ECU 산출물·설계 반영·보안 실험 자료 전달 | 전체 인수·데모·제출과 공통 일정·릴리즈 관리 |

필수 기능은 축약 과정에서 삭제하지 않는다. ECU 측은 CAN/Mock/Publisher, 센서 입력, SOC·SOH·Fail-safe·Watchdog, SecOC, 공격·IDS·실험·측정, 단위시험과 IVI 인계가 포함돼야 한다. IVI 측은 플랫폼 결정, CAN 수신·파싱, SecOC 검증, 데이터 전달 계층, BMS 표시·Fail-safe·IDS 경보, 지연 측정, 통합·안정성·배포 준비가 포함돼야 한다. 공식 요구사항에 있는 미구현 기능은 구현 과제로 남긴다.

각 실행 과제는 아래 항목으로 작성한다. 본문에서 이미 정의한 항목을 월별 요약·부록·최종 QA 표에 다시 복사하지 않는다.

| 필드 | 작성 기준 |
|---|---|
| ID·작업명·책임자 | 한 과제를 식별하고 주관자와 협력자를 구분 |
| 상태·근거 | 미착수/진행/검증대기/완료/차단 중 하나와 실제 파일·시험 기록 |
| 선행 조건 | 상대 과제 ID, 필요한 입력·장비·결정 |
| 수행 내용 | 구체 행동과 필요한 최소 명령; 단순 설치 교육·전체 코드 제외 |
| 산출물 | 실제 또는 예정 경로를 명확히 표시 |
| 완료 기준 | 관련 공식 FR/TC 링크와 필요한 시험·인수 증거 |
| 인계 | 받는 사람·제공물·인수 확인 방법 |

#### 8.6 일정·IVI 방향·시험 기준을 잘못 계승하지 않는 방법

- 기존 M1~M8은 작업 순서를 대조하는 기준으로 활용한다. 현재 날짜만 보고 앞선 단계를 완료로 처리하거나 기존 2026-06~2027-01 일정을 임의로 새 일정으로 확정하지 않는다. 실제 완료 증거와 남은 작업을 확인한 후 목표일을 공통 일정 표에서 재설정한다. 확정되지 않은 날짜는 미정으로 표시한다.
- 현재 IVI는 빈 측정 스크립트뿐이다. Android 계획이나 다른 브랜치의 Qt 설명을 현재 구현으로 승격하지 않는다. 실제 통합 시 플랫폼 채택 결정·코드 확보 범위를 확인하는 과제를 맨 앞에 둔다. 결정 후 채택 경로만 상세화하고 대안은 전환 조건·영향·ADR 링크로 축약한다.
- CI/Docker/QEMU 역시 현재 구현이 없으므로 기존 구성 완료 표시를 복사하지 않는다. 필요한 CI 목표는 유지하되 도입 여부·실행 환경·선행 조건을 명시한다.
- `Plan/팀간_연계_분석.md:788` 이후에는 계약 일부 확정 상태의 진행, 단축 안정성 시험 등 우회 제안이 있다. 이를 공식 합격 기준의 대체 수단으로 자동 채택하지 않는다. 부분 검증은 부분 검증으로 기록하고 ICD 변경이나 합격 기준 완화는 별도 승인 절차를 따른다.
- 통합 시험은 공식 `TC-INT-001`~`TC-INT-004`로 추적한다. 기존 IT 시나리오 중 서로 다른 정상·변조 조건은 보존하되 기존 대응표에 따라 공식 TC의 하위 수행 조건으로 통합한다. 이름이 비슷하다는 이유로 시험 조건을 삭제하지 않는다.

### 2. 보존 및 복원

수정 전 파일 82개를 `tmp/cleanup_backup_20260905_212357/originals.zip`에 보존했다. 같은 폴더의 `manifest.json`은 원본 경로·SHA-256 목록이다. ZIP 무결성과 82개 항목의 해시 일치를 검증한 뒤 원본을 교체했다. 백업은 프로젝트 내 `tmp/` 임시 복원 공간이며 최종 운영 계획이 아니다. 장기 보존 시 별도 보관 또는 버전 관리가 필요하다. Git 생성·커밋·푸시는 수행하지 않았다.

### 5. 남은 구현·문서 한계

- IVI·CI·실측 도구는 여전히 미구현이다. 이 작업은 기능 구현 요청이 아니므로 코드를 생성하지 않았다.
- 실제 센서 I2C·Watchdog 복구·CAN 공격/실시간 IDS 경로 등 기존 요구와 구현 간 차이는 계획 과제에 남겼다. 공식 기준을 조용히 수정하지 않았다.
- TC-PERF-001 등 측정 설명과 지표의 지점 차이는 Common/IVI 측정 과제에서 확인하도록 기록했다. 판단이 필요한 실제 기준 변경은 인터뷰 후 수행한다.
- 역사 문서의 과거 경로·브랜치·수치와 제외된 외부 자료 링크는 당시 기록이다. 활성 안내로 사용하지 않도록 표시했다. 보안 연구 HTML은 본문을 보존했으며 현재 방향은 Plan을 따른다.

### 2. 의미 단위 병합과 충돌 처리

과제별 `새 위치 / 보존한 조건 / 대체 이유`는 [공동 병합 기록](../../../plan/detail/common/00_협업_규약.md#plan-merge-20260908)의 24행과 연결된 상세를 따른다. 이 표는 상태를 복제하는 표가 아니며 실행 상태·결과는 기존 역할 진행 표와 공동 인수 기록에 남긴다. 과제 ID는 공식 FR/NFR/TC를 대체하지 않는다. 원문의 요구/시험 색인은 기존 공동 연계 §10~11의 원천 매핑에 연결한다.

### 3. 병합 후 검증과 판정

검증 명령: `python tmp/validate_plan_merge.py`. 원문 8개 해시, 과제 ID 24개의 단일 주관 앵커, 기존 Plan 앵커의 안내 도달, FR/NFR/TC 원천 참조, 활성 24문서·Plan 안내·보고서의 링크/앵커/펜스, 변경 범위를 확인했다. 결과는 `tmp/plan_merge_20260908/validation.json`에 보존한다.

- 원문 8개 모두 보존 위치에서 SHA-256 일치.
- 과제 ID 24개 모두 활성 plan에서 단일 주관 앵커로 연결.
- 기존 Plan 앵커 427개 보존, 새 위치 안내 링크 확인.
- 활성 계획 24개·Plan 안내 8개·보고서 3개의 로컬 링크 1,026회와 앵커/ID/펜스 검사 오류 0건.
- 짧은 원문 3개에 명시적으로 등장하는 공식 참조 76종이 활성 계획에 존재함을 확인. 이 수는 축약 범위 전체나 의미상 시험 충족의 건수가 아니다.
- 제품 소스·공식 계약·기존 archive 파일의 변경 없음. 추가 보존 원문 3개는 텍스트 증거이며 기존 원본을 덮어쓰지 않음.

**병합 판정: 완료.** 일관성·통일성은 현재 원천/결정으로 충돌을 처리하고 단일 주관 위치로 연결했다. 호환성·적합성은 플랫폼/입출력·단계 인계와 기존 실행 관문을 보존했다. 정확도·신뢰도는 단위/측정 정본·증거/실패 처리와 IF 필수 조건을 유지했고, 확장성은 기존 계약 변경 절차를 유지했다. 기존 계획 문서 확정 판정을 유지한다.

판정 범위는 문서 병합과 기존 계획 인수 조건의 보존이다. 실제 CTest·Android·CAN·장비·CI 실행은 수행하지 않는다. 기존 계획 확정의 효력과 E1~E6 실행 관문은 유지하며, 동일 원문의 런타임 검증을 다시 완료했다고 주장하지 않는다.


### 4. 폴더 단일화 정정

앞선 통합은 Plan 폴더에 안내 파일을 남겼으므로 물리적인 폴더 단일화가 아니었다. 사용자 지적을 반영하여 안내 파일 8개와 Plan 폴더를 제거하고 저장소 내부 링크를 현행 plan 또는 보존 원문으로 수정했다. 이전 §3의 Plan 앵커 보존 검사는 안내 파일이 존재하던 시점의 결과다. 삭제한 Plan 경로의 외부 북마크는 유지되지 않으며, 과제 ID 24개의 주관 앵커는 plan에서 유지한다.

원문 8개의 보존 해시는 그대로 검증한다. AGENTS의 스냅샷·경로와 CLAUDE의 대응 안내를 동기화했고 CODEX/SKILL의 plan 참조는 변경할 필요가 없음을 확인했다. 검증은 `python tmp/validate_plan_folder_cleanup.py`로 수행한다.
