## 1. 개요와 핵심 결과

두 Raspberry Pi 노드를 물리 CAN으로 연결해 정상 BMS 전달, 인증 후 상태 게시, ADC 입력에 따른 Fail-safe 전이, Qt 표시 경로와 보안 방어 구성의 동작을 관측했다. 본 실험은 C1 무방어, C2 SecOC, C3 SecOC+규칙·Isolation Forest(이하 IF)의 세 구성과 flooding·fuzzy·replay·spoofing 네 입력 조건을 비교한다.

**계획된 12조건×100개 시행 번호의 기록은 수집되었다.** 최초 시도 기준 1,200개 중 VALID 1,196개와 INVALID 4개이고, C1 flooding의 재시도 1개를 포함한 전체 원장은 1,201개다. 수집 완료는 모든 요구사항 합격 또는 모든 전송의 무손실을 의미하지 않는다. 실패와 미수집 항목은 분석의 일부로 남긴다.

| 핵심 항목 | 관측 결과 | 논문 해석 범위 |
|---|---|---|
| 정상 소프트웨어 표시 경로 | 1,000표본, T1→T4 평균 6.473276ms, 최대 65.029527ms | Qt frameSwapped 기준 프로젝트 지연 조건 충족 |
| 정상 BMS 주기 | 1,498간격, 99.917~100.267ms | 해당 정상 시험의 100ms±10ms 조건 충족 |
| ADC·Fail-safe | BMS 인증 1,057건, WARNING→CRITICAL 전이 인증 간격 약 32.626초 | 노브 입력과 인증 이벤트·화면 관측 연결 |
| 정상 오탐 | 규칙 0/298창, 규칙+IF 1/298창 | constant 정상 캡처 재생 평가에 한정 |
| C3 참조 탐지 | flooding 98/98유효, 나머지 각 100/100유효 | 탐지 여부이며 공격 유형 분류 정확도가 아님 |
| C3 지연 | flooding 23개 채택 표본, 나머지 각 100개 | 탐지된 유효 시행의 조건부 지연 |
| 보안 해석 | C2/C3 spoofing 주입 게시 0건, replay 주입 게시 각각 116/137건 | 게시 출처와 인증 프레임 출처를 구분해야 함 |

수치의 상세 분모, 제외 사유, 원본 경로는 아래 표와 [기계 집계](physical-ablation-formal-2026-10-04/publication/summary.json)에 연결한다.

## 3. 시스템과 실험 환경

### 3.1 구성과 역할

Node A는 C++ ECU의 정상 BMS 송신과 Python 실험 실행기·주입기·참조 수신기·IDS 프로세스를 실행한다. Node B는 SocketCAN 수신, SecOC 검증, 서비스 상태 갱신 및 Qt Quick 대시보드를 실행한다. 참조 수신기는 별도 관측 프로세스이지만 공격 주입·ECU·IDS와 같은 호스트 자원을 사용한다. 독립 장비의 공격 발생기로 간주하지 않는다.

CAN ID·DLC·레이아웃·스케일·HMAC 입력 순서는 [ICD](../../ICD.md)를 따른다. 보고서에서 계약을 새로 정의하거나 변경하지 않는다. BMS와 인증, Fail-safe와 인증, IDS 경보 경로는 각각의 원본 프레임과 수신 결과로 대조한다.

**표 1. 본 실험의 주요 환경과 고정 조건**

| 항목 | 기록된 조건 | 주의점 |
|---|---|---|

| CAN | can0, 500kbps, sample point 0.750, restart-ms 100 | 가상 CAN 시험과 구분 |

실험 코드 전체 해시, 바이너리 해시와 시계 정의는 [run별 요약](physical-ablation-formal-2026-10-04/publication/runs/) 및 [전체 provenance](physical-ablation-formal-2026-10-04/publication/provenance.json)에서 확인한다. 기반 커밋만으로 미커밋 변경이 포함된 전달본을 식별하지 않는다. 실제 키·장비 주소·자격 증명은 보고서에 포함하지 않는다.

### 3.2 실행 검증과 실측의 구분

장비에서 ECU CTest 17개 통과, IVI CTest 12개 통과·SocketCAN 1개 skip 기록이 있다. Python 보완 전달본은 v7 83개, v8 88개 시험 통과 기록이 있으며, 후속 오프라인 분석 보완의 97개 통과는 [감사 조치 기록](../reviews/experiment-evidence-audit-2026-10-04/REMEDIATION.md)에 별도로 남아 있다. 단위 시험 통과가 본 실험의 모든 물리 전송·화면 동작 합격을 대신하지 않는다.

## 4. 실험 설계

**표 2. 방어 구성**

| 구성 | SecOC | 실시간 IDS | 목적 |
|---|---|---|---|
| C1 | OFF | OFF | 인증 없는 수신 기준선 |
| C2 | ON | OFF | 인증 추가 시 수신·게시 변화 관측 |
| C3 | ON | 규칙+IF | 탐지·경보 전달 및 정상 전달 동시 관측 |

**표 3. 본 실험 입력과 반복 조건**

| 입력 | 요청 송신률 | 공격 구간 | 시행 전/후 구간 | 계획 번호 수/구성 | 평가 초점 |
|---|---:|---:|---|---:|---|
| flooding | 2,800fps | 3초 | baseline 2초 / post 1초 | 100 | 부하·정상 전달·IDS 경보 |
| fuzzy | 1,000fps | 3초 | 동일 | 100 | 무작위 입력 처리·형식 거부·경보 출처 |
| replay | 1,000fps | 3초 | 동일 | 100 | 재전송 입력·counter 거부·게시 출처 |
| spoofing | 1,000fps | 3초 | 동일 | 100 | 위조 BMS 입력 게시·인증·탐지 |

fps는 실행기에 전달한 요청값이다. 실제 송신 수, 실제 구간 길이와 canbusload 결과를 구분한다. 공격의 구현·seed·실행 인수는 원장과 manifest를 기준으로 재현한다. 각 공격은 같은 이름의 모든 가능한 공격 전략을 대표하지 않는다.

이번 flooding 입력은 ID 0x000의 8바이트 프레임, fuzzy는 무작위 11비트 ID와 8바이트 payload, spoofing은 SOC 목표값을 조작한 0x100 입력이다. 실시간 replay는 baseline에서 수락된 데이터를 캡처하며 C1은 BMS, C2/C3는 BMS·인증 쌍을 재전송한다. 따라서 replay의 세 구성이 완전히 같은 wire sequence를 사용한다고 표현하지 않는다. 공격별 seed는 `100000 + 1000 × 공격 인덱스 + 시행 번호`이며 인덱스는 fuzzy=0, replay=1, spoofing=2, flooding=3이다. 같은 번호에 구성별 seed는 같지만 실제 프레임 수·시각은 실행 결과를 따른다. 근거는 [입력 생성 코드](../../../security/attacks/attack_simulator.py), [실시간 실행기](../../../security/experiments/live_ablation.py), [seed 정의](../../../security/experiments/ablation_core.py)와 각 run 소스 해시다.

IVI를 먼저 새 인스턴스로 준비하고 receiver JSONL·오류 프레임 포함 candump·canbusload·CAN 전후 통계를 수집했다. ECU는 준비 확인 뒤 실행기를 시작했다. 종료 뒤 양측 원본과 종료코드를 보존했다. 초기 실행 일부의 독립 실행 명령 파일·정확한 프로그램 시작/종료 시각은 미수집이며, before/after-time을 그 대체값으로 쓰지 않는다.

### 4.1 정상 IF 데이터 분리

fit, calibration, evaluation을 서로 다른 연속 300초 구간으로 수집했다. 세 구간의 프레임 수는 각각 5,994 / 5,996 / 5,995개이며 원본 해시가 서로 다르다. calibration 299벡터의 alpha=0.01, 순위 297로 정한 임계는 0.16895086896792122다. evaluation은 warmup 2초를 제외한 완전한 298창을 사용한다. 시간 구간을 분리했지만 동일 장비·constant 조건이므로 운전 조건 전반에 독립적인 데이터셋이라고 확대 해석하지 않는다.

IF 구현은 기본 트리 수 100, contamination 0.05, random_state 42이며 별도 정상 calibration으로 판정 임계를 보정한다. contamination과 calibration alpha를 최종 실측 FPR로 대신 쓰지 않는다. 1초 창의 7차원 특징은 메시지 수, 평균·표준편차 IAT, 고유 ID 수, ID 엔트로피, 동일 ID의 payload 변화, 단일 ID 최대 프레임 수다. [IF 구현](../../../security/ids/if_detector.py)과 [특징 추출](../../../security/ids/feature_extractor.py)의 해시는 본 실험 16실행 manifest와 일치한다. 최종 FPR은 독립 evaluation의 실제 판정으로 보고한다.

### 4.2 중단·재시도 처리 정책

원래 TEST_PLAN은 조건별 유효 100회를 요구했다. 수행 중 사용자 지시로 오류도 포함한 계획 100회 수집으로 운영했으며 이를 **DEV-EXP-001**로 기록했다. INVALID는 삭제하거나 성공으로 바꾸지 않는다. 비교 표의 기본 표본은 계획 번호별 최초 기록이고, 재시도는 보조 증거다.

C1 flooding 7번은 처음 INVALID 뒤 재시도에서 VALID였지만 최초 INVALID를 유지한다. C3 flooding의 3번·77번 중단도 INVALID로 남기고 다음 번호로 이어갔다. 수집 정책 변경을 보안·성능 요구사항의 소급 완화로 해석하지 않는다.

## 5. 지표 정의와 분석 방법

**표 4. 지표별 관측 단위와 분모**

| 지표 | 정의·분모 | 해석 제한 |
|---|---|---|
| VALID / INVALID | 실행기가 해당 시행의 송신·관측·프로세스 조건을 판정 | VALID는 IVI 무손실 또는 제품 PASS가 아님 |
| 참조 탐지율 | 공격 후 평가 구간에서 비주입 경보가 관측된 VALID 시행 수 / 해당 VALID 시행 수 | C3만 적용; 유형 라벨 정답 여부와 별도 |
| 참조 탐지 지연 | 최초 주입 own echo → 참조 수신기의 첫 경보 | IVI 화면 표시 시각·순수 알고리즘 계산 시간이 아님 |
| 정상 전달률 | 공격 구간에 유래한 비주입 BMS 게시 수 / 기대 BMS 수 | 기대 수는 실제 공격 구간 길이/0.1초를 반올림 |
| 주입 게시 수 | own echo 출처로 연결된 입력이 참조 수신기에서 게시된 수 | IVI 전체 인증 성공 건수와 별도 |
| 참조 공격 성공 시행 | 공격별 실행기 성공 조건을 만족한 시행 / 측정 가능한 VALID 시행 | 공격 간 단일 의미의 성공률로 합치지 않음 |
| 정상 FPR | 정상 평가 중 이상 판정 창 / 완전한 정상 평가 창 | 프레임 단위 FPR 아님 |
| T1→T4 지연 | IVI CAN 수신 직후 → Qt frameSwapped 처리 | 물리 픽셀 표시 시각 미측정 |
| 버스 점유율 | canbusload 설정과 수신 프레임 기반 산정 | 요청 fps만으로 계산·판정하지 않음 |

baseline은 실제 baseline 시작부터 공격 시작까지, 공격 구간은 공격 시작부터 종료까지다. 참조 판정은 공격 시작부터 post 종료까지 수집한 결과를 사용하되 정상 데이터의 원래 수신 시각이 공격 구간에 속하는지 확인한다. 시행 길이 변동으로 기대 합계가 항상 3,000이 되는 것은 아니다. C3 replay의 분모 3,001을 임의로 3,000으로 바꾸지 않는다.

참조 성공 정의는 replay의 주입 데이터 게시, spoofing의 목표 BMS 값 게시, fuzzy의 비정상 BMS/Fail-safe 입력 게시 여부를 사용한다. flooding은 임의의 전달률 임계를 사후 추가하지 않아 성공 여부를 N/A로 둔다. fuzzy 성공 0건은 비인증 IDS 경보 경로까지 안전했다는 뜻이 아니다.

지연 평균·p95·최대는 **탐지된 유효 시행에 조건부**다. p95는 nearest-rank이며 미탐지·INVALID를 0ms로 넣지 않는다. C1/C2는 IDS가 꺼져 있어 탐지율을 0% 대신 N/A로 표시한다. 공격별 반복은 같은 장비에서 순차 수행되었으므로 독립·동일분포 표본으로 가정한 신뢰구간이나 인과적 유의성 검정을 추가하지 않았다.

### 5.1 양측 로그 대조

ECU 프레임 원장, own echo, IVI candump와 receiver를 CAN ID·payload·순서로 대조한다. 캡처 시작/종료 범위가 달라 생긴 tail과 공통 관측 구간의 누락을 구분한다. IDS는 로컬 탐지 이벤트, ALERT_SENT, ECU 비주입 0x200 및 IVI 수신을 연결한다. fuzzy가 주입한 0x200은 실제 IDS 송신에서 제외한다.

인증 게시 출처 분석은 프레임 순서와 직전 대기 BMS·인증 프레임의 관측상 대응이다. 반복 payload가 동일하면 개별 프레임의 일대일 신원은 모호할 수 있다. 오프라인 도구는 비밀 키를 사용해 MAC을 다시 계산하지 않는다. [재현 절차](physical-ablation-formal-2026-10-04/REPRODUCE.md)와 [판정 코드](../../../security/experiments/live_trial.py)를 함께 참조한다.

| C3 spoofing | 주입 2프레임 미관측, IVI RX 오류 증가 | 동일 payload의 개별 신원 모호성 포함 |
| C3 경보 전송 | 기록된 ALERT_SENT와 ECU 비주입 경보·IVI 수신 대응 | 송신 실패 진단·로컬 탐지 이벤트는 별도 |

모든 C3 경보 라벨이 주입 공격 이름과 같지는 않다. 예를 들어 flooding 중 UNKNOWN_ID 기반 경보가 Fuzzy로 표시될 수 있다. 따라서 이 결과는 “공격 존재 탐지” 표이며 다중 클래스 분류 정확도 표가 아니다. IVI에서 유지된 경보 배너만으로 현재 공격이나 새로운 IDS 판정을 추정하지 않는다.

## 9. 방어 구성별 비교 분석

### 9.1 C1과 C2: 인증 적용 후 게시 양상의 변화

spoofing에서 참조 주입 게시가 C1의 278,232건에서 C2의 0건으로 달라졌다. replay는 C1 278,319건과 C2 116건이었다. 이 관측은 해당 입력과 설정에서 인증 적용에 따라 게시 양상이 크게 달라졌음을 보여준다. 비교는 순차 실험이므로 무작위 배정된 인과 효과나 일반적인 공격 전량 차단율로 표현하지 않는다.

replay의 남은 게시 116건은 payload 출처와 인증 출처를 함께 검토해야 한다. 재전송 payload와 정상 송신 payload가 같고 새 정상 인증 프레임이 결합되는 경우, 주입 출처로 대응된 payload가 게시될 수 있다. 이를 곧바로 과거 인증 counter를 재수락한 replay 방어 실패나 MAC 위조 성공으로 판정하지 않는다. 반대로 “replay 입력은 단 한 건도 게시되지 않았다”도 사실과 다르다.

fuzzy는 세 구성 모두 실행기 정의의 공격 성공 게시가 0건이다. C1에서도 0건이므로 이를 SecOC만의 효과로 설명할 수 없다. 형식 검사와 해당 입력의 특성이 함께 작용한다. 특히 0x200 경보 경로는 SecOC 보호 대상 밖이므로 주입 입력이 UI 경보로 처리된 별도 한계를 기록한다.

### 9.2 C2와 C3: 경보 추가와 정상 전달의 병행 관측

C3는 유효 시행에서 비주입 IDS 경보를 관측했다. 그러나 IDS는 탐지·경보 기능이며 CAN의 모든 공격 프레임을 직접 제거하는 차단기로 평가하지 않는다. C3가 C2보다 모든 공격 데이터 게시나 정상 전달에서 우수해야 한다는 전제를 두지 않는다.

replay의 주입 게시 수는 C2 116건, C3 137건인 반면 게시가 있었던 시행 수는 각각 72회와 46회다. 프레임 수와 시행 수는 서로 다른 집계 단위이므로 한쪽만 선택해 일관된 개선을 주장하지 않는다. 정상 전달은 C2 2,880/3,000, C3 2,864/3,001로 관측되었다.

spoofing의 정상 전달은 C2 2,759/3,000과 C3 2,802/3,000이고 주입 게시 수는 둘 다 0건이다. 이 차이를 IF의 개선 효과로 귀속하지 않는다. 이번 공격 원장에서는 IF 이벤트가 0건이며 규칙 처리·큐·호스트 스케줄링·인증 대기 데이터 경쟁이 분리 통제되지 않았다.

### 9.3 flooding과 가용성

정상 전달은 C1 2,929/2,940, C2 2,967/3,000, C3 v8 부분집합 446/690이다. C3에서 경보가 탐지되어도 정상 전달이 보장되는 것은 아님을 보여준다. C3 부분집합과 C1/C2 전체를 동일 계측·동일 버전의 공정한 성능 순위로 제시하지 않는다. IDS·주입기·ECU가 같은 호스트를 사용하므로 CPU/큐 경쟁과 CAN 부하 효과를 분리한 추가 설계 없이는 원인을 확정할 수 없다.

canbusload의 공격 내부 완전한 1초 표본에서 50% 이상 관측한 기록과 “공격 시작 1초 이내 점유율 50% 도달”은 다른 주장이다. 후자는 기존 내부 표본만으로 일괄 인수하지 않는다. qdisc drop 증가 역시 로컬 큐 문제이며 양측 CAN 캡처의 실제 누락과 동일한 숫자로 사용하지 않는다.

## 11. 결론과 후속 과제

이번 실험은 물리 ECU–IVI 환경에서 정상 인증·상태 전이·Qt 표시 경로를 연결했고, 세 방어 구성과 네 공격 조건의 계획 시행 기록을 확보했다. SecOC 적용 시 해당 spoofing 입력의 참조 게시가 0건으로 관측되었고, C3의 유효 시행에서는 IDS 경보가 관측되었다. 동시에 정상 전달 저하, 경보 출처 혼재, 동일 payload의 인증 결합 및 계측 버전 차이를 확인했다.

논문은 이 관측과 한계를 함께 제시할 수 있다. 모든 요구를 충족한 제품 인증이나 IF의 단독 우수성을 결론으로 삼지 않는다. 현재 자료로 작성 가능한 결론과 추가 자료가 필요한 결론은 다음과 같다.

| 후속 항목 | 현재 자료로 수행 가능 | 추가 실험 필요 여부 |
|---|---|---|
| 본 보고서 기반 방법·결과·고찰 작성 | 가능 | 불필요 |
| 원본 기반 표·그림 재생성 및 출처 표기 | 가능 | 불필요 |
| 전체 100회가 동일 최종 버전에서 유효하다는 주장 | 불가 | 그 주장을 원할 때 별도 재시험 |
| IF의 규칙 대비 추가 탐지 기여 | 현 자료로 분리 불가 | 동일 조건의 구성 분리 실험 |
| 다양한 ADC 운전 조건의 FPR | constant 결과만 있음 | 별도 정상 데이터 수집 |
| 실제 화면 픽셀 지연·Qt 경고 영향 | 미측정 | 화면/광학/추적 계측 설계 |
| 0x200 인증·출처 신뢰 보완 | 취약한 경계 관측 있음 | 계약 영향 검토와 승인 후 별도 개발·시험 |

추가 실험을 이미 수행한 것으로 기록하지 않는다. 현재 논문의 주장 범위를 위 관측 수준으로 정하면 자료 정리와 원고 작성을 진행할 수 있다.

### 12.2 바로 활용할 수 있는 서술 예시

**실험 방법 예시**

> RPi4 기반 ECU와 IVI를 500kbps 물리 CAN으로 연결하고, 무인증 구성(C1), SecOC 구성(C2), SecOC와 규칙·IF IDS를 함께 실행하는 구성(C3)을 비교하였다. 네 입력 조건별로 100개 시행 번호를 계획하였다. 분석은 최초 시도를 기본 단위로 하며 INVALID와 재시도를 별도로 보존하였다. 공격 주입과 정상 ECU 및 IDS가 동일 호스트에서 실행된다는 자원 공유 조건을 명시하였다.

**반복·실패 보고 예시**

> 12조건의 계획 번호 1,200개를 수집하였고 최초 시도 기준 VALID 1,196개, INVALID 4개였다. C1 flooding의 추가 재시도 1개를 포함한 전체 원장은 1,201개였다. 따라서 계획 번호 수집은 완료되었으나 두 flooding 조건은 원래의 조건별 유효 100회 기준을 충족하지 않았다.

**정상 성능 결과 예시**

> 정상 인증 ON 조건에서 1,000개 완료 표본의 CAN 수신부터 Qt frameSwapped까지 평균 지연은 6.473276ms, 최대는 65.029527ms였다. 이 값은 소프트웨어 표시 경로의 지표이며 물리 픽셀 표시 시각을 의미하지 않는다.

**IDS 결과 예시**

> C3에서 flooding은 98개 유효 시행 모두, 나머지 입력은 각각 100개 유효 시행 모두에서 비주입 경보가 관측되었다. 경보 관측과 공격 유형 분류는 별도로 해석하였다. flooding의 지연은 계측 보완 후 23개 시행만 채택했으며 조건부 평균은 1.1416ms였다. 본 공격 원장에 IF 이벤트는 기록되지 않아 IF의 추가 탐지 기여는 입증하지 못했다.

**replay 해석 예시**

> C2와 C3의 참조 수신기에서 주입 출처로 대응된 replay payload가 각각 116건과 137건 게시되었다. 동일 payload와 새 정상 인증의 결합 가능성이 있어 이 건수를 과거 인증 counter 재수락이나 MAC 위조 성공 건수로 동일시하지 않았다.

### 12.3 표·그림을 논문에 넣는 방법

표 8의 표본 구성을 결과 절 첫 표로 배치한다. 표 9는 게시와 가용성, 표 10은 경보 탐지와 지연을 설명하는 별도 표로 사용한다. 지면이 부족해 축약하더라도 분모·INVALID·C3 flooding 23회 각주는 유지한다. 표 6·7은 정상 평가 표로 두어 공격 중 성능과 섞지 않는다.

| 권장 그림 | 데이터·구성 | 반드시 넣을 설명 |
|---|---|---|
| 시스템 및 신뢰 경계도 | Node A 프로세스, CAN, Node B 인증·Qt 경로 | 0x200 비인증 경로와 같은 호스트 자원 공유 |
| 계획 시행 결과 누적 막대 | 표 8의 최초 VALID/INVALID | 재시도는 별도 표시, 100유효처럼 표시하지 않음 |
| 정상 전달률 비교 | 표 9 | C3 flooding은 23회 부분집합이라는 별도 패턴·각주 |
| 지연 분포·ECDF | 채택된 개별 지연 원장 | 조건부 표본 수, C3 flooding 버전 제외 |
| replay 출처 타임라인 | 개별 원장의 BMS·인증·own echo 대응 | 같은 payload 식별 한계와 새 인증 결합 |

이 그림들은 후속 원고용 제작 제안이다. 이 문서에는 원본에 없는 분포나 그림을 만들어 넣지 않았다. 평균·p95·최대만으로 가상의 ECDF나 박스플롯을 구성하지 않는다. 그림을 제작할 때는 개별 채택 표본에서 다시 계산한다.

표 캡션 예: “물리 CAN 방어 구성별 참조 수신 결과. 계획 번호별 최초 시도를 사용하며 INVALID는 별도 집계하였다. C3 flooding의 전달률은 계측 보완 후 23개 시행에 한정한다.”

### 12.4 피해야 할 표현과 대체 표현

### 13.3 오프라인 재현

저장소 루트에서 아래 명령을 사용한다. 출력 경로는 아직 존재하지 않는 경로여야 한다. CAN 송신이나 장비 키 읽기는 수행하지 않는다.

```text
python -m security.experiments.publication --base docs/development/experiments/physical-ablation-formal-2026-10-04 --policy docs/development/experiments/physical-ablation-formal-2026-10-04/publication-policy.json --out tmp/publication-report-check
```

상세 절차는 [REPRODUCE](physical-ablation-formal-2026-10-04/REPRODUCE.md)를 따른다. `provenance.json`은 입력·정책·분석기 해시, `outputs-sha256.json`은 생성물 해시를 기록한다. 과거 분석기 38개는 이력용으로 보존되어 있으며 현재 재현 명령과 구분한다. 본 보고서의 네 생성 표는 보존된 summary.json과 대조 검증한다.

보고서 자체의 수치·참조 검증은 [검증기](../reviews/experiment-evidence-audit-2026-10-04/verify_final_report.py)와 [검증 결과](../reviews/experiment-evidence-audit-2026-10-04/final-report-validation.json)에 보존한다. 저장소 루트에서 `python -X utf8 docs/development/reviews/experiment-evidence-audit-2026-10-04/verify_final_report.py`로 다시 확인할 수 있다.

### 13.4 백업과 문서 범위

원본 실험 결과와 기존 문서의 로컬 검증 백업은 [BACKUP](physical-ablation-formal-2026-10-04/BACKUP.md)에 연결된다. 사용자는 해당 백업을 Google Drive에 업로드했다고 보고했다. 원격 파일의 재다운로드·해시 확인은 별도로 검증하지 않았다. **이 보고서는 기존 백업 생성 이후 추가된 문서이므로 기존 업로드 파일에 들어 있다고 간주하지 않는다.** 보고서와 이번 문서 연결 변경분은 다음 백업에 포함해야 한다.

이 문서의 서술은 결과 활용을 위한 종합본이다. 원본 로그·실패 판정·미수집 자료를 소급 변경하지 않았으며, 지표 정의와 수치가 충돌할 경우 연결된 원본·재현 정책부터 확인한다.
