# S-21 SOC 합성 사전 실험 결과와 후속 계획

문서 역할: 합성 실험의 조건·결과와 후속 제품 반영 이력이다. 현재 반영 기록은 §7~11을 함께 읽고, 채택 근거는 [SOC-1 답변](../governance/의사결정_기록.md#decision-soc1)·[ADC 답변](../governance/의사결정_기록.md#decision-adc), 합격 기준은 [공식 시험 계획](../../TEST_PLAN.md)을 따른다. 현재 실행 관문은 [종합 검토](../reviews/문서_종합정합성_검토.md#execution-gates-current)에 있다.

> 최신 상태: SOC-2=A에 따라 제품 코드·시험을 수정했다(§7). §1~6의 선형 제품·수정 대기 설명은 당시 검토 이력이다. C++ 실행 검증은 아직 완료되지 않았다.

실행일: 2026-09-08. 서버에서 받아오는 작업은 사용자 담당으로 제외했다. [공식 시험](../../TEST_PLAN.md)의 S-21=A와 [ECU M3](../../../plan/detail/ecu/M3_EKF_Failsafe_SecOC.md)의 목표 3차 모델을 수치 검토했다. **실제 ECU 실행 또는 TC-BMS-002 합격 결과가 아니다.**

## 1. 실행 조건과 범위

가상 용량 50Ah, 초기 SOC 80%, 참 전류 -2A, dt 0.1초, 36,000 update, 10직렬이다. 참 SOC는 시간과 참 전류로 독립 계산하며 최종 76%다. 관측 전류만 바이어스를 더하고, 참 SOC의 가상 OCV에 단셀 전압 바이어스를 더한 뒤 10배하여 팩 관측을 생성했다. 추정기는 팩 관측을 10으로 나눠 사용한다. 동일 전류 관측과 초기 상태를 전류 적분 비교기에 제공했다.

OCV 계수는 내림차순 `[2.1667, -3.7321, 2.7655, 3.0]`, 미분은 해당 다항식의 해석 미분이다. Q=1e-5, R=0.02, P0=0.01은 계획 예제의 기본값이며 실험 후 조정하지 않았다. 실장비 운용값으로 확정하지 않는다. Python 3.14.3 float64, 결정적 입력으로 seed 없음. 오차는 t=0을 제외한 update 직후 36,000개 표본의 SOC 백분율 포인트(pp)다. 참 상태 생성과 추정기가 같은 OCV를 사용하므로 모델 불일치·실제 셀 정확도를 검증하지 않는다.

## 4. 다음 실험 순서와 종료 증거

1. 목표 C++ 구현을 적용하는 작업에서 팩/단셀 경계와 기존 호출부·시험을 먼저 대조한다. 동일 7개 입력을 제품 추정기에 공급하고 본 결과와 수치 차이·원인을 보고한다. 공식 판정은 제품 출력으로 다시 계산한다.
2. ADS1115와 가변저항의 저·중·고 입력에서 기준계측 전압, raw ADC, 변환 전압, 가상 팩 전압을 함께 기록한다. ±4.096V 설정과 0~3.3V 입력 매핑은 기존 승인 조건을 유지한다. 실제 배선·전압 확인 전 연결 완료로 표시하지 않는다.
3. 측정한 전압 편향을 적용한 합성 재실험을 수행한다. 측정 전 편향값·보정계수·Q/R을 임의 확정하지 않는다. 보정이나 운영값 변경 판단이 필요하면 결과와 선택안을 제시해 인터뷰한다.
4. 가변저항 경로의 변화·복구를 검증한 뒤 시간 여유가 있으면 사용자 선택대로 실제 보조배터리 검증을 별도 수행한다. 실측 근거 없는 OCV 모델을 실제 배터리 정답으로 사용하지 않는다.

이 단계의 완료는 계획 모델의 사전 검토 완료다. 실제 하드웨어 시험, 상세 계약 승인, 네 기준 최종 판정은 남아 있으며 Plan 통합은 사용자 지시 전 수행하지 않는다.

## 5. 실제 호출부·설정 교차 검증 (2026-09-08)

`adaptive_ecu/src/app/sensor_simulator.cpp`는 팩 30~42V를 사용하고 `main.cpp`는 전압을 변환 없이 추정기에 전달한다. 그러나 `src/app/ekf_soc_estimator.cpp`는 단셀 선형 OCV를 사용한다. 기존 `test/test_ekf_soc.cpp`의 3개 시험 입력은 3.9/4.08/3.6V로 팩 입력 불일치를 직접 검사하지 않는다. 제품 기본 용량도 2.6Ah다. 이는 정적 대조 결과이며 제품 실행 결과가 아니다.

제품 소스 그대로 아래 컴파일을 시도했으나 MinGW GCC 6.3.0에서 `std::clamp` 미지원 오류로 실패했다. CMake도 PATH에서 확인되지 않았다. 제품 코드에 호환 기능을 삽입하거나 새 도구를 설치하지 않았다. C++17 표준 라이브러리가 있는 환경에서 제품 시험을 다시 수행해야 한다.

```text
g++ -std=c++17 -Wall -Wextra -Werror -I adaptive_ecu/include -c adaptive_ecu/src/app/ekf_soc_estimator.cpp -o tmp/s21_product_ekf.o
```

SDD §3.4.1은 R=0.01/P0=1.0/일반 초기 SOC=50%, M3 예제는 R=0.02/P0=0.01/일반 초기 SOC=75%로 다르다. 앞 절은 M3 예제 설정의 결과이며 공식 SDD 설정을 대표하지 않는다. `python tmp/s21_settings_review.py`로 R/P0만 SDD 값으로 바꿔 추가 비교했다. S-21의 초기 SOC 80%와 나머지 조건은 유지했고 최초 결과를 덮어쓰지 않았다.

후속 제품 회귀 검증에는 팩 OCV 입력 시 SOC 유지, 단셀 변환을 정확히 한 번 수행, S-21 7개 조건 비교를 포함한다. 기존 단셀 입력 시험은 목표 팩 입력 경계에 맞춰 수정하고 CAN 송신 전압은 팩 단위를 유지한다. 실제 장비 시험은 기준계측기와 배선 확인 후 §4 순서를 따른다. 서버 가져오기와 Plan 통합은 현재 수행 범위에서 제외한다.

유지 시험에서는 선택한 SOC의 3차 OCV를 팩 전압으로 만들어 입력한다. 방전 방향 시험은 시작 SOC에 해당하는 팩 전압과 음의 전류를 사용한다. 팩 입력을 0회 또는 2회 변환하는 잘못된 구현을 이 시험이 검출하는지도 확인한다. S-21의 필수 주 비교 2개는 각각 엄격 우위를 판정하고 민감도 4개는 역전까지 기록한다. 기존 TC-BMS-001·002를 사용하며 새 공식 TC ID를 임의로 만들지 않는다.

현재 확인한 로컬 PATH에는 GCC 6.3만 있고 clang++·cl·cmake는 확인되지 않았다. 전체 CMake 구성은 OpenSSL·Threads·GTest를 요구하고 SocketCAN 소스도 포함한다. 따라서 새 컴파일러 하나를 준비했다고 전체 ECU 시험 환경이 완성됐다고 보지 않는다. 의존성 설치·서버 가져오기는 이번에 수행하지 않았다.

## 7. SOC-2=A 제품 적용 결과 (2026-09-08)

후속 시험 보완: 무오차 대조군의 최대 오차를 float epsilon×36,000회×100의 보수적 수치 회귀 한계와 비교하고, 두 RMSE의 유한값을 검사한다. 이 한계는 센서 정확도나 공식 합격 기준을 새로 정한 값이 아니다. 낮음·중간·높음 SOC에서 독립 double 단일 갱신식을 사용해 SOC 의존 미분의 적용을 확인하는 시험도 추가했다. Python으로 세 기준 사례가 잘못된 상수 미분 1.2를 시험 허용차 1e-5보다 큰 차이로 구분함을 확인했다. C++ 변조 시험 통과를 뜻하지 않는다. 출력 정밀도는 12자리로 높였다.

로컬 PATH와 추가로 확인한 표준 Visual Studio/LLVM 위치에서 사용할 대체 C++ 도구를 찾지 못했다. 전 PC에 도구가 없다는 단정은 아니다. C++ 실행 증거를 만들 수 없는 현재 조건에서 동일 컴파일 실패를 반복하지 않고, 다음 실행은 C++17·CMake·의존성이 준비된 환경에서 수행한다. 서버 가져오기는 사용자 담당이며 별도 요청하지 않는다.

`adaptive_ecu/include/ekf_soc_estimator.h`와 `src/app/ekf_soc_estimator.cpp`에 목표 10직렬·50Ah·3차 OCV·SOC 의존 미분을 적용했다. 기본 SOC 75%, Q=1e-5/R=0.02/P0=0.01은 유지한다. 팩 입력은 `update()` 내부에서 한 번만 10으로 나눈다. `main.cpp`와 CAN/HAL 계약은 변경하지 않았다.

`test/test_ekf_soc.cpp`의 기존 3개 시험을 팩 입력에 맞춰 수정하고 저·고 SOC 유지 시험과 S-21 7조건 비교 시험을 추가했다. C++ 시험은 동일하게 float로 전달된 관측 전류·dt·초기 상태를 비교기에 사용하고 참 SOC는 독립 해석식으로 계산한다. Python float64 결과와 양자화 차이가 있으므로 출력이 완전히 같다고 가정하지 않는다. 무오차군·민감도 결과도 출력하며 엄격 우위는 주 비교 2개에만 적용한다.

제품 소스 컴파일을 다시 시도했으나 GCC 6.3에서 `std::clamp` 오류로 실패했고, 기본 CMake 구성 명령도 `cmake`를 찾을 수 없어 실패했다. 따라서 추가한 C++ 시험·변조 검출 확인·전체 CTest는 미실행이다. Python 계획 모델의 7조건 재실행은 통과했지만 제품 결과를 대신하지 않는다. 코드 적용 완료와 제품 검증 완료를 구분한다.

환경 확보 후 저장소 루트에서 AGENTS의 CMake 구성·빌드 명령을 실행하고 `ctest --test-dir adaptive_ecu/build -R test_ekf_soc --output-on-failure`로 검증한다. 7조건 지표를 보존할 때는 `ctest --test-dir adaptive_ecu/build -R test_ekf_soc -V`의 출력과 컴파일러·소스 해시를 함께 기록한다. 이후 공유 모듈 전체 회귀시험과 §6 장비 측정으로 이어간다. 서버 가져오기는 사용자가 직접 수행하므로 에이전트 선행 과제로 요청하지 않는다.

## 8. ADC 실험 착수 전 확인 (2026-09-08)

현재 `SensorSimulator::next()`의 ADS1115_HARDWARE 분기는 `adc_data_`를 반환한다. 초기값은 42V/-2A/25°C이며 실제 I2C 취득 코드는 없다. `setAdcVoltage()`는 외부 주입값을 범위 제한하는 함수로 하드웨어 드라이버가 아니다. 해당 모드 선택만으로 실측 시험을 시작할 수 없다.

`python tmp/adc_mapping_precheck.py`로 문서의 raw 0~26400 전체 26,401개 값에 대한 변환 범위·단조 증가와 0/13200/26400 기준 벡터를 확인했다. ADC 1코드는 계산상 0.000125V, 가상 팩에서는 약 0.000454545V다. 실제 분해능·정확도 측정값이 아니다. raw=-1과 26401이 명목 범위를 벗어남도 확인했다. 처음 검사에서 float 계산의 3.3V 끝점 반올림 때문에 비교가 실패하여 검증 도구에만 1e-12 수치 허용차를 적용했다. 센서 허용오차·제품 정책을 바꾸지 않았다.

출력은 `tmp/adc_mapping_precheck.json`, 도구 SHA-256은 `351c3a522b2eeb78488289d908c251f320e4c3ace954d3eaed01131d44065a63`이다. 이 검사는 레지스터·바이트 순서·설정 적용·I2C 오류·실제 전압을 검증하지 않는다.

따라서 후속 순서는 **실제 ADC 취득 구현과 오류 처리 → 드라이버 단위시험 → §6의 장비 기준전압 대조 → ECU/IVI 전달 시험**이다. 취득 구현은 SOC-2에서 승인한 EKF 파일 수정 범위와 별도다. 기존 M3 센서 오류·복구 정책을 따라야 하며 샘플 유효성·오류 상태 전달을 단순 정상값 반환으로 대체하지 않는다. 제품 ADC 드라이버는 이번에 추가하지 않았다.

## 9. ADC 제품 변환 모듈 실행 검증 (2026-09-08)

승인 범위 정정: 센서 상태 통신 목표는 ICD §8의 S-3=A로 이미 승인되어 있다. 앞선 ‘미확정’ 설명은 오래된 M3 표현에 근거한 것으로 정정한다. 승인과 제품 형식 전환 완료는 구분한다.

이어서 진행하라는 사용자 지시에 따라 확정된 산술 변환을 `adaptive_ecu/include/ads1115_conversion.h`와 `src/app/ads1115_conversion.cpp`로 구현했다. raw 0~26400만 명목 입력으로 받아 ADC 전압과 가상 팩 전압을 반환한다. 범위 이탈은 false를 반환하고 출력 인자를 수정하지 않는다. 정수 공간에서 범위를 검사해 float 반올림으로 상단 코드가 거부되지 않게 했다. 정상 범위로 강제 제한하거나 센서 허용오차를 새로 만들지 않았다.

실제 제품 소스를 별도 호스트 검사기와 연결해 다음 명령으로 실행했다.

```text
g++ -std=c++17 -Wall -Wextra -Werror -I adaptive_ecu/include adaptive_ecu/src/app/ads1115_conversion.cpp tmp/adc_conversion_host_check.cpp -o tmp/adc_conversion_host_check.exe
tmp/adc_conversion_host_check.exe
```

결과: signed 16bit 전체 65,536개 코드 검사 통과. 정상 26,401개에서 독립 환산식 `raw/8000`, `30+raw/2200`과 수치 오차 내 일치·유한값·단조 증가를 확인했다. 나머지 코드는 거부하고 출력 인자가 그대로임을 확인했다. 검사 허용차 1e-6V/1e-5V는 float 수치 비교용이며 장비 인수 허용오차가 아니다. `std::clamp`를 쓰지 않는 독립 변환 모듈이므로 기존 GCC에서도 실행 가능했으며, EKF 또는 전체 ECU 컴파일 장애가 해결된 것은 아니다.

소스 SHA-256: `61954b220b1a65987865751517ac88e7a85917c56f952f9bd7d0d1b45cbf8a0b`, 헤더 SHA-256: `cc6fe98d350cbaf792a551d1379da67a7f590e36c176a2e4430768c6d036c3e0`.

CMake에 제품 소스와 `test_ads1115_conversion`을 등록하고 GoogleTest 시험 2개를 추가했다. 해당 CTest는 환경 문제로 미실행이며 독립 호스트 실행과 구분한다. SensorSimulator·주기 루프에는 아직 연결하지 않았고 POTENTIOMETER 기존 시험도 보존했다. I2C 레지스터 취득·freshness·재시도·3회 복구·상태 통신은 이 함수의 책임이 아니다. 후속 드라이버가 false를 정상 샘플로 처리하지 않도록 연결 시험이 필요하다.

## 10. 승인된 센서 상태 전이 구현·검증 (2026-09-08)

최신 결정: 아래 ADC-1·2 답변 대기는 A/A 답변으로 종료됐다. 적용 범위와 증거는 §11을 따른다.

후속 취득 설계 확인: TI 공식 데이터시트의 동작 모드·완료 확인을 검토했다. SDD의 연속변환을 단일 요청 방식으로 바꾸는 안과 첫 시험 설정을 [의사결정 기록 ADC-1·2](../governance/의사결정_기록.md#decision-adc)에 제시했다. 기존 상태 정책을 다시 승인받는 질문이 아니다. 답변 전 변환 모드·시간 후보를 제품에 적용하지 않는다. [근거 자료](https://www.ti.com/lit/ds/symlink/ads1115.pdf)의 명목 변환시간과 호스트 실측 지연을 구분한다.

ICD §8을 직접 대조해 `adaptive_ecu/include/sensor_quality.h`에 상태 1~6과 최초·복구 시 새 정상 변환 3회 확인을 구현했다. 오류는 연속 횟수를 초기화하고 이전 정상값 인수 여부에 따라 상태 3/4를 구분한다. 복구 1~2회는 5/6이다. 중복 조회는 상태나 횟수를 바꾸지 않는다. 반환값 true인 새 입력만 호출자가 정상값으로 인수하도록 하는 내부 모듈이며 값 자체·측정 시각은 저장하지 않는다.

재현: `g++ -std=c++17 -Wall -Wextra -Werror -I adaptive_ecu/include tmp/sensor_quality_host_check.cpp -o tmp/sensor_quality_host_check.exe`, 이어 `tmp/sensor_quality_host_check.exe` 실행. 실제 헤더 구현을 대상으로 새 정상 변환/중복/오류의 길이 10 이벤트 열 59,049개, 총 590,490회 상태 비교를 통과했다. 이는 해당 길이의 상태 논리 검사이며 전체 입력 길이에 대한 증명이나 실제 fresh 변환 검증은 아니다.

GoogleTest 2개와 CMake의 `test_sensor_quality` 등록을 추가했으나 CTest는 미실행이다. 호출자는 실제 새 변환을 식별하고 실패·시간 초과를 error()로 전달해야 한다. 원시값이 같다는 이유로 중복으로 판단해서는 안 된다. 센서값 보존·EKF 입력 차단·송신 snapshot·HAL/UI 연결은 아직 미구현이며 CAN 형식은 변경하지 않았다.

## 11. ADC-1/2=A 시간 제어 적용 (2026-09-08)

후속 전송 진척은 §12를 따른다. 이 절의 ‘다음’은 당시 실행 순서다.

사용자 A/A 답변을 SDD·M3에 반영했다. `adaptive_ecu/include/adc_acquisition_gate.h`는 단조 시각을 받아 요청 간격·조회 간격·인수 마감·진행 중 요청 소유권을 관리한다. 마감만으로 pending을 해제하지 않고 실제 작업 반환 후 finish()에서 해제한다. 늦은 정상 결과·중복 finish·동일 간격 재시도는 인수하지 않는다. 시간 비교는 20ms 도달 시 만료로 정의했다. 이벤트 시각은 호스트 제어 시각이며 실제 ADC 측정 시각으로 표시하지 않는다.

실행: `g++ -std=c++17 -Wall -Wextra -Werror -I adaptive_ecu/include tmp/adc_acquisition_gate_host_check.cpp -o tmp/adc_acquisition_gate_host_check.exe` 후 해당 exe 실행. 완료 시각 0~200ms의 201개 경우와 조회 중복·늦은 결과·요청 겹침·실패 후 재시도 제한 검사를 통과했다. CMake에 GoogleTest 시험 2개를 등록했지만 CTest는 환경 문제로 미실행이다.

이 모듈은 I2C를 호출하거나 스레드를 생성하지 않는다. 후속 취득 작업자는 단일 요청 시작·완료 확인·raw 읽기를 수행하고 실제 호출이 모두 끝난 뒤 finish()를 호출해야 한다. 주기·감시 경로와 작업자 사이 동기화는 아직 구현하지 않았다. 따라서 CAN 비차단·OS I2C 제한·새 변환 실장비 식별이 검증됐다는 뜻은 아니다. 다음은 레지스터 및 전송 계층 구현·가짜 전송을 이용한 오류 시험·실장비 취득 검증이다. 서버 가져오기와 Plan 통합은 제외한다.

## 12. 레지스터 프로토콜과 가짜 전송 검증 (2026-09-08)

`ads1115_registers.h`와 `src/bsw/ads1115_registers.cpp`에 전송 인터페이스·단일 요청·완료 조회·raw 해석을 구현했다. [TI 데이터시트 §8.1](https://www.ti.com/lit/ds/symlink/ads1115.pdf)와 대조한 Config 요청은 0xC383이며 AIN0/GND·±4.096V·single-shot·128SPS·comparator 비활성이다. 시작 전 장치가 busy이면 새 요청을 쓰지 않는다. 조회 시 OS 외 설정 비트가 요청과 다르면 오류로 처리한다. MSB 우선 2바이트를 signed 값으로 명시 변환하며 기다림·오류는 출력 raw를 수정하지 않는다.

재현: `g++ -std=c++17 -Wall -Wextra -Werror -I adaptive_ecu/include adaptive_ecu/src/bsw/ads1115_registers.cpp tmp/ads1115_registers_host_check.cpp -o tmp/ads1115_registers_host_check.exe` 후 해당 exe 실행. 실제 제품 소스와 가짜 전송을 연결하여 raw 65,536개 디코딩, 설정 15비트 개별 변조 거부, 읽기/쓰기 실패·busy·중복 요청·중복 인수 검사를 통과했다. GoogleTest 2개와 CMake 등록도 추가했으나 전체 CTest는 미실행이다.

전송 구현은 정확한 바이트 수 전송에만 성공을 반환해야 한다. 현재 인터페이스와 레지스터 프로토콜만 구현했으며 실제 Linux I2C 시스템 호출 어댑터는 없다. 장비 주소 0x48 연결·부분 전송·반복 시작·권한·작업자 동기화·시간 제어 결합·실제 fresh 식별은 후속 검증이다. abandon()은 진행 중 시스템 호출을 취소하지 않으며 작업자 반환 뒤에만 사용한다. 즉 이번 결과는 물리 I2C 취득 성공이 아니다.
