2026-09-22 실제 파일과 Git 상태 기준이다. 파일의 존재와 기능의 구현·시험 통과는 구분한다. 이 안내는 탐색용이며 계약과 정책을 복제하지 않는다. 최신 실제 파일과 [전체 경로 매핑](../../aidlc/structure/path-map.csv)을 함께 확인한다.

## 1. 처음 참여했을 때

1. [루트 README](../../../README.md)에서 프로젝트 목표와 주요 경로를 확인한다.
2. [공통 지침](../../../AGENTS.md)에서 원본 우선순위·변경 범위·검증 기준을 확인한다. AI 도구는 대응 CODEX/CLAUDE와 루트 SKILL도 따른다.
3. 담당 [ECU 계획](../../../plan/ECU.md) 또는 [IVI 계획](../../../plan/IVI.md)과 [공동 규약](../../../plan/detail/common/00_협업_규약.md)을 읽는다. IVI 담당자는 [Plan B 진행 안내](IVI_Plan_B_진행상황_및_구조_안내.md)를 함께 읽는다.
4. [연계·의존성](../../../plan/detail/common/01_연계_의존성.md)에서 상대 담당자의 선행 과제·인계물을 확인한다.
5. [협업·형상관리 전략](협업_형상관리전략.md)과 [작업 흐름](../workflow.md)에 따라 작업·증거를 연결한다. GitHub 브랜치·커밋·PR 명령은 [GitHub 형상관리 실행 매뉴얼](commit.md)을 순서대로 따른다. 현재 저장소에는 `main`·`develop`이 있으며 작업 때 실제 원격·기준본·dirty 상태를 다시 확인한다.

ECU C++·Python 보안 소스는 존재한다. IVI는 README만 있고 C++/Qt 제품 소스는 없다. 현 실행 기준은 ADR-010의 Qt Plan B이며 Android 자료는 역사 자료다. tools/workflow의 Python 파일은 미구현 골격이며 실행 성공을 기대하는 제품 명령이 아니다. MCP·hook 설정의 존재도 활성화를 뜻하지 않는다. 실제 사용 상태는 [tooling](../tooling.md)을 따른다.

## 3. 비슷한 이름의 폴더 구분

| 구분 | 사용하는 곳 |
|---|---|
| 보안 기능을 구현·시험한다 | 루트 `security/`, ECU C++은 `adaptive_ecu/` |
| 보안 설계를 보충하고 인계한다 | `docs/development/security/` |
| 평가 프로그램을 작성한다 | `security/experiments/` |
| 보존할 실험 해석·보고서를 작성한다 | `docs/development/experiments/`, 실제 실행 증거는 해당 CHG 기록에 연결 |
| 반복 절차를 안내한다 | `docs/development/playbooks/` |
| 특정 작업의 요청·설계·결과를 기록한다 | `docs/aidlc/changes/CHG-번호/` |
| 공식 제품 합격 기준을 확인한다 | `docs/TEST_PLAN.md` |
| 개발 운영 자동화의 검증 시나리오를 확인한다 | `docs/development/verification/` |

공식 원본의 우선순위는 [AGENTS의 Source of Truth](../../../AGENTS.md#4-source-of-truth)를 따른다. 후보 설계·합성 실험·과거 보고서는 현행 계약이나 실장비 인수의 대체물이 아니다. 과거 계획은 [보관본 안내](../../../plan/_archive/README.md), 구조 제안은 [현재 구조 매핑](../../aidlc/structure/document-map.md)으로 현재 상태와 구분한다.

## 4. 담당별 작업 예시

### ECU 담당

ECU 상위 계획에서 이번 M단계 과제를 찾고 detail/ecu의 해당 문서로 내려간다. ICD·SDD-ECU·공식 TC와 상대 인계물을 확인한 뒤 adaptive_ecu 또는 루트 security에서 작업한다. [ECU 플레이북](../playbooks/ecu.md)·[보안 플레이북](../playbooks/security.md)에 따라 가장 가까운 시험을 실행하고, 해당 작업 기록에 대상 버전·결과·미실행 사유를 남긴다. CAN/SecOC/HAL 계약 변경은 기존 승인 절차를 따른다.

### IVI 담당

[Plan B 진행 안내](IVI_Plan_B_진행상황_및_구조_안내.md)와 IVI 상위 계획에서 과제를 찾고 ICD·SDD-IVI 및 ECU가 제공할 벡터·환경을 확인한다. [IVI·통합 플레이북](../playbooks/ivi-integration.md)을 따른다. `ivi_platform`은 C++/Qt 제품 구현 경계이며 이전 작업 폴더에서는 검토한 파일만 선택 이관한다. 제품 구현·빌드·장비 검증은 실제 수행 후 기록하며 예정 CI 명세를 실행 중인 CI로 취급하지 않는다.

### 문서·실험·인계

새 문서는 먼저 [배치 기준](../README.md#document-placement)을 확인한다. 기존 원본을 보완할 내용과 새 자료를 구분한다. 실험은 공식 시험과 역할별 계획에서 조건을 확인하고 실행 입력·버전·결과를 CHG 증거에 연결한다. 보고서는 그 증거를 참조한다. PR·팀원 인계에는 관련 과제·계약·실제 변경·검증·재현 방법을 연결하며 절차 원본은 [협업·형상관리 전략](협업_형상관리전략.md)을 따른다.

### AI에게 실험 정리를 요청하는 예시

아래 요청에 실제 자료 경로를 덧붙여 사용한다.

> 프로젝트 지침과 협업·형상관리 전략에 따라 이번 보안 실험의 설계·실행 증거·결과를 정리해줘. 기존 작업 기록과 배치 기준을 확인하고 중복 없이 정해진 위치에 반영해줘. 보고서의 각 수치를 원자료·분석 코드·실행 환경과 연결하고, 합성·vcan·물리 CAN 결과를 구분해줘. 없는 수치는 추정하지 말고 누락된 근거와 미검증 항목을 표시해줘. 관련 목록·매핑·링크도 확인해줘.

- 자료 위치: 로그·측정 CSV·분석 코드·환경 기록의 경로
- 대상: 실험명, 알고 있는 CHG ID·run ID·코드 버전
- 기존 정리본: 있다면 설계·보고서·표·그림의 경로

확인되지 않은 항목은 모른다고 명시한다. 키·토큰 등 비밀은 제공하지 않는다. 이 요청은 기존 결과의 문서 정리용이며 새 실험 실행이나 제품 코드 변경을 지시하지 않는다.

## 5. 작업 기록의 사용 순서

[작업 구조 안내](../../aidlc/changes/README.md)에 따라 실제 작업 ID를 정한다. CHG-template은 복사용이며 완료한 작업이 아니다. 작은 변경에는 change 양식, 다단계에는 spec과 aidlc-state를 사용한다. 모든 질문에 전체 폴더를 복사할 필요는 없다.

- inception: 기존 구현 조사 → 요구 영향 → 작업 분해·설계 중 필요한 자료를 기록한다.
- construction: 실제 작업 단위의 설계·변경 요약과 build-and-test의 증거를 연결한다.
- construction 내부 code: 제품 코드 사본을 두지 않고 실제 소스 경로·변경 요약을 남긴다.
- aidlc-state: 다단계 진행 상태의 원본이다. 인덱스·Issue에는 원본을 연결한다.

검증 명령은 [AGENTS의 Verification Baseline](../../../AGENTS.md#6-verification-baseline)을 직접 따른다. 이 안내의 작성은 제품 빌드·시험 통과를 의미하지 않는다.

## 6. 안내와 파일 색인 유지

새 파일·이동·통합이 발생하면 배치 기준에 따라 관련 인덱스와 경로 매핑을 갱신하고 이 안내의 해당 설명·색인도 동기화한다. 정책·계약 전문을 이곳에 복제하지 않는다. 파일별 설명은 탐색 목적이며 상세 동작은 실제 파일과 공식 원본을 확인한다. 그림은 촬영 대상·배선 참고 용도로 사용하며 장비 검증 증거와 구분한다.

## 7. 파일별 목적 색인
