## ECU·IVI 협업 및 저장소 관리 전략

작성일: 2026-09-10. 사용자=ECU 담당, 팀원=IVI 담당인 두 사람의 협업 안내다. 하나의 저장소에서 담당 경로별로 병렬 개발하고 작은 변경을 자주 통합한다. 이 문서는 기존 계획·규칙을 실행에 적용하는 안내이며 새 계약이나 추가 승인 권한을 만들지 않는다.

원본은 [공동 협업 규약](../../../plan/detail/common/00_협업_규약.md), [연계·의존성](../../../plan/detail/common/01_연계_의존성.md), [ECU 계획](../../../plan/ECU.md), [IVI 계획](../../../plan/IVI.md)이다. 세부 인계표·시험 기준·정책이 바뀌면 이 안내보다 원본을 우선하고 관련 참조를 함께 갱신한다. 기술 계약과 변경 절차는 [ICD](../../ICD.md) 및 [AGENTS](../../../AGENTS.md)를 따른다.

<a id="collaboration--1-같은-기준본에서-시작"></a>
### 1. 같은 기준본에서 시작

현재 확인한 작업 폴더에는 Git 메타데이터가 없다. 아래는 실행할 운영 절차이며 저장소 초기화·연결·보호·브랜치 생성이 완료됐다는 뜻이 아니다.

1. 기존 원격 저장소와 보존할 이력이 있는지 확인한다. 있다면 이력을 유지하며 현재 정리본을 검토·반영한다. 각자 독립 초기화하거나 원격 이력을 덮어쓰지 않는다.
2. 기존 저장소가 없다면 공동 저장소를 만들고 현재 프로젝트 기준본을 등록한다. 공개 범위·소유자·참여 권한은 실제 팀 계정으로 정한다.
3. 두 사람 모두 같은 원격·기준 커밋에서 clone한다. 기준 커밋, 사용 환경, 담당을 기록한다. 골격이 등록됐다는 사실은 빌드·시험 통과를 의미하지 않는다.
4. 등록 전에 기존 .gitignore와 제출 범위를 확인한다. 키·토큰·장비 자격 증명·대형 로그·AOSP 전체 소스·빌드 산출물을 무심코 포함하지 않는다. 보존할 경량 결과와 재현 방법은 공식 기록에 연결한다.

기존 자료를 삭제하거나 다른 저장소의 구현을 자동 도입하는 단계가 아니다. 폴더 사본을 각각 장기간 관리한 뒤 한 번에 합치는 방식은 피한다.

<a id="collaboration--2-담당-경계와-공동-변경"></a>
### 2. 담당 경계와 공동 변경

| 영역 | 주 담당 | 상대방이 확인할 내용 |
|---|---|---|
| adaptive_ecu/ | ECU 담당 | CAN 송신·SecOC·상태 통보의 계약 일치 |
| security/ | ECU 담당 | IDS 경보·인증 이벤트·실험 조건·통합 측정 |
| ivi_platform/ | IVI 담당 | HAL·verifier·Service·UI의 ECU 인계물 수용 |
| CI·빌드·배포 | IVI 담당 중심 | ECU 빌드·시험 입력과 의존성은 ECU 담당 검토 |
| ICD·공동 요구·시험 | 공동, 편집 담당 한 명 지정 | 양측 영향·합격 기준·동시 전환 여부 |
| 작업별 CHG 기록 | 해당 작업 담당 | 관련 계획·PR·증거 연결과 인계 |
| 루트 지침·공통 자동화 | 해당 과제 담당 한 명 지정 | 양측 작업 방식·권한·검증에 미치는 영향 |

담당은 주 책임을 뜻하며 상대방의 수정 자체를 금지하는 소유권이 아니다. 상대 영역과 공통 문서를 수정할 때 영향과 편집 구간을 미리 공유한다. 특히 같은 ICD 절·공통 상태표·경로 목록은 동시에 별도 기준으로 고치지 않도록 담당과 병합 순서를 정한다.

<a id="collaboration--3-작업별-브랜치와-작은-pr"></a>
### 3. 작업별 브랜치와 작은 PR

브랜치 이름·명령·병합 방식의 원본은 공동 규약 §3이다. 아래는 해당 흐름의 적용 예시다.

```text
develop
  ├─ feat/ecu-m2-can-cdd
  ├─ feat/ivi-m3-can-parser
  └─ docs/icd-영향주제
       ↓ 상대 리뷰·필요 검증
     develop
       ↓ 양측 릴리즈 인수
      main → 태그·Release
```

develop은 양측 변경을 통합하는 기준, main은 공동 인수한 릴리즈 기준으로 사용한다. 과제 브랜치는 검토 가능한 한 작업을 맡는다. 기존 규약의 작업 브랜치→develop Squash Merge, develop→main Merge Commit을 따른다. ECU·IVI 이름의 장기 브랜치에서 모든 작업을 쌓아 마지막에 한 번에 합치지 않는다.

작업 시작과 병합 전 최신 대상 브랜치의 변경을 확인한다. 공유 브랜치의 이력을 임의로 다시 쓰지 않는다. Draft PR로 예상 변경과 의존성을 일찍 공유하고, 종속 PR은 선행 PR과 병합 순서를 적는다. 상대 구현이 없어도 Mock·벡터로 진행 가능한 부분은 분리한다.

<a id="collaboration--4-issuepr작업-기록의-역할"></a>
### 4. Issue·PR·작업 기록의 역할

| 기록 | 관리할 내용 |
|---|---|
| Issue | 과제 담당·범위·완료 조건·차단 요인, M단계와 선행 과제 링크 |
| PR | 실제 변경·리뷰·검증 결과·인계 방법·병합 근거 |
| CHG 기록 | 요청 원문·설계 판단·진행 상태·재현 증거 |
| 공식 문서 | 계약·요구사항·설계·공식 시험의 원본 |

같은 설계·결과를 여러 곳에 복제하지 않는다. 다단계 작업 상태의 원본은 기존 workflow의 aidlc-state.md이고 Issue에는 해당 기록과 차단 요인을 연결한다. 작은 작업은 기존 change.md 방식으로 충분할 수 있다. CHG-template은 복사용이며 실제 작업으로 집계하지 않는다. [작업 흐름](../workflow.md)과 [AIdlc 안내](../../aidlc/README.md)를 따른다.

PR에는 다음을 확인할 수 있게 적는다.

- 변경 전후의 동작과 변경 이유
- 관련 Issue·계획 과제·FR/NFR/TC/ADR 연결
- 상대 노드와 ICD에 대한 영향 또는 영향이 없는 근거
- 실행한 검사·대상 버전·실제 결과·미실행 이유
- 상대방이 재현하거나 인수할 방법

일반 PR은 공동 규약의 상대방 리뷰와 검증 조건을 따른다. 코드 소유자나 자동 검사 설정이 사람의 계약 검토를 대신하지 않는다. 공동 규약의 양측 합의는 작성자의 설계·변경 근거와 상대방의 명시적 확인으로 추적하고, GitHub 리뷰 수를 기계적으로 2로 정해 두 명 팀의 PR을 막지 않도록 실제 설정을 확인한다. 본인 단독 인수나 무승인 계약 변경을 허용하는 예외가 아니다.

<a id="collaboration--5-ecu와-ivi의-인계"></a>
### 5. ECU와 IVI의 인계

인계 항목·시점·담당·선행조건의 원본은 공동 연계 문서 §2다. 아래는 제공물을 준비할 때 사용할 관점이며 별도 인수표를 새로 운영하지 않는다.

| ECU 담당이 제공 | IVI 담당이 확인·회신 |
|---|---|
| 적용 ICD 버전·CAN 예제 프레임 | 파싱 결과·단위·경계값 피드백 |
| 명시적 더미 키 기반 정상·실패 SecOC 벡터 | 검증·폐기 결과와 사유 |
| 주기·상태·오류 발생 조건 | UI 반영·stale·복구 관측 |
| 실행 명령·빌드 식별자·환경 조건 | 동일 조건의 통합 시험 결과 |
| IDS 경보·인증 이벤트의 합의된 의미 | 수신·표시·전달 결과와 증거 |

인계 종료는 파일 송부가 아니라 수신자의 재현·확인으로 판단한다. 적용 커밋·계약 버전·입력·설정 식별과 기대·실제 결과를 연결한다. 실제 키는 예제·문서에 넣지 않는다. IVI 전체 완성을 기다리거나 ECU 전체 완성까지 상대를 대기시키지 말고, 계약이 정해진 Mock·벡터부터 교환한다.

ICD 변경이 필요하면 기존 게이트에 따라 영향 분석과 승인을 진행하고 관련 요구·양측 설계·구현·시험을 같은 변경 단위로 동기화한다. 승인 전 서로 다른 계약을 기준으로 제품 구현을 확정하지 않는다.

<a id="collaboration--6-저장소-보호와-ci"></a>
### 6. 저장소 보호와 CI

브랜치 보호·필수 검사·라벨·마일스톤의 원본은 공동 규약 §2다. GitHub의 실제 기능 지원과 권한을 확인해 main/develop에 PR 리뷰·강제 푸시 방지·필요한 상태 검사를 적용한다. 설정이 적용됐다고 문서만으로 판단하지 않는다.

1. 두 환경에서 기존 ECU·Python 검증 명령을 재현한다.
2. 예정 CI를 구현하고 실제 검사 이름과 정상·실패 결과를 확인한다.
3. 확인된 검사만 필수 병합 조건으로 등록한다. 존재하지 않는 검사 이름을 먼저 요구해 PR을 막지 않는다.
4. CI 도입 전 필요한 검증은 공동 규약에 따라 수동 증거로 확인하고, 그 결과를 CI 통과로 표시하지 않는다.
5. 물리 CAN·Node B Ubuntu/Qt·장비 시험은 별도 환경과 증거로 인수한다. 소스 없음·장비 없음에 따른 미실행은 전체 제품 합격이 아니다.

기능 설명과 설정 가능 범위는 도입 시 [GitHub 브랜치 보호 안내](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)를 확인한다. 작업 브랜치·PR의 기본 흐름은 [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)를 참고하되 프로젝트의 main/develop 규약을 임의로 변경하지 않는다.

<a id="collaboration--7-통합충돌릴리즈"></a>
### 7. 통합·충돌·릴리즈

통합 시험에서는 양측 실행 커밋·적용 계약·설정 식별자·장비 환경을 기록한다. 한쪽의 최신 브랜치와 다른 쪽의 오래된 실행 파일을 비교한 결과를 같은 버전의 인수로 사용하지 않는다. [공동 통합 시험](../../../plan/detail/common/02_통합시험.md)의 공식 기준을 적용한다.

충돌이 발생하면 파일 작성자와 의미를 대조한다. 자신의 변경을 통째로 선택하거나 상대 변경을 삭제해 해결하지 않는다. 코드뿐 아니라 계약 의미·시험 기대값·문서 링크를 확인하고 영향받은 검사를 다시 실행한다. 구조 골격을 공유했다는 사실은 병합 충돌을 없애거나 기능 호환성을 보장하지 않는다.

공동 규약에 따라 양측 인수 후 IVI 담당이 릴리즈 조정자로 동일 태그를 한 번 생성하고 ECU 담당이 커밋과 증거를 확인한다. 제출물은 [공동 발표·제출](../../../plan/detail/common/03_발표_제출.md)의 기준을 따른다. 실패한 통합을 릴리즈로 올리지 않고 필요한 수정은 별도 과제로 추적한다.

<a id="collaboration--8-시작-순서와-자동화"></a>
### 8. 시작 순서와 자동화

공동 원격·기준본 확인 → 역할·첫 Issue·인계물 합의 → 각자 작업 브랜치 → 초기 CAN·SecOC 벡터 교환 → 작은 PR → 통합 검증 → 공동 릴리즈 순서로 시작한다. 회의·일정·마일스톤 운영은 공동 규약을 따르고 실제 가용 시간과 차단 요인을 공유한다.

반복되는 검토·검증·기록은 [자동화 지침](../tooling.md#automation)에 따라 skill·CLI·hook으로 보조한다. 외부 저장소·CI 조회는 필요한 경우 MCP 연결을 검토한다. 도구가 승인·계약 합의·실장비 인수를 대신하지 않으며 자동화를 완성할 때까지 제품 개발을 일괄 중단하지 않는다.

이 문서는 운영 전략을 정리한 것이다. Git 초기화·원격 설정·브랜치 보호·팀원 초대·PR 생성·외부 메시지 전송을 수행하지 않았다. 실제 실행 결과와 접근 정보는 해당 과제 기록에서 필요한 범위만 관리한다.


코드·계약·환경·릴리즈와 보안 실험 설계·원자료·분석 결과의 버전 연결은 [형상관리 전략](#configuration)을 참조한다. 이 문서의 담당·브랜치·인계 규칙은 그대로 유지한다.

<a id="configuration--프로젝트-및-보안-실험-형상관리-전략"></a>
## 프로젝트 및 보안 실험 형상관리 전략

작성일: 2026-09-10. 형상관리의 목표는 어떤 코드·계약·환경·입력으로 무엇을 만들고 시험했는지 추적하고 재현하는 것이다. 최종 보안 실험 보고서의 수치도 원자료와 계산 과정까지 역추적할 수 있게 한다.

브랜치·PR·담당·인계는 [협업 전략](#collaboration), 규칙 원본은 [공동 협업 규약](../../../plan/detail/common/00_협업_규약.md)과 [연계·의존성](../../../plan/detail/common/01_연계_의존성.md)을 따른다. 계약은 [ICD](../../ICD.md), 요구는 [SRS](../../SRS.md), 공식 인수는 [TEST_PLAN](../../TEST_PLAN.md), 보안 실험 절차는 [ECU M5](../../../plan/detail/ecu/M5_Ablation.md)를 우선한다. 이 문서는 기존 반복 수·합격 기준·승인 조건을 바꾸지 않는다.

<a id="configuration--1-형상관리-대상과-보관-위치"></a>
### 1. 형상관리 대상과 보관 위치

| 대상 | 관리 방식 | 연결할 정보 |
|---|---|---|
| ECU·보안·IVI 소스와 시험 | Git 커밋·PR | 관련 계획 과제·요구·시험 ID |
| ICD·요구·설계·시험 계획 | 구현 영향과 같은 변경 단위 | 승인 근거·변경 이유·적용 커밋 |
| 빌드 스크립트·CI·공유 설정 | Git 관리 | 적용 환경·빌드 옵션·실제 검증 |
| 의존성·도구·플랫폼 | 검증한 정확한 버전 기록 | 패키지·컴파일러·OS·이미지 식별 |
| 작은 시험 입력·더미 벡터 | Git 관리 | 생성 근거·버전·해시 |
| 대형 CAN 로그·모델·영상·이미지 | 별도 보관 또는 필요 시 Git LFS 검토 | 위치·버전·SHA-256·보관 담당·복구 방법 |
| 실행 파일·배포 이미지 | 릴리즈 산출물로 보관 | 소스 커밋·빌드 환경·파일 해시 |
| 판단·진행·시험 결과 | 작업별 CHG와 증거 기록 | Issue·PR·공식 원본·실행 ID |

Git에 넣지 않는 자료도 보존 대상일 수 있다. 기존 .gitignore를 존중하며 재생성할 빌드 중간물, 보존할 결과, 민감 자료를 구분한다. Git LFS는 선택지이며 도입 시 두 사람의 접근 환경과 저장 정책을 확인한다. 원자료 경로만 적지 말고 보관 담당·공동 접근·백업·복구를 확인한다. 해시는 동일성을 확인할 뿐 파일 자체를 복구하지 않는다.

실제 키·토큰·장비 자격 증명은 코드·문서·로그·릴리즈에 넣지 않는다. 비밀이 제거된 설정 식별자와 더미 벡터를 사용하고 공개 보고서와 제한 보관 자료를 구분한다. 이미 추적된 파일은 .gitignore 추가만으로 추적에서 제외되지 않으므로 실제 등록 목록을 확인한다.

<a id="configuration--2-세-종류의-기준본"></a>
### 2. 세 종류의 기준본

| 기준본 | 의미 | 식별 |
|---|---|---|
| 구조 기준본 | 현재 계획·문서·골격의 공통 출발점 | 공동 저장소 기준 커밋 |
| 통합 시험 기준본 | 특정 ECU·IVI 조합을 실행·시험한 상태 | 소스 커밋·환경·설정·산출물 해시·시험 증거 |
| 릴리즈 기준본 | 양측이 공식 인수한 결과 | 기존 마일스톤 태그·Release·검증 증거 |

현재 구조 골격 준비를 M1 구현 완료로 표시하거나 구현 인수 태그를 먼저 부여하지 않는다. Git 메타데이터가 없는 동안에는 파일 목록·해시로 구분하고 존재하지 않는 커밋·브랜치 상태를 쓰지 않는다. 공동 저장소를 준비할 때 기존 원격과 보존할 이력을 확인하고 양측이 같은 기준 커밋에서 시작한다.

모든 파일에 별도 수동 버전을 붙이지 않는다. 커밋을 기본 식별자로 사용하고 계약·프로토콜·실험 설계처럼 독립 식별이 필요한 대상만 구분한다. Git 이후에도 외부 자료와 배포 파일은 파일 해시로 연결한다.

<a id="configuration--3-ecuivi-실행-조합의-식별"></a>
### 3. ECU·IVI 실행 조합의 식별

통합 시험마다 하나의 실행 ID로 다음을 묶는다.

- 소스 커밋과 작업 트리 수정 여부. 미커밋 변경이 있으면 패치·파일 해시를 명시하고 커밋만으로 재현 가능하다고 하지 않는다.
- 적용 ICD·설계·프로토콜·profile 버전 또는 해당 문서 커밋
- ECU 실행 파일, IVI 앱·이미지의 SHA-256
- 양측 OS·아키텍처·의존성·설정 식별자
- 모델·입력 데이터·시험 벡터·seed와 해시
- 명령·공식 TC·실제 결과·미실행 이유·증거 위치

“양쪽 최신 버전” 대신 실제 실행 파일을 식별한다. 서로 다른 소스 커밋을 시험했다면 그 조합을 그대로 기록하고 최종 릴리즈와의 대응을 확인한다. 증거는 기존 construction/build-and-test/ 및 [증거 양식](../templates/evidence.md)에 연결한다. 별도 중복 상태판은 만들지 않는다.

<a id="configuration--4-실행-환경과-의존성-재현"></a>
### 4. 실행 환경과 의존성 재현

현재 security/requirements.txt는 최소 버전 범위를 사용하고 ECU CMake는 시스템 OpenSSL·GoogleTest를 찾는다. 따라서 소스 커밋만으로 동일 환경이 보장되지 않는다. 검증에 성공한 환경을 근거로 다음을 기록·고정한다. 이번 문서는 기존 의존성 파일을 수정하거나 임의 버전을 채택하지 않는다.

| 영역 | 기록할 항목 |
|---|---|
| Python | Python과 실제 설치 패키지 버전, 플랫폼, 사용한 의존성 고정 자료 |
| ECU | OS·아키텍처·컴파일러·CMake·OpenSSL·GoogleTest·빌드 옵션 |
| IVI | Linux 이미지·커널·Qt/CMake/OpenSSL 버전·기기 설정·소스 commit·빌드/실행 명령 |
| 컨테이너 도입 시 | 실제 이미지 식별자, 빌드 입력과 옵션 |

지원 가능한 범위와 특정 실행에서 사용한 정확한 버전을 구분한다. 환경 고정 파일이나 도구는 실제 플랫폼에서 재현한 후 선택하며 불필요한 여러 방식의 중복 관리를 피한다.

<a id="configuration--5-변경-추적과-릴리즈복구"></a>
### 5. 변경 추적과 릴리즈·복구

Issue → CHG 판단·설계 → 브랜치·PR → 계약·구현·시험 → 검증 증거 → 통합 기준본 → 릴리즈를 연결한다. 관련 문서를 복제하지 않고 원본 절·공식 ID와 변경 차이를 참조한다.

CAN/SecOC/HAL 변경은 기존 인터페이스 게이트를 따른다. IDS 모델·특징·임계 변경은 학습·평가 입력과 결과를 연결한다. 빌드·설정 변경은 실행 동작과 이전 증거의 유효성을 확인한다. 경로 변경은 import·빌드 입력·문서 참조·전체 경로 매핑까지 확인한다.

main/develop·PR 병합 방식·릴리즈 담당은 공동 규약을 유지한다. 양측 인수 후 IVI 담당이 릴리즈를 조정하고 ECU 담당이 해당 커밋·산출물·증거를 확인한다. Release에 소스 태그, 실행 산출물·체크섬·재현 방법·시험 요약을 연결한다.

- 공개·인계한 태그를 다른 커밋으로 옮겨 같은 버전의 의미를 바꾸지 않는다. 수정본은 새 버전으로 발행한다.
- 이전 인수본의 실행 파일·설정·필요 모델을 함께 보존한다.
- 장비 복구는 호환성이 확인된 ECU·IVI 조합으로 한다. 한쪽 바이너리만 임의로 되돌리지 않는다.
- 소스 변경 취소와 실제 장비 복구는 별개로 확인하고 복구 후 필요한 smoke·통합 검증을 수행한다.

저장소는 유일한 보관 장소라고 가정하지 않는다. 외부 대형 자료·배포 이미지·접근 방법도 복구 가능하게 관리하고 릴리즈 전 필요한 증거가 팀원 환경에서 열리는지 확인한다.

<a id="configuration--6-보안-실험의-설계실행분석-버전"></a>
### 6. 보안 실험의 설계·실행·분석 버전

최종 보고서에서 수치 하나를 선택했을 때 설계·코드·장비·설정·입력·원자료·계산 과정까지 확인할 수 있어야 한다.

| 구분 | 고정·기록할 내용 |
|---|---|
| 실험 설계 | 목적·가설, 공격·방어 구성, 평가 구간, 반복 기준, 지표·분모·무효 기준 |
| 실행 환경 | 양측 코드·바이너리·계약·장비·OS·의존성·설정·모델·입력·seed |
| 분석 방법 | 분석 코드 버전, 포함·제외 시행, 집계·누락 처리, 그림 생성 옵션 |
| 최종 결과 | 실행 ID·분석 버전·표·그림·보고서 위치 |

코드·환경·설정을 바꿔 다시 실행하면 새 실행 ID를 부여한다. 같은 원자료를 분석 코드 수정 후 다시 집계하면 새 분석 버전을 부여한다. 실행과 분석의 식별을 혼합하거나 이전 결과를 덮어쓰지 않는다. 기존 run/trial 식별과 manifest가 있으면 확장·연결하고 병렬 원장을 추가하지 않는다.

<a id="configuration--7-평가-전-설계-고정"></a>
### 7. 평가 전 설계 고정

pilot·학습·튜닝·최종 평가를 분리한다. [ECU M5](../../../plan/detail/ecu/M5_Ablation.md)의 데이터 분리와 평가 기준을 원본으로 하여 본 평가 전에 다음을 기록한다.

- 학습·튜닝·평가 데이터와 겹치지 않는 seed 집합
- 모델·전처리·특징 순서·임계와 판정 방향
- 공격 입력·방어 구성·적용 코드·양측 설정
- 측정 구간·평가 단위·분자·분모·포함/제외 기준
- 준비·종료·복구·계측 불능 판정 조건

결과를 본 뒤 조건을 바꾸면 변경 사유와 영향을 기록하고 별도 평가로 구분한다. 좋은 결과가 나온 조건만 남기지 않는다. 계획 목표값과 실측을 구분하고 후보 시험값을 운영값으로 무단 확정하지 않는다.

<a id="configuration--8-전체-시도-원장과-재시도"></a>
### 8. 전체 시도 원장과 재시도

기존 공식 기준인 4종 공격 × 3가지 방어 구성 × 유효 100시행, 별도의 정상 FPR 평가, 보조 A5/A6 사례 구분을 유지한다. 1,200행 존재만으로 인수하지 않고 유일한 조합·유효 시행·관측 증거를 확인한다.

| 상태 | 처리 |
|---|---|
| 미탐 | 유효한 실험 결과로 유지. 불리한 결과라는 이유로 무효 처리하지 않음 |
| 계측 불능 | 고정한 기준과 근거가 있을 때 INVALID로 기록 |
| 재시도 | 원시도를 지우지 않고 원시도 ID·이유·새 시도 식별 연결 |
| 미실행 | 결과 없음과 이유를 남김 |

기존 run/trial 체계를 유지하고 필요하면 attempt 식별자를 추가한다. 동일 시행의 방어 구성 간 입력·seed를 연결하고 물리 CAN에서는 실제 송수신 관측도 확인한다. 같은 seed가 모든 실제 타이밍과 장비 상태의 동일성을 보증하지는 않는다.

전체 시도 원장과 유효 평가 집합을 구분하고 유효 집합 생성 규칙을 보존한다. 중복·결측·잘못된 타입·분모 0 등을 조용히 보정하지 않는다. 미탐지 지연을 0으로 채우지 않고 탐지된 표본의 통계와 미탐·기한 초과 수를 함께 보고한다.

<a id="configuration--9-실험별-증거-묶음의-배치"></a>
### 9. 실험별 증거 묶음의 배치

다음은 실제 실험 작업에서 사용할 배치 예시다. 현재 생성되거나 채워진 실험 결과가 아니며 기존 M5 결과 경로를 일괄 이동하라는 지시도 아니다. 이미 정해진 결과 파일은 원래 경로를 유지하고 아래 기록에서 연결하는 방식을 우선한다.

```text
CHG-<실험작업>/
├── inception/plans/                 실험 설계·원본 계획 연결
└── construction/build-and-test/
    └── <run-id>/
        ├── manifest.json           설계·코드·환경·입력 식별
        ├── evidence.md             명령·진행·판정·한계
        ├── attempts.csv            전체 시도·무효·재시도 원장 또는 원본 연결
        ├── raw-index.csv           원자료 위치·해시·보관 담당
        └── analysis/               분석 버전·요약·그림 연결
```

실제 manifest와 원장 형식은 구현 시 기존 M5·IVI 측정 형식과 대조해 하나로 관리한다. 제시한 이름을 별도 중복 원본 생성의 근거로 삼지 않는다. 작은 요약과 재현 명령은 Git, 대형 원자료는 정한 별도 보관 정책에 따른다.

<a id="configuration--10-원자료가공-결과양측-증거"></a>
### 10. 원자료·가공 결과·양측 증거

원자료는 수집 후 그대로 보존하고 정제·필터링·집계는 분석 코드로 수행한다. 원자료 수정이 필요한 오류를 발견하면 사유와 파생본을 남기며 원본을 소리 없이 바꾸지 않는다.

원자료의 고유 식별·SHA-256·수집 조건·보관 위치 → 처리 코드와 가공 데이터 → 유효 시행·분자·분모·요약 통계 → 그림 스크립트·옵션·캡션 순으로 연결한다. 수정된 집계와 과거 집계는 분석 버전으로 구분한다.

ECU 담당은 공격·송신·모델·IDS 관측을, IVI 담당은 수신·인증·UI·지연 관측을 같은 실행 ID에 제공한다. 장비별 시계·타임스탬프 기준·측정 시작과 끝을 기록한다. 동기화·대응 근거 없이 서로 다른 장비의 시각을 빼서 지연을 계산하지 않는다.

다음 구분을 원장·요약·캡션에 유지한다.

- 공격 성공 / 인증 차단 / IDS 탐지: 각각 독립 관측하며 탐지를 차단으로 계산하지 않음
- 공격 시행 / 프레임 / 정상 윈도우: 지표 단위와 분모를 혼합하지 않음
- 합성 / vcan / 물리 CAN: 준비 결과를 물리 시험 인수로 대체하지 않음
- 공식 평가 / 보조 사례 / pilot: 합산하여 공식 반복 수를 채우지 않음
- Q2 producer/receiver/consumer: epoch·event_seq와 원장으로 대조하고 같은 유실 사건을 중복 합산하지 않음

<a id="configuration--11-최종-보고서의-수치-출처와-인계"></a>
### 11. 최종 보고서의 수치 출처와 인계

| 보고서 항목 | 연결할 근거 |
|---|---|
| 실험 설계 | 설계 버전·공식 요구·TC·변경 이력 |
| 탐지율·오탐률 | 실행 ID·유효 시행·분자·분모·분석 버전 |
| 지연 그래프 | 측정 구간·시간 기준·표본·누락 처리·환경 |
| 구성별 비교 | 공통 입력 조건·서로 다른 설정·실제 실행 환경 |
| 한계·실패 사례 | 무효·미실행·미탐·재시도 원장 |
| 재현 절차 | 커밋·의존성·설정 식별·자료 해시·명령 |

제출 전 보고서 → 표·그림 → 분석 결과 → 시행 원장 → 원자료·실행 구성의 연결을 역으로 확인한다. 보존한 자료와 명령으로 주요 표·그림을 재생성해 검증한다. 사용한 자료와 해석이 달라지면 캡션·결론·한계까지 함께 확인한다. 미실측 수치를 채워 보고서를 완성하지 않는다.

공식 제출 구성은 [공동 발표·제출](../../../plan/detail/common/03_발표_제출.md)을 유지한다. 이 전략의 출처 표는 기존 제출 자료를 보강하는 연결이지 새로운 중복 보고서의 의무가 아니다.

<a id="configuration--12-시작-순서와-자동화"></a>
### 12. 시작 순서와 자동화

공동 Git 기준본 확립 → 관리 대상·대형 자료 보관 방식 합의 → 양측 검증 환경 기록 → 실험 설계·평가 분리 고정 → 첫 통합 run의 버전·증거 묶음 작성 → 분석 재현 → 릴리즈·최종 보고서 인계 순서로 적용한다.

반복되는 해시 수집·원장 검사·수치 출처 확인·릴리즈 목록 생성은 [자동화 지침](../tooling.md#automation)에 따라 도입한다. 수동 기록 형식과 입력·판정이 안정된 뒤 CLI·hook·MCP로 연결하고 자동화 성공을 실장비 인수나 사용자 승인으로 대신하지 않는다.

현재 작업 기록은 [workflow](../workflow.md), 전체 문서 연결은 [구조 매핑](../../aidlc/structure/document-map.md)을 따른다. 본 문서 작성은 Git 초기화·의존성 고정·실험 실행·외부 업로드·릴리즈 발행을 수행한 것이 아니다.

## 문서 배치와 구조 변경 참조

문서 생성·이동 시 [배치 기준](../README.md#document-placement)을 따른다. 공통 운영 안내와 작업별 CHG 기록·실험 보고서·실행 증거의 위치를 구분하고 원본을 중복 관리하지 않는다. 현재 배치와 이전 경로 대응은 [구조 매핑](../../aidlc/structure/document-map.md#current-development-layout)에서 확인한다. PR·인계 시 이동 문서의 내부 링크뿐 아니라 외부 참조와 경로 목록도 함께 검토한다. 기존 담당·브랜치·승인·실험 조건은 유지한다.

커밋의 세부 분리·파일 선택·메시지는 [공통 규칙](../../../.agents/skills/commit/rules.md), ECU·IVI별 상세 실행은 [매뉴얼](commit.md)을 따른다. AI에게 맡길 때의 공통 절차와 도구별 연결은 [tooling](../tooling.md#commit-skill)에 있다.
