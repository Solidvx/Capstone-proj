## Part 1 · 질문리스트 — 질문 원문과 사용자 답변

### REP-1: A 답변 반영 완료 — 재현성 차이 5%p

2026-09-08: 사용자 A 답변을 접수했다. 성공률 차이의 절댓값 5퍼센트포인트 이하로 M7 판정식·출력·완료표와 M8 설명을 통일했다. 아래 답변 전 보류 설명은 당시 질문 이력이며 현재는 종료됐다. 제품 구현이나 실제 재현성 시험을 수행한 것은 아니다.

계획 M7은 재실험 차이 ‘5% 이하’를 요구하지만 기존 예제는 상대 변화율과 퍼센트포인트를 혼용한다. 공식 시험·요구사항에서 이 추가 재현성 기준의 단일 계산식을 확인하지 못했다. 원래 실험의 탐지율·오탐률 합격 기준은 바꾸지 않는다.


| 번호    | 질문                                 | 선택안                                                                                                                                | 나의 답변 |
| ----- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ----- |
| REP-1 | 공격 성공률을 재실험했을 때 어느 차이로 재현성을 판단할까요? | A(권장): 퍼센트포인트 차이로 통일. 20%→24%는 4%p로 5%p 이내, 0%→4%도 동일. B: 상대 변화율 5% 이내. 20%→24%는 20% 변화로 초과. 이전 0%는 상대율을 계산할 수 없으므로 별도 판정안을 추가 설계. | A     |


A 권장은 0%를 포함한 모든 방어 조건에서 같은 식을 쓸 수 있기 때문이다. 통계적 신뢰성을 입증하는 검정이라는 뜻은 아니다. 시행 수·seed·조건·실패 사례는 함께 보고한다. A를 선택해도 0%→4%를 보안 성능 합격으로 자동 인정하지 않으며 원래 TC 기준을 별도로 적용한다. 기존 5라는 수치를 다른 단위에 자동 적용하지 않기 위해 사용자 판단을 요청한다. 답변 전 문서의 최종 판정식 변경은 보류한다.

### ADC-1·ADC-2: A/A 답변 반영 완료

2026-09-08: 두 항목 모두 A, 추가 조건 없음으로 접수했다. SDD와 M3에 단일변환·첫 시험 설정을 반영하고 요청 시간 제어 모듈을 추가했다. 실장비 최적값·I2C 통합 완료를 뜻하지 않는다. 아래 질문·답변은 결정 이력이며 현재 추가 답변은 필요 없다.

2026-09-08: 변환 함수와 3회 정상 확인 모듈은 C++ 호스트 검사를 통과했다. 다음 I2C 취득 구현은 아래 두 선택에 따라 진행한다. 기존 SDD는 연속변환이므로 다른 방식을 조용히 적용하지 않고 확인한다.

#### ADC-1. 센서에 언제 측정을 시킬까요?

**A(권장): 필요할 때 한 번씩 측정을 요청한다.** ‘측정 시작 → 완료 확인 → 결과 1회 인수’를 한 묶음으로 관리한다. 같은 값이 나와도 새 요청의 완료 결과이면 새 측정으로 센다. 완료 확인용 추가 GPIO 배선 없이 I2C 상태를 조회하는 설계다. SDD의 연속변환 설명을 단일변환으로 바꾼다.

**B: 기존 연속 측정을 유지한다.** ADC는 계속 측정하고 완료 신호를 이용해 새 결과를 구분한다. 이 선택안은 ALERT/RDY 신호 연결과 GPIO 이벤트 처리까지 설계·확인하는 방식이다. 추가 핀은 현재 지정하지 않는다. 연속 측정이 반드시 이 핀을 요구한다는 뜻은 아니며, 여기서는 새 변환 식별 근거를 명확히 하기 위한 안이다.

가변저항이 멈춰 있으면 새 측정도 같은 숫자가 나올 수 있다. 따라서 숫자가 달라졌는지로 새 측정을 판정하지 않는다. 근거: [TI ADS1115 데이터시트 §7.4.2·§8.1](https://www.ti.com/lit/ds/symlink/ads1115.pdf).

#### ADC-2. A 방식의 첫 시험 설정을 어떻게 시작할까요?

**A(권장): 아래 값을 첫 시험용으로 사용하고 실측 후 재검토한다.** 내부 변환 속도 128SPS, BMS 100ms 주기당 측정 요청 최대 1회, 완료 상태 조회 간격 1ms, 요청 후 인수 마감 20ms를 후보로 둔다. 오류·마감 초과 시 같은 주기에서 재시도하지 않고 다음 주기에 새 요청을 시도한다. 기존 ‘최초·복구 새 정상 입력 3회’ 규칙은 유지한다.

128SPS의 명목 변환시간은 약 7.8125ms다. 20ms는 여유를 둔 **시험 후보**이며 Linux/I2C 실측 보장값이 아니다. 마감 후 돌아온 결과는 정상 인수하지 않는다. 진행 중 I2C 호출이 남았으면 새 호출을 겹쳐 시작하지 않는다. 시간 감시와 CAN 통신은 취득 대기 때문에 멈추지 않도록 분리해야 하며, 커널 호출 자체가 20ms 안에 종료된다고 주장하지 않는다.

**B: 이 시험 후보값은 채택하지 않고, 원하는 조건을 답변에 적는다.** 아직 숫자를 정하고 싶지 않다면 ‘보류’라고 적어도 된다. 이 경우 모형·레지스터 검증은 가능하지만 실제 취득 실행 설정은 미확정으로 남는다. ADC-1=B이면 ADC-2에는 ‘연속방식 후속 설계’라고 적고 A의 값을 자동 적용하지 않는다.

#### S-21. 합성 SOC 평가의 필수 합격 범위를 어디까지 둘까요?

이미 선택한 ‘1시간 합성 입력으로 EKF와 쿨롱 적분 비교’의 **구체 조건 후보**를 ECU M3에 작성했다. 가상 50Ah·초기 80%·-2A·0.1초 간격·1시간, 목표 3차 전압 모델을 사용한다. 모두 소프트웨어 시험 설정이며 실제 배터리/ADS1115 오차를 측정한 값이 아니다.

- 무오차 대조군: 단위·시각·참 상태 계산을 확인한다. 정답과 같은 적분 오차 0보다 EKF가 더 작아야 한다고 요구하지 않는다.
- 주 비교 2개: 전류 관측에 +0.1A 또는 -0.1A의 고정 오차를 넣고 전압 오차는 0으로 둔다. 각 조건에서 EKF RMSE가 적분보다 작아야 한다.
- 민감도 4개: 위 전류 오차와 단셀 전압 오차 +0.01V/-0.01V를 조합한다. 불리한 조건도 숨기지 않고 보고한다.


| 선택     | 필수 합격 범위                                        | 영향                                                       |
| ------ | ----------------------------------------------- | -------------------------------------------------------- |
| A (추천) | 주 비교 2개 각각에서 기존 엄격 비교를 통과하고, 민감도 4개는 한계 분석으로 보고 | 전류 누적 오차 보정과 전압 오차 민감도를 분리. 실제 셀 정확도나 모든 조건 우월성을 주장하지 않음 |
| B      | 주 비교 2개와 민감도 4개 모두에서 기존 엄격 비교를 통과해야 함           | 더 넓은 합격 범위. 전압 오차로 EKF가 불리하면 설계 보완이 필요하고 완료 시점을 예측하기 어려움 |

시험용 수신기는 지금 먼저 도착한 것만 보관한다. 입력 순서를 바꾸면 선택 내용도 바뀌는 것을 확인했다. 같은 내용의 단순 중복은 이 질문의 대상이 아니다.

### 세션 결합 검토 질문 — S-15~S-16

상태: **S-15=A·S-16=A 답변 확인 완료, 추가 조건 없음.** 제한된 인증 데이터 정렬과 기존 receipt 조각 형식의 제한 재시도를 검토 방향으로 반영했다. 세션 설계안 §23에 재검증과 계약 영향안을 기록했다. 아래 사용자 답변 원문은 보존한다. 구체 시간·용량·공식 계약·제품 구현은 아직 확정/반영되지 않았다. Plan 융합·융합 결과 재검사는 이번 작업에서 제외한다.

#### S-15. 진짜 데이터라도 도착 순서가 바뀌면 버릴 수 있는데, 어떻게 처리할까요?

ECU가 **배터리 잔량(번호 10)**을 보내고 이어서 **위험 상태 변화(번호 11)**를 보냈다고 가정하자. IVI가 11을 먼저 처리하면 ‘11까지 받았다’고 기록한다. 그러면 늦게 온 10은 진짜 데이터여도 오래된 번호라서 버린다. 이 순서를 계속 반복한 시험에서는 위험 상태 변화만 받고 배터리 값은 갱신하지 못했다.

실제 장비에서 반드시 생긴다는 의미는 아니다. 다만 계획에 순서 역전 시험을 넣었으므로 처리 방향을 정해야 한다.


| 선택           | 쉽게 설명한 방식                                                      | 얻는 점과 감수할 점                                                                |
| ------------ | -------------------------------------------------------------- | -------------------------------------------------------------------------- |
| A (우선 검토 추천) | 인증된 데이터를 짧고 제한된 시간 동안 모아 번호 순서대로 반영한다                          | 늦게 도착한 정상 데이터도 살릴 수 있음. 대기 중 위험 상태 표시도 늦어질 수 있어 대기 상한과 공식 지연 기준을 함께 검증해야 함 |
| B            | 현재처럼 즉시 반영하고 이미 지나간 번호는 버린다. 다음 배터리 데이터가 제때 도착하도록 송수신 순서를 보강한다 | 별도 정렬 대기는 줄어듦. 순서가 바뀐 개별 데이터의 손실은 허용하며, 반복 누락 방지와 복구 조건을 입증해야 함            |

#### S-16. ‘현재 상태 받았어’라는 답장의 조각 번호를 더 자세히 붙일까요?

IVI의 확인 답장은 CAN 한 장에 들어가지 않아 **5조각**으로 나눠 보낸다. 현재 후보는 ‘어느 연결의 답장인지’는 표시하지만, 같은 연결에서 **첫 번째 답장인지 재시도 답장인지**를 모든 조각에 표시하지는 않는다. 그래서 늦은 첫 답장 조각이 두 번째 답장에 섞이면 인증이 실패해 다시 시도해야 한다.

정상적인 다음 재시도로 회복하는 경우를 확인했지만, 계속 섞이면 제한 횟수 안에 연결을 완료하지 못했다. 잘못 섞인 답장을 정상으로 받아들이지는 않았다.


| 선택           | 쉽게 설명한 방식                                   | 얻는 점과 감수할 점                                                        |
| ------------ | ------------------------------------------- | ------------------------------------------------------------------ |
| A (우선 검토 추천) | 현재 조각 형식을 유지하고, 조립 폐기·재개·제한 재시도로 처리한다       | 형식 변경을 줄임. 반복 지연/혼합에서는 연결 실패가 가능하므로 실패 표시·재연결과 정상 조건에서의 회복을 검증해야 함 |
| B            | 모든 조각에 ‘몇 번째 확인 답장인지’ 구별할 정보를 추가하는 방향으로 바꾼다 | 서로 다른 답장의 조각을 더 일찍 구분 가능. 헤더·프레임 수·인증 결합·재사용 규칙과 양측 파서를 다시 검토해야 함  |


A를 추천하는 이유는 현재 캡스톤 후보의 변경 범위를 줄이면서 먼저 필요한 회복 조건을 확인할 수 있기 때문이다. 시간/유실 조건에서 인수가 불가능하면 그대로 확정하지 않고 결과를 보고한다. B도 버스 점유 공격이나 모든 유실을 해결하는 방식은 아니다. 정확한 바이트 형식은 B 선택 후 영향안을 만들어 검증하며 임의 확정하지 않는다.

| ------- | --- |
| S-16 선택 | A   |
| 추가 조건   |     |

### 세션 동작 정책 질문 — S-13~S-14

상태: **S-7=A 답변 확인 완료.** NASA 재생·합성 정확도·하드웨어 취득/전달을 분리하도록 공식 시험과 계획을 반영했다. 생성 모델·오차 조건과 실제 검증은 미완료다. S-4~S-6과 모든 기존 답변은 아래에 보존했다.

#### S-7. NASA 재생 확인과 SOC 정확도 비교를 나눠서 검증할까요?

SOC는 배터리 잔량이다. EKF가 잔량을 잘 맞추는지 확인하려면 정답이 필요하다. 조사한 NASA 파일에는 전압·전류·용량은 있지만 직접 SOC 정답은 없다. 전류를 더해 만든 값을 정답으로 삼으면, 똑같이 전류를 더하는 비교 방법인 쿨롱 카운팅이 정답과 같아져 오차가 0이 된다. 그러면 EKF가 더 낫다는 시험을 공정하게 하기 어렵다.

추천 방향은 NASA 자료는 계속 재생·입력 검증에 사용하고, 정확도 비교에는 잔량 정답을 미리 정한 가상 배터리 시나리오를 별도로 사용하는 것이다. 예를 들어 숨겨 둔 실제 가상 잔량과 센서 오차가 섞인 관측을 따로 만들고, 두 방법이 같은 관측을 받아 잔량을 얼마나 잘 맞추는지 비교한다. 그 결과는 시뮬레이션 성능이며 실제 배터리 정확도 증명은 아니다.

| ------ | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| A (추천) | NASA 자료는 원시 단셀 조건의 재생·데이터 검증에 유지하고, 1시간 정확도 비교는 참 상태가 알려진 별도 합성 시나리오로 분리한다. 10직렬/50Ah 가변저항 장비 시험은 취득·상태 통보·화면 전달을 검증한다 | SRS의 1시간 개선 요구는 유지하되 TC-BMS-002의 NASA 입력만으로 정확도를 비교한다는 조건을 수정한다. NASA/합성/하드웨어 증거를 분리하고 모델·오차 조건은 추가 근거 검토 후 확정한다 |

A에서도 잡음이나 모델을 임의로 조절해 EKF가 이기도록 만들지 않는다. 가상 시나리오의 모델·오차 조건과 결과 주장 범위를 먼저 정해야 한다. 이 선택은 정확도 검증의 구성에 관한 것이며 실제 배터리 실험이나 NASA 자료를 없애는 승인이 아니다.

| 6      | 복구 확인 중, 이전 정상값 있음 | 마지막 정상값·복구 확인 중        |
| 7~255  | 미지원 코드             | 상태 확인 불가; 정상으로 간주하지 않음 |


최초 정상 입력 3회 전에는 1을 유지한다. 오류가 있으면 3 또는 4, 이후 새 정상 입력이 1~2회 들어오면 5 또는 6, 연속 3회에서 2가 된다. 복구 중 오류가 재발하면 다시 3/4로 돌아간다. 실제 비정상 입력을 정상값으로 clamp해서 인수하지 않는다.

**HAL 제안:** 기존 VehicleData 필드와 콜백을 유지하고, 이미 승인한 `bool stale`과 함께 `uint8_t sensorState`를 추가한다. 이 번호에서 이전 정상값 존재를 판별하므로 같은 뜻의 boolean을 중복 추가하지 않는다. CAN의 100/102 인증을 통과한 payload만 동일 snapshot으로 반영한다. 101/103 Fail-safe 계약과 200 IDS 계약은 별개다. R-2 수신 경과시간은 IVI 내부 정상 수신 기록을 사용하므로 ECU 측정시각 CAN 필드를 추가하지 않는다.

**호환성:** 현재 ICD는 byte 7=0이므로 새 IVI가 예전 ECU를 정상 센서로 오인하지 않게 한다. ECU/IVI/Python 참조/Mock/직렬화/시험은 같은 규약으로 전환해야 하며 구형 혼합 실행을 정상 인수하지 않는다. 품질 포함 8바이트 payload 전체를 기존 HMAC 입력 순서로 인증한다. 정상 입력이 없는 코드의 숫자 바이트는 측정값으로 사용하지 않는다. byte 7만 보고 이전 Fail-safe 확정 여부나 공백 후 SOC 정확도까지 추론하지 않는다.


| 선택     | 결정                                                                 |
| ------ | ------------------------------------------------------------------ |
| A (추천) | 이 byte 7 상태표와 HAL 필드 추가를 목표 계약안으로 채택하고 공식 문서·양측 구현/시험 동시 변경 과제로 연결 |
| B      | 상태 의미는 유지하되 번호표 또는 HAL 표현을 수정한 안이 필요함. 원하는 변경을 아래에 기입              |


승인해도 제품 코드를 지금 구현하는 것은 아니다. 목표 계약과 현재 구현을 구분하며 실제 전환에는 ICD·SRS·양측 SDD·TEST_PLAN·ADR 및 양측/참조 구현·시험의 동기화가 필요하다. 이 제안은 센서 품질 계약이고 세션 암호 프로토콜 후보의 자동 승인이 아니다.


| 나의 답변              | 입력칸 |
| ------------------ | --- |
| S-3 선택             | A   |
| 바꾸고 싶은 상태 번호/필드/조건 |     |

#### R-1. “오류”만 알려줄까요, “복구를 확인 중”인 것도 알려줄까요?



##### 상황과 판단할 점

가변저항/ADC 연결에 오류가 났다가 정상 입력이 두 번 들어왔다고 하자. 이미 정한 정책상 **세 번째 새 정상 입력 전까지는 오류가 해제되지 않는다.** 이때 화면이 단순히 오류라고만 표시할지, “다시 읽히지만 정상 복구를 확인 중”이라고도 알려줄지 정해야 한다.

기존 BMS 메시지의 예약 영역을 쓰는 결정은 유지한다. 별도 센서 상태 메시지를 추가할지는 다시 묻지 않는다.


| 선택                       | 쉬운 설명                                                         | 장점과 부담                                        |
| ------------------------ | ------------------------------------------------------------- | --------------------------------------------- |
| A — 상태를 구분해서 전달 **(추천)** | 정상 / 오류 / 정상 복구 확인 중 / 최초 측정 대기를 구분하고, 마지막 정상값이 있는지도 표현한다     | 배선 시험과 오류 원인 구분이 쉽다. ECU·IVI가 같은 상태표를 사용해야 한다 |
| B — 최소 정보만 전달            | 현재 값 사용 가능 여부와 마지막 정상값 존재 여부만 전달한다. 오류 원인·복구 진행은 ECU 로그로 확인한다 | 통신·화면 상태가 단순하다. 화면만으로 오류와 복구 확인 중을 구분하기 어렵다   |


**추천 이유:** 실제 연결을 끊고 다시 붙이는 시험에서 복구 대기와 지속 오류를 구분할 수 있다. 복구 횟수를 화면에 매번 표시할 필요는 없고 `복구 확인 중`이라는 문구면 된다.

두 안 모두 정상으로 확인되지 않은 값은 현재 측정값으로 표시하지 않는다. 이전 형식·알 수 없는 상태값은 정상으로 간주하지 않고 `상태 확인 불가`로 취급하는 방안을 함께 제안한다. 기존 ICD는 byte 7을 0으로 채우므로, 0을 곧바로 “새 규약의 정상”으로 해석하는 방식은 피한다.

**이 답변으로 확정되는 범위:** 전달할 상태의 의미다. 실제 byte 7 인코딩과 HAL 필드 변경은 이 상태표를 바탕으로 변경 전후표를 작성해 별도 계약 검토를 거친다. 영향 대상은 ECU 송신, IVI parser·HAL·화면, 전체 payload를 인증하는 SecOC와 양측 시험이다. 지금 CAN ID·DLC·HMAC 입력 순서를 변경하지 않는다.


| 나의 답변                     | 입력칸 |
| ------------------------- | --- |
| 선택: A / B / 직접 작성         | A   |
| `상태 확인 불가` 처리에 다른 의견이 있다면 |     |
| 추가 조건                     |     |




#### R-2. “마지막 값의 시간”은 수신 기준이면 될까요, 실제 측정 기준이어야 할까요?



##### 상황과 판단할 점

ECU가 정상값을 보낸 직후 센서 오류가 났다고 하자. IVI는 자신이 **마지막 정상 데이터를 언제 받았는지**는 기록할 수 있다. 그러나 그 데이터가 ECU에서 **정확히 언제 측정됐는지**까지 알려면 측정 시각 또는 데이터 나이를 전달하는 별도 설계가 필요하다.

현재 BMS payload에는 측정 시각 필드가 없다. 앞선 “마지막 정상 측정 시각 또는 경과시간 표시”를 어떤 의미로 구현할지 구체화하는 질문이다.


| 선택                          | 실제 화면 예시                     | 장점과 부담                                                              |
| --------------------------- | ---------------------------- | ------------------------------------------------------------------- |
| A — 수신 기준임을 명확히 표시 **(추천)** | `마지막 정상 데이터 수신 후 5초 · 센서 오류` | IVI의 경과시간 기록으로 설계할 수 있다. 실제 측정 후 5초라고 주장하지 않는다                      |
| B — 실제 측정 기준을 전달            | `마지막 정상 측정 후 5초 · 센서 오류`     | 측정 시점 기준의 정보를 제공한다. 시간/데이터 나이 표현, 예약 영역 용량, 전송 지연·시계 기준을 추가 설계해야 한다 |


**추천 이유:** 현재 가상 배터리 통합 시험에서는 오류와 오래된 표시를 명확히 구분하는 데 A가 단순하다. 다만 **측정 시각을 표시한다는 기존 목표를 수신 기준 표시로 구체적으로 변경하는 선택**이므로 동의 없이 적용하지 않는다. 실제 측정 시각이 연구 결과나 필수 기능에 필요하면 B를 선택하면 된다.

A에서도 오류 상태 프레임이 계속 들어온다고 이 경과시간을 0으로 되돌리지 않는다. 앱이 재시작돼 과거 수신 기록이 없다면 `경과시간 확인 불가`로 표시하고 임의 시간을 만들지 않는다. B 선택은 새 CAN ID나 특정 시간 단위까지 승인하는 뜻이 아니며, 예약 영역과 함께 수용 가능한지 조사 후 구체안을 제시한다.


| 나의 답변                        | 입력칸 |
| ---------------------------- | --- |
| 선택: A / B / 직접 작성            | A   |
| 측정 시점의 정확한 시간이 꼭 필요한 이유가 있다면 |     |
| 추가 조건                        |     |




#### R-3. 처음 전원을 켰을 때도 정상 입력을 3번 확인할까요?



##### 상황과 판단할 점

오류 **후 복구**는 새 정상 입력 3회로 정했다. 그러나 처음 프로그램을 켠 경우는 아직 정상값도 오류 이력도 없을 수 있다. 첫 정상 입력 하나를 바로 사용할지, 처음에도 3회 확인할지가 남아 있다.


| 선택                         | 시작 직후 동작                             | 장점과 부담                                    |
| -------------------------- | ------------------------------------ | ----------------------------------------- |
| A — 최초 시작도 3회 확인 **(추천)**  | 처음에는 `측정 준비 중`, 연속 새 정상 입력 3회 후 값 사용 | 시작과 복구의 확인 규칙을 맞춘다. 최초 값 표시가 입력 확인만큼 늦어진다 |
| B — 최초 시작은 1회, 오류 후 복구는 3회 | 첫 정상 입력부터 값 사용. 이후 오류가 나면 기존대로 3회 확인 | 최초 표시가 빠르다. 시작과 복구의 조건이 달라진다              |


**추천 이유:** 실제 센서 초기 연결 확인과 오류 후 복구를 같은 기준으로 설명하기 쉽다. 3회는 이미 정한 복구 정책을 최초 시작까지 확장하는 제안이며, 실측 최적값이라는 뜻은 아니다.

두 안 모두 첫 정상값을 인정하기 전 기본 SOC를 실제 측정값처럼 표시하지 않는다. 이때 화면의 배터리 위험 판정도 `판정 대기`로 구분하는 방안을 제안한다. 이는 새 CAN Fail-safe 상태나 이유 코드를 추가하자는 뜻이 아니다. ECU 내부 초기 상태와 IVI의 판정 가능 여부를 연결하는 세부 계약은 별도로 명세한다. 정상 운전 중에는 기존대로 즉시 갱신하며 세 샘플씩 모아서 갱신하지 않는다.


| 나의 답변                 | 입력칸 |
| --------------------- | --- |
| 선택: A / B / 직접 작성     | A   |
| 최초 측정/판정 대기 표시에 대한 의견 |     |
| 추가 조건                 |     |




#### R-4. 계산이 멈춘 동안의 배터리 변화를 추정해서 채울까요?



##### 상황과 판단할 점

BMS 작업을 마지막 검증된 계산 상태에서 복구하기로 했다. 예를 들어 SOC 60%에서 작업이 멈췄고 얼마 뒤 다시 시작됐다면, **멈춘 동안 전류가 어떻게 변했는지 모르는 구간**이 생길 수 있다. 저장된 상태를 복원하는 것과 이 빈 구간의 배터리 변화를 계산하는 것은 다른 문제다.


| 선택                        | 복구 방식                                                         | 장점과 부담                                                                     |
| ------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------- |
| A — 측정 공백을 남김 **(추천)**    | 검증된 상태를 복원하고 새 유효 입력부터 계산을 재개한다. 관측하지 못한 구간을 임의 전류로 적분하지 않는다  | 존재하지 않는 측정을 만들지 않는다. 중단 구간을 포함한 SOC/SOH 정확도는 보장할 수 없어 별도 표시·평가 제외 조건이 필요하다 |
| B — 검증된 누락 구간 데이터가 있어야 재개 | 작업 외부에서 시간순 입력을 따로 보관하고, 끊긴 구간을 재계산할 수 있을 때만 상태 복구를 성공으로 인정한다 | 누적 계산의 연속성을 확인할 수 있다. 독립 수집·버퍼·시간순 재처리가 필요하고 데이터가 없으면 복구 실패다               |


**추천 이유:** 현재 작업 복구 범위에서는 A가 구현 부담을 줄인다. 다만 “실행이 다시 됨”을 “SOC 정확도도 회복됨”으로 처리하지 않는다. 시간 공백은 로그·평가 증적에 남기고 정확도 시험은 연속 입력 구간과 구분한다. 허용 가능한 공백과 정상 추정으로 다시 인정할 조건은 근거를 마련해 검토한다.

B도 마지막 전류가 계속 흘렀다고 가정하는 방식이 아니다. 실제로 검증된 입력 기록이 있어야 한다. 두 안 모두 계산 상태 전체를 검증해 복원한다는 기존 Q-5=A와 인증 세션·counter·Fail-safe를 임의 초기화하지 않는 결정을 유지한다.


| 나의 답변                  | 입력칸 |
| ---------------------- | --- |
| 선택: A / B / 직접 작성      | A   |
| 중단 구간까지 계산 연속성이 꼭 필요한지 |     |
| 추가 조건                  |     |




#### R-5. 복구의 시간 제한은 측정 후 정할까요, 원하는 제한을 먼저 제시할까요?



##### 상황과 판단할 점

두 시간 기준이 아직 없다. 하나는 **얼마나 오래된 계산 저장 상태까지 재사용할지**, 다른 하나는 **멈춘 작업의 종료를 얼마 동안 기다릴지**다. 첫 번째가 너무 길면 오래된 상태를 복원할 수 있고, 두 번째가 너무 길면 운영자 개입 안내가 늦어진다. 반대로 너무 짧으면 복구 가능한 경우도 실패로 처리할 수 있다.

이 두 값은 서로 다른 기준이며 같은 숫자로 맞출 필요가 없다. 기존 Watchdog 감시 주기·timeout·재시작 횟수와도 구분한다.


| 선택                             | 다음 작업                                                       | 장점과 부담                                                  |
| ------------------------------ | ----------------------------------------------------------- | ------------------------------------------------------- |
| A — 측정·분석 후 구체적 수치 제안 **(추천)** | 취득/저장 간격, 작업 종료 지연, 중단 구간 오차 영향을 조사해 두 제한값과 근거를 제시한 뒤 답변받는다 | 근거 없는 시간을 지금 확정하지 않는다. 수치가 필요한 구현/인수 절차는 그때까지 미확정으로 남는다 |
| B — 사용자가 원하는 제한을 먼저 제시         | 원하는 최대 시간 두 개를 목표로 기록하고 달성 가능성을 검토한다                        | 발표·운영 요구를 먼저 반영할 수 있다. 제시한 수치가 검증 없이 보장되는 것은 아니다        |


**추천 이유:** 아직 실제 장비 조건과 측정 결과가 없어 A가 합리적이다. A는 “아무 값이나 자동으로 정해도 된다”는 위임이 아니다. 근거가 있는 후보 수치를 가져온 뒤 다시 확인한다. 장비 정보가 필요한 실측은 기존 후속 입력 뒤 수행하고, 그 전에는 코드 경로·Mock으로 확인 가능한 부분만 진행한다.

종료·회수 실패 시 운영자가 서비스를 재시작한다는 Q-6=A는 그대로다. 이 질문은 그 안내까지 기다리는 한도를 정하는 방법에 관한 것이다.

#### Q-1. 센서 오류를 전달하는 통신 형식은 어떻게 확장할까요?



##### 상황을 쉽게 설명하면

현재 ECU는 “SOC·전압·온도 등 배터리 값”을 IVI로 보낸다. 센서가 고장 나도 통신은 유지하기로 했으므로, IVI에 **“이 값은 마지막으로 정상 측정한 값이고, 현재 센서는 오류 상태다”**라는 정보도 보내야 한다.

이 오류·유효성 정보를 보내겠다는 결정은 끝났다. 이번 질문은 **기존 배터리 메시지에 표시를 넣을지, 별도 상태 메시지를 추가할지**다. 어느 쪽도 지금 ICD에 구현돼 있다고 볼 수 없으며, 양측과 시험의 계약 변경이 필요하다.

##### 선택안


| 선택                            | 쉬운 설명                                           | 장점                                          | 추가로 해결할 점                                                                     |
| ----------------------------- | ----------------------------------------------- | ------------------------------------------- | ----------------------------------------------------------------------------- |
| A — 별도 상태 메시지와 인증 추가 **(추천)** | 배터리 값 옆에 “센서 상태 설명서”를 따로 보낸다. 설명서도 변조 여부를 검증한다. | 현재 배터리 값의 배치를 유지하면서 오류 원인·유효성 정보를 확장하기 쉽다.  | CAN ID와 인증 메시지/규칙을 추가해야 한다. 상태 설명서가 유실되거나 배터리 값과 순서가 바뀌는 경우의 결합·만료 처리가 필요하다.  |

#### Q-2. 센서 오류가 나면 마지막 배터리 숫자를 화면에 남길까요?



##### 상황을 쉽게 설명하면

화면에 **SOC 60%, 전압 38V**가 표시되다가 ADC 연결이 끊겼다고 가정하자. 60%와 38V는 마지막 정상값이지, 지금 측정한 값은 아니다. 이전에 선택한 정책에 따라 통신과 오류 전달은 계속한다.

숫자를 남기면 직전 상태를 알 수 있지만 현재값으로 오해할 수 있다. 숫자를 감추면 오류가 분명하지만 직전 상태를 한눈에 보기 어렵다.

##### 선택안


| 선택                            | 화면 예시                                                                                  | 장점·한계                                                      |
| ----------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| A — 마지막 값과 오류를 함께 표시 **(추천)** | `60% · 마지막 정상값`과 `센서 입력 오류`를 표시한다. 정상 표시와 다른 색/상태 표시를 사용하고 마지막 정상 측정 시각 또는 경과시간을 보여준다. | 이전 상태를 확인할 수 있다. 숫자만 보고 현재값으로 오해하지 않도록 오류·유효성 표시가 명확해야 한다. |
| B — 주 표시를 비우고 마지막 값은 보조 표시    | 주요 SOC·전압 영역은 `—` 또는 `측정 불가`로 바꾸고, 작은 보조 영역에 마지막 정상값을 남긴다.                             | 현재값이 없다는 사실이 뚜렷하다. 직전 상태를 보려면 보조 영역을 확인해야 한다.              |


**추천 이유:** 기존에 마지막 유효값을 보존하기로 한 방향에는 A가 자연스럽다. B도 내부 마지막 값 보존과 충돌하지 않으며 표시 방식만 다르다. 어느 쪽이든 실제 값이 없는 상황을 SOC 0%로 대신 표시하지 않는다. 오류 발생 전에 있던 CRITICAL/SHUTDOWN 경고를 지우는 선택도 아니다.

프로그램 시작 이후 정상 입력을 한 번도 받지 못했다면 '마지막 정상값' 자체가 없다. 이 경우에는 두 안 모두 `측정값 없음`으로 표시하고 기본 상수를 실제 측정값처럼 보여주지 않는 방향을 제안한다.

#### Q-3. 센서가 다시 읽히면 언제 정상으로 복구할까요?



##### 상황을 쉽게 설명하면

느슨한 선 때문에 **오류→정상→오류→정상**이 반복될 수 있다. 정상 입력이 한 번 들어오자마자 복구하면 빠르지만, 화면 상태가 자주 바뀔 수 있다. 여러 번 연속 정상인지 확인하면 복구가 조금 늦지만 접촉 불량을 구분하기 쉽다.

여기서 '정상'은 단순히 읽기 함수가 성공했다는 뜻만이 아니다. 선택한 ADC 설정에 맞는 변환 완료·입력 범위·새 샘플인지까지 확인해야 한다. 화면만 정상으로 바꾸고 데이터가 계속 오래된 상태여서는 안 된다.

##### 선택안


| 선택                               | 복구 조건                                                       | 장점·한계                                                           |
| -------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------- |
| A — 정상 입력 3회 연속 확인 후 복구 **(추천)** | 중간에 오류가 나오면 연속 정상 횟수를 다시 센다. 세 번 모두 정상인 새 입력이면 센서 오류를 해제한다. | 간헐적으로 한 번 읽힌 값을 곧바로 복구로 오인할 가능성을 줄인다. 복구에 몇 차례의 입력 확인 시간이 추가된다. |
| B — 정상 입력 1회 확인 후 복구             | 첫 정상 새 입력에서 센서 오류를 해제한다.                                    | 복구가 빠르다. 간헐적 접촉 불량에서는 정상/오류 표시가 반복될 수 있다.                       |


**추천 이유:** 가변저항·ADC 연결을 실제로 시험할 예정이므로 A를 제안한다. '3회'는 이번에 제안하는 정책값이며 실측으로 정당화된 수치는 아니다. 실제 확인 시간은 ADC 취득 주기·변환 시간에 따라 달라진다. 이 선택은 오류 후 복구에만 적용하며 정상 운전 중 숫자·게이지 갱신을 세 번씩 묶거나 늦추지 않는다.

**질문: 정상 복구를 A 또는 B로 정할까요? 다른 횟수가 필요하면 직접 적어 달라.**


| 나의 답변             | 입력칸 |
| ----------------- | --- |
| 선택: A / B / 직접 작성 | A   |
| 다른 연속 횟수 또는 복구 조건 |     |




#### Q-4. 센서 오류만으로 Fail-safe 상태도 바꿀까요?



##### 상황을 쉽게 설명하면

**“센서가 읽히지 않는다”**와 **“배터리가 위험하다”**는 다른 사실이다. 센서 오류를 알리기로는 했지만, 그 오류만으로 배터리 상태를 NORMAL에서 WARNING으로 올릴지는 아직 결정하지 않았다.

센서 오류가 났다고 SOC가 낮다거나 과열됐다고 추정해서 기존 위험 사유 코드를 보내면 안 된다. 현재 `0x07`은 Watchdog 재시작 실패 사유이므로 센서 오류에도 같은 뜻으로 사용할 수 없다.

##### 선택안


| 선택                                      | ECU·화면 동작                                                                            | 장점·변경 영향                                                                          |
| --------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| A — 센서 오류와 기존 Fail-safe 상태를 분리 **(추천)** | 별도 센서 오류를 표시하고 마지막 확정 Fail-safe 상태를 유지한다. 잘못된 입력으로 새 위험 판정이나 정상 복귀를 하지 않는다.          | 가상 배터리 시험의 오류와 배터리 위험 상태를 구분한다. 센서 오류에 대한 새 Fail-safe 전이·사유 코드를 추가하지 않는다.         |
| B — 센서 오류 전용 WARNING 전이 추가              | 센서 오류가 확인되면 전용 사유로 WARNING을 요청하는 변경안을 작성한다. 기존 CRITICAL/SHUTDOWN을 더 낮은 상태로 바꾸지는 않는다. | 입력 신뢰성 상실을 Fail-safe 상태에도 반영할 수 있다. 새 사유 코드·전이 조건·복구 조건과 SRS/ICD/SDD/시험 변경이 필요하다. |


**추천 이유:** 현재는 실제 배터리 제어가 아니라 가상 입력 기반 통합 검증이 주 범위이므로 A가 기존 계약을 덜 변경하면서 오류를 명확히 표현한다. B를 선택하면 실제 배터리 차단 기능을 추가하는 것으로 확대 해석하지 않는다. 세부 코드와 복구 전이는 별도 변경안에서 확인한다.

**질문: 센서 오류를 별도 상태로 관리하는 A와 Fail-safe 전이까지 확장하는 B 중 어느 쪽으로 할까요?**


| 나의 답변                 | 입력칸 |
| --------------------- | --- |
| 선택: A / B / 직접 작성     | A   |
| 센서 오류 시 반드시 일어나야 할 동작 |     |




#### Q-5. BMS 작업이 재시작될 때 계산 상태를 이어갈까요?



##### 상황을 쉽게 설명하면

Watchdog가 BMS 작업을 재시작하면 코드 실행뿐 아니라 **SOC 추정값·추정기의 내부 상태·SOH 누적값**을 어떻게 다룰지도 정해야 한다. 무조건 초기값으로 시작하면 화면의 SOC가 갑자기 바뀔 수 있다. 반대로 문제가 있는 상태를 그대로 다시 사용하면 같은 오류가 반복될 수 있다.

이 질문은 프로그램 전체나 RPi 전원을 재시작하는 경우가 아니라, **main이 살아 있고 BMS 작업만 복구하는 경우**다. 인증키·세션 counter와 기존 Fail-safe 상태를 초기화하는 승인이 아니다.

##### 선택안


| 선택                                | 처리                                                                               | 장점·한계                                                                      |
| --------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| A — 마지막으로 검증한 계산 상태에서 복구 **(추천)** | main 등 작업 외부에 보관한 마지막 정상 상태를 검증해 넘긴다. SOC만이 아니라 추정기와 누적 계산에 필요한 상태를 한 묶음으로 관리한다. | 재시작 후 값의 불필요한 급변을 줄일 수 있다. 상태 snapshot의 일관성·유효성·오래된 정도를 검증해야 한다.           |
| B — 추정기를 다시 초기화                   | 추정기의 초기 상태를 다시 만들고 재초기화 중임을 표시한다. 안정화된 새 결과를 정상값으로 인수하는 조건을 정한다.                 | 손상된 추정 상태를 재사용하지 않는 구조가 단순하다. SOC 급변·SOH 연속성·초기화 구간의 표시와 시험 조건을 다시 정해야 한다. |


**추천 이유:** 기존 세션·화면·누적 상태와의 연결을 고려하면 A가 자연스럽다. 다만 검증할 정상 snapshot이 없거나 훼손됐다면 정상 복구로 처리하지 않고 실패로 남기는 조건을 함께 제안한다. 오래된 값을 계속 현재값으로 보내거나, 장기 전원 재부팅까지 상태 보존이 구현됐다고 주장하지 않는다.

**질문: BMS 작업 복구 시 계산 상태는 A 또는 B 중 어느 방식으로 관리할까요?**


| 나의 답변                 | 입력칸 |
| --------------------- | --- |
| 선택: A / B / 직접 작성     | A   |
| 상태가 없거나 잘못됐을 때 원하는 처리 |     |




#### Q-6. 멈춘 BMS 작업이 종료 요청에도 응답하지 않으면 어떻게 할까요?



##### 상황을 쉽게 설명하면

작업을 다시 시작하려면 이전 작업이 끝나고 자원이 정리돼야 한다. 그런데 이전 작업이 완전히 멈춰 종료 요청도 받지 못하면, 같은 작업을 또 실행해 중복 송신이나 자원 충돌을 만들 수 있다.

main이 BMS 작업을 관리한다는 기본 선택은 그대로다. 이번에는 **그 복구마저 불가능한 예외 상황의 마지막 대응**을 묻는다. 단순 timeout 횟수를 실제 재시작 실패 횟수로 대신 세지는 않는다.

##### 선택안


| 선택                                | 마지막 대응                                                                        | 장점·변경 영향                                                                        |
| --------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| A — 복구 실패를 표시하고 운영자가 재시작 **(추천)** | 종료·회수에 실패한 작업 위에 새 작업을 만들지 않는다. 가능한 감시 경로에서 복구 실패를 기록·표시하고 운영자가 서비스를 다시 시작한다. | 자동 복구 범위를 명확히 제한하며 프로세스 재시작 루프를 추가하지 않는다. 이 예외 상황은 무인 복구가 아니다.                  |
| B — 최후 수단으로 ECU 프로세스 전체 재시작       | 작업 단위 복구가 실패했음을 기록한 후 외부 서비스 관리자가 ECU 프로세스를 재시작하도록 별도 정책을 설계한다.               | 작업 내부에서 해결하지 못한 장애도 자동 복구를 시도한다. 재시작 반복 제한·세션 재인증·실패 횟수 보존·시작 시 상태 처리 과제가 늘어난다. |


**추천 이유:** A는 이미 확정한 작업 단위 복구와 세션 사전 검증 범위를 유지하는 데 유리하다. 더 높은 자동 복구 수준이 필요하면 B를 택할 수 있지만, 기존 `Restart=always` 한 줄만으로 요구가 충족된 것으로 처리하지 않는다. main 자체나 CAN도 멈춘 경우 경고 전송을 보장할 수 없다는 한계는 두 안 모두 검토한다.

**질문: 작업을 회수하지 못하는 최종 실패에서는 A 또는 B 중 어떤 대응을 원하나요?**


| 나의 답변                  | 입력칸 |
| ---------------------- | --- |
| 선택: A / B / 직접 작성      | A   |
| 자동 복구 범위·운영자 개입에 대한 조건 |     |

### 2. 배터리 시험 범위 — 사용자 답변 확정

**주 계획은 가변저항으로 가상 배터리를 모사하는 방식이다.** RPi4·CAN·ADC 등 실제 하드웨어 경로를 사용하더라도 실제 배터리 팩의 SOC/SOH 정확도를 검증한 것으로 표현하지 않는다. 10직렬·50Ah 등 문서의 모델 수치는 가상 배터리의 설정으로 구분하며, 물리 제품 사양으로 기입하지 않는다.

시간적 여유가 있으면 **실제 보조배터리 시험을 검토**한다. 주 계획의 필수 완료 조건에 추가하지 않으며, 구체적인 계측·배선은 아직 승인·확정되지 않았다.

- [ ] 전원 공급 확인, USB 출력 전압·전류 계측, 배터리 SOC 추정 중 무엇을 검증할지 인터뷰한다.
- [ ] 주 계획의 가상 팩 모델과 실제 보조배터리 데이터의 단위·적용 범위를 분리한다.

세션 설계안 §21에 독립 A/B 논리 교환과 별도 receipt 자동 재개 검증을 기록했다. 시험 7개 실패 0·오류 0. 메시지 최초 유실 조합 243개와 재부팅 15개에서 완료를 관찰했다. 확인 조각 충돌 후 다음 정상 재시도에서는 회복했으며 반복 충돌은 제한 내 실패했다. 이 수치는 실제 CAN 성공률·지연이 아니다.

완료 범위는 독립 로컬 타이머/더미 nonce에 의한 READY 이전 자동 교환 및 별도 확인 조립의 자동 재개다. 두 모형의 전체 연결, READY 캐시와 실제 세션 수명, 전체 조각/공유 counter·재부팅 경합은 아직 남았다. 시험의 READY 이후 40 tick 만료를 정상 세션 운영 정책으로 채택하지 않는다. 구체 정책 비교 후 모호한 선택만 인터뷰하며 이번에 새로운 사용자 결정을 추정하지 않았다.

다음 순서: 전체 수신 경로 결합 검증 → 세션 미정 정책·계약 영향 인터뷰 → 위험 근거/합성 조건/복구 수치와 장비별 실행 조건 정리 → 6번 네 기준 최종 심사 → 통과 후 7번 Plan 융합·재검사. 기존 계획 구조·답변·공식 계약·제품 코드는 보존했다. 하드웨어 및 Android 정보는 빈칸을 유지하며, 최종 계획 확정 검토 전과 실장비 작업 전 반드시 입력을 다시 안내한다.

### 40. Plan 융합 제외·전체 후보 프레임 결합 결과

최신 사용자 지시에 따라 **Plan 융합·융합 결과 재검사는 이번 범위에서 제외**했다. ECU/IVI 상위 계획과 공동 연계·의존성의 현행 순서를 맞췄다. 과거 기록의 병합 예정 문구는 이 지시를 덮어쓰지 않는다. 기존 Plan/보관 구조와 사용자 답변은 보존했다.

세션 설계안 §22에서 독립 A/B의 조각 수신부터 상태 적용·receipt·일반 BMS/전이까지 연결했다. 검사 8개 중 1개는 counter 역순 처리 반례 재현이며 전체 설계 합격이 아니다. 첫 유실 31개와 재부팅 30개 경우 복구를 관찰했다. 실제 CAN arbitration·C++/Android/HAL·장비·전체 공격 조합은 검증하지 않았다.

새 선택은 질문리스트 맨 위 S-15(인증 데이터 순서 처리)·S-16(receipt 조각 식별/재시도)에 설명·선택안·답변칸을 작성했다. 사용자 지시대로 답변 전 해당 정책을 확정하지 않는다. 과거 ECU M3에 남은 ‘상태 미확인 중 일반 송신 미확정’ 문장은 이미 답한 S-13=A에 맞게 정정했다.

남은 작업과 종료 조건의 현행 목록은 공동 연계·의존성 「현재 작업 범위와 종료 조건」을 따른다. 순서는 답변 반영/반례 재검증 → 세션 상세·계약 영향 → 합성 조건·복구 수치·위험 근거/장비 실행 조건 → 네 기준 최종 심사다. 실제 측정이 필요한 수치를 계획 검토용 모형으로 대신하지 않는다. 하드웨어·Android 정보 빈칸은 유지하며 최종 확정 검토 전 및 장비 작업 전 반드시 입력을 재안내한다.

### 41. S-15=A·S-16=A 반영과 정렬 모형 재검증

사용자 작성 답변은 모두 A, 추가 조건 없음. 원문 선택칸은 보존했다. 인증 완성 쌍의 제한 정렬과 기존 receipt 조각 형식/제한 재시도 방향을 양측 M3·공동 통합시험에 반영했다. 세션 설계안 §23에 검사 12개 통과, 역순 배치 반례 해소 범위, 첫 유실 31개/재부팅 30개 재검증과 계약 영향표를 기록했다. 실제 제품·장비 인수는 아니다.

2 tick 대기·8건 큐·포화 시 신규 거부는 비교용 시험 조건이며 사용자 승인 상수/정책이 아니다. 정상 BMS 수신 시각과 정렬 후 반영 시각을 구분하고 기존 화면 지연 구간·합격 기준을 유지한다. 큐/조립/캐시 기한과 위험 전이 포화·세션 전환/HAL 세부·공식 계약 확정은 남아 있다. S-15/S-16 방향을 다시 인터뷰하지 않는다.

현재 완료: 답변 반영 → 제한 모형 재검증 → 양측 수행 과제와 공식 계약 영향표 작성. 남은 순서는 상세 세션/수치 근거·필요 선택 구체화 → S-7 합성 조건·R-5 복구 수치·위험 근거/장비별 실행 조건 → plan 네 기준 최종 심사다. Plan 융합·재검사는 계속 제외한다. 하드웨어/Android 빈칸은 유지하며 최종 확정 검토 전과 실장비 작업 전에 반드시 입력을 재안내한다.

### 42. 예외 처리 인터뷰와 운영 수치 확정 절차

세션 설계안 §24에 큐 포화·상충 본문의 두 제한 모형 반례, S-17/S-18 처리 후보, 운영 기한/용량의 기산점·측정 근거·승인 순서를 작성했다. 검사 2개는 문제 재현이며 제품 취약점 확정이나 해결 완료가 아니다. 인증된 SHUTDOWN 전이가 시험 큐 포화로 누락될 수 있어 기존 신규 거부 정책을 임의로 확정하지 않았다.

질문리스트 맨 위 S-17(위험 메시지 공간/포화 처리)·S-18(같은 번호의 인증 상충 내용)에 쉬운 설명·선택안·빈 답변칸을 작성했다. 답변 전 해당 정책 변경은 대기한다. S-15/S-16 방향은 재질문하지 않으며 장비 근거가 필요한 숫자를 지금 사용자에게 추정 입력하도록 요구하지 않는다.

완료: 예외 조건 재현과 선택안 작성, 운영 수치 확정 절차 및 공동 인수 조건 보완. 다음: S-17/S-18 반영·예외 검증 → 운영 전환/HAL·세션 상세 계약 → 합성 조건·복구 수치·위험/장비 실행 조건 → 네 기준 최종 심사. Plan 융합·재검사는 계속 제외한다. 하드웨어/Android 빈칸은 유지하고 최종 확정 검토 전과 실장비 작업 전에 반드시 입력을 재안내한다.

### 43. 자율 진행·S-17/S-18 반영 및 최종 심사 준비

사용자는 별도 계속 지시 없이 PLAN 통합 직전까지 작업하고 통합 자체는 직접 지시할 때만 수행하도록 요청했다. 이 범위를 유지한다. S-17=A·S-18=A 원문을 보존하고 예약 큐/인증 상충 실패·제한 재연결 방향을 양측 M3·공동 시험에 반영했다. 제한 모형 검사 16개가 통과했으며 운영 수치·제품/장비 인수는 아니다.

이어 세션 설계안 §25에 구세션 송신 중단/HAL 사유 부재 후보, ECU M3에 구체 합성 조건/대조군/합격 범위 후보를 작성했다. TARA의 근거 없는 일괄 의무 준수 표현은 참조와 입증 여부를 구분하도록 정정했고 기존 위험 점수를 추정 갱신하지 않았다. 질문리스트 맨 위 S-19~S-21에 질문/선택안/답변칸을 묶었다. 이 선택이 필요한 변경만 대기하며 기존 답변은 다시 묻지 않는다.

**하드웨어 재안내 수행:** 최종 확정 심사 준비를 위해 질문리스트와 사용자 안내에서 §1 하드웨어 및 §6 Android 정보 입력을 요청했다. 현재 빈칸은 아직 채워지지 않았으며 장비별 호환/실행 조건과 최종 판정에 영향을 준다. 실제 장비 작업 전 재안내 약속도 유지한다.

남음: S-19~S-21 반영·대응 검증, 세부 계약 전환과 운영 수치/위험 근거·장비 입력 확인, plan 내부의 과거/현행 중복 정리 및 네 기준 최종 심사. 미입력·미결정을 통과로 바꾸지 않으며 PLAN 통합은 하지 않는다. 사용자 응답이 도착하면 별도 계속 지시 없이 이어간다.

### 44. 하드웨어 정보 입력 반영

사용자가 제공한 구매 목록·실물 사진, 두 microSD가 모두 SanDisk 128GB라는 확인, 레벨 컨버터 총 5개라는 확인과 기존 `컨버터O_배선완결판.html`을 다시 대조했다. §1에 원래 질문 순서를 유지한 필수 9개 항목, 보조 장비·소모품, 근거 파일, 실장비 착수 전 점검을 기록했다. ECU 상위 계획·ECU M1·ECU M3·공동 통합시험의 하드웨어 사양과 배선 조건도 앞선 변경에서 동기화했다.

Node A와 Node B는 각각 MCP2515-I/SO+TJA1050 8MHz 모듈 1개와 4채널 레벨 컨버터 2개를 사용한다. LC#1 네 채널은 SCK·SI·CS·SO, LC#2 한 채널은 GPIO25 INT에 사용하며 남은 레벨 컨버터 1개는 예비품이다. ADS1115는 3.3V·ADDR-GND(0x48)·A0 단일종단·PGA ±4.096V를 초기 설정으로 기록했고 가변저항 실제 입력은 0~3.3V로 제한했다.

실물에서 온보드 종단저항 점퍼는 초록색 `J1`로 확인됐으나 기존 HTML에는 `J3`라고 적혀 있어 §1에 실물 `J1`을 기준으로 명시했다. 외장 120Ω 저항 허용오차도 구매 목록 5%와 종합 촬영 문서 표제 1%가 충돌하므로 측정 전 확정하지 않았다. ADS1115의 분리된 핀헤더, 브레드보드/전원 레일 분리, 멀티미터·CAN 꼬임선, USB-CAN Analyzer 드라이버·종단, 전체 전력 예산, 이전 성공 당시 SPI clock도 실제 진행 전에 확인할 항목으로 추가했다.

완료된 것은 보유 사양·수량·계획 배선 확인이다. 전원 인가 전 HV/LV·공통 GND·단락·약 60Ω 종단을 측정하고, 두 노드의 `can0`·INT·500kbps 양방향 CAN과 ADS1115 원시값을 실장비에서 검증해야 한다. Android 소스/이미지와 빌드 환경 입력은 §6에 계속 남아 있다. S-19~S-21과 나머지 plan 최종 심사 과제도 유지하며 `Plan/` 통합은 수행하지 않았다.
### 45. S-19=A·S-20=A·S-21=A 답변 반영

세 답변의 A와 빈 추가 조건을 확인하고 원문을 보존했다. CONFIRM 인증 성공 시 구세션 송신 중단, HAL 사유 없음=0, 합성 평가의 주 비교 2개 필수·민감도 4개 한계 보고를 세션 설계안·양측 M3·공동 통합시험·TEST_PLAN에 반영했다. 후보 CAN ID/형식·키 파생·운영 상수 전체 승인이나 제품 구현 완료는 아니다.

검증: 기존 `python tmp/reserved_queue_review.py` 16개 검사 재실행, 실패 0·오류 0. 문서 8개 로컬 링크 197회 검사 오류 0, S-19~S-21 원문 A 보존 확인. 기록은 `tmp/s1921_validation.json`. 새 HAL 구현과 합성 SOC 정확도는 실행하지 않았으며 기존 모형의 재통과를 이 두 검증의 증거로 사용하지 않는다.

다음 순서: 상세 세션 계약 전환 영향 정리 → 복구/운영 수치 측정·승인 조건 및 위험 근거 → Android 환경 대조 → 활성 계획 24개 최종 심사. 하드웨어 입력은 완료했고 실제 전압/송수신/ADC 시험은 대기다. Android §6은 후속 입력이며 Plan 통합은 사용자 별도 지시 전 수행하지 않는다.

### 46. 세션 상세 계약 전환 영향 정리

현행 ICD의 고정키·래핑/재동기화, 실제 C++/Python counter 처리와 세션 v2 후보를 대조했다. 세션 설계안 §27에 변경 항목 10개, 담당·인수 연결, 후보의 읽기 순서와 공식 문서→구현→시험·배포 전환 순서를 정리했다. 초기 후보 v1/ACK 직후 송신·시험 시간 값을 현행 운영 설정으로 혼동하지 않도록 안내했다.

최초 상태 동기화까지 REQUEST 제외 31프레임, 포함 32프레임은 형식의 정적 합계이며 실제 성능이 아니다. 일반 BMS 큐 초과 시 신규 거부는 아직 시험 가정이므로 S-22에 쉬운 설명·선택안·빈 답변칸을 작성했다. 위험 공간 예약/포화·인증 상충의 기존 답변은 다시 묻지 않는다.

완료: 상세 계약 영향과 전환 순서 정리. 대기: S-22의 일반 BMS 포화 정책. 독립 진행 과제: 운영·복구 수치의 측정/승인 조건, 위험 근거와 Android 환경 대조, plan 전체 정합성 심사. 현행 ICD·제품 코드·Plan은 이번 단계에서 변경하지 않았다.

### 59. 서버 작업 제외와 S-21 합성 사전 실험 (2026-09-08)

현재 작업 범위 재정렬: 사용자 지시에 따라 제품 추가 구현을 멈추고 계획 완성을 위한 의존성·일관성·정확도·신뢰도·확장성 검토로 복귀했다. 공동 연계 §15를 계획 인수 기준으로 추가하고 ECU/IVI 상위 계획에서 연결했다. SDD의 실측 피팅 근거 없는 OCV 설명을 정정했다. 활성 24문서의 로컬 링크 460회·코드 펜스 오류 0건, 고유 FR/NFR/TC/ADR 표기 107개의 원천 존재를 확인했다. 상세 의미·앵커·실패 처리의 전체 대조는 남아 있으며 최종 통과로 표시하지 않는다. 서버 가져오기·Plan 통합은 제외한다.

레지스터 단계 완료: ADS1115 단일 요청·설정 검증·MSB 우선 signed 해석을 제품 소스에 구현하고 가짜 전송 C++ 검사를 통과했다(SOC 결과 §12). 실제 Linux I2C 어댑터·스레드 결합·장비 취득은 남아 있다. 추가 질문은 현재 없고 서버 가져오기·Plan 통합은 제외한다.

최신 답변 반영: ADC-1=A·ADC-2=A를 접수하여 단일변환·128SPS·100ms 요청 간격·1ms 조회 간격·20ms 인수 마감을 SDD/M3에 반영했다. 시간 제어 헤더의 실제 C++ 호스트 검사 통과, I2C/스레드 연결은 미완료다(SOC 결과 §11). 아래 ADC 질문 대기는 종료됐으며 추가 답변은 현재 필요 없다. 시험 후보값은 실측 후 재검토한다.

현재 답변 필요: 질문리스트 맨 위 ADC-1(단일 요청/연속 완료 신호 방식)·ADC-2(첫 시험 설정)를 작성했다. SDD의 기존 연속변환과 새 변환 식별의 구현 선택을 정리하기 위한 인터뷰다. 20ms 등 제안값은 실측값이 아니며 답변 전 적용하지 않는다. 이미 승인된 센서 상태·3회 규칙·보유 사양은 재질문하지 않는다.

센서 상태 전이 진척: ICD §8의 S-3=A 목표 승인을 재확인해 과거 ‘비트/HAL 미확정’ 설명을 정정했다. 승인된 최초·복구 3회 상태 모듈을 구현하고 실제 C++ 호스트에서 59,049개 이벤트 열 검사를 통과했다(SOC 결과 §10). I2C fresh 식별·시간 상한·실제 통신 연결은 미완료이며 CAN/HAL 형식 전환은 수행하지 않았다.

ADC 제품 변환 모듈 완료: 실제 C++ 변환 함수를 추가하고 독립 호스트 실행으로 65,536개 signed 입력 검사를 통과했다. CMake 소스·시험을 등록했지만 전체 CTest는 미실행이다. 상세 증거는 SOC 결과 §9를 따른다. I2C 드라이버·샘플 유효성·3회 정상 확인·오류 상태 통신·실장비 측정은 여전히 남아 있다. 기존 SensorSimulator와 CAN/HAL 계약은 변경하지 않았다.

ADC 착수 점검: ADS1115_HARDWARE 모드는 현재 I2C 취득 없이 저장값을 반환하므로 즉시 실측 가능한 상태가 아니다. 변환식의 raw 26,401개 범위·단조 증가·3개 기준 벡터를 오프라인 검증했다(SOC 결과 §8). 다음 하드웨어 단계에는 실제 취득 구현·오류 처리·단위시험이 먼저 필요하다. 측정값은 여전히 빈칸이며 보유 정보와 실측 완료를 구분한다. SDD/M3의 수정 전 선형 EKF 상태 설명도 최신 소스 상태와 구분했다.

시험 보완 완료: 무오차군 수치 회귀 검사·RMSE 유한값 검사·SOC 의존 미분 단일 갱신 검사를 추가하고 결과 출력 정밀도를 높였다. 독립 수식 검사로 세 SOC 지점에서 상수 미분 오류를 구분할 수 있음을 확인했다. 실제 C++ 시험은 여전히 미실행이다. 추가 문서 답변은 필요 없으며 다음 외부 증거는 준비된 C++17 환경의 실행 로그와 장비 ADC 측정 기록이다. 서버 가져오기는 요청하지 않는다.

최신 적용: SOC-2=A를 접수해 실제 추정기 헤더·구현·시험을 수정했다. 10직렬·50Ah·3차 OCV·추정기 내부 1회 변환을 적용했으며 상세 결과는 SOC 합성실험 결과 §7을 따른다. C++ 컴파일/CMake 구성은 환경 문제로 실패해 제품 시험은 미검증이다. 서버 가져오기는 사용자가 수작업으로 담당하므로 에이전트 요청 대상에서 제외한다. 현재 추가 인터뷰는 없으며 다음은 C++ 실행 증거와 실제 ADC 측정이다. Plan 통합은 보류한다.

다음 단계 구체화: SDD의 전압 변환 위치를 M3와 동일하게 추정기 내부 1회로 명확히 했다. SOC 결과 §6에 제품 수정 파일·회귀시험·장비 실측 기록표를 추가했다. 실제 제품 수정 착수 범위는 질문리스트 맨 위 SOC-2로 확인하며, 답변 전 제품 파일을 변경하지 않는다. 장비 측정값은 비워 두었다.

최신 결정: SOC-1=B 답변을 반영하여 SDD 일반 초기값을 R=0.02, P0=0.01, SOC=75%로 M3와 통일했다. Q=1e-5와 S-21 시험 초기 SOC 80%는 유지한다. 아래 답변 대기는 종료됐으며 실제 제품 팩/단셀 불일치, C++17 환경 검증, ADS1115 측정과 최종 운영값 검토는 남아 있다. 제품 코드·Plan은 변경하지 않았다.

후속 갱신: 실제 호출부의 팩/단셀 전압 불일치와 SDD/M3 초기 설정 불일치를 확인했다. SDD R/P0로 추가 7개 합성 조건을 계산해 주 비교 우위·전압 편향 역전을 재확인했다. 상세 결과는 SOC 합성실험 결과 §5에, 설정 통일 질문은 질문리스트 맨 위 SOC-1에 기록했다. GCC 6.3의 `std::clamp` 미지원으로 제품 컴파일은 실패했으며 제품 시험을 통과로 표시하지 않는다. 답변 전 설정 변경은 보류한다.

A-14의 GitHub clone 가능 답변을 접수했다. 사용자가 서버에서 받아오는 부분을 직접 담당하겠다고 지정했으므로 현재 작업에서 제외하고 저장소·서버 연결 추가 답변을 요구하지 않는다. 실제 서버 빌드·HIDL·부팅 검증은 미완료로 유지한다.

[SOC 합성실험 결과](../experiments/SOC_합성실험_결과.md)에 7개 조건의 계획 모델 계산과 다음 실험 순서를 기록했다. 전압 무오차 주 비교 2개는 EKF RMSE 약 0.000274 pp, 적분 약 0.115472 pp였다. 단셀 전압 ±0.01V 민감도 4개에서는 EKF가 약 1.096~1.133 pp로 역전됐다. 제품 C++와 하드웨어 합격을 뜻하지 않는다.

다음은 제품 목표 모델·호출부 대조 후 동일 입력 비교, ADS1115 기준 전압 대조, 측정 편향 기반 재실험 순서다. 실제 장비 시험 착수 시 §1에 배선·전압·측정 정보를 반드시 보완한다. 미측정 값은 비워두고, 보정·운영값 판단이 필요하면 인터뷰한다. Plan 통합은 보류한다.
