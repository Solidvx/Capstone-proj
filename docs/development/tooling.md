## 프로젝트 자동화 지침

작성일: 2026-09-10. 이 문서는 사용자와 합의한 자동화 방향이다. 특정 도구의 도입·연결·동작이 완료됐다는 기록이 아니다. 기존 [AGENTS](../../AGENTS.md), [루트 SKILL](../../SKILL.md), 공식 계약과 사용자 승인 범위를 따른다. 실제 구현·연결 상태는 [tooling](#tooling-runtime), 작업 기록 방식은 [workflow](workflow.md)를 참조한다.

<a id="automation--1-기본-방향"></a>
### 1. 기본 방향

프로젝트 구현을 진행하며 실제로 반복되는 작업을 찾고 필요한 자동화를 점진적으로 만든다. 모든 도구를 먼저 구현하는 것을 제품 개발의 선행조건으로 삼지 않는다. 반복되는 판단 절차와 기계적으로 실행할 검사를 구분하고, 효과가 확인된 기능부터 도입한다.

| 수단 | 역할 | 프로젝트 적용 예 |
|---|---|---|
| skill | 상황별 판단과 반복 작업 절차를 안내 | 관련 계획·ICD 확인, 영향 분석, 적절한 시험 선택, 결과·인계 기록 |
| CLI | 사람이 직접 실행하고 결과를 재현할 수 있는 검사 진입점 | 경로·링크·공식 ID·기록 형식 검사, 대상 범위와 결과 출력 |
| hook | 지원되는 특정 이벤트에서 짧고 명확한 검사를 호출 | 관련 문서 변경 후 좁은 범위 검사, 완료 시점이 지원되면 증거 확인 |
| MCP | 모델이 외부 서비스 또는 내부 도구의 자료·기능에 접근 | 저장소 이슈·PR 조회, CI 결과 확인, 협업 자료 검색, 내부 검사 조회 |

이 표는 적용 후보 예시다. 특정 외부 서비스나 플랫폼 이벤트를 이미 채택한 것으로 해석하지 않는다.

<a id="automation--2-도입-순서와-판단-기준"></a>
### 2. 도입 순서와 판단 기준

1. 실제 작업에서 무엇이 반복되는지 기록한다. 입력·출력·담당·실패 사례와 수동 절차를 확인한다.
2. 문맥 판단과 작업 순서가 반복되면 skill로 정리한다. 기존 지침을 복제하지 않고 정확한 원본과 관련 플레이북을 연결한다.
3. 입력과 판정이 명확한 검사는 공통 로직과 수동 CLI로 구현한다. 먼저 사람이 명시적으로 실행해 정상·실패·미실행을 확인한다.
4. 실행 조건이 안정적인 검사만 지원이 확인된 hook에 연결한다. 반복 호출 비용과 범위, 중복·재귀 실행을 검증한다.
5. 외부 자료나 기능이 필요하면 해당 서비스의 연결 수단과 권한을 확인하고 MCP를 선택한다. 내부 고유 도구를 모델에 제공할 필요가 생기면 자체 MCP를 검토한다.
6. 사용하면서 드러난 제약·오탐·누락을 근거로 보완한다. 사용되지 않는 자동화나 전체 빌드를 매 저장마다 수행하는 연결은 만들지 않는다.

외부 MCP 연결이 필요한 작업은 내부 CLI 구현을 기다릴 필요가 없다. 반대로 자체 MCP가 내부 검사를 노출한다면 공통 로직을 재사용해 판정이 갈라지지 않게 한다.

<a id="automation--3-현재-구조에-적용하는-방법"></a>
### 3. 현재 구조에 적용하는 방법

| 위치 | 구현·작성 방향 |
|---|---|
| .agents/skills/capstone-workflow/SKILL.md, .claude/skills/capstone-workflow/SKILL.md | 공통 workflow와 분야별 원본을 안내한다. 역할이 다른 새 skill은 실제 반복 필요가 확인될 때 별도로 설계한다. |
| tools/workflow/core.py | 프로젝트 내부 검사에 공통으로 사용할 로직. CLI·MCP 연결부마다 판정 본문을 중복 구현하지 않는다. |
| tools/workflow/check.py | 검사 범위·입력을 명시하고 결과를 재현하는 CLI. 잘못된 입력·검사 실패·미실행을 구분한다. |
| tools/workflow/tests/ | 정상·경계·실패·미지원 입력 및 공통 판정 일치 시험. README 존재는 시험 통과가 아니다. |
| tools/workflow/mcp_server.py | 내부 고유 조회·검사 기능을 모델에 노출할 때 구현한다. 외부 MCP를 사용하기 위한 필수 서버가 아니다. |
| .claude/settings.json, .codex/config.toml | 현재는 골격이다. 실제 제품·버전의 설정 형식과 지원 여부를 확인하고 필요한 연결만 구성한다. |
| docs/aidlc/changes/CHG-번호/ | 해당 자동화 작업의 요청·영향·설계·진행·검증 증거를 기록한다. CHG-template은 복사용이며 실제 작업이 아니다. |

이 안내의 경로 존재는 실행 기능의 존재를 뜻하지 않는다. 제품 코드·시험은 기존 도메인 경로에서 관리하고 자동화 의존성을 security/requirements.txt에 혼합하지 않는다.

<a id="automation--4-외부-mcp와-자체-mcp-구분"></a>
### 4. 외부 MCP와 자체 MCP 구분

외부 서비스를 연결하려고 자체 MCP 서버부터 만들 필요는 없다. 필요한 서비스에 적합한 기존 연결이 있다면 제공 기능·인증·권한·데이터 전달 범위·운영 조건을 확인해 활용한다. 현재 사용할 수 있는 연결이라고 추정하지 말고 실제 환경에서 확인한다.

프로젝트 고유 기능을 제공해야 하고 기존 연결로 충족되지 않을 때 자체 MCP를 검토한다. 내부 조회·검사는 가능한 한 같은 CLI와 공통 로직을 사용한다. 외부 서비스의 원본 정보를 불필요하게 프로젝트에 복제하지 않는다.

연결 자체는 외부 쓰기·메시지 전송·배포·계약 변경의 승인이 아니다. 사용자 요청 범위와 기존 권한을 따르며 새 권한을 지침이나 연결 설정으로 만들어 내지 않는다.

<a id="automation--5-동작-경계와-실패-처리"></a>
### 5. 동작 경계와 실패 처리

- skill은 공식 계약을 대신하지 않는다. ICD 영향 변경에는 기존 인터페이스 변경 절차를 적용한다.
- hook은 파일 저장·빈 답변·특정 문자열을 승인이나 구현 요청으로 해석하지 않는다. 제품별 이벤트 지원을 확인하며 동일 이벤트 이름을 모든 환경에 가정하지 않는다.
- 초기 내부 자동화는 조회·검사 중심으로 구성한다. 자동 수정·상태 쓰기가 필요하면 대상 경로·동시 수정·충돌·복구를 별도 설계한다.
- MCP가 실패하면 해당 작업을 수동으로 수행하거나, 같은 기능을 제공하는 CLI가 있을 때 대체한다. 모든 외부 MCP 기능에 로컬 CLI가 있다고 가정하지 않는다.
- 실패·미실행·제외를 성공과 구분한다. 토큰·키·실제 장비 주소는 문서·로그·예제에 저장하지 않는다.

<a id="automation--6-완료와-인계"></a>
### 6. 완료와 인계

실제 제품명·버전·실행 방식·대상 루트·설정 위치·사용 명령·검사 범위·기대 결과·실제 결과·실패 복구를 [증거 양식](templates/evidence.md)에 기록한다. 관련 [WF 시나리오](verification/steering-tests.md)를 선택해 확인하고 한 환경의 성공을 다른 환경에 확대하지 않는다.

도입 결과에 따라 tooling.md의 상태·사용법을 갱신하고, 새로운 경로와 참조는 [전체 구조 매핑](../aidlc/structure/document-map.md)에 연결한다. 이 문서는 선택·구현 원칙, tooling.md는 실제 상태와 사용 안내, workflow.md는 개발 과정의 사용 시점을 담당한다. 기능이 미구현이면 명시하고 작업별 증거가 준비됐을 때만 완료로 기록한다.

## 운영 도구와 연결 상태

기준: 2026-09-10 구조 적용. [구조 개선안](../../프로젝트구조개선.md)의 후속 자동화 설계를 안내한다. 현재 제공되는 프로젝트 실행 명령이나 API 명세가 아니다.

| 구성 | 위치·역할 | 현재 상태 |
|---|---|---|
| 수동 운영 | [workflow](workflow.md), [루트 SKILL](../../SKILL.md) | 문서를 명시적으로 읽고 기존 검증 명령 사용 가능 |
| 참조형 skill | .agents/skills/capstone-workflow/SKILL.md, .claude/skills/capstone-workflow/SKILL.md 후보 | 배치 결과는 구조 검증 기록 참조. 실제 자동 로딩 미검증 |
| 커밋 skill | [공통 절차·Claude 진입점](#commit-skill) | 후속 배치 완료·문서 정합성 확인; 실제 CLI 인식 미검증 |
| 공통 로직 | tools/workflow/core.py 후보 | 골격 파일 존재·판정 로직 미구현; 루트·작업·검사 범위를 받아 공통 결과 반환하는 후속 설계 |
| CLI | tools/workflow/check.py 후보 | 골격 파일 존재·CLI 기능 미구현; text/JSON 결과와 실패·미실행 구분 예정 |
| MCP | tools/workflow/mcp_server.py 후보 | 골격 파일 존재·서버 미구현·미연결; workflow_status/workflow_check는 제안 이름 |
| hook | .claude/settings.json 후보 | 빈 JSON 객체로 골격 생성·미활성화; 실제 지원 이벤트 확인 후 연결 |
| MCP 설정 | .codex/config.toml 후보, Claude 위치는 후속 확인 | 주석 전용 TOML 골격 생성; MCP 서버 등록·연결 없음 |

<a id="tooling-runtime--후속-구현과-확인-순서"></a>
### 후속 구현과 확인 순서

1. aidlc-state.md의 수동 기록 형식과 기계 판독 버전·필드를 확정한다. state.json을 동시에 원본으로 운영하지 않는다.
2. 공통 읽기 전용 판정 로직과 수동 CLI를 구현하고 정상·실패·입력 오류·미실행을 구분해 시험한다. --root/--scope/--task/--format 및 종료 코드 0/1/2/3은 개선안의 후보이며 실행 가능한 현재 명령이 아니다.
3. 실제 제품·버전·실행 방식에서 skill 탐색 경로와 루트 해석을 확인한다. MCP는 같은 공통 로직을 호출하도록 연결하고 CLI와 같은 입력에 대한 판정을 비교한다.
4. 지원이 확인된 이벤트만 hook에 연결한다. 시작/저장은 논리적 시점이며 모든 제품에 같은 이벤트 이름이 있다고 가정하지 않는다. 저장은 승인이나 구현 요청이 아니다.
5. 연결 실패 시 같은 범위의 CLI로 대체한다. CLI도 없으면 문서와 파일을 수동 대조하고 미검증 범위를 기록한다. 장애를 통과로 처리하지 않는다.

초기 연결은 조회·검사 중심이다. 자동 수정·상태 쓰기·커밋·제품 빌드 실행은 이 구조 배치에 포함되지 않는다. 후속 쓰기는 허용 경로, 중복 이벤트, 동시 수정과 충돌 처리 검증 후 별도 도입한다. 운영 도구 의존성은 제품 security/requirements.txt에 혼합하지 않는다.

<a id="tooling-runtime--실제-연결-시-기록할-항목"></a>
### 실제 연결 시 기록할 항목

제품명/버전, 실행 방식, 정규화한 프로젝트 루트, 준비 조건, 설정 위치, 실제 호출 명령, 기대·실제 결과, 실패 복구, 대상 해시와 증거 경로를 [증거 양식](templates/evidence.md)에 작성한다. 비밀·토큰·실제 장비 주소는 넣지 않는다. 한 실행 조합의 성공을 다른 조합에 확대하지 않는다.

[운영 검증 시나리오](verification/steering-tests.md) · [배치·검증 결과](../aidlc/structure/verification.md)


최신 배치·전체 경로는 [현재 구조 매핑](../aidlc/structure/document-map.md)을 따른다. 골격 존재는 실제 도구 기능·연결 성공을 뜻하지 않는다.


자동화 대상 선정·역할 분담·도입 순서는 [자동화 지침](#automation)을 따른다. 이 문서에서는 실제 구현·연결 상태와 사용법을 관리한다.

## 자동화 문서의 배치 참조

새로운 자동화 안내·절차·양식·검증 시나리오는 [문서 배치 기준](README.md#document-placement)에 따라 분류한다. 구축 작업의 상태와 증거는 기존 CHG 기록에서 관리한다. skill·CLI·hook·MCP의 실제 코드·설정 위치는 위 구현 방향을 유지하며, 문서 분류를 이유로 실행 파일을 이동하지 않는다. 현재 문서 경로는 [최신 구조 매핑](../aidlc/structure/document-map.md#current-development-layout)을 따른다.

## 커밋 skill 배치와 사용

2026-09-10: [Codex·공통 절차](../../.agents/skills/commit/SKILL.md)·[규칙](../../.agents/skills/commit/rules.md)·[Claude 진입점](../../.claude/skills/commit/SKILL.md)을 배치했다. 기존 capstone-workflow는 작업 기록 탐색, commit은 ECU·IVI 변경의 커밋 검토·분리·요청된 로컬 커밋을 담당한다. 사람용 [매뉴얼](governance/commit.md)은 필요한 경우에만 읽는다.

이 배치는 상시 자동 커밋 hook이나 전체 프로젝트 snapshot 기능을 추가하지 않는다. skill의 발견·선택은 stage·commit·push 권한을 추가하지 않으며 사용자 요청 범위는 공통 규칙을 따른다. 앞 Part의 CLI·MCP·hook 골격 상태는 그대로다.

프로젝트 루트에서 새 CLI 세션을 시작하여 Codex skill 목록 또는 Claude의 `/commit` 표시를 확인한다. 개인·플러그인에 같은 이름의 skill이 있으면 선택된 경로를 확인하고, 모호하면 위 공통 원본 경로를 지정해 읽도록 요청한다. **“공통 commit 절차에 따라 변경을 검토만 해줘”**로 참조 경로·ECU/IVI 범위 구분·stage/commit 미실행을 확인한 뒤 제품명·버전·결과를 기록한다. 현재 문서·배치 정합성만 검증했으며 실제 CLI 인식과 GitHub 동작은 미검증이다.

배치 근거: [OpenAI skill 안내](https://learn.chatgpt.com/docs/build-skills), [Claude Code skill 안내](https://code.claude.com/docs/en/skills). 변경 증거는 [CHG-001](../aidlc/changes/CHG-001/audit.md)에 둔다.
