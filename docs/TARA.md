## 3. 위협 시나리오 (STRIDE)

### 3.1. STRIDE 카테고리

| 카테고리 | 설명 | CAN 버스 적용 예시 |
|----------|------|-------------------|
| **S**poofing (스푸핑) | 다른 노드/사용자로 위장 | 가짜 BMS CAN ID로 조작 데이터 전송 |
| **T**ampering (변조) | 데이터 무단 수정 | CAN 프레임 페이로드 변조 |
| **R**epudiation (부인) | 행위 사후 부인 | 로그 없는 공격 수행 후 부인 |
| **I**nformation Disclosure (정보 노출) | 기밀 정보 유출 | CAN 버스 전체 트래픽 도청 |
| **D**enial of Service (서비스 거부) | 가용성 침해 | CAN 버스 포화 공격 |
| **E**levation of Privilege (권한 상승) | 미인가 권한 획득 | ECU 제어 권한 탈취 |

### 3.2. 위협 시나리오 목록

#### TS-001: BMS 데이터 스푸핑 (Spoofing Attack)

| 항목 | 내용 |
|------|------|
| **위협 ID** | TS-001 |
| **STRIDE** | Spoofing, Tampering |
| **관련 자산** | A-02 (SOC/SOH), A-05 (IVI 표시) |
| **공격자 프로파일** | CAN 버스 물리 접근 가능, python-can 수준 CAN 지식 보유 |
| **공격 시나리오** | CAN ID 0x100으로 SOC=100%(raw=200), SOH=100% 등 조작된 데이터 전송 |
| **피해 시나리오** | 배터리 방전 임박 상태임에도 충분히 충전된 것으로 IVI에 오표시 → 주행 중 배터리 고갈 |
| **현재 대응** | SecOC HMAC 인증 — MAC 불일치 시 Node B HAL 즉시 폐기 |
| **잔존 위험** | SecOC 키 유출 시 유효한 MAC 생성 가능 → A-04 키 관리 중요 |

#### TS-002: Replay 공격 (Replay Attack)

| 항목 | 내용 |
|------|------|
| **위협 ID** | TS-002 |
| **STRIDE** | Tampering |
| **관련 자산** | A-02, A-03 |
| **공격자 프로파일** | CAN 트래픽 사전 캡처 능력 보유 (USB CAN 분석기 활용) |
| **공격 시나리오** | 정상 BMS 상태(SOC=80%) 메시지를 캡처하여 반복 재전송. Fail-safe 전이 후에도 NORMAL 상태 메시지를 지속 주입하여 경보 억제 시도 |
| **피해 시나리오** | 배터리 과열 상태에서도 NORMAL 상태 데이터로 Fail-safe 억제 → 배터리 손상 또는 화재 |
| **현재 대응** | 롤링 카운터 — ICD §2.3의 uint32 차이 윈도우 검사. 범위 밖 MAC 유효 메시지로 기준값을 변경하지 않음 |
| **잔존 위험** | 수신 counter 이력이 사라지면 과거 유효 MAC도 수락 가능. 취약 기간의 상한은 입증되지 않았으며 고정키 counter 순환도 신선함을 보장하지 못함 |

#### TS-003: CAN 버스 포화 공격 (Flooding/DoS)

| 항목 | 내용 |
|------|------|
| **위협 ID** | TS-003 |
| **STRIDE** | Denial of Service |
| **관련 자산** | A-06 (CAN 버스 가용성), A-01 (BMS 상태 통보), A-03 |
| **공격자 프로파일** | CAN 버스 물리 접근, 단순 반복 전송 도구 사용 |
| **공격 시나리오** | 낮은 CAN ID(예: 0x001 — 높은 버스 우선순위)로 ~10,000 msg/s 전송. CAN CSMA/CA 메커니즘에 의해 0x100 BMS 메시지 전달 지연/차단 |
| **피해 시나리오** | Node B가 Fail-safe 상태 변화를 인지 못해 SHUTDOWN 명령이 전달되지 않음 → 배터리 손상 |
| **현재 대응** | ML IDS — msg_count 급증, interval_mean 급감으로 Flooding 탐지 후 0x200 경보 전송 |
| **잔존 위험** | IDS는 탐지만 가능. CAN 버스 가용성 침해 자체는 물리적으로 방어 불가 |

#### TS-004: 퍼징 공격 (Fuzzy Attack)

| 항목 | 내용 |
|------|------|
| **위협 ID** | TS-004 |
| **STRIDE** | Tampering, Denial of Service |
| **관련 자산** | A-01, A-03, A-06 |
| **공격자 프로파일** | CAN 버스 물리 접근, 자동화 공격 도구 사용 (최소 기술 수준) |
| **공격 시나리오** | 무작위 CAN ID + 무작위 8바이트 페이로드로 수천 개 메시지 전송. ECU 소프트웨어 입력 검증 취약점 탐색 및 오작동 유발 |
| **피해 시나리오** | BMS 상태머신이 오입력으로 잘못된 상태 전이 → 불필요한 Fail-safe 진입 또는 실제 위험 미탐지 |
| **현재 대응** | ML IDS (payload_std 급증 탐지) + BmsComponent 입력 범위 검증 |
| **잔존 위험** | 유효 범위 내 정교한 퍼징은 탐지 어려움 |

#### TS-005: CAN 버스 도청 (Information Disclosure)

| 항목 | 내용 |
|------|------|
| **위협 ID** | TS-005 |
| **STRIDE** | Information Disclosure |
| **관련 자산** | A-02, A-04 |
| **공격자 프로파일** | USB CAN 분석기 또는 차량 OBD-II 포트 접근 가능 |
| **공격 시나리오** | `candump can0` 등으로 모든 CAN 트래픽 수집, SOC/SOH/온도 데이터 지속 수집 및 패턴 분석 |
| **피해 시나리오** | 배터리 상태 정보 유출(프라이버시). 트래픽 패턴 분석으로 Replay 공격 준비 |
| **현재 대응** | SecOC 공유 키(`/etc/secoc/key.bin`)는 도청으로 유출되지 않음. 단, 페이로드 자체는 평문 |
| **잔존 위험** | CAN 버스 암호화 미적용. 물리 접근 가능 공격자에게 모든 트래픽 노출 |

#### TS-006: Fail-safe 트리거 위조 (Privilege Escalation)

| 항목 | 내용 |
|------|------|
| **위협 ID** | TS-006 |
| **STRIDE** | Tampering, Elevation of Privilege |
| **관련 자산** | A-01, A-03 |
| **공격자 프로파일** | CAN 버스 물리 접근, 0x101 메시지 포맷 사전 분석 |
| **공격 시나리오** | CAN ID 0x101로 PrevState=NORMAL, NewState=SHUTDOWN, Reason=0x04 (온도>60°C) 가짜 Fail-safe 전이 메시지 전송 |
| **피해 시나리오** | 가상 배터리가 정상인데 Node B가 위조된 SHUTDOWN 상태를 인수 → 잘못된 풀스크린 경고·상태 오인. 실제 전류 차단 경로는 이번 필수 범위에 없음 |
| **현재 대응** | SecOC HMAC 인증 (0x101도 0x103으로 MAC 인증 적용) |
| **잔존 위험** | TS-001과 동일 — SecOC 키 유출 시 유효 MAC 생성 가능 |

#### TS-007: SecOC 공유 키 유출/탈취 (Key Compromise)

| 항목 | 내용 |
|------|------|
| **위협 ID** | TS-007 |
| **STRIDE** | Information Disclosure, Elevation of Privilege |
| **관련 자산** | A-04 (SecOC 공유 키), A-01 (BMS 상태 통보), A-02 (SOC/SOH 데이터) |
| **공격자 프로파일** | Node A 또는 Node B에 물리/원격 접근하여 파일시스템 읽기 권한 획득, 또는 펌웨어 덤프를 통한 키 추출 |
| **공격 시나리오** | 1) Node A의 `/etc/secoc/key.bin` 파일을 직접 읽거나 펌웨어 이미지에서 추출 → 2) 유출된 키로 유효한 HMAC-SHA256 MAC을 생성 → 3) TS-001(스푸핑) 또는 TS-006(Fail-safe 위조) 공격을 SecOC 인증을 통과하며 수행 |
| **피해 시나리오** | SecOC 인증 체계 전체 무력화 — 모든 CAN 메시지에 유효한 MAC 부여 가능. 스푸핑·위조 공격이 차단 없이 성공하여 배터리 오표시, 강제 SHUTDOWN 등 안전 사고 직결 |
| **현재 대응** | 키 파일 퍼미션 `chmod 400 root:root`, OS 계정 접근 통제 |
| **잔존 위험** | 물리 접근 시 SD카드 직접 마운트로 OS 퍼미션 우회 가능. 키 로테이션 메커니즘 미구현 (프로젝트 범위 외) |

## 4. 공격 경로 분석 (Attack Path Analysis)

### 4.1. TS-001 공격 경로 (BMS 스푸핑)

```
[공격자 노드]
    │
    Step 1. CAN 버스 물리 연결
    │       (차량 하부 커넥터, OBD-II 포트, 또는 배선 직결)
    │
    Step 2. CAN ID 0x100, SOC raw=200(=100%), SOH raw=190(=95%) 가짜 프레임 생성
    │
    Step 3. CAN 버스에 프레임 주입 (python-can bus.send())
    │
    ├─ [Config-1: 방어 없음] ──────────────────────────────────────▶
    │   Node B HAL 수신 → VehicleDataService → 대시보드 SOC 100% 오표시  [공격 성공]
    │
    ├─ [Config-2: SecOC만] ────────────────────────────────────────▶
    │   Node B HAL: 0x102 인증 프레임 없음 또는 MAC 불일치
    │   → ERR_HMAC_VERIFY_FAIL, 폐기                                [공격 실패]
    │
    └─ [Config-3: SecOC+IDS]
        SecOC 폐기 (동일)
        IDS: Spoofing 특징(id_mean ≈ 0x100, payload 비정상) 탐지 → 0x200 경보  [차단+탐지]
```

### 4.2. TS-002 공격 경로 (Replay)

```
[공격자 노드]
    │
    Phase 1. 정상 CAN 트래픽 10초 캡처 (USB CAN 분석기 + candump 로그 저장)
    │
    Phase 2. 캡처 메시지 반복 재전송 (RollingCounter = 이전에 캡처된 값 그대로)
    │
    ├─ [SecOC 없음] → Node B 수신, 대시보드 과거 데이터로 덮어씌워짐  [성공]
    │
    └─ [SecOC 있음]
        수신된 RollingCounter <= last_counter
        → ERR_COUNTER_MISMATCH, 즉시 폐기                            [실패]
```

### 4.3. TS-003 공격 경로 (Flooding)

```
[공격자 노드]
    │
    Step 1. CAN ID 0x001 (최고 우선순위), 최대 속도 전송 시작
    │       (python-can Flooding: while True: bus.send(msg) → ~10,000 msg/s)
    │
    Step 2. CAN CSMA/CA 메커니즘: 0x001 > 0x100 우선순위
    │       → 0x100 BMS 데이터 전송 기회 획득 불가 → 전달 지연/차단
    │
    ├─ [IDS 없음] ─────────────────────────────────────────────────▶
    │   Node B: 100ms 주기 데이터 수신 중단, Fail-safe 상태 갱신 불가  [성공]
    │
    └─ [IDS 있음]
        msg_count > 50/s, interval_mean ≈ 0ms → Isolation Forest 탐지
        → CAN ID 0x200 경보 전송 → Node B AlertBanner 표시          [탐지됨]
        ※ CAN 버스 가용성 침해 자체는 물리적으로 방어 불가
```

### 4.4. TS-006 공격 경로 (Fail-safe 위조)

```
[공격자 노드]
    │
    Step 1. ICD §1.3 BMS_FailSafe 포맷 분석
    │       (Byte0=PrevState=0x00, Byte1=NewState=0x03, Byte2=Reason=0x04 ...)
    │
    Step 2. CAN ID 0x101로 가짜 SHUTDOWN 메시지 전송
    │
    ├─ [SecOC 없음] ────────────────────────────────────────────────▶
    │   Node B HAL: onFailSafeTransition(NORMAL→SHUTDOWN) 콜백 호출
    │   → 잘못된 풀스크린 경고·상태 표시                        [성공]
    │
    └─ [SecOC 있음]

```

### 4.5. TS-007 공격 경로 (SecOC 키 유출)

```
[공격자]
    │

    │

    │   MAC 불일치 → 폐기                                         [실패]
```

## 7. 위험 처리 (Risk Treatment)

### 7.1. 처리 전략

| 전략 | 정의 |
|------|------|
| **Reduce** | 대응 수단을 통해 Risk Level 낮춤 |
| **Accept** | 비용/기술적 제약으로 현 수준 수용 |
| **Avoid** | 해당 기능/자산 제거 (본 프로젝트 적용 불가) |
| **Transfer** | 보험/외부 기관에 위험 이전 (범위 외) |

### 7.2. 위협별 처리 계획

> 대응 수단과 과거 예상 잔여 등급을 구분한다. 표의 Accept는 이번 사용자 승인으로 간주하지 않는다. S-9=A로 통제된 실험에서 오프라인 SD 읽기 방어를 필수 구현에서 제외하는 범위는 승인됐다. 이는 다른 Accept나 과거 잔여 등급의 일괄 승인이 아니다. 새 잔여 등급이나 수용 결정을 임의로 부여하지 않는다.

| 위협 ID | Risk Level | 처리 전략 | 대응 수단 | 잔존 Risk |
|---------|:----------:|-----------|-----------|:---------:|
| TS-001 | High→Low | **Reduce** | SecOC HMAC-SHA256 인증 (MAC 불일치 즉시 폐기) | Low |
| TS-002 | Critical→Negligible | **Reduce** | 롤링 카운터 (`last < received <= last+100`) | Negligible |
| TS-003 | Critical→Medium | **Reduce** | ML IDS Flooding 탐지 + 0x200 경보. 단, 가용성 침해 자체 방어 불가 | Medium |
| TS-004 | High→Low | **Reduce** | ML IDS Fuzzy 탐지 + BmsComponent 입력 범위 검증 | Low |
| TS-005 | High | **Accept** | CAN 버스 설계상 암호화 없음. 물리 접근 가정 하 수용 | High |
| TS-006 | Critical→Low | **Reduce** | SecOC HMAC 인증 (0x101 → 0x103으로 보호) | Low |
| TS-007 | Medium | **Reduce + Accept** | 키 파일 퍼미션 `chmod 400 root:root` + OS 접근 통제. 물리 SD카드 접근은 수용 (키 로테이션은 프로젝트 범위 외) | Low |

> **TS-005 Accept 근거**: CAN 버스는 설계상 평문 전송 프로토콜이며, 프로젝트 범위(2노드 실험 환경)에서 암호화 계층 추가는 과도한 오버헤드. 도청 공격은 물리 접근 가정이며, `/etc/secoc/key.bin` 파일 접근은 OS 퍼미션으로 보호됨.

## S 답변 반영 위협 범위와 평가 한계

S-2=A에 따라 필수 검증 대상은 가상 배터리 상태 통보와 IVI 표시다. TS-006의 실제 차량 전원 차단 피해 연쇄는 이 구현의 기능으로 주장하지 않는다. 기존 위험 등급·안전 피해 가정은 이 범위에서 재평가하기 전 과거 분석값으로 취급하며 임의로 새로운 등급을 부여하지 않는다. 키 유출은 인증 상태 통보의 위조를 허용할 수 있으므로 키 보호와 replay/변조 거부 검증은 유지한다.

S-3=A의 다음 목표는 ICD §8이다. 품질을 정상으로 위조하거나 구형/미지원 번호를 정상으로 해석하는 경우를 TS-001/004·보안 통합 시험의 하위 사례로 포함한다. 센서 오류·통신 stale·추정 공백을 섞어 경고를 지우지 않는다. 0x200 비인증 참고 경보의 한계는 그대로이며 센서 품질 계약 승인으로 IDS 인증이 추가됐다고 주장하지 않는다.


### 2026-09-07 정합성 검토와 남은 위험 재평가

Fuzzy 목표는 SRS의 공격별 90%로 정정했고 상태 통보를 제어 명령과 구분했다. 이는 새 실측이나 위험 수용 승인이 아니다. §5~7의 기존 공격 가능성·피해·잔여 위험 수치는 과거 분석으로 보존한다. S-2의 가상 상태 통보 범위, Node A root/Node B 미확정 권한, 미확정 세션 후보와 준비 확인 단계를 반영한 재평가가 필요하다.

재평가는 각 TS별 현재 자산·공격 전제·관측 가능한 피해·기존 등급의 근거·달라진 가정을 나란히 기록한다. 근거 없는 등급 하향이나 잔여 위험 수용은 하지 않고 판단이 필요한 항목을 인터뷰한다. 공유 키 유출은 새 세션 도입만으로 해결되지 않으며 키 갱신과 세션별 키 파생을 혼동하지 않는다. Node A 키 파일 권한 결정을 Node B Qt 서비스의 키 배포·권한 설계 완료로 확대하지 않는다.

### 설계·경계별 추가 확인

- **세션 후보:** 새 nonce/세션 키는 이전 데이터 재생 대응 후보이지 유출된 공유 키의 교체가 아니다. S-6의 준비 확인 추가는 미확정 메시지·타이머·캐시/자원 경계를 바꾸므로 이전 모형 통과를 그대로 적용하지 않는다. 미인증 입력에 의한 pending 교체·재시도 폭주·카운터 소진 반례를 후속 시험한다.
- **경보 신뢰:** 0x200의 현재 ICD 보호 범위를 직접 대조한다. UI가 표시한 경보를 인증된 ECU 판단이라고 확대하지 않으며, 추가 MAC 보호가 필요하다고 판단되면 새 계약 영향과 선택안을 제시한다. 이번 검토로 메시지 보호 범위를 변경하지 않는다.
- **위험 점수:** 공격자 정보 접근 범위·장비 접근·키 읽기 경로·관찰 가능한 손해를 먼저 고정한다. 기존 합계 계산이 맞는 것과 입력 가정이 타당한 것은 다르다. 각 점수의 근거가 없으면 미확정으로 두고 임의의 낮은 등급으로 대체하지 않는다.
- **처리 정책:** 위조/재생 차단·탐지·키 파일 접근 제한이라는 기존 과제는 유지한다. 실측 없는 잔여 위험 감소와 과거 Accept를 승인 완료로 표시하지 않는다. [질문리스트](development/governance/의사결정_기록.md#part1-questions) S-9=A로 통제된 실험의 오프라인 SD 읽기 위험을 명시하고 해당 방어를 필수 구현에서 제외한다. 모든 키 유출 경로를 수용하거나 위험 등급을 낮추는 결정은 아니다.

현재 판정: TS 7개의 범위·근거 차이를 식별했으나 수용 결정·점수 재확정·제품 보안 시험은 미완료다. 현재 범위를 벗어난 차량 피해 설명은 확장 가정으로만 보존한다.



### S-9=A — 물리 SD 접근의 승인된 처리 범위

2026-09-07 사용자 답변 A, 추가 조건 없음. 이번 통제된 실험에서는 장비·SD카드를 관리하고, SD를 분리해 오프라인으로 읽는 공격의 기술적 방어는 필수 구현에서 제외한다. 해당 노출 위험은 한계로 명시한다. Node A root 실행·root 소유 0400 키 파일, 키 비공개·인증 위조/재생 검증은 유지한다. Node B Qt 서비스의 실행 계정·키 공급 방식은 별도 확정한다.

이 선택은 물리 키 탈취 방어 달성, 모든 키 유출 위험 수용, TS-007의 과거 Low 잔여 등급 승인을 뜻하지 않는다. SD에 접근한 공격자가 공유 키를 얻으면 인증 위조가 가능할 수 있음을 보고한다. 새 세션 생성만으로 노출된 공유 키를 교체했다고 하지 않는다.

실행 계획에는 장비/SD 보관·반출·반납 확인 담당과 공유 범위를 기록한다. 실제 키가 포함된 SD 이미지·백업을 제출/공유 산출물에 넣지 않는지 확인하며 공개 자료에는 더미 키만 사용한다. 분실·노출이 의심되면 기존 키를 계속 신뢰한 채 시험을 재개하지 않고 원인·영향과 키 재설정 절차를 검토한다. 구체적인 키 교체·저장 기술을 이번 선택만으로 추가 채택하지 않는다.

후속 개선은 장비가 지원하는 보안 저장·키 공급·저장매체 보호와 부팅/복구의 운영 조건을 비교하는 것이다. 제품·일정·수치·위험 등급은 근거와 인터뷰 후 확정하며 현재 프로젝트의 필수 구현에 자동 편입하지 않는다.



### 표준 참조와 현행 위험 증거의 사용 경계

UN R155의 공식 문서 안내는 차량 사이버보안 및 관리체계를 대상으로 한다. 본 문서에서 적용 국가·차종·승인 대상 확인 없이 ‘2024년 전 차종 적용/의무 준수’를 이 캡스톤의 인수 조건으로 사용하지 않는다. [UNECE 규정 안내](https://unece.org/transport/documents/2021/03/standards/un-regulation-no-155-cyber-security-and-cyber-security), [UN 조약 등록 정보](https://treaties.un.org/Pages/ViewDetails.aspx?chapter=11&clang=_en&mtdsg_no=XI-B-16-155&src=TREATY)를 참고한다. 이번 확인에서 UNECE 본문 직접 열기는 403으로 실패했고 규정 조항별 법적 적용성 판정은 수행하지 않았다.

[AUTOSAR FO R23-11 SecOC Protocol](https://autosar.org/fileadmin/standards/R23-11/FO/AUTOSAR_FO_PRS_SecOcProtocol.pdf)의 공식 검색 발췌는 authenticity/freshness 검증 및 외부 Freshness Manager를 설명한다. 본문 직접 열기는 timeout으로 실패했다. 따라서 이 참조를 프로젝트 고유 HKDF/READY/receipt 구성의 표준 적합성 증명으로 사용하지 않는다. ISO 평가표의 기존 조항/점수 일치도 이번 작업에서 원문 대조한 것으로 표시하지 않는다.

현행 위험 평가에는 §11의 TS별 피해/가정/시험 연결을 사용하고 과거 수치 등급은 역사 기록으로 유지한다. 최종 등급 재확정에는 공격자 문서/키 접근 범위, 시험 버스 접근 조건, 장비/SD 관리, 예상 피해와 점수 근거를 함께 기록한다. 정보 없음은 낮은 위험 점수가 아니다. 세션 모형 통과·S-17/S-18 실패 대응 선택은 공격 탐지율/위험 감소 실측이나 잔여 위험 수용 결정이 아니다.

### 점수 재확정을 막는 정보와 처리

문서 공개 범위·시험 버스 접근·장비/SD 보관·키 포함 복사본 생성 여부는 아래 S-23 답변으로 확인됐다. 같은 사실을 재질문하지 않는다. 실제 권한·키 공급 검증은 Node B Ubuntu 이미지와 Qt 서비스 실행 계정에서 수행한다. 이미 선택한 오프라인 SD 방어 제외를 모든 키 유출의 수용으로 확대하지 않는다.

기존 §5~7의 점수/등급은 역사 기록으로 유지한다. 사실 입력 후에도 평가 척도·점수별 근거·처리 결정이 부족하면 미확정으로 보고하며 낮은 위험으로 추정하지 않는다. 현재 단계의 종료는 7개 위협의 피해/가정/검증 연결 확인이고, 최종 위험 수용은 별도 검토다.

### S-23 서면 답변 확인 — 확정 사실과 남은 정보

- S-23-1: 현재 팀 내부에서 관리하며 계획 설계 완료 후 private GitHub 저장소로 관리할 예정이다. 보안 실험 설계·결과에 기반한 논문 작성도 계획한다. 저장소 생성/업로드나 논문 공개가 이미 완료됐다는 뜻은 아니다.
- S-23-2: 시험 CAN 장치 연결·접근은 팀원에게만 허용된다. 공격 실험은 허가된 팀원이 수행하는 조건으로 기록한다.
- S-23-3: 팀장(ECU 담당)이 RPi·SD를 관리하고 안전한 장소에 보관한다고 답했다. 구체 장소를 공개 문서에 적을 필요는 없으며 실제 보관의 보안성을 이번 문서 검토로 입증하지 않는다.
- S-23-4: SSH로 Raspberry Pi에 접속해 vcan0 테스트를 수행한 경험을 확인했다. 로그·OS 버전·시험 범위는 미제공이다. 실제 MCP2515 물리 CAN·Qt 앱·인증 통합 시험 통과로 확대하지 않는다. 키 포함 SD 이미지/백업 생성·공유 여부는 이 답변으로 확인되지 않는다.

private 저장소 계획만으로 공격자가 프로토콜을 모른다고 가정하지 않는다. 논문에 공개할 범위가 확정되면 TS-001/005의 정보 접근 가정을 다시 대조한다. 실제 키·키 포함 이미지·자격 증명은 논문/저장소/제출물에서 제외하는 기존 규칙을 유지한다. 현재 답변을 모든 키 유출 위험의 수용이나 기존 위험 점수 승인으로 해석하지 않는다.

### S-23-4 추가 답변 반영

사용자는 SD 이미지/키 포함 복사본 생성·공유 여부에 “아직 전혀 진행되지 않음”이라고 답했다. 해당 백업·공유 작업은 미수행이라는 사용자 보고로 기록하고 S-23 사실 확인을 닫는다. 이 답변에서 키 설치 여부나 다른 유출 경로의 부재까지 추론하지 않는다. 앞선 S-23-4 미확인 문장은 추가 답변 전 기록이다. 앞으로 백업/논문/저장소 공유를 시작할 때는 실제 키 포함 여부를 확인하는 기존 과제를 유지한다. 위험 점수나 잔여 위험 수용을 자동 변경하지 않는다.

## 13. 위험 처리의 현재 효력과 종료 증거 (2026-09-08)

S-9의 통제된 실험 범위와 S-23의 사실 입력은 완료다. 과거 점수·잔여 등급은 최신 근거로 재평가된 값이 아니다. 현재 수행할 완화 과제는 아래와 같으며 새 위험 수용 결정이나 계약 변경을 추가하지 않는다.

| 위협 | 유지할 처리 과제 | 담당·종료 증거 |
|---|---|---|
| TS-001·TS-002·TS-006 | 현행 ICD 인증/재생 거부와 경고 전달 검증. 세션 후보는 별도 사전 검증 | ECU·IVI: TC-SEC-001~003, TC-INT-002/003 결과, 적용 계약 버전과 미통과 조건 |
| TS-003·TS-004 | 실제 CAN 공격 평가와 입력 검사, 포화·실패 복구 관찰 | 보안·공동: 공격별 탐지·오탐·부하·유실 결과와 UI/로컬 계산 영향. 탐지 성공을 버스 가용성 회복으로 해석하지 않음 |
| TS-005 | 공유 자료의 내용·접근 범위 점검, 인증과 암호화 구분 | 공동 제출 담당: 로그·영상·문서 목록 및 키/자격 증명 제외 확인. CAN 기밀성 달성 주장 금지 |
| TS-007 | S-9 범위의 SD 관리, 키 파일 접근 제한과 노출 시 대응 검토 | ECU 보관 담당·IVI: 장비/SD 취급 기록, 실제 Qt 서비스 계정으로 접근 시험, 키 포함 백업 여부 점검. 개발 계정의 넓은 권한만으로 접근 통제 인수 금지 |

위협별 최종 평가에는 현재 피해 범위, 공격 가능 조건, 적용한 평가 척도의 정의, 점수별 근거, 실행한 완화책, 남은 노출과 처리 결정자를 기록한다. 시험 결과가 없으면 계획상 완화와 검증된 효과를 구분한다. 점수·등급·수용을 임의로 채우지 않는다. §12의 계획 근거 연결은 완료됐지만 최종 잔여 위험 판정은 보류다.

특히 0x200 경보에 추가 MAC 보호가 있다고 가정하지 않는다. 기존 계약을 유지한 표시·입력 검증과 인증 보장 범위를 분리하고, 보호 범위 확대가 필요하면 ICD·IDS 송신·IVI 수신·시험 영향을 갖춘 변경안으로 인터뷰한다. 서버 사양이나 기존 S-23 사실 확인을 이 판단의 대기 사유로 다시 사용하지 않는다.


## 2026-09-09 승인된 SecOC 현행 규칙 정정

현행 고정키 수신 규칙은 [ICD §2.3~2.5](ICD.md#23-수신-검증-절차-node-b)를 따른다. 단순 대소 비교나 범위 밖 유효 MAC만으로 counter를 재동기화하는 이전 설명은 적용하지 않는다. 실제 C++/Python verify는 이 정정과 일치하며 알고리즘 변경은 없다. 첫 수신 MAC 성공은 새 부팅을 증명하지 못하고, 수신기 재부팅 후 과거 메시지 수락 위험이 남는다. 요구사항의 replay 방어 기준을 낮추거나 전체 보안 인수를 완료 처리하지 않는다.

인증 세션 자동 복구의 승인된 방향은 유지한다. 세션 상세 계약·양측 전환·재부팅 보안 시험은 [세션 설계안](development/security/CAN_세션인증_설계안.md)의 별도 관문이다. 새 wire·키 파생·HAL 변경을 이번 정정 승인으로 포함하지 않는다.
